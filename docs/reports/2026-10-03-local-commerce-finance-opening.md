# 资金期初与已付提成承接验证

范围：`codex/ark-local-commerce` 的历史银行付款、有效核销、已发生退款及已付提成余额承接。复用 ReceiptBatch / Receipt / Receivable / FinanceEvent，不新建资金主账。本报告不是整体 R01–R22 完成声明；测试中的整单关联是显式合成 proof fixture，整单、历史发货、生产责任和切换放行仍需实现。

## 已实现行为

- `commerce_migration:admin` 专用只读预览及原子导入，完整付款期末核销、客户附加费用、退款、未分配预收必须与逐笔原事实相等。源文件摘要、核验说明、来源/租户/对象身份不可覆盖。
- 付款须关联同来源已核验的强客户身份，按逻辑归属 overlay 判断客户；未分配预收也不能借其他客户名义重归属。核销须有整单关联证据，并核对原客户、订单、币种、日期及应收组成。
- 所有应收检查总额、费用和本金的独立上限，预售再检查冻结首款/尾款子池；跨付款合计同样核验。旧付款已有银行账户、流水、汇率、确认元数据、扣费或净到账不能被清单覆盖；旧回款用途及非空应收关联必须一致，原 presale_goods 明确映射为 presale_balance。旧回款编号、完整金额、附件、原请求身份和内部 ID 保留，承接推进版本。
- 使用资金账簿串行边界，完整锁定父对象后重验；正式写入不以旧预览代替当前核验。SAVEPOINT 保证晚阶段异常后即使外层 commit 也没有资金残留。
- 历史原正提成及已发生负调整必须是明确已确认/已付批次，逐笔原币金额、费用、USD/CNY 折算和原受益人保持一致。承接只保存剩余依据，不创建历史正收入；以后冲回继承原已付 USD/RMB 余额，累计尾差最终归零。不同历史负调整允许各自不同冻结汇率，不能将净原币按当前汇率重算。
- 存量 native 投影的 NULL RMB 元数据继续沿用原显示舍入金额；已有负投影固定已消费边界，后续只分摊剩余责任，微额退款不会返付已扣分。
- 同批次重放返回原结果；跨批次同源记录复用原关联。发生新退款或全额冲回之后重放不重置余额。跨批读取原导入结果使用当前读，旧 RR 视图不能隐藏已提交映射。

## 实际验证

- 后端资金期初、提成期初/原生、原生资金、部分冲回及售后资金六组：**83 passed in 25.14s**。包含旧 NULL RMB、首尾款重分类拒绝、跨付款超额、已有银行证据、替换预览仍重验、已收汇总重复累计拒绝、原回款复用、后置故障回滚、跨币逐笔及混合汇率。
- 独立 agent 最新资金/提成期初两组：**44 passed in 12.16s**。发现并修复旧舍入多扣/返付一分、历史首款被改成尾款、普通应收本金侵占费用三项问题；最终复核无未解决项。该独立运行使用 SQLite，不冒充 MySQL 锁证据。
- 真实 MySQL 8.4.6、loopback 33079、一次性随机 schema：完整 base → 125 → 受控 126 证据链 → 173 → 唯一 head `189_commerce_opening_links`，**13 passed in 120.72s**。189 的真实 FK/唯一约束、汇率 Numeric(18,8)、三角色可空 RMB 字段已检查；旧 `650.123456` 汇率及旧付款全部字段原样保留，没有除100回写旧行。
- 在真实迁移结构上，两个同批请求与一个异批同源请求同时建立旧 RR 视图后竞争：结果关联相同，仅一份付款/核销/期初提成依据产生。有效核销400、既有退款200；分三次133.33/133.33/133.34冲回，新增负提成合计4.67 USD、30.35 RMB；再实际退款400，原订单已收0/余额1000、付款退款累计600，对账无差异；再次同/异批导入不恢复已退余额。原650缩放汇率保留，新冻结有效汇率6.5精确存储。
- 证据：工作树忽略目录 `tmp/commerce-finance-opening-chain.log`、`tmp/local-migration-chain/ark_chain_test_58449e6a084140b0/result.json`。结果已读回，测试 schema 与测试 writer 均已删除。初次完整链资金 fixture 的通用 create 请求键与前序 native fixture 冲突；改用各场景独立命令键后通过，未弱化幂等校验。

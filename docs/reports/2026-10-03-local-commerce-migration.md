# 方舟交易接管：完整 MySQL 迁移与业务验证

本报告证明隔离 MySQL 中完整历史迁移可执行，并在实际迁移出的结构上完成原生订单、收款、检验、发货与售后退货。它不代表生产维护批准、真实业务期初对账或整体切换验收完成。

分支 `codex/ark-local-commerce`，基点 `d9266945`。数据库为本工作树临时 MySQL 8.4.6，仅监听 `127.0.0.1:33079`；测试每次生成独占随机 schema 和锁定 writer，结束后实际查询确认二者已删除。没有连接生产数据库或启动对外 worker。

## 创建与升级路径

1. 按仓库原始 `database/auth_init.sql`、`database/dingtalk_init.sql` 安装九张 Alembic 之前的前置表；只执行 CREATE，不执行旧初始化用户语句，不用当前 ORM 建库。
2. 实际 Alembic 从 base 升级至 `125_invoice_integration`，插入合成旧订单、商品行、已批准售后单和关联媒体。
3. 生成内容寻址的合成切换证据，实际创建 writer 账户、授予并撤销 DML 权限，读回 grants、角色和活动事务。运行原始 preflight、停写门禁及 `apply_reset` 到 126，并在后续 DDL 前运行 `verify_after`；保留 DDL proof 和执行 receipt。批准标记仅代表测试拥有该随机 schema，不能作为生产批准。
4. 实际升级至 `173_task_center`，插入统一客户档案，再升级到唯一 head `187_local_replenishment`。
5. 逐列比较旧订单、明细、售后、媒体与既有客户档案。历史订单仍为 legacy，新增本地客户/SKU/售后行关联保持 NULL；迁移没有重放库存或交易事件。

126 的物理合同从该 revision 的冻结资源加载并校验固定摘要，不再随当前 ORM 字段漂移。切换脚本严格停在126进行门禁复验，后续普通升级单独执行；未使用 stamp 或降级绕过。

## 目标与依据

减少发布总等待，以及因不必要重启、冷启动误判、恢复过程依赖完整发布而延长的不可用时间。上轮复盘的 67 分 30 秒包含准备、恢复和重复核验，不能当成单次切换耗时；没有应用进程的约 20 分 28 秒也不同于外部用户完整故障时长。本轮没有执行新生产发布，因此没有新的生产提速或停服秒数。

## 已实现

| 问题 | 机制变更 | 用户影响与保护 |
| --- | --- | --- |
| 静态变化也重启 API | 在后端/连接器/schema 不变且静态文件满足安全条件时，资源先复制、HTML 原子替换 | 静态根目录与 API 持续存在；保留旧资源，配置或共享文件覆盖等不安全变化仍走原发布 |
| 旧版本恢复被冷启动误判 | 北京成功、未变更、回滚统一就绪等待，HTTP/DB 与 systemd 状态共同验证 | 等待预算 300 秒，不是固定停服时间；首次停止返回异常也进入恢复；DDL 后不自动降级 |
| 恢复服务等待整轮发布 | readiness 恢复入口增加 `--restore-service-only` | 只恢复经固定检查点核验的旧 API，输出接续计划；不解冻其他 writer，不冒充发布完成 |
| 相同候选重复静态复制 | 绑定 revision、线上完整摘要、目标清单的暂存复用 | 每次重新校验暂存字节；线上变化重新准备，篡改阻断，不缓存数据库/协议检查 |
| 出库 activate 后 verify 再次暂停等待 | 新的已确认 fence 回执支持无调度变更复核 | 重查身份/字节/数据库/模式/timer，保留执行中批次；旧回执仍走原完整 fence 流程 |
| 应用健康后仍等待资源清理 | 默认登记待维护，独立入口执行；可用 `--inline-maintenance` 保留同步方式 | 应用结果与维护结果分别记录；维护仍受发布锁/保留策略保护，成功才关闭对应任务 |
| 难以定位真实切换时段 | 添加办公室/北京停止请求、启动请求、HTTP 就绪、回滚就绪时间 | 北京时间记录；命令请求时间不能当作精确用户中断时间，记录失败不会阻断恢复 |

热静态更新不是跨全部 HTML 的单一原子事务。所有新资源先到位，单个入口再原子替换。普通失败恢复完整旧入口、Git 和成功回执，保留新资源；若备份损坏或进程中断，`office-static-switch.json` 保留 applying，所有 Office 准备/激活均阻断，需核验并受审恢复。没有新增自动清日志或盲目续跑机制。

维护任务未自动定时执行：应在维护窗口运行现有 `--static-retention-only`、`--candidate-retention-only`，或使用同步选项；长期不维护会积累制品。具体命令与失败恢复边界见 [部署说明](../../deploy/README.md)。

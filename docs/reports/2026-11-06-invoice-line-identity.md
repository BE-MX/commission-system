## 已复现的缺陷

普通订单的 `_replace_items` 原先每次清空全部明细，再新建行。本地 ID 因此改变，只有请求回传的 ID 仍对应当前行时才能继承 `xiaoman_unique_id`。旧页面再次提交旧 ID，后端没有校验身份是否有效，原行进入待删除快照，新行失去小满行号。相同 SKU、不同价格的两行因此都成为新增行，触发小满编辑去重保护。

隔离 SQLite 回归在修复前失败：重复保存后本地 ID 改变且两条小满行号丢失；未知 ID 未拒绝；推单错误被通用提示替换。修复后相同输入保留 ID、行号和 70/69 美元两档小计。

Wasan 1751 的生产记录已证明原行号落入待删除快照，且前一轮已独立恢复并同步；但生产未保存足以还原当次提交 ID 的请求体，不能断言业务员具体执行了哪一种页面操作。当前前端已有保存响应 ID 回填逻辑，其连续编辑回归通过。本次在后端消除 ID 无谓变更，并拒绝旧 ID，覆盖旧页面及其他调用方；未按 SKU、单价或位置自动猜测历史绑定。

## 修复

- 普通订单复用已有明细对象；只删除真正移除的行。重排保持原 ID/行号，重复 ID 的复制行仅首条继承身份，新增行独立建行。
- 无效、过期、外单 ID 在明细分组/删行前拒绝，提示第几行已变化并要求刷新。错误由现有事务入口回滚。
- 重新解析定制产品映射，避免复用对象留下旧 `custom_product_id`。预售保持原归档、出货和修订逻辑。
- 同步执行器透出基础校验与推单映射的具体原因。重复 SKU 提示具体行号、缺少独立小满行号以及恢复/分次新增的处理方式。前端沿用现有 409 提示逻辑，新增测试确认原文展示且不自动重试。

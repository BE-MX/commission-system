# 主站前端历史资源清理与部署保留机制

2026-10-10，用户授权清理历史资源、修改保留机制并按最新 Git 更新生产。首次完整发布固定候选 `1864176c2f5d1ac5bb7128ac435b43d4e4db8bb7`，办公室、北京后端及登记的静态站点发布成功后，通过 `deploy/deploy.bat` 的维护钩子清理三处主站静态目录，实际 exit 0。维护时限补充提交为 `5e1a3de9`。

## 原因与范围

旧发布流程将原站 `assets/` 全量继承到新制品，并无限保留办公室备份及云端版本目录。带内容 hash 的 JS、CSS 因每次构建变化形成许多历史副本；每份备份又复制累计资源，造成文件数量与磁盘占用持续增长。这些是前端构建资源，不是订单、发票、回款业务记录。

本次只处理办公室 `frontend/dist`、严格匹配 `office-previous-frontend-<数字>` 的主站备份，以及两云端 `component=frontend` 的受管版本目录。PM、媒体、业务附件、数据库、源码工作树、构建缓存和其他备份不在清理范围。

## 新保留规则

- 当前版本与最近两份回滚版本保留完整自有制品；额外保留连续七天内退役版本的浏览器资源。
- 以实际退役时间计算 604800 秒窗口，历史清单在旧目录删除后仍保留至窗口结束，资源 mtime 不决定保留范围。
- 云端旧版本没有可靠退役时间，首次持久化七天过渡窗口；此次保留 90 / 91 个版本目录的各自制品，移除其中大量继承的重复资源。窗口不会因重跑续期，过渡期结束后的成功部署或独立维护再淘汰过期版本。
- 未激活的已准备候选单独保护；正常新发布不会无限保留旧版本目录。
- 所有目标先核验摘要、资源冲突和路径/链接边界，再在发布锁内重新计算并清理。Windows 使用原生 PowerShell LiteralPath 删除，复制采用临时文件加原子替换。
- 每次正式发布成功后触发；没有新增定时任务。专项维护仍通过同一部署入口，可先使用 `--prepare-only` 预检。维护失败不会把已成功的应用发布标成失败，但 CLI 返回非零并保存维护错误。
- 维护 SSH 命令单目标时限为 1800 秒，普通静态操作仍为 300 秒；超时时先查询远端进程、锁与本轮回执，不能假定未执行或立即重复写入。

完整政策和恢复入口见 [主站前端资源保留与清理](../../deploy/static-retention.md)。

# 预售出库创建中断后的原任务恢复

## 结果与发布边界

2026-10-23，本地分支 `codex/shipment-absent-recovery` 补齐“核实未生成并恢复”入口。尚未合并、推送或部署。未修改触发订单的价格、运费、回款、资金分配、库存或生产任务，也未重发出库。

原故障链：出库创建发送中断，租约回收后为 `outbound_uncertain / uncertain`，没有远端 ID；原“核对出库单”只能绑定已有单据，“重试出库单”仅接受明确失败，因而未知创建结果缺少正式人工恢复入口。

## 用户操作与事实来源

| 原行为 | 修复后行为 | 原因 |
| --- | --- | --- |
| 无远端 ID 时只能填写已有单据 ID | 符合条件的原批次增加管理员“核实未生成并恢复” | 不另建批次，不释放原数量或资金 |
| 发送结果未知时容易把“查不到”理解为“未发送” | 确认框默认未勾选；必须提供原请求已结束、未生成且不会随后生成的核实事实与记录引用 | 实时404只证明当前查询未见，不能替代外部终态事实 |
| 迟到创建成功只写日志 | 持久化不可变审计；阻止恢复以及恢复后的再次发送 | 让已知远端效果持续阻断重复创建 |
| 早发详情可能覆盖恢复回执 | 恢复开始使旧详情请求失效，随后只读刷新原批次 | 保持状态和余额与新版本一致 |

操作入口：订单分批出库 → 出库结算记录 → 原待核对批次 → **核实未生成并恢复**。操作者须同时拥有当前 `shipment:write`、`shipment:admin` 和实际发票范围。先核实小满侧原请求已终止且不会再生成单据，填写处理记录／工单号并主动勾选声明；系统再查询原编号。若已经存在原单，改用“核对出库单”绑定；没有终态核实事实时继续保留待核对，不能仅凭404勾选。

通过后仅将原出库任务改为 `pending`、原结算改为 `outbound_pending`，由既有执行器重新核验资金、库存、主单和原编号后处理。恢复命令自身不发送小满 POST，不新增结算、回款、运费单或资金应用。

小满[公开出库接口文档](https://open.xiaoman.cn/api-3478296)没有提供本改动可依赖的“未知请求已终止”或 serial 幂等保证；因此终态来自有权限员工的外部核实声明，系统审计明确记录 `employee_external_confirmation`，不冒充系统自动证明。

## 后端约束

- 当前授权、Invoice范围及完整业务图捕获两次；外部GET期间释放业务行锁，但全程持有与出库执行器相同的 `executor_fence`，直到最终提交。
- 客户端挑战绑定原结算版本、任务版本、任务token、编号和载荷指纹；旧页面不能对新尝试作终态声明。最终再次核对全图及确认历史／创建审计指纹。
- 只接受原创建未知状态、无远端ID、无行快照、无租约、无实际出库确认历史、无迟到出库或回款事实的任务。小满鉴权失败、超时、响应异常、已有单据和并发图变化均阻断。
- 原任务ID、编号、载荷、报价、商品与费用、回款及资金应用保留。结构化审计完整记录原尝试、人工核实依据、实时404观察与真实操作者；不截断依据塞入500字备注。
- 提交回执不明时返回私有503并读取原批次；不自动重放声明。已提交但ack失败的事务关闭处理已通过真实MySQL测试。
- 无数据库迁移，复用 `AuditEvent` 与 `SettlementEvent`。

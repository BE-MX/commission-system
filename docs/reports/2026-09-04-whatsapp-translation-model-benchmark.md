# WhatsApp 翻译模型基准报告

生成时间：2026-09-04 23:31 +08:00

## 结论

推荐优先灰度 `openlux API / gpt-5.6-sol`。它在三组模型中响应最快：P50 为 5.88 秒，P95 为 11.59 秒；成功返回的翻译全部通过 JSON 契约与 SKU、数字、Emoji、换行保持检查。

`TeamRouter-Chat / claude-fable-5` 的成功率最高（30/30），P50 仅比 GPT 慢 0.19 秒，但 P95 达 23.66 秒，连续对话中的等待感明显。当前生产翻译模型 `GLM API / glm-5.3-flash` 的 P50 为 7.99 秒、P95 为 15.54 秒，整体慢于 GPT。

本报告不自动修改生产 Preset。切换模型属于独立生产配置决策，应先做小范围灰度并观察真实成功率、当日 Token 与供应商可用性。

## 方法与边界

- 从生产 AI 管理页读取 25 个已启用 Preset，按“提供商 + 模型”去重并排除生图模型，得到 3 个文本模型候选。
- 每个模型预热 1 次（不计入结果），再顺序执行 30 次：英语、德语、荷兰语、西班牙语、瑞典语 × 短/中/长文本 × 2；样本顺序固定随机化。
- 三个候选收到相同的 WhatsApp 收件翻译指令和相同合成文本。由于开发机无法解析生产数据库内网地址，本轮通过已登录的生产 AI Preset 测试 API 执行；每个 Preset 仍保留自身系统提示词，公共翻译指令放入相同的用户消息中。这比直接在生产服务器调用 Provider 多一层 API/日志开销，因此适合比较当前端到端体验，不代表供应商裸接口延迟。
- 成功率按客户端 30 秒时限计算；契约正确率检查 JSON 字段与语言值域；关键内容保持率检查 SKU、数字、Emoji 和换行。
- 所有输入均为合成商务文本。本文档不保存提示词、翻译正文、API 地址、密钥或原始响应；生产测试端点会按现有规则留下合成测试调用日志。
- 系统没有统一、可核验的模型单价配置，因此不编造费用；Token 合计仅用于相对消耗参考。语义风格和商务语气仍需人工小样盲评。

## 非模型优化结论

本次版本同时处理了影响体感和稳定性的非模型因素：消息扫描不再被连续 DOM 变更无限延后；最多 3 条并发翻译并提供逐条手动触发；浏览器到方舟、方舟到 Provider 各只对瞬时网络/网关错误重试 1 次，并复用同一请求 ID 和同一次额度预留；旧聊天结果不能写入新聊天；输入框替换必须回读成功才显示完成。

这些改动直接解决“连续消息漏一条”“按钮看似没反应”“瞬时断连直接失败”和“重试重复计费”四类问题。模型切换只能改善生成阶段，不能替代上述队列、幂等和写入验证。

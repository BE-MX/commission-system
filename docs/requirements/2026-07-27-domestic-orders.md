# 内贸订单管理与生产跟踪 — 方案设计

日期：2026-07-27　状态：待亮哥确认
需求来源：内贸部门《内贸内部标签.xlsx》（下单模板 + 头套/发片/特单三个案例）

---

## 一句话方案

新建独立领域模块 `app/domestic/`（内贸订单域）：主站下单（选属性自动生成产品、自动匹配工艺路线）→ 打印带二维码的流转卡 → 小程序内贸模块扫码按数量报工（默认整批一键报，可改数字拆批）→ 明细级发货登记。**只复用四样全局资产（工序字典、工艺路线、工人工序绑定、二维码签名算法），订单/客户/产品/进度全部独立建表，现有外贸链路零改动、零回归风险。**

## 访谈共识（2026-07-27 确认）

1. **一单多品**：一个订单号下可有多行不同产品，每行各自有数量、各自走工艺路线 → 订单主表 + 明细表两层。
2. **路线按工艺自动映射**：维护「产品类型+工艺 → 路线」映射配置，新产品生成时自动继承路线，下单人零操作；个别产品可在产品管理页人工改绑。
3. **内贸工人是独立一批人，但同样按工序分工**：复用现有 `user_process_binding` 表，把内贸工人绑上各自工序即可。扫码后系统自动定位到该工人绑定的工序，默认带出可报数量。

## 为什么平行建表而不是给现有表加"内贸"标记

调查结论（2026-07-27，两个探索 agent 交叉验证）：

- 现有进度表 `order_product_process_progress` 的外键**硬绑**外贸生产订单明细（`ark_production_order_items.id`，ON DELETE CASCADE），改成双来源要动报工/看板/小程序/打印/重置工艺共 5 处，回归面大。
- 现有报工是**整行流转**：进度表无数量字段，UNIQUE(明细,工序) 锁死一工序一条记录，无法表达"500 件完成了 300 件"。内贸的拆批需求必须改结构——与其动老表，不如新表按数量模型设计。
- 用户明确要求内贸的订单/产品/客户与现有模块**区分开**。

代价是进度表逻辑有一份平行实现；换来的是外贸链路一行不动。~30 日活的内部系统，回归安全 > 代码复用。

## 数据模型（7 张新表，全部 `ark_domestic_` 前缀）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `ark_domestic_customers` | shop_name(UNIQUE)、contact、phone、address、remark | 客户店名是主标识（Excel 的"客户店名"）；下单时搜索选择或就地新建 |
| `ark_domestic_orders` | domestic_no(系统号 DO{YYYYMMDD}-{NNN}, UNIQUE)、order_no(客户订单号,原样文本如"710"/"特涵5-506")、order_date、customer_id FK、order_type(普货/特单)、status、remark、created_by、deleted_flag | 客户订单号格式不统一，只存不约束；系统号做内部唯一引用 |
| `ark_domestic_products` | product_type(头套/发片)、craft(工艺)、net_color(网底颜色,头套限定)、size(尺寸,含"取模定制")、length(长度)、density(发量)、name(属性自动拼接)、attrs_key(属性组合归一化键, UNIQUE)、route_id FK→process_route、status | 下单选属性后 find-or-create；"取模定制"是一个属性值，具体尺寸细节走明细图文区（与 Excel 结构一致：属性区+图文区分离） |
| `ark_domestic_craft_routes` | product_type + craft(UNIQUE 联合)、route_id FK | 工艺→路线映射配置，产品生成时查此表自动绑路线 |
| `ark_domestic_order_items` | order_id FK、product_id FK、product_name/attrs 快照、order_qty、hairstyle/color/style_requirement/remark 四个图文字段(文本+图片路径JSON数组)、status、ship_time、ship_weight(克,数值)、route_id 快照 | 发型/颜色/发型要求/备注四区支持文字+多图（复用 AppUpload）；发货时间/克重是**明细级**（克重是单件属性，案例 38g/54.5g）；路线在下单初始化进度时快照锁定，后改映射不影响在制单 |
| `ark_domestic_item_progress` | item_id FK、step_order、process_id、route_id、completed_qty(累计完成数)、status；UNIQUE(item_id, step_order) | 每明细按路线展开一行/工序，**记累计数量而非 0/1** |
| `ark_domestic_report_logs` | item_id、process_id、step_order、report_qty、reported_by_user_id、reported_at、revoked/revoked_at | 报工流水，支持撤销回减、计件统计、全程追溯（现有外贸报工无流水表，撤销即抹掉——内贸补上这一课） |

属性下拉值域（头套工艺 5 项/发片工艺 5 项/网底颜色 3 项/尺寸/长度 6 项/发量 3 项）进**系统数据字典**管理，内贸主管可自行增删选项不用改代码；前端按产品类型条件渲染（头套显示头套工艺+网底颜色+头套尺寸，发片显示发片工艺+发片尺寸）。

## 核心设计：数量流转报工（拆批的实现方式）

**流水账模型，不引入"批次"实体。** 每道工序记累计完成数：

```
可报数量(第N道) = 上一道累计完成数 − 本道累计完成数    （第1道的上游 = order_qty）
```

- **整批报工（大多数场景）**：扫码 → 系统定位工人绑定的工序 → 默认带出全部可报数量 → 一键确认。和现在外贸报工一样只按一次。
- **拆批报工（少数场景）**：同一界面把默认数字改小即可（20 件改成 12），剩余 8 件停在上道工序，之后任何人再扫同一张码继续报。**不需要拆卡、不需要重新打码，一张流转卡贯穿全程。**
- **数量守恒天然成立**：下游永远报不出超过上游完成数的量，不需要人为对账。
- **完工判定**：末道工序累计数 = order_qty → 明细完工；订单全部明细完工 → 订单完工。
- **撤销**：只能撤自己最近一条未撤流水；回减后若下游已报数量会超过上游累计，则拒绝撤销并提示原因。

为什么不做批次实体（拆批时生成子批次卡）：批次模型要拆卡、重打码、管理批次合并，工人和跟单的操作复杂度暴涨；流水账模型下拆批只是"改一个数字"，系统承担全部复杂性。

## 二维码与流转卡

- 复用现有 HMAC 签名函数，新前缀：`ARK-D:{item_id}:{sign}`（现有外贸码是 `ARK-P:`，前缀分流互不干扰）。
- 内贸流转卡照抄 `PrintCard.vue` 模式：产品名+属性、数量、图文要求（含图片，工人在卡上能看到发型参考图）、工序链、二维码。下单成功即可逐明细打印。

## 小程序改造（在现有报工小程序上加独立模块)

- **新页面组 `pages/domestic/`**（navigateTo 页面栈，不动 tabbar——tabbar 是 3 文件索引联动的高危区）：
  - `domestic-scan`：内贸扫码报工。扫 ARK-D 码 → 展示产品/属性/参考图 + 该工人工序的可报数量（默认全量）→ 数字可改 → 确认提交。含今日记录+左滑撤销，交互复刻现有 scan 页。
  - `domestic-progress`：内贸订单进度。订单/明细列表 + 每道工序在制数量分布，供跟单和管理者跟进。
- **入口双保险**：scan 首页加「内贸报工」入口按钮；同时主扫码按钮识别 ARK-D 前缀自动转入内贸确认流程——工人从哪个入口扫都不会错，零思考。
- 后端：业务逻辑全在 `app/domestic/service`；小程序端点挂 `app/mini/` 薄路由（沿用 `get_current_mini_user` 鉴权 + 裸 dict 响应风格，与现有 mini 端点一致，注释说明不接 RBAC 的原因）。

## 状态机

- 订单：`1 生产中`（下单即生产，Excel 无审批环节）→ `2 已完工` → `3 已发货`；`4 已终止`（手工，有在制报工时需确认）。
- 明细：`0 生产中` → `1 已完工`（末工序数量齐）→ `2 已发货`（登记发货时间+克重后）。允许部分明细先发货，全部明细发货后订单置已发货。

## 实施切分（小步提交，每步可独立回滚）

1. 迁移 + 模型（7 表，revision ≤32 字符，建前查撞号）
2. `app/domestic/` 四件套：客户/产品(find-or-create)/映射/订单 CRUD + 下单时进度初始化
3. 报工核心：数量流转 service + 流水 + 撤销 + **pytest（管货数量，必须有测试：整批/拆批/守恒校验/撤销边界/并发幂等）**
4. mini 端点 + 小程序两页 + 主扫码 ARK-D 分流
5. 主站前端：下单/列表/产品/映射页
6. 流转卡打印
7. 文档同步（api-reference/database/auto-memory）+ 对抗性审查（涉库存数量+状态机+迁移，DoD 第 5 条必审）

## 开放点与已定假设

- **假设**：内外贸共用一套工序字典（工序名如有冲突再加前缀区分）；发货登记用 `domestic:write` 不单设权限；报工并发用行锁+流水幂等处理。
- **开放**：内贸是否需要独立看板（首版不做，进度查询已覆盖）；客户管理页是否首版就要（建议后置）；发货是否强制全工序完工（首版强校验，可再放开）。

## 2026-08-17 内贸订单优化补充方案

- 116 迁移采用维护窗口：先停止全部旧版写实例，再升级数据库并只启动新版本；禁止新旧版本滚动混写建单、充值和报工。
- 客户增加自定义编码、会员等级、省/市和充值余额；充值与订单扣退款全部写不可变流水。
- 订单增加 `0 草稿`：保存草稿不扣余额，提交时原子扣款；生产中改数量/单价只结算差额，终止/允许删除退回已扣额。
- 明细增加单价、明细金额和订单总额；每行有稳定的 A1/A2/… 编号。
- 建单与追加明细都使用客户端幂等键；追加明细由订单行内的下一序号计数器分配编号，避免并发重复编号和锁序反转。每单限制 50 行/5000 件，单明细限制 2000 件。
- 每件产品物化独立单件码 `ARK-DU`，如 A1 数量 10 生成 A1-01…A1-10。数量模式报 3 件依次消耗 01/02/03，再报 1 件消耗 04；逐件模式扫哪件就报哪件，且下游必须精确承接该件的上游状态。
- 数量报工按尾批倒序撤销，不能先撤 A1-01…03 而保留 A1-04；逐件提交在写端再次校验二维码签名，不能只凭可枚举的 unit_id 报工。
- 小程序报工模式由 `domestic_quantity_report:write` / `domestic_unit_report:write` 权限决定；普通工人只授其一。
- 进度小程序码页展示完整订单、全部明细、图文、金额、发货与进度；客户可见工序由 `process.show_in_domestic_track` 属性控制。

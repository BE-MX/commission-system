# 客户获客到邮件发送 MVP 实施约定

用户已授权：使用已绑定的 `leshinehair@agent.qq.com` 跑通功能；验收邮件发送至 `86muliang@163.com`；通过正式入口发布到当前正式方舟站点。未授权向其他客户发送测试邮件或 push 远端。

## 范围

保留现有搜索、背调和事实账本，补齐：收件人准备、开发信生成与审核、数据库唯一发送队列、受限 worker、发送回执、收件事件与停发；单邮箱首封人工审批 MVP。通过既有用户界面完成流程，不要求业务员执行 CLI。

## 分工与依赖

1. 后端负责人：实现收件人准备与证据校验、现有审批/列表 ACL/排程契约修复，发送认领/临发授权/结果与事件 API，以及普通角色和并发回归。
2. 前端负责人：修复审核字段、保存刷新、审批 payload，增加收件人准备、邮箱管理/健康和事件入口，补关键交互测试，沿用现有 UI。
3. 主代理：受限 Node worker 与 CLI 契约、北京服务部署、集成、真实验收。worker 不读取业务数据库，以机器凭证调用主站；OAuth 凭据不进入 AI 或前端。
4. 独立审查：检查状态机、跨客户访问、发件身份、重试/租约、撤销竞争及前后端契约。

## 接口约定

- 现有 `/api/mail-outreach` 保留，响应统一 `{code,message,data}`；前端只读已序列化的 `claims/risk_flags/schedule_policy`，不读 ORM 字段名。
- `GET /context/{customer_id}`：联系人邮箱与缺项，背调联系事实候选。
- `POST /customers/{customer_id}/recipients`：人工确认联系人姓名/邮箱/语言/IANA 时区/国家、来源事实或人工核验说明；独立记录邮箱核验和联系许可，不能自动把 unknown 批量改成有效。
- `GET /drafts/{id}`：精确收件人姓名、邮箱、验证状态、客户名及当前 revision。
- `POST /drafts/{id}/approve`：当前版本/内容哈希、邮箱、发送时间和原因。前端不得多传未定义字段；人工选时为 MVP 可用路径，保留修正后的智能预览。
- 邮箱 `GET/POST/PUT /mailboxes` 复用；普通用户仅本人绑定，管理权限可维护；状态/健康在队列页可见。
- `GET /events`、`POST /events/{id}/classify`：受客户权限限制的回复/退信/退订人工处理。
- worker 独立路由：认领、临发授权、发送结果、收件 ingest、健康。机器身份只能访问绑定邮箱，不能批准草稿。

## 关键发送约束

总开关默认关闭；服务器允许名单用于上线验收，仅 `86muliang@163.com`。原子认领，认领可恢复、已开始发送不可重发；CLI `ok=true,data.queued=true` 仅表示通道接受，message ID 可后续通过 sent 目录对账。CLI 失败/超时只在确定未调用通道前可安全失败，调用后未知一律待核对。

每次发前核对审批未撤销、当前内容/收发件身份、客户权限、联系限制、证据未过期及配额。共享 mailbox 行锁串行配额预留；退订/硬退信抑制并取消尚未开始任务。发送结果与客户事件可追溯，不能把 provider accepted 显示为送达。

## 验收与发布

内存 SQLite/隔离数据库回归与前端构建先通过；独立审查修复后通过官方 `deploy/deploy.bat` 发布固定候选。真实 CLI 通道已初步验证，后续必须从方舟生成/审批/队列发送到验收地址，查到发送记录并验证回执；不以直接 CLI 测试代替主站闭环。

北京 worker 需在独立 workspace 完成人工 OAuth（Windows DPAPI 不复制跨机）；服务器凭据只存受限目录。发布与 OAuth 分别验证，不把本机登录成功当作线上服务就绪。

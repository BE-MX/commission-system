# 方舟开发动态看板 设计稿

> 状态：P0 已在本地实现，待部署｜日期：2026-11-23｜作者：Claude Code｜已确认决策：受众两层（技术视图 + 全员更新日志）、允许开发机把**提炼后的摘要**经 API 上传生产、统计单位为「一件事」

## 1. 一句话

开发机上的采集器把 Git、发布记录、Codex/Claude 会话、handoff 里散落的痕迹**自动归并成「事项」**，状态由证据推导（不靠人填卡），摘要去敏后推到生产方舟；技术视图按日/周/月看「做了什么、修了什么、走到哪一步」，挑选后的已发布事项生成面向全员的「方舟更新日志」。

## 2. 旧任务为什么效果差，这次怎么改

参考了两个 Codex 自动化（`~/.codex/automations/`）：

| 旧任务 | 原理 | 问题 | 本设计的做法 |
|---|---|---|---|
| `commission-system 看板自动领单`（已暂停） | 每 30 分钟查本地 Taskboard 待办卡，认领→实现→回填 | **推模型**：要有人先建卡。11-14 到 11-23 约 300 次运行全部「待办 0 张」，看板始终是空的；每轮都起一次大模型，成本白花 | **拉模型**：只读已有痕迹，不需要任何人额外录入；采集是确定性脚本，大模型只在证据变化时调用 |
| `每3小时整理Codex会话标题`（运行中） | 给会话标题打「开发中/待合并/待推送/已提交」，状态以 Git 证据为准，增量指纹无变化就跳过 | 结果只体现在 Codex 侧栏标题里，不能统计、不能按时间看；状态推理靠大模型读历史，state 文件已 1MB、memory 140KB | **沿用它最有价值的三条规则**：①状态以可核实的 Git 证据为准，历史记录只作参考；②增量指纹，无实质变化不重算；③共享 main 的脏改动不能算到某个任务头上。推理改成确定性代码 |

## 3. 核心模型：事项 + 证据，状态是算出来的

**事项（Item）**＝一件事，例如「跨境申报核对一期」「客户跟进策略截断修复」「1751 单数据修复」。
**证据（Evidence）**＝挂在事项上的痕迹：分支、commit、会话、handoff 条目、发布记录、数据修复脚本目录、交付报告。

### 3.1 状态推导（代码事项）

按顺序取第一个满足的，**只看证据，不看任何人写的状态词**：

| 看板列 | 细分状态 | 判据 |
|---|---|---|
| 已发布 | 已发布 | 事项全部 commit 的**内容**都已出现在某次全局发布的 revision 中（见下方「内容等价」） |
| 已提交 | 待发布 | 已在 `origin/main`（同样按内容等价），未进全局发布 |
| 已提交 | 待推送 | 已在本地 `main`，不在 `origin/main` |
| 已提交 | 待合并 | 有 commit 在 feature 分支，未进 `main` |
| 开发中 | 开发中 | 有关联 worktree 未提交改动，或会话近 3 天仍活跃且无 commit |
| 开发中 | 停滞 | 以上任一状态 14 天无新证据（不自动删除，仅加角标） |

**内容等价，不用祖先关系**：生产版本是发布候选分支（如 `codex/release-followup-strategy-20261123`）上 cherry-pick 出来的，不是 main 的后代。已核实：11-23 的跟进策略修复 `07c450d8` 在 main 上，生产跑的是内容相同的 `d1f5bbb7`，二者没有祖先关系，按祖先判断会永远显示「待发布」。所以判定一律用 `git cherry` / patch-id 比较内容，并参考发布回执里的 `latest`（候选包含的 main 基点）。热修复只在发布分支、不在 main 的情况同样能识别，并额外标「未回合 main」。

「已合入 main ≠ 已部署」是项目里最容易错的点，所以**待发布**单独计数、在顶部 KPI 高亮。

**状态变化记事件**：每次状态变化写一条事件（`ark_devlog_item_events`：事项、从→到、发生时间、触发证据）。统计按事件时间落桶，这样上周的「开发中」在本周发布后仍能在上周的周报里回看。

### 3.2 非代码事项（数据修复 / 运维）

没有 commit 可追踪，状态只有：进行中 → 已执行 → 已核验。为不违反「只看证据」，判据只认**结构化回执**：修复脚本写出 `repair-receipt.json`（操作对象、影响行数、执行时间、校验结果）即「已执行」，校验结果为通过即「已核验」。会话最终报告只用来生成摘要，不用来定状态。现存 `.deploy_state/<topic>/` 历史目录没有这种回执，回填时统一标「证据不足」，人工可以一键确认。从 P1 起把「数据修复必须写回执」补进完工清单（`completion-checklist`），先改规范再改实践。

### 3.3 事项类型

新功能 / 改进 / BUG 修复 / 数据修复 / 运维发布 / 规范文档。先由规则判断（commit 前缀、分支名、`.deploy_state` 目录名含 repair/recovery），判断不了交给摘要步骤的大模型，人工可改。

## 4. 数据源与采集

### 4.1 来源清单（全部在开发机，只读）

| 来源 | 取什么 | 位置 |
|---|---|---|
| Git | 所有 worktree、本地分支、`main`、`origin/main`（采集前 `git fetch`，失败则沿用上次并标注）；commit 信息、时间、作者代理 | 主目录 + `git worktree list` |
| 发布账本 | 不由开发机采集：部署器在生产侧直接写入，见 §4.2 | 生产 `ark_devlog_releases` |
| Codex 会话 | 会话 id、标题、cwd/分支、最近实质更新时间、最后一条 agent 总结 | `~/.codex/sessions/**/rollout-*.jsonl`、`~/.codex/archived_sessions/`，元数据补充读 `state_5.sqlite`（只读） |
| Claude Code 会话 | 会话 id、cwd/分支、`wrap_up` recap；没有 recap 的会话（如 CLI）取最终回复 | `~/.claude/projects/D--MyProgram-commission-system*/*.jsonl`（含 worktree 对应目录） |
| handoff | 条目标题里的日期、代理、状态词、正文提到的 commit/分支 | `docs/handoff.md` |
| 数据修复 / 专项操作 | 目录名、脚本名、回执文件 | `.deploy_state/<topic>/`、`docs/reports/` |

会话只取**元数据 + 代理自己写的最终总结**，不读工具输出全文。Kimi / Accio 首期不接，账本结构预留 `agent` 字段。

### 4.2 「已发布」的权威来源

现状：生产版本只记在 handoff 的自由文本里；`.deploy_state/global-release-*/revision.json` 是每次发布各自建的目录（含 `baseline/latest/candidate/branch`），不是统一账本。`deploy.bat` 在办公室生产机上运行，开发机上的发布状态不完整（开发机的 `publish-current.json` 停在 10-14），所以**账本不能放在开发机**。方案：

1. **部署器直接写账本**：全局发布验收成功后，部署器在生产侧向 `ark_devlog_releases` 写一行（发布时间（北京时间）、候选 revision、`latest` main 基点、范围 global/组件、主机、release_id）。账本写入失败只告警，不影响发布结果。只有 `scope=global` 用于判定「已发布」；专项发布只作为证据展示，符合「只发一台不代表全局版本」的规则。
2. **采集器拉账本**：开发机采集器从 ingest 接口取回账本的 revision 列表，再在本地做内容等价比较，然后上传结果。服务端不需要 Git。
3. **历史回填**：一次性脚本从 `global-release-*/revision.json` 和 handoff 的全局发布条目回填，人工核对后入账。
4. **运行版本校验**：不读运行目录的 `HEAD`（北京用 `deploy/<SHA>` 引用，办公室可能从候选目录启动，`HEAD` 不可信）。改由部署器把 revision 和 release_id 写进制品里的版本文件，健康端点只读返回。看板顶部显示「生产运行 `d1f5bbb7` ／账本最新 `d1f5bbb7` ✓」，不一致标红，说明账本漏记或有人绕过了发布入口。
5. **与 handoff 对账**（P1）：handoff 写「已部署」但账本里没有、或账本里有但 handoff 没记录，都在看板上标红。

### 4.3 归并：痕迹 → 事项

优先级从强到弱，强规则命中就不再往下：

0. **先排除过程分支**：`*/global-release-*`、`*/release-*`、`*-main-integration`、`*-integration-*` 这类发布/集成分支不产生事项，只作为证据，沿 merge 链和 patch-id 把里面的 commit 归回原始功能分支，避免同一件事被数两三次（现有约 149 个分支、87 个 worktree，这类分支占相当比例）。
1. **功能分支**：`<tool>/<topic>` 作为默认主键；merge commit 的信息里带分支名，可把已删除分支的 commit 找回来。
2. **会话 ↔ 分支**：按会话实际 cwd 当时所在的分支 + 时间窗匹配，**不按 worktree 目录名**（已核实目录名与分支不一定对应，例如 `annual-battle-awards` 目录实际在 `codex/deployment-availability` 分支上）；会话里出现分支名或 commit sha 也算命中。
3. **handoff ↔ 事项**：条目正文出现 commit sha 或分支名。
4. **直接提交到 main 且无分支的 commit**：同一天、同一会话产生的归为一件事；没有会话的单独成一件。
5. **以上都不中**（如只有会话、没有 commit 的数据修复）：会话本身成一件事。

模糊匹配（例如只能靠标题相似度）**不自动归并**，只在详情抽屉里给「可能是同一件事：XXX」的建议，点一下合并。

**人工修正永远优先**：合并、拆分、改名、改类型、隐藏、标为放弃，存在生产库的 overlay 表里；采集器每次上传后服务端先套 overlay 再展示，下次采集不会把人工改过的东西冲掉。

## 5. 摘要与去敏（在开发机完成）

- 对每个事项生成：标题（≤20 字）、做了什么、解决了什么问题、类型、影响模块。输入只有 commit 信息、会话最终总结、handoff 正文，截断到固定长度。
- **只在证据指纹变化时调用**（指纹＝该事项全部证据 id + 最后更新时间的哈希），平时一轮采集零模型调用。
- 调用通道：本机 `claude -p`（小模型），失败时降级为「分支名 + 最后一个 commit 标题」，事项照常上传、标「待摘要」。不走后端 `app.ai.service`——那意味着原文要先上传到生产，违背「原始会话不出开发机」。
- 去敏两道：提示词要求不写客户名、员工姓名、订单号、金额、联系方式、密钥；输出再过一遍规则（邮箱、手机号、金额、长数字串、`sk-`/token 形态、URL 查询串）命中即打码。正则拦不住中文人名和客户名，所以再加一道：用生产已有的员工名册和客户名单（采集器经 ingest 接口拉取哈希列表）做词典匹配。
- **只有摘要出机**：证据上传只带 id、sha、时间、类型，**不上传任何原文**（会话标题、handoff 正文、`.deploy_state` 目录名都可能带客户名或金额，例如 handoff 里有员工姓名加美元金额）。技术视图展示证据时显示「commit `07c450d8`」「Codex 会话 11-23」这类结构化标签，原文只在开发机本地可查。
- **P0 没有大模型时**：标题只用 commit 首行（项目约定为英文意图描述，风险最低）经同一套规则过滤；handoff 正文 P0 不上传。
- **全员更新日志一律人工确认**（§7）。

## 6. 上传与调度

- **接口**：生产 `POST /api/devlog/ingest`，机器对机器，用 Settings 里的 `DEVLOG_INGEST_TOKEN`（只存哈希比较，不进代码），按红线 3 在白名单注释说明。按 `item_key` + 指纹批量 upsert，幂等，重复上传无副作用。
- **通道防护**：服务端 schema 只接受白名单字段，文本字段限长（标题 40 字、摘要 300 字），整包限大小；超限或出现未知字段整批拒收，防止有人把原文塞进来。token 支持新旧两个并存以便轮换，轮换步骤写进 `docs/runbook.md`。
- **采集器**：`scripts/devlog/collect.py`，本地增量状态放 Git 忽略的 `.devlog_state/`。只在生产 `commission_db` 写自己的 `ark_devlog_*` 表，不碰 `lsordertest`。
- **触发**：
  - Windows 计划任务：8:00–23:00 每 2 小时一次；
  - 手动：`python scripts/devlog/collect.py --push`。
  - 发布后不用触发：账本由部署器在生产侧直接写，页面即时显示「新发布待核对」，下一轮采集完成内容比对。
- **缺源不等于消失**：某个来源读取失败时，本轮只更新读到的部分，已有事项不降级、不删除，同步记录里写明哪个源失败。
- **数据过期时整体降级**：超过 6 小时未同步，KPI 和看板整体置灰，并在顶部写明「数据截至 XX:XX，开发机可能未开机」，避免拿过期的「待发布」数字做决策。

> ⚠️ 启用门槛：这是一条新的「开发机 → 生产」定时写入通道。按项目宪法，远端写入需亮哥明确授权——上线时单独确认一次，开关放在计划任务上，随时可停。

## 7. 页面

> 可交互原型：[docs/prototypes/ark-devlog-board.html](../prototypes/ark-devlog-board.html)（顶部黑条切换「技术视图 / 全员更新日志」和「数据过期」状态，示例数据为虚构的摘要）。

### 7.1 技术视图「方舟开发动态」 `/system/devlog`（权限 `devlog:read`）

- **顶栏**：时间范围（今日 / 本周 / 本月 / 自定义）＋ 类型、模块、代理（Codex/Claude/人工）筛选；右侧同步健康状态。时间范围按状态事件的时间落桶（§3.1），所以过去的时间段可以如实回看。
- **首屏不被旧分支淹没**：回填起点之前的、以及内容已等价进 main 的旧分支默认不显示；「停滞」默认折叠成一行「另有 N 项停滞」。
- **待发布清单**：点 KPI「待发布」进入专门列表，逐项列出上线前提——迁移编号、需新增的配置/开关、需分配的权限、需要的启用日。这些前提由采集器从迁移文件和 diff 中确定性提取（新增 Alembic revision、`config.py` 新字段、`seed_role_permissions` 新 code），回答「这次能不能发、发之前要做什么」。
- **KPI 一行**：上线功能 · 修复问题 · 数据修复 · 开发中 · **待发布**（已合入未部署，有数字就高亮）。
- **主体两种视图（Tab）**：
  - 看板：开发中 / 已提交 / 已发布 三列，卡片显示标题、类型标签、模块、代理、停留天数；「已提交」列卡片上带细分状态（待合并/待推送/待发布）。
  - 时间线：按天分组的流水，每天一段「上线了什么、修了什么、修了哪些数据」，适合周报和汇报。
- **详情抽屉**（沿用 DetailDrawer）：摘要 + 证据清单（分支、commit、会话标题与 id、handoff 条目、发布记录、修复回执），以及操作：合并到…、拆分、改名、改类型、隐藏、标为放弃、「生成更新日志草稿」。
- **导出**：本周/本月时间线一键复制为 Markdown。

### 7.2 全员视图「方舟更新日志」（所有登录用户）

- 只收**已发布**且经技术侧确认的条目；业务语言（「订单发票页现在可以……」），按日期倒序、按模块分组，不出现分支、commit、客户、订单号。
- 发布流程：技术视图里点「生成更新日志草稿」→ 大模型改写成业务语言 → 亮哥改/确认 → 发布。新内容在顶栏给一个小红点，看过消失。
- 工作台可加一张「最近更新」卡片（复用 cards.js 注册表），P2 再做。

## 8. 后端结构（领域模块 `app/devlog/`）

表（按命名宪法，带表/列中文注释）：

| 表 | 用途 |
|---|---|
| `ark_devlog_items` | 事项：key、标题、摘要、类型、模块、状态、各状态时间、指纹 |
| `ark_devlog_evidences` | 证据：类型（branch/commit/session/handoff/release/repair）、外部 id、时间（不存原文） |
| `ark_devlog_item_events` | 状态事件：事项、从→到、发生时间、触发证据；统计按它落桶 |
| `ark_devlog_overrides` | 人工修正：合并/拆分/改名/改类型/隐藏，记录操作人与时间 |
| `ark_devlog_releases` | 发布账本镜像：时间、revision、范围 |
| `ark_devlog_changelog_entries` | 全员更新日志条目：业务文案、关联事项、发布人、发布时间 |
| `ark_devlog_sync_runs` | 每次采集的时间、各来源结果、上传条数 |

权限：`devlog:read`（看技术视图）、`devlog:write`（人工修正、发布更新日志）、`changelog:read`（全员视图，默认授予所有角色）。状态与时间全部北京时间（红线 23）。

## 9. 分期

| 期 | 内容 | 价值 |
|---|---|---|
| P0 | Git + 部署器写账本（含回填）+ 采集器（内容等价判定、过程分支排除、事项键持久化）+ ingest 接口 + 技术视图看板/时间线/待发布清单；标题用过滤后的 commit 首行，无大模型 | 先回答「哪些在开发、哪些待发布、哪些已上线、发之前要做什么」，全部是确定性数据，可信 |
| P1 | 接 Codex/Claude 会话与 handoff 归并、handoff 对账、数据修复回执、摘要与去敏、人工修正 overlay | 回答「做了什么、解决了什么、修了什么数据」 |
| P2 | 全员更新日志 + 小红点 + 工作台卡片 + Markdown 导出 | 对全员公开成果 |

> 2026-11-23 P0 实施范围：
> - **运行版本文件推迟到 P1。** 它要写进候选源码目录，会碰到部署器「无本地改动、无未知文件」的门禁；P0 由部署器在全部验收通过后才写账本作为替代。
> - **恢复入口暂不写账本**（`release_finalize.py`、`recover_release_completion.py` 等），发生恢复发布后用回填脚本 `--add` 手工补一条。

# WhatsApp 话术第一、第二阶段

范围：改进草稿质量并支持持续询盘复盘；不包含自动发送、库存/核价工具、实际订单或任务派发。代码在 `codex/whatsapp-reply-continuity`，生产发布另行授权。

## 对话行为

- 继续采用两次有界调用。Planner 生成本轮具体动作、责任人、完成信号、未回应客户请求、已回答问题、证据摘录；不生成长篇推理。Generator 先回答当前问题，只补当下阻塞，通常1至3句，不必每轮追问。
- 客户先要目录再选款时，数量不是提供资料的统一前提。初步数量与确认订单分开。来源严格区分客户、卖方自述和人工核实，草稿/goal不能充当消息证据。
- 数字检查增加客户明确提供的 SKU、款数和件数，支持有效历史需求及人工核实。禁止无依据推算总件数和引用已替代的旧数量；金额、交期、库存等动态承诺仍禁止。
- 近似重复已回答的问题会被独立校验拦截；语义改写仍需要完整对话质量评估，结构检查不宣称能证明所有事实正确。

## 知识和资料

`config/whatsapp-reply-phase12.json` 保留原3条必要政策、9段方法，加入8段已逐段检查的公开FAQ事实：混合供体、Double Drawn条件、硅油处理、原发长度边界、客户自行检测、定制色样、配色过程和批次色差。所有绑定固定修订号及SHA-256，并有别名和适用范围。

不采用旧范文的single-donor泛化、工艺温度冲突、行业收益、隐含价格/交期、内部审批门槛。未重新发布或更改线上知识正文。

显式 `shareable_text` 只允许 public_fact，资料片段由服务端从授权来源输出，模型不能生成任意资料链接。当前交付是可对客FAQ片段，不是假装已准备产品目录/PDF；目录原件、图片和受控附件检索属于后续实际资料接入。缺少目录时生成内部待办，不说“已经发送”或“正在整理”。

读取按单次操作缓存同一文档，避免逐章节重复数据库读取；每次请求、生成返回、缓存使用仍重新核对发布修订和ACL，不能跨用户复用文档缓存。

## 询盘状态和界面

- 默认开启“保存询盘复盘”；每个新聊天首次生成创建随机记录，可先选既有记录或切换为仅本次片段。标签只供人工识别。
- 扩展没有可靠客户唯一标识，因此当前聊天内连续使用；切换、整个消息区替换或页面重载后不自动恢复。恢复必须先预览记录、确认属于当前客户及采购事项。同一客户完整历史重绘也可能断开，这是保守的身份边界。
- 最多100份有效记录/账号，记录只在准确方舟用户与配对设备范围内可读写。重新配对产生新设备时，不自动迁移旧记录。
- 保存内容：最多80项需求/已问问题/客户请求/承诺，每项摘要240字符、最多3条摘录（每条240字符）及角色、请求UUID、片段索引、观察时间；完整聊天、未发送草稿、姓名地址和WhatsApp标识不入库。联系方式进行保守遮蔽，语义个人信息仍需避免选入摘要。
- 确认需求、初步意向、卖方提及、卖方声称完成、人工核实/完成分开。人工修正附说明并优先用于当前复盘，模型不能覆盖人工纠正。人工状态不等同于工具回执；不自动创建CRM任务。
- 回复先展示，记录/承诺和内部接管摘要折叠；可查看证据、人工核实/取消/重新待办、删除记录。接管可暂停生成并保留摘要；不向其他人发送通知。

## 保存、并发与保留

生成只返回候选。前端确认 operation/epoch/context/draft仍有效后发送独立commit；后端仅采用自己的120秒进程内缓存，重检权限、所属记录、实例UUID和CAS版本。重复commit幂等，旧revision不得覆盖人工修正，删除重建同UUID也不能接受旧实例候选。

取消或新消息先于提交发出时不保存该候选；提交已经发出后保存当时有效的观察快照，不是“切换后回滚任何既有写入”。同聊天新消息到达时，已成功的保存/人工修改结果仍同步记录版本；跨聊天迟到结果不改变新聊天状态。保存失败保留错误供重试/刷新，不自动重跑付费模型。

默认自创建日起固定30天，到期立即不可读，现有配对清理任务负责物理删除。`WHATSAPP_REPLY_MEMORY_RETENTION_DAYS`范围1至90；关闭记忆开关不会删除已有记录。数据库/备份的既有保留策略另行生效，不宣称能撤回客户已收到的信息。

## 配置与上线准备

1. 经统一部署入口执行迁移143；不从开发机升级共享数据库。迁移只新增表，回滚代码时保留业务复盘表。
2. `WHATSAPP_REPLY_MEMORY_ENABLED=true`，`WHATSAPP_REPLY_MEMORY_RETENTION_DAYS=30`；原话术总开关/人员权限保持现有范围。
3. 校验并生成本地配置片段：

```powershell
python -X utf8 -m scripts.validate_whatsapp_reply_profile --env-file PATH_TO_EXISTING_ENV --profile ../config/whatsapp-reply-phase12.json --user-id 1 --write-fragment PATH_TO_LOCAL_FRAGMENT
```

命令只读数据库，拒绝直接覆盖`.env`，不刷新变版哈希、不写知识、不调用模型。生成片段包含完整20项绑定；正式应用前复核是否替代现有配置中的其他用途，不盲目覆盖后来新增的绑定。

4. Planner新预设默认max_tokens=3200，Generator=1800；已有管理员自定义预设不会被bootstrap覆盖，上线需按当前预设核对Planner预算。温度和模型不因本次改动自动更换。
5. 后端配置、143迁移及扩展一起验证；发布后先使用合成对话验证记录更新和质量，再开放业务试用。单轮翻译耗时不能当作带历史记忆的两阶段回复SLA。

本次验证使用隔离SQLite、合成消息及本地浏览器fixture。真实模型效果、MySQL生产迁移及实际WhatsApp线上操作须在对应授权和发布后验收，不用模拟调用冒充真实谈单效果。

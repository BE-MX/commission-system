# 私海助理「今日建议」推荐能力补齐方案

> 2026-11-16 · 状态：评估与方案稿，未开发。v1 经独立 Agent 对照源码审查一轮，意见逐条核实后并入本稿（见第七节）。
> 范围：`/client-desk` 私海助理的「今日建议」。不涉及内贸客户跟进（`/domestic/followups`）。
> 事实依据：当前 main 源码 + 2026-11-16 09:10 北京生产机对 Rina（用户 37）的只读汇总查询（只取计数，未读聊天与背调正文）。配置读自北京机；调度器运行在办公室机，其配置文件未单独核对，但生产结果与北京配置一致。
> 上位设计：[私海助理设计文档](../2026-11-04-private-sea-assistant-design.md)、[实现记录](../2026-11-04-private-sea-assistant/implementation-status.md)、[阿里询盘接入设计](../2026-11-05-alibaba-feed-integration/design.md)。

## 一、目标

业务员打开页面，第一眼看到「今天该先找谁、为什么、说什么」。期望覆盖四类场景：

1. 询盘会话里需要继续跟进或回复的客户
2. WhatsApp 近期聊天里有复购或跟进机会的客户
3. 按历史订单推算已到复购周期的客户
4. 订单已发货、需要跟进收货的客户

## 二、现状

### 推荐机制

今日建议分两层，**AI 不选客户**：

| 层 | 做什么 | 位置 |
|---|---|---|
| 规则层 | 工作日 06:30 扫描本人私海，8 条确定性规则命中即成为候选；排序分 = 规则权重之和 × 等级系数 | `client_desk/rules.py`、`queue.py` |
| AI 层 | 每人每天最多 40 位候选送模型（`client_desk_daily` 预设，DeepSeek `deepseek-flash`），产出理由、策略、话术草稿、画像与标签 | `client_desk/runner.py`、`pack.py`、`validator.py` |

AI 结果能反过来影响选人的通道有三个：给客户定 30 天内的复核日期，到期由 R3 重新提名；判为「跳过」时给命中的规则加最长 14 天冷却并隐藏该建议；分析成功后清掉 R4。反过来，分析失败的客户 R4 永远不清，每天重复入队。

### Rina 的实际数据（2026-11-16）

私海 80 位客户。今日建议可展示 **11 位，全部来自 R8「新建客户没跟上」**；11-11 至 11-13 每天 12～13 位，原因相同。

| 规则 | 今日命中 | 未命中原因 |
|---|---|---|
| R8 新建客户没跟上 | 11 | — |
| R4 新增订单或背调资料 | 67 | 设计上不单独展示，仅用于触发画像更新 |
| R1 待回复 / R7 已发未回 / R6 久未联系 | 0 | WhatsApp 账号已接入（103 个会话），但关联到客户的会话为 0，AI 读取授权未开 |
| R5 复购到期 | 0 | `CLIENT_DESK_RULES` 为空，订单分类未校准；11 位 ≥3 笔订单的客户全部判为「暂不推断复购」 |
| R2 跟进日期到期 | 0 | 未设置过跟进日期，手工跟进记录 0 条 |
| R3 复核到期 | 0 | 仅 6 位客户有过成功分析 |

其他：47 位未分级，29 位 E、4 位 D，无 S/A/B（R6 只对 S/A/B 生效）。

### AI 层结果

**全员近 6 天（11-10 至 11-15，28 位有例行分析的业务员）**：

| 结果 | 轮数 |
|---|---|
| 校验失败 | 2944 |
| 成功 | 64（其中 32 条判为跳过） |
| 租约过期 | 4 |

每位业务员的失败率在 91%～100% 之间。这不是 Rina 个人的问题，是全员的 AI 分析基本不可用。Rina 自己每天 40 轮里失败 35～36 轮，成功的 1～3 轮全部判为跳过，上线以来没有得到过一条带策略与话术的可展示建议。

**主因：模型输出被长度上限截断（强证据，未取得 finish_reason 直接证明）。**

- `runner.py` 把单次输出上限固定为 1800 token。
- 2941 轮例行失败里，2791 轮（95%）的单次输出落在 1700～1800 token，即顶到上限；成功的 64 轮多数低于 1700。
- 协议允许的内容远超 1800 token：摘要 600 字 + 画像 5 块各 200 字 + 草稿 1600 字 + 标签与要点。输出被截断后不是合法 JSON，`validator.py` 直接判失败。
- 失败轮全部正好调用 2 次（首轮 + 一次纠正），纠正轮同样被截断。
- 若该模型带推理过程且推理计入输出额度，截断会更早；这一点未核实。

**次要问题（修掉截断后会接着暴露）：**

| 问题 | 证据 |
|---|---|
| 话术里出现 account manager、swift reply、bank transfer 等常见英文词会被当成银行账号拦截 | `validator.py` `CONTACT` 的银行分支，本地已复现 |
| 模型写出资料包里没有的日期（或 2025-2026 这类区间）会被当成电话号码拦截；建档日期在资料包里带时分秒，模型只写日期也对不上 | 同上，本地已复现 |
| `metadata:` 等普通文本被当成危险链接 | `UNSAFE` 的 `data\s*:`，本地已复现 |
| 所有结构类错误（非 JSON、截断、多余键、超长、类型错）统一归为一个代码，且最终只落 `validation_failed` | `validator.py` 96-99 行、`runner.py` 253 行 |
| 调用不带 JSON 模式，模型输出带代码围栏即失败 | `ai/text_snapshot.py` 不允许 `response_format` |
| 资料包里规则写作 `R8_NEW_LEAD`，合法引用键却是 `R-R8_NEW_LEAD`，容易引错（推测） | `pack.py` |

**名额分配**：纯 R4 候选排在最后，不会挤掉可展示的候选；但全员近 6 天有 1694 轮失败落在纯 R4 客户上，这些客户永不展示，纯属消耗。

### 四类场景对照

| 场景 | 现状 | 差距性质 |
|---|---|---|
| 询盘需跟进/回复 | 无规则。阿里询盘是 `manual_only_v1`：业务员显式勾选并手动重分析才读取，不进例行规则。OKKI 邮件、跟进动态未接入 | 既定边界 + 能力缺失 |
| WhatsApp 复购/跟进 | R1/R7/R6 只看末条消息方向与时间，不读内容；且只覆盖已关联并授权的会话 | 数据未就绪 + 能力缺失 |
| 复购周期 | R5 已实现，订单分类未配置时对所有客户失效 | 配置缺失 |
| 已发货跟进收货 | 无规则。「在途」仅用于抑制 R5 | 能力缺失 |

## 三、方案

按「先让已有的东西工作，再加新的」排序。每阶段独立交付、可单独验证。

### 阶段 0：恢复 AI 层（全员受益，最高优先）

**为什么最先做**：现在全员 98% 的分析被丢弃。不修这层，后面补的任何信号都只显示一句规则原因，达不到「说什么」。

1. **解除输出截断**：提高 `runner.py` 的输出上限（建议 4000），同时核对预设里的 `max_tokens`（两者取小）和 85 秒总超时是否够用。若模型的推理过程计入输出额度，改用不带推理的模型或关闭推理。
2. **失败原因可诊断**：`validate()` 把结构类错误拆成「非 JSON / 截断 / 结构不符（记字段位置与错误类型，不含正文）」；`runner.py` 把细分原因和失败轮次落库。前端 `AgentProgress.vue` 按 `validation_failed` 精确匹配文案，细分原因另存字段或前端同步改，不能直接加后缀。
3. **修校验器误伤**：银行分支要求后面跟的是账号形态（含数字）而不是任意单词；日期与年份区间不视为电话；`data:` 仅在 URI 语境拦截；资料包里的时间按日期也计入可信集合。补对应单测。安全边界（不输出未知联系方式、收款指令）不放松。
4. **纠正轮说清错在哪**：现在的纠正语只说「未通过检查」。把细分原因（不含正文）告诉模型。
5. **停止纯 R4 客户的无效消耗**：纯 R4 且没有任何订单、聊天、背调的客户不送模型；失败后设短冷却，避免每天重复失败。
6. **零资料的 R8 客户不走「跳过即冷却 14 天」**：这类客户模型判跳过是合理的，但会让它从今日建议里消失。R8 无资料时只展示规则原因，不送模型。

**验收**（沿用[既有验收口径](../2026-11-04-private-sea-assistant/acceptance.md)）：失败率 ≤5%（跳过不算失败）；另加一项「每人每天非跳过的可展示 AI 建议数」，修复后不得低于修复前的可展示规则建议数。

### 阶段 1：补数据与配置（与阶段 0 并行）

| 事项 | 做法 | 效果 |
|---|---|---|
| 订单分类校准 | 配置 `CLIENT_DESK_RULES.order_classification`。**前置问题**：Rina 客户的 OKKI 订单 `status` 只有一个主值，`status_name` 是「已结束 / 部分回款 / 待回款」类回款状态，没有发货或取消语义；现有代码只能按 `status` 取键、只能读订单表顶层列作样品标识；样品标识若在 `custom_fields` 里，或需要按 `status_name` 区分，**必须改 `sources.py`**，不是纯配置 | 激活 R5 |
| WhatsApp 会话关联 | Rina 在页面「未关联会话」里把会话关联到客户 | 关联即激活 R1/R7/R6（规则扫描不需要 AI 授权） |
| WhatsApp AI 读取授权 | 账号本人明确同意后开启 | AI 才能读聊天写话术；未授权时这些客户的分析会以「资料变化」中止，只显示规则原因 |
| 客户分级 | 有订单的客户优先补 S/A/B | 激活 R6，排序分有区分度 |
| 跟进日期 | 引导业务员在档案里设下次跟进日期 | 激活 R2 |

会话关联、分级、跟进日期不依赖阶段 0，现在就可以做。订单分类的代码改动并入阶段 2。

**验收**：Rina 今日建议中出现 ≥3 种不同规则原因。

### 阶段 2：补规则与呈现

1. **R9 已发货待确认收货**（新规则）
   - 数据来源待定，两个候选：
     - `shipment_tracking`（运单跟踪）：有发出、签收、预计送达时间，但只有收件公司名文本，**没有 OKKI 客户 ID**，需要建立运单到客户的关联。
     - 出库/发票链路：有客户归属，需确认是否带运单与签收状态。
   - 触发口径建议：已签收 N 天内未有接触 → 提醒回访；预计送达已过且未签收 → 提醒查件。
   - 做之前先用只读查询评估运单到客户的可关联率，低于可用线则先补关联再做规则。
2. **今日建议由「按原因筛选」改为「按原因分组」**：页面已有按原因的筛选项（`deskController.js` 的 `REASON_FILTERS`），后端 `today` 已返回 `rule_codes` 和各类计数。把默认视图改成分组：待回复 / 到期跟进 / 复购 / 发货回访 / 新客 / 久未联系，让业务员不用点筛选就知道每位客户为什么在这里。纯前端改动。
3. **询盘规则 R10** 不在本阶段做，见第四节决策 D1。

**验收**：R9 有测试覆盖（含红线 23 的跨日与非东八区用例）；分组在 1440 与 390 宽度下可用。

### 阶段 3：AI 语义信号

让 AI 读内容后能提名客户，但不绕过规则层。

- 复用现有「复核」机制：模型分析时若发现明确的后续事项（客户说下月补货、有问题未答完、样品已到待反馈），输出结构化的复核日期与条件，到期由 R3 提名。当前协议已支持，问题是阶段 0 之前几乎没有成功分析，这条通道实际是断的。
- 扩展点：给复核增加类型字段（复购意向 / 待答复 / 样品反馈），用于阶段 2 的分组展示和效果统计。类型值域从字典运行时注入，不写死在协议里（红线 7）。
- 不新增「全量会话每日过模型」的批处理：成本与外发范围都会扩大，先看复核通道修通后的效果。

**验收**：有成功分析的客户中，复核到期后被 R3 提名并展示的比例可统计。

## 五、风险与边界

- **规则层数据只核了 Rina**：其他业务员的规则命中分布未查。AI 层失败率已核全员。
- **截断是强证据而非直接证明**：依据是输出 token 顶到上限的分布，未取得模型返回的结束原因。阶段 0 第 2 步上线后可直接证实。
- **WhatsApp AI 授权**是业务员本人的同意事项，系统不能代开。
- **订单分类校准错了会误报复购**：校准后先人工抽查 R5 命中名单再放开。
- 所有数据库结构变更走 Alembic、由部署入口执行；阶段 0 与阶段 2 第 2 项预计不需要迁移，R9 与复核类型字段可能需要。
- 本方案不改变「模型输出不落正文日志」「询盘 manual_only」两条既有边界。

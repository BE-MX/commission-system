# Accio 背调智能体（Client Scout）复用评估

> 2026-11-16 · 状态：评估稿，未开发。v1 经独立 Agent 对照源码与压缩包审查一轮，意见逐条核实后并入（第八节）；第九节 Monid 部分为审查后新增，未送审。
> 输入：`agent-core.zip`（Accio Work 上的「客户情报专家 Client Scout」完整配置，含规则、技能、记忆、日记与工具结果）。
> 对照对象：方舟现有背调链路（OpenClaw 销售 Agent + `ark-company-research` 技能 + `customer_research_v1` 结果契约）及私海助理的背调展示。
> 事实依据：压缩包内文件、当前 main 源码、2026-11-16 北京生产库只读汇总（只取计数，未读报告正文）。
> 关联：[今日建议补齐方案](README.md)。

## 结论

1. **不能整体搬**。两个智能体跑在不同的运行环境、用不同的工具、交付不同形态的结果，而且 Accio 那套有几处做法与方舟已定的数据边界冲突。
2. **值得搬的是方法和报告结构**。Accio 背调「内容完善」来自三样东西：来源面广、行业判读细、报告有固定骨架。这三样都能移植到方舟现有技能里。
3. **方舟背调现在的问题比「格式不够好」严重**：生产上 390 份已完成的背调，140 份是「查不到」的空结果，250 份有内容的里只有 5 份过了审核，其余 245 份待审。私海助理只展示已审核的，所以业务员实际上几乎看不到背调内容。这个要先解决，否则移植完也没人看得到。
4. **两边正好互补**：Accio 的顽疾是「编造精确细节」（反思记录里同一类教训重复了 19 条），方舟的「事实入库再引用」机制正是治这个的；方舟的顽疾是「查得太窄太薄」，Accio 的来源地图和判读框架正是治这个的。

## 一、两套背调的差异

| | Accio Client Scout | 方舟现有背调 |
|---|---|---|
| 运行环境 | Accio Work 桌面端，Windows | OpenClaw，北京服务器 |
| 触发 | 业务员在对话里丢线索，逐个做 | 方舟排任务，Agent 定时领取，一次一个 |
| 输入 | 任意线索：公司名、官网、邮箱、人名、社媒号 | 方舟客户 ID + 冻结的客户资料与订单摘要 |
| 工具 | 搜索、抓网页、小满 AiReach 基线情报、Maigret 用户名扩展、x315 海关数据 | 搜索、抓网页、方舟 MCP（读任务、写事实、交结果） |
| 来源范围 | 官网、工商、社媒、预约平台、品牌认证目录、海关、口碑站 | 可入库的来源事实只有 4 种，全部要求出自公司官网页面：主体、经营概况、产品目录、公开商业联系方式。供应商与风险只能写成推断。Agent 模板虽允许拿社媒、Google Business、预约页当线索，但这些内容没有对应的事实类型可以入库 |
| 结果形态 | 一篇完整的中文报告，直接贴在对话里 | 结构化结论：每条结论必须引用本次采集入库的事实及其哈希 |
| 内容 | 结论、公司概况、决策人与触达、采购潜力、海关数据、活跃度与风险、销售下一步、来源链接；外加 A～D 客户等级、开发难度、试探话术 | 六类结论：客户主体、经营情况、产品适配、供应商现状、风险与缺口、建议动作。明确禁止输出等级、成交概率、触达草稿 |
| 审核 | 无 | 需人工审核通过才对业务员可见 |

### 方舟背调的生产现状

| 指标 | 数值 |
|---|---|
| 已完成背调 | 390 |
| 其中空结果（查不到） | 140（36%） |
| 有内容的报告 | 250 |
| 已审核通过 | 5 |
| 待审核 | 245 |
| 每份报告结论数 | 中位数 3 条，90% 的报告不超过 5 条 |
| 只覆盖 1 类结论的报告 | 115 / 250 |
| 六类全覆盖的报告 | 12 / 250 |
| 各类结论总数 | 客户主体 301、产品适配 132、经营情况 121、风险 48、建议动作 46、供应商现状 17 |

对比 Accio：单个客户的一份报告通常包含团队成员、双店地址、社媒规模、接发实证、经营特征、政策风险、切入口等十余个要点。

私海助理的展示（`board.py` `research_report`、`ResearchReport.vue`）：只取已审核或免审的结果；空结果显示「无背调结果」；有内容时显示一句结论（取第一条「建议动作」的前 160 字）加各类结论的文字列表，页面有「查看背调来源」入口和来源条数。不显示每条结论的置信度（事实上已存有置信度，只是没带到界面）和联系人。

**为什么薄（审查后补充，已对照代码）**：

- 私海补全任务的任务书只要求 4 件事：官网与主体关联、公司业务与经营模式、公开商业联系方式、主营产品（`private_enrichment_service.py`）。与可入库的 4 种事实一一对应。所以「客户主体 301 条、供应商现状 17 条」是任务设计的结果，不是 Agent 偷懒。
- 每条结论必须至少引用一条已入库事实。没有官网的小沙龙，四种事实一条都写不进去，只能交空结果。
- 空结果只允许出现在「私海补全 + 主体不确定 + 零事实」的任务上；其他类型查不到只能记失败。所以 36% 这个比例只对私海补全有意义。
- 统一客户档案设计里本来规划了「已核验平台」「次级公开来源」两个来源级别，后端一直没登记。
- 待审核的任务会挡住同一客户再次发起补全；审核只有管理员逐条操作的接口。
- Agent 使用的模型能力也可能是原因之一，未验证。

|---|---|---|
| 整套 agent-core（规则、SOUL、心跳、工具注册） | 为 Accio 运行时和 TeamLeader 路由写的，方舟侧没有这些概念 | 不搬 |

| 试探话术、破冰句 | 方舟背调禁止输出触达草稿；话术由私海助理的分析环节出 | 背调只出「建议验证的问题」 |

| 小满 AiReach 基线情报 | 依赖个人令牌，放在个人电脑的用户目录里 | 若要用，需改为服务端凭据并走方舟配置；本稿不纳入 |

| 切入角度里的「性价比」 | 私海助理输出校验把「性价比」列为禁用词，带这个词的建议会被整条丢弃 | 移植分类时改名 |

## 四、建议的做法

顺序按依赖关系排。第 1、2 步是地基，不做的话移植内容进不来、进来了也看不到。

### 第 1 步：让已有背调对业务员可见

「只展示已审核」是私海助理设计时定的风险对策，且「审核通过」还会触发客户资格判断，所以不能简单地批量改成通过。建议：

- 展示层增加「未审核」状态：业务员能看到自己客户的待审背调，带明显的「未经审核」标记，审核状态本身不动。
- 未审核内容是否送给私海助理的分析模型，单独决定（第六节 D1）。
- 空结果显示已存的缺口原因和缺失信息清单，而不是「无背调结果」。
- 把结论所引事实的置信度带到界面。不需要改契约。

### 第 2 步：扩任务书、事实类型和来源级别

这是「薄」的根因，三样要一起改：

- 任务书从 4 项重点扩到覆盖采购潜力、活跃度、供应商线索、风险。
- 事实类型增加对应的可入库种类，并允许「查过但未查到」的缺口条目不带引用。
- 把设计里已有的「已核验平台」「次级公开来源」两个来源级别登记上，让 Google Business、预约平台、品牌认证目录、公开商业社媒主页的内容可以入库，置信度低于官网。
- 改动点：后端事实登记与校验、MCP 说明、Agent 模板、技能。

### 第 3 步：移植判读框架与报告结构

- 把双轨流程、来源地图、发制品分类、停止条件写进 `ark-company-research`。
- 客户分类作为结构化子项。公开商业联系人走现有的「商业联系方式」事实类型，不新增联系人字段：新增个人联系人类字段可能把整份报告的密级抬高，导致业务员看不到。
- 私海助理的背调页按 Accio 报告骨架重排：结论 → 概况与分类 → 联系方式 → 采购潜力 → 风险 → 建议验证的问题 → 来源。

### 备选：直接导入 Accio 报告

让 Accio 智能体继续按现在的方式出报告，方舟只负责存和展示（标注「外部背调 · 未结构化核验」）。

- 好处：最快，内容立刻达到现在 Accio 的水平。
- 代价：绕过事实闭包，Accio 反复出现的编造问题会原样进入方舟；报告里的个人信息范围超出方舟边界；仍然是业务员手动逐个触发，不能批量覆盖私海。
- 不建议作为主路径。如果希望试点期先有内容可看，可以作为过渡，但要明确标注来源并设下线时间。

## 五、Accio 智能体自身可优化的地方

| 问题 | 证据 | 建议 |
|---|---|---|
| 同一类错误反复出现：工具结果被截断或失败时仍输出精确细节 | `REFLECTION_MEMORY.md` 从 09-01 到 11-11 共 19 条几乎相同的教训 | 靠追加提醒已经证明无效。要改成机制：精确事实先落证据清单再写报告，报告里的每个数字、人名、地址必须能对上清单条目 |

| 无关技能占位与重叠 | SEO 竞品分析、亚马逊评论分析、Twitter 关系图、组织架构调研与背调无关；`company-research`、`people-research` 与背调技能功能重叠 | 无关的停用，重叠的二选一 |
| MCPC 定义不一致 | `AGENTS.md` 写的是 Market、Customer、Product、Channel；技能注册里写的是 Market、Client、Product、Consumer | 统一 |
| 技能补丁未合并 | `SKILL.patch.md` 单独放着 | 合并进正文后删除 |
| 记忆文件承担了客户库的职责 | `MEMORY.md` 约 30KB，混着客户档案、对外签名、手机号、服务地址；单日日记最大 41KB，全是客户细节 | 客户事实回写 CRM 或方舟；记忆只留方法论 |
| 个人信息采集范围过宽 | 反思记录提到采集过配偶名、年龄、房产估值等；技能鼓励用个人邮箱做精确检索 | 收窄到商业身份：公司、公开职务、公开商业联系方式 |
| 目录里有杂物 | 技能目录下有名为 `nul` 的空文件和一个路径被压扁的文本文件、`__pycache__`、嵌套的 zip | 清理 |

## 六、需要决策

| 编号 | 问题 | 建议 |
|---|---|---|
| D1 | 待审背调是否对业务员可见、是否送模型 | 业务员可见并标「未审核」；暂不送模型，等抽检一批确认质量后再放开。审核状态不改，避免连带触发资格判断 |

## 七、未核实事项

- Accio「反复编造」的 19 条记录来自其自动反思机制，按被截断的工具输出判定，可能含误报，未抽样核对。
- 没有读方舟背调报告的正文，报告「薄」是按结论条数和分类覆盖判断的，不是按内容质量。
- 空结果占比高的原因（来源限制、Agent 执行深度、客户本身无公开信息）没有拆分验证。
- Accio 智能体当前实际可用的工具以压缩包里的注册文件为准，没有在其运行环境里核对。
- 压缩包里的工具结果和日记含客户个人信息，本次只读取了配置与方法部分。

## 九、Monid 能补什么

Monid（monid.ai）是一个数据接口的统一网关：一个账号、一个预付钱包，按次付费调用上百家数据供应商的接口。Agent 用「搜接口 → 看参数和价格 → 调用」三步使用，支持 MCP 和服务端 API 两种接法。2026-11-16 公开目录为 3192 个接口、102 家供应商。

以下价格取自当天公开目录，实际以调用时为准；接口质量没有实测。

| 背调缺口 | Monid 上的接口 | 单次价格 |
|---|---|---|
| 小沙龙没有官网，只有 Instagram / TikTok / Facebook | 公开主页资料：简介、粉丝数、近期帖子 | 约 $0.0002～0.015 |
| 实体是否真实、在营 | Google 地图商家信息与评论、Yelp 商家与评论、Trustpilot | 约 $0.0002～0.05 |
| 海关与供应商线索 | 腾道（Tendata）：按进口商查询、提单级记录、公司画像 | 进口商排名 $0.019/条，公司画像 $0.08/条，提单记录为阶梯价需查看详情 |
| 公司规模与团队 | LinkedIn 公司主页、员工列表 | 约 $0.0002～0.02 |
| 公开商业邮箱 | Hunter 按域名查邮箱 | $0.0245/条 |
| 域名注册时间 | WHOIS、域名年龄 | $0.02～0.03 |

粗估：每个客户做「社媒主页 + 地图商家 + 评论」约 $0.01～0.05；加海关公司画像约 $0.1～0.3。

### 对两套背调各自的意义

- **对方舟**：它补的正是第 2 步要放开的那几类来源，而且返回的是结构化数据，比让 Agent 自己抓网页稳定（Instagram 这类页面普通抓取基本拿不到内容）。
- **对海关数据**：服务端接口，不需要一台登录了会员账号的 Chrome。这比 x315 的浏览器桥接方案简单得多，值得优先试。
- **对 Accio**：可以直接用 MCP 接上，立刻扩大来源面。

### 怎么接

| 方式 | 做法 | 适用 |
|---|---|---|
| 直接接 MCP | 在 Agent 里加 `https://mcp.monid.ai/v1`，Agent 自己搜接口、自己调 | 试用和评估。不适合直接上生产 |
| 方舟后端封装（Monid 文档里的「精选接口」模式） | 方舟只挑 5～8 个只读接口，封装成方舟自己的 MCP 工具给 OpenClaw；密钥走后端配置；返回结果自动登记为对应来源级别的事实 | 生产 |

不建议生产上直接接 MCP 的原因：

- 目录里不只有查询类接口，还有打电话、开邮箱、生成视频等会产生实际动作和持续费用的接口，Agent 可以自己发现并调用。
- 返回的数据不经过方舟的事实入库，防编造机制就绕过去了。
- 方舟规则要求不把内部 ID 和私人联系信息发给外部；封装层可以强制只发公开的商业标识（公司名、域名、公开账号名）。

### 风险与未核实

- 北京服务器能否稳定访问 Monid 未测。开发机查公开目录时出现过一次连接中断。
- 数据经 Monid 再到上游供应商，是两层第三方。
- 社媒抓取类接口的合规性与稳定性取决于上游供应商；Monid 提供接口健康度指标和争议退款机制，效果未验证。
- 腾道接口对小沙龙的覆盖率未知：小客户多走快递小包，海关记录本来就少。
- 需要注册账号并充值，支持预算上限和单次调用上限。
- Monid 解决的是「来源」，不解决第 1 步的可见性和第 2 步的任务书与事实类型。只接 Monid 不改这两处，查到的东西仍然入不了库、业务员仍然看不到。

### 建议的试法

挑 10 个此前交了空结果的私海客户，用 Monid 的社媒主页、地图商家、腾道三类接口各查一遍，记录命中率、信息量和花费。结果好再做后端封装。

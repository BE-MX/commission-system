# 展会试戴 · 扫码上传照片入口

- 日期：2026-08-01
- 模块：`app/expo/`（展会 AI 试戴）
- 状态：设计定稿，待实现

## 1. 要解决什么

展位现场客户用平板拍照，有两类客户走不通：

1. **相册里有更好的照片**——现场光线与状态拍不出想要的样子，手机里本来就存着满意的照片；
2. **手机相机比展位平板好**——客户自己的手机成像质量高于平板前置摄像头。

因此在拍摄页增加一个扫码入口：客户用自己手机打开上传页，从相册选或现场拍一张，照片回到 kiosk 走既有生成管线。

**这是次级入口，不替代现场拍照。** 快门仍是主入口，现有操作习惯不变。

## 2. 已确认的产品决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 入口形态 | 拍摄页上的次级按钮，点开才显示二维码 | 不分散快门的注意力 |
| 等待模型 | 二维码面板开启期间挂起 60 秒无操作清场 | 扫码→翻相册→上传必然超过 60 秒，不挂起则功能上线即坏 |
| 照片把关 | 传到后进 kiosk 既有预览态，「重传 / 就用这张」 | 顾问能当场拦下全身照、合影这类会让面容分析翻车的图 |
| 手机页能力 | 相册选择 **与** 现场拍摄并列 | 两类痛点各占一条路，只做相册会漏掉「手机拍得更好」的客户 |
| 令牌有效期 | 10 分钟 | 够客户翻相册，又限制二维码被拍走后的滥用窗口 |
| 手机页是否显示客户称呼 | **不显示** | 共享屏发出的码带姓名是隐私风险，收益（防扫错码）不足以抵消 |

## 3. 架构选择：签名令牌 + 待取文件（无迁移）

### 3.1 为什么不建表

候选方案有三个：签名令牌 + 文件、新建 `ark_expo_upload_tickets` 表、令牌挂在客户行上。选第一个。

**唯一需要持久化的东西是照片文件本身。** 令牌的两个职责——绑定到哪个客户、什么时候作废——都能用密码学表达，不需要存储。若另立一张 ticket 表，「照片有没有传上来」就有了两份真相（表里的 status 与磁盘上的文件），必须保持同步；本项目已经在这类不同步上栽过（素材域 folder_upload 静默失败、内贸 RR 快照）。

**接受的代价：令牌在 10 分钟有效期内可重复使用。** 有人拍下二维码后，可在窗口内反复往该客户名下传图。两道防线：有效期短；kiosk 预览确认由顾问把关。要做成严格一次性必须落库——如果日后现场真出现滥用，再补 ticket 表，届时令牌格式不用变。

### 3.2 令牌格式

```
{customer_id}-{exp}-{sig}
sig = HMAC-SHA256(EXPO_UPLOAD_SIGN_SECRET, f"{customer_id}:{exp}")[:16]
```

沿用 `app/asset/asset_service.py:622` 的既有签名范式，密钥经 `app/core/config.py` 的 Settings 读取（禁止直读 os.environ）。`customer_id` 与 `exp` 明文随令牌传输，篡改任一项签名即失配。校验先查过期再比签名，比较用 `hmac.compare_digest`。

## 4. 数据流

```
kiosk 拍摄页 ──点「扫码传照片」──▶ POST /kiosk/upload-ticket?customer_id=
                                    ↓ {upload_url, expires_at}
                              画二维码 + 挂起 idle 清场
客户手机  扫码 ──▶ GET  /api/expo/upload/{token}   免鉴权，服务端渲染 HTML
              ──▶ POST /api/expo/upload/{token}   multipart → uploads/expo/pending/
kiosk 轮询 ──▶ GET  /kiosk/pending-photo?customer_id=   → {photo_url, uploaded_at}
              ↓ 一旦拿到：关闭二维码面板、恢复 idle 计时、进既有预览态
        ──▶ POST /sessions (pending_photo=<文件名>) ──▶ 既有分析/合成管线
```

轮询沿用 `useTryOnFlow.js` 既有的 `POLL_MS`（2 秒）与在途守卫，不新引入一套节奏。

确认「就用这张」后，待取文件**复制**到 `PHOTO_DIR`，`commit` 成功之后才删除待取原件（删除失败只记日志，`sweep_stale` 兜底）。

> **2026-08-01 修订**：本节原写的是「移动而非复制，避免磁盘留两份」，代码审查用探针证伪了——把 `db.commit` 打桩抛异常后，待取文件已不在、会话没建成、`photos/` 里留下孤儿，客户只能被打发回去重新扫码。展位连的是公网 RDS，连接抖动是真实故障率。而「省一份磁盘」这个收益本来就已经有了：`sweep_stale` 按 2 小时窗口回收 pending 目录，不依赖这里的移动来收敛。等于拿崩溃安全性换了一个已经拥有的性质。

## 5. 端点

| 端点 | 鉴权 | 说明 |
|---|---|---|
| `POST /api/expo/kiosk/upload-ticket` | `expo:write` | 发码；顺带清理该客户的旧待取文件 |
| `GET /api/expo/upload/{token}` | 免鉴权（令牌即凭证） | 手机上传页，服务端渲染 HTML |
| `POST /api/expo/upload/{token}` | 免鉴权（令牌即凭证） | 收图，落 pending 并 downscale |
| `GET /api/expo/kiosk/pending-photo` | `expo:write` | 取该客户最新待取照片 |
| `POST /api/expo/sessions` | `expo:write` | **改造**：`photo` 与 `pending_photo` 恰好二选一 |

两个免鉴权端点须在代码内注释说明「令牌即凭证」的白名单理由（CLAUDE.md 后端约定第 3 条）。

### 5.1 `POST /sessions` 的改造方式

`photo: UploadFile = File(None)` + `pending_photo: str | None = Form(None)`，两者必须恰好提供一个，否则 400。

**不新开建会话端点**：会话创建带着分析管线启动的副作用（`ai_pipeline.start_analysis`）与同意校验，两条路会分叉，日后改一条漏一条。`service.create_session` 内部只在「照片从哪来」这一处分支，落盘之后的逻辑完全共用。

`pending_photo` 只接受纯文件名，服务端拼接到 pending 目录后校验解析出的真实路径仍在该目录内，防路径穿越。

## 6. 三个必须处理的坑

### 6.1 云端展会实例 `SCHEDULER_ENABLED=false`

北京展会实例刻意关闭了 APScheduler（防与办公室实例定时任务双跑），而那台正是跑展会的机器。**待取照片的清理不能挂定时任务**，挂了也不跑。

改用机会式清理：发码时与确认时各扫一次 pending 目录，删除 mtime 超过 2 小时的文件。残留上界由此有保证，不依赖调度器。

### 6.2 二维码 URL 必须降级到 http

展位平板自己走 https 只为拿 secure context 开相机，服务器挂的是自签证书；客户手机（尤其微信内置浏览器）不认，扫出来白屏。

`frontend/src/views/expo/kiosk/ResultScreen.vue` 的分享二维码已有这套降级逻辑（裸 IPv4 主机名且无显式端口 → 降 http）。本次抽成共享 helper 供两处共用，不复制第二份——两份必然在换域名时漏改一份，而漏改的症状是「客户扫码白屏」，现场无人能定位。

### 6.3 idle 挂起要有上界

二维码面板开着就抑制 60 秒清场，但客户可能扫完就走，kiosk 会永久停在拍摄页。令牌 10 分钟到期时面板自动关闭、重新武装 idle 计时。

## 7. 手机上传页

- 服务端渲染 HTML，与 `GET /api/expo/share/{short_code}` 同范式，**不进前端路由**——顺带绕开 CLAUDE.md 前端约定第 21 条（`/m/` 已冻结为素材域专用）。
- 两个并列入口：**从相册选择**（`<input type="file" accept="image/*">`）与**现在拍一张**（同上加 `capture="user"`）。
- 复用 kiosk 拍摄示范的三条要点文字：略微俯拍、微侧面容、构图靠上。
- 重申隐私说明：照片仅用于本次体验与效果回看，保留 90 天，可随时联系删除。免鉴权页更需要写明。
- 视觉沿用 share 页的黑金语系。
- 状态反馈：上传中、成功（提示「请回到展位屏幕查看」）、失败（可重试）。令牌过期或非法时返回一个说明页而非裸 404。

## 8. 安全与校验

| 风险 | 处理 |
|---|---|
| 免鉴权端点被刷 | 单文件上限 15MB；`Content-Type` 与 Pillow 实际可解析双重校验；非图片直接拒 |
| 令牌伪造 | HMAC 校验 + `compare_digest`；过期先于签名校验 |
| 路径穿越 | `pending_photo` 只收纯文件名，解析后校验仍在 pending 目录内 |
| 传错客户 | 令牌绑定 `customer_id`，无法跨客户投递 |
| 未同意即上传 | `create_session` 既有的 `consent_at` 校验不变，未同意仍然拦下 |

## 9. 测试

- **令牌**：正常签发可验；过期拒；改 `customer_id` 拒；改 `exp` 拒；改签名拒。
- **上传端点**：非法令牌拒；超限体积拒；非图片内容拒；正常上传落到 pending 且完成 downscale。
- **待取发现**：同一客户多次上传取最新；无待取时返回空而非报错。
- **建会话互斥**：`photo` 与 `pending_photo` 都传拒、都不传拒；只传 `pending_photo` 时 `photo_path` 与现场拍照落到同一形态。
- **路径穿越**：`pending_photo` 传 `../` 之类被拒。
- **机会式清理**：删超期文件、不误删仍在有效期内的文件。
- **前端**：http 降级 helper 的裸 IP / 域名 / 带端口三种输入。

## 10. 明确不做

- 不做二维码常驻（分散快门注意力，且拍摄页将永久无法清场）。
- 不做客户离开后的异步补传队列（流程改动远大于收益，本次痛点不在排队分流）。
- 不做手机页上的裁剪与美化（把关交给 kiosk 预览，客户手机上多一步只会增加流失）。
- 不做令牌严格一次性（需落库，见 3.1；现场若出现滥用再补）。

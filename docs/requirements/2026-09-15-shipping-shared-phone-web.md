# 共用手机发货检验网页开发方案

日期：2026-09-15
状态：已在 `codex/shipping-shared-phone` 实现并完成本地验收；已获授权合并推送；不创建账号或授权、不执行生产迁移或部署。
依据：现有发货检验实现，以及用户确认的“专用账号登录、每单选择操作人、明确显示人员切换”方案。

## 1. 目标与范围

手机浏览器打开独立页面后直接进入扫描页。共用手机提前以方舟专用账号登录，质检人员无需反复切换登录账号；每单开始前必须选择本人，后续上传、删除及提交记录归属所选人员。

第一版包括：人员列表及单选、浏览器扫码、扫码记录、出库单和明细、整单/明细拍照、相册视频、媒体预览/删除、备注、提交、撤回后的继续编辑，以及明确的人员选择动画。

延续既有规则：至少一张照片才能提交；视频不计照片数、不进入验货打印；已提交只读，PC 撤回后才能继续编辑。网页和小程序共享同一张检验单及媒体数据。

身份口径：点选姓名属于人员归属登记，不声称完成本人身份认证。第一版不加入个人 PIN、短信或人脸验证；今后若需要更强的责任认证再单独设计。专用账号只承载登录和设备入口权限，不作为业务操作人，但保留在后台审计中。

## 2. 当前实现与复用边界

| 现状 | 本次处理 |
| --- | --- |
| 小程序 `pages/shipping/check` 完成扫码、整单/明细媒体上传与提交 | 网页复用流程、数据口径与纯业务辅助逻辑，改用 Vue 页面和浏览器设备接口 |
| `wx.scanCode / chooseMedia / uploadFile` 依赖微信运行环境 | 浏览器适配摄像头、二维码解码、拍照与文件上传，不能直接执行小程序原生 API |
| 后端 `shipping_inspection/service.py` 以传入 user_id 写上传人/提交人 | 保持统一业务服务，增加受控的操作上下文，区分业务操作人和登录人 |
| 当前扫码只验签、读数据，不持久化扫码人员 | 新增成功扫码事件；单纯扫码后退出也留下人员记录 |
| 小程序使用登录用户和实时入口权限 | 身份口径保持原样，不接受网页式任意 operator_id |
| 主站手机登录可能跳转 `/m/login.html` | 为独立质检入口设计登录返回及刷新边界，避免跳入素材移动端 |

建议路径：`/shipping/scan`，同方舟域名、独立全屏页面，不带桌面侧栏。登记在现有导航配置体系，通过页面布局标记支持全屏，避免制造第二套菜单来源。遵守 `/m/` 素材域专用规则，不将本功能放入 `/m/`。

复用现有登录与令牌刷新，不把“避免频繁切换人员账号”实现为永不过期的登录。登录失效时显示明确说明，重新登录后返回扫描页并重新选人。

## 3. 用户流程与状态

### 3.1 开始一单

1. 读取当前账号权限及候选人员列表。列表加载中、失败或为空时，不允许开始扫描；显示重试或联系管理员说明。
2. 扫描按钮下方移除示例图，显示“第一步：选择本次操作人”和姓名卡片。
3. 初始无选中人员，不默认第一人，不从 localStorage 恢复上一次人选。
4. 点击姓名立即显示明确的单选状态和“已选择 张三”反馈。扫描按钮文案变为“以 张三 身份扫描”。
5. 点击扫描，调用摄像头识别二维码。扫码取消或识别失败，停留本轮选择；成功后由后端重新校验人员、权限和二维码，并创建与本单绑定的操作会话。
6. 后端成功后进入单据页，顶部常驻“本单操作人：张三”，之后的业务操作全部使用这份绑定。

### 3.2 完成、退出和接手

- 同一单内锁定操作人，上传中/提交中不能换人、扫码另一单或重复提交。
- 操作区显示“由 张三 提交验货”，提交无需额外的人选确认弹窗。
- 提交成功：显示“张三已提交 · 出库单号”，结束操作会话；返回扫描页时清空选择，下一单重新选人。
- “结束本次操作 / 换人接手”：若存在未提交备注，明确提示保存状态；关闭当前会话并返回人员选择。已落盘照片和视频保留原上传人。
- 接手人重新选择、扫码同一单，继续补充和提交；不批量改写前任上传人或历史扫码记录。
- PC 撤回后，原网页先刷新状态取得新的 edit_version，当前操作会话仍有效才允许继续；过期或已结束的会话必须重新选人扫码。
- 浏览器刷新、关闭页面重新打开：不自动恢复操作人。已上传内容由重新扫码恢复；未保存备注离开前提示。
- 第一版会话超时默认无活动 15 分钟、绝对时长 8 小时。超时锁住写入并要求重新选人扫码，保留已上传内容；上传最长 300 秒，开始和写库前均校验有效性。超时值集中配置，经现场试用可调整。

### 3.3 状态表

| 状态 | 操作人显示 | 扫描/写入行为 |
| --- | --- | --- |
| 加载人员 | 加载中 | 不可扫描 |
| 未选择 | 尚未选择操作人 | 点击扫描仅提示并定位人员区，不打开相机 |
| 已选择 | 已选择 张三 | 可扫描，不能直接上传 |
| 扫码识别/校验中 | 正在以 张三 身份扫描 | 暂停换人及重复请求 |
| 单据编辑中 | 本单操作人：张三 | 可上传、删除、填写备注、提交 |
| 单据已提交 | 本单操作人：张三；只读 | 可查看；撤回后刷新 |
| 会话失效/权限变化 | 操作身份已失效 | 禁止写入，明确返回重新选人 |

## 4. 人员选择 UI 与动画规格

### 4.1 必须同时具备的三个提示位置

1. **姓名卡片**：明显的单选底色、加粗姓名、实线边框和右上角“✓”勾选标记。
2. **身份提示卡**：扫描页顶部始终保留固定高度的区域，未选时提示“请选择本次操作人”；选中后大字显示姓名。
3. **扫描按钮**：动态显示“以 张三 身份扫描”。进入单据后，顶部固定身份条与底部提交按钮继续显示姓名。

手机首屏的阅读顺序：标题“发货检验” → 当前人员提示 → 扫描按钮 → 人员选择区。提示区紧凑，320px 窄屏至少能看到人员区标题及第一行人选；按钮不挤占整个屏幕。

姓名卡片按用户紧凑化要求改为三列、最小触控高度 52px、间距 8px，姓名 16px/750；去除每卡重复的“选择/已选择”文字，保留金色描边及勾选。顶部姓名 28–32px/800。长姓名允许两行，不能只显示省略号；同名用户显示系统内可辨识的用户名作为次行，不展示手机号等额外资料。人员较多时自然滚动，超过 12 人提供姓名搜索，选中身份仍在顶部常驻。

### 4.2 动画与反馈矩阵

| 触发 | 视觉与文案 | 时间及行为 |
| --- | --- | --- |
| 点击姓名 | 卡片轻压缩至 0.97，恢复至 1；勾选标记出现，描边增强 | 按压 100–140ms，选中切换 180–220ms；状态立即更新 |
| 首次选中张三 | 卡片外围一圈柔和金色光晕扩散；顶部出现“已选择”及大字“张三” | 单次光晕 280ms；姓名从 0.96 到 1、轻上移 4px 并淡入，220ms |
| 从张三改选李四 | 旧卡片取消勾选，新卡片发光；顶部明确显示“已切换为 李四” | 同步短动画；完整切换提示停留 1.5 秒后变为“当前操作人：李四” |
| 未选人员点扫描 | 人员区描边亮起，提示“请先点击下方姓名，选择本次操作人” | 单次 240ms 强调，定位人员区；不打开摄像头 |
| 成功进入单据 | 身份条固定显示“本单操作人：李四” | 160–200ms 淡入，之后保持静态 |
| 当前人失去资格 | 撤去选中标记并显示具体原因 | 立即禁用写入；不播放成功光效 |

设计原则：**短动画负责让用户注意到切换，常驻大字与勾选负责让用户持续确认身份。** 用户明确要求人员选择具有动画，本场景即使高频也保留上述短反馈，但不使用持续闪烁、跑马灯、文字逐字跳动或无限呼吸光。姓名始终清晰可读，不靠闪光才能辨识。

实施约束：

- 色彩复用 `tokens.css` 的 `--color-primary`、`--color-primary-light`、`--color-primary-glow` 和语义文字/边框变量；只在缺少语义令牌时集中补充，不散落裸色值。
- 选中底色、描边、勾选和文字同时变化，不仅凭颜色区分。光效放卡片外缘，不能降低姓名对比度。
- 光晕用伪元素 opacity/transform 实现，避免持续计算大面积模糊阴影；姓名动画不改变布局尺寸，不推挤按钮位置。
- 使用明确属性过渡和 `cubic-bezier(0.23, 1, 0.32, 1)`，避免 `transition: all`；切换立即可操作，不等待动画结束。
- 快速点击张三→李四→王五，只显示最新王五，取消旧动画计时器，任何延迟回调不能覆盖当前人选。
- `prefers-reduced-motion` 下关闭位移、缩放和扩散，仅保留静态高亮、勾选、大字及切换文案；不降低信息强度。
- 姓名用原生单选语义和可见焦点，身份区使用 `aria-live="polite"` 通知切换；动画装饰不重复朗读。
- 第一版不依赖震动或声音，静音、拒绝系统权限时仍完整可用。摄像头打开后暂停扫描页装饰动画，离开时释放摄像头。

## 5. 身份、权限和数据范围

### 5.1 候选人员

由后端读取当前数据库角色成员，限定指定“发货质检”角色且 is_active=true，去重返回；专用登录账号从候选列表排除。实现前只读核对该角色的实际唯一标识，持久配置绑定 role_id，不依赖前端硬编码姓名或可修改的中文角色显示名。

新增专用动作权限，建议 `shipping_station:write`，用于允许账号访问共用手机入口并在本领域登记操作人；遵守权限 seed 与管理员分配流程，不默认授予所有普通用户。候选人员资格以指定角色为准，沿用既有小程序权限体系，不为入选列表静默补授权限。

专用账号无须获得用户管理、PC 全部订单列表、PC 撤回或其他模块权限。网页只允许凭有效出库二维码进入单据，单据访问口径与现有小程序仓管扫码一致；不能将“展示人员列表”扩成读取完整用户资料。

### 5.2 操作绑定

- 浏览器仅在开始一次扫码时提交候选 operator_id 和二维码原文。
- 后端校验登录账号及实时专用权限、人员启用状态和指定角色成员资格、二维码签名及出库单存在性。
- 校验成功后建立随机不可猜的操作会话，绑定登录账号、操作人、出库单、创建/过期时间和来源 web_station。会话编号是业务绑定凭据，不替代登录令牌。
- 后续读取、上传、删除、提交只引用会话，忽略或拒绝额外 operator_id；后端从会话取得操作人，不签发被选用户的通用登录 JWT。
- 每次请求校验会话归属与有效性；写入前重新查登录账号权限、所选用户状态及角色，移除角色或停用立即阻止下一次业务写入。
- 媒体读取/删除验证 media → inspection → 当前会话出库单的归属；替换媒体 ID 或路径不能跨单访问。
- 会话和既有 edit_version 各司其职：会话确定人员及单据，edit_version 防止旧页面越过撤回轮次。沿用行锁及提交幂等规则。

## 6. 数据和审计设计

现有业务字段继续表达实际操作人：检验单 created_by/updated_by/submitted_by、媒体 created_by 均使用后端绑定的 operator_user_id。创建人只在首次建单时写入；其他人接手、重新扫码不得覆盖原创建人。PC 撤回人仍为执行撤回的 PC 登录用户。

新增两类持久数据，正式表名和迁移编号在开发时核对全分支后确定：

| 数据 | 最小字段 | 用途 |
| --- | --- | --- |
| 发货操作会话 | 随机会话标识、login_user_id、operator_user_id、outbound_record_id、created_at、last_active_at、expires_at、ended_at | 固定本次人员/单据，支持失效、结束及防跨单 |
| 发货操作事件 | event_id、request_id、source、action、login_user_id、operator_user_id、姓名快照、outbound_record_id、inspection_id 可空、media_id 可空、edit_version、created_at | 持久记录成功扫码、上传、删除、提交、结束和撤回等动作 |

扫码事件可只有 outbound_record_id，不为了“扫过”就懒建检验草稿，避免改变现有 none/draft 口径。扫描成功事件与会话创建同事务落库；相同扫描 request_id 重试返回原会话且只记一次事件。刷新单据不是新扫码事件，真正再次扫码另起请求编号。

业务数据库写入与对应审计事件在同一事务提交，明确由统一服务负责提交/回滚，避免出现“上传已成功但没有人员记录”；文件操作沿用失败清理与提交结果核对机制。媒体删除后仍保留删除事件，不把审计行随媒体级联删除。小程序调用同一服务时 login_user_id=operator_user_id=当前登录用户；来源记为 mini，纯扫码事件也按相同规则记录。

时间使用 `beijing_now()`；ID 类型匹配实际 ark_users 主键。历史数据不回填虚构扫码记录；已有真实上传人和提交人保持不变。会话过期不删除审计，不进行自动历史清理。日志不记录登录令牌、会话凭据或完整媒体内容。

PC 当前列表和打印继续显示实际提交人。详情新增折叠的“操作记录”，展示人员、动作、时间及来源；登录账号信息仅对发货模块管理员可见，不写到验货打印上。

## 7. 接口与模块划分（拟定）

网页接口放 `app/shipping_inspection/station_router.py`，统一响应信封；小程序保持既有接口响应兼容。

| 方法与路径（前缀 `/api/shipping-inspection/station`） | 契约 |
| --- | --- |
| GET `/operators` | 返回候选用户 id、姓名及必要的同名区分信息 |
| POST `/scan` | qr_raw、operator_id、request_id → 会话标识、操作人快照、单头/明细/媒体和 edit_version；落成功扫码事件 |
| GET `/sessions/{id}` | 刷新本会话单据与权限状态，不重复落扫码事件 |
| POST `/sessions/{id}/photos`、`/videos` | 文件、item_id 可空、edit_version、request_id；实际人员和单据均由会话解析 |
| GET `/sessions/{id}/media/{media_id}` | 登录鉴权、会话和归属校验后返回私有媒体 |
| DELETE `/sessions/{id}/media/{media_id}` | edit_version、request_id；当前编辑轮次删除，保留人员审计及文件清理机制 |
| POST `/sessions/{id}/submit` | remark、edit_version、request_id；提交成功结束会话，重复请求可确认原结果 |
| POST `/sessions/{id}/end` | 幂等结束本次操作；不能删除已上传媒体 |

会话已结束时通常禁止新操作，但应允许确认同一 request_id 的提交回执，避免网络丢响应后显示假失败。失败响应使用稳定错误码区分未选人、资格失效、会话过期、跨单访问、旧编辑版本与上传不确定；前端给出明确恢复动作。

上传 request_id 按会话限定唯一；丢响应后刷新核对，不能自动创建第二份文件/审计事件。不得长时间持有数据库行锁等待大文件网络上传；开始校验后写临时文件，写库前再校验并短事务提交，失败清理无引用文件。

前端建议 `views/shipping/ShippingScan.vue` + 人员选择组件、扫码组件、检验明细组件及对应 composable，API 加入现有 shipping client。纯数据整理可抽到当前项目可共享的无平台依赖模块；不将 wx 对象带入网页，不为复用引入新跨端框架。

## 8. 浏览器扫码与媒体适配

- 使用 HTTPS、后置摄像头优先；扫描仅由用户点击启动，拒绝权限时解释如何恢复。
- 采用兼容的浏览器 QR 解码实现；不只依赖支持有限的 BarcodeDetector。库选型在开发阶段以目标手机实测和现有依赖为准。
- 读取现有 `ARK-I:` 二维码原文，继续由后端验签；不改已打印二维码，不把原始二维码当网页地址导航。
- 识别成功后立即停止相机，进入单据。离开、切后台、组件销毁时释放摄像头；返回不意外重复扫入同一单。
- 照片默认引导后置相机，浏览器是否提供相机/相册由平台决定；验收真实手机行为，不承诺纯 HTML 属性能强制所有浏览器只拍照。
- 视频使用手机文件/相册选择器，保留当前 100 MiB 限制；不进入打印。上传过程显示进度，失败可明确重试，切人期间禁止并行提交。
- 新站点上传 URL 必须加入受限 Nginx 配置：当前视频精确路径只覆盖小程序，网页新路径不会自动获得 101m/300s。照片上限按现有后端校验匹配；只调整本功能上传路由。
- 网页与小程序必须使用同一已核验的后端媒体归属；现有私有文件存放在各后端，不能因换域名或代理目的地导致同一单查得到记录却取不到文件。发布前核对目标域名及路由，不在本任务附带实施存储迁移。

技术依据：[摄像头 HTTPS 与授权要求](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)、[原生二维码识别支持范围](https://developer.mozilla.org/en-US/docs/Web/API/Barcode_Detection_API)。

## 9. 开发顺序与验收证据

| 阶段 | 工作 | 完成判据 |
| --- | --- | --- |
| 1. 核对与设计落图 | 核对角色标识、专用账号权限、目标手机/浏览器和域名；做人员选择静态及动态预览 | 未选、选中、切换、失效四态清楚，方案无身份歧义 |
| 2. 后端最小闭环 | 会话、扫码事件、身份校验、统一写入及迁移 | 隔离数据库跑通选人→扫码→上传→提交，人员正确 |
| 3. 网页交互 | 独立登录返回、人员动画、摄像头和完整检验流程 | 手机浏览器完成一单；换人无需重新登录 |
| 4. 一致性与故障 | 小程序审计、PC 记录、撤回续传、重试幂等和文件清理 | 两端操作相互可见，旧版本/越权请求被拒绝 |
| 5. 集成与交付 | 独立审查、构建、文档、路由配置及迁移检查 | 提供测试结果、真机记录及发布步骤；获得对应授权后才合并推送/部署 |

必要测试：

- 人员未选/列表失败/无人可选时无法调用相机；停用或移出角色后无法继续写入。
- 张三上传、李四接手提交，上传人仍为张三、提交人为李四；扫码与删除事件可追溯，专用账号只出现在审计身份中。
- 伪造人员 ID、他账号会话、跨单媒体、过期/结束会话均失败；小程序不能通过额外 operator_id 冒用其他用户。
- 快速连续选人、动画未完成就扫描、相机取消、重扫与切后台不串人；扫描后冻结人选，提交后无残留选择。
- 刷新不增加扫码次数；相同请求重试不重复媒体/提交/事件；提交丢响应可查询成功结果。
- 撤回后旧 edit_version 被拒绝，新轮次可继续；只有视频不能提交，验货打印无视频。
- 服务端非东八区与北京时间零点跨日的审计时间正确；迁移仅使用隔离数据库并保持历史数据。
- 320/375/430px、长姓名/同名/超过 12 人、字体放大和减少动态模式均可用；切换后的姓名在正常环境光下可立即辨认。
- 实际共用手机验证相机权限、后置镜头、纸张二维码、照片上传、相册视频、长上传和锁屏恢复；拍摄一段人员切换验收录像。
- 前端构建、相关后端/前端测试、路由配置及迁移单 head 检查、`check_conventions.py` 和 `git_sweep.py --no-fetch`；代码开发阶段按项目完工技能安排状态机/迁移/权限契约独立审查。

## 10. 文档与发布边界

实施时同步 `docs/api-reference.md`、`docs/database.md`、`deploy/README.md` 和 `docs/handoff.md`。数据库编号不得沿用本方案猜测：创建迁移前检查所有分支及在途工作，合并后再次验证单 head。

发布顺序为已审查代码与迁移 → 网页上传路由 → 专用账号权限和指定角色配置 → 目标手机登录验收 → 开放使用。生产迁移只走项目统一部署入口，保留数据库和媒体，不在开发机升级共享生产库。账号创建/授权及生产部署均按届时具体授权执行。

本方案完成后即可进入实现；目标手机、指定角色标识和正式入口域名属于开工核对项，能够从现场查明的由开发者自行核对，只有无法查明且影响结果时再集中确认。

# 外贸退货单功能设计

日期：2026-10-30。本文保存已确认的产品与实施契约；现已进入本地实现验收，实际交付与验证见[实施验收记录](../reports/2026-10-30-sales-return-implementation.md)。后续 Git 交付已获得用户授权，生产仍未部署。

## 1. 目标与已确认口径

在方舟新增「退货单」，选择客户、已实际出库的订单、原产品明细、退货数量、金额、原因和处理类型。单据提交生效后，自动生成对应的负数回款，并使 GMV、应收、提成和实物退货保持一致。

亮哥已在本次对话确认：

| 事项 | 确认结果 |
| --- | --- |
| 首期业务范围 | 外贸已出库订单；内贸不在本期范围 |
| 两种类型 | 退货退款、仅退款 |
| 负数回款归属 | 仅方舟记账，不同步小满 |
| 跨期提成 | 按原回款对应的人员和比例，在退货生效当期扣回；保留已结算历史 |
| 实物库存 | 仓库实际收货、检验后再入库 |
| 部分付款订单 | 分开计算货款冲减与实际退款。例如订单 1,000、已收 600、整单退货：GMV -1,000，负数回款 -600，免除未收 400，提成按退款 600 扣回 |

以下未单独确认的细节是本设计的推荐默认值，实施时按此契约落地；不据此扩大为发送通知、自动银行付款或生产操作。

## 3. 用户流程与页面

入口放在现有订单、回款业务分组中，名称「退货单」。订单详情、出库单详情提供「新建退货单」快捷入口，预填客户和订单；售后单可选关联，不强制先走售后审批。

首期一张退货单对应一个客户、一张原订单、同一币种，可包含多条产品及多批实际出库。跨订单分别建单，避免金额分摊和撤销含义不清。

### 3.1 新建与编辑

1. 选择客户，只列权限范围内存在可处理已出库明细的客户。
2. 选择该客户已实际出库的订单，展示订单号、原币、原货款、净已收、未收、已退金额。支持历史小满订单，不要求先有方舟 PI。
3. 选择「退货退款」或「仅退款」。
4. 选择原产品明细，展示名称、SKU、规格、原净成交价、实际出库量、累计实退量、剩余可退量、累计货款冲减、剩余可冲减货款。
5. 输入本次数量及各行货款冲减金额，填写退货原因。自动推荐实际退款，允许在服务端返回的合法区间内调整。
6. 预览本次影响：货款冲减、实际退款、未收款减免、预计 GMV 扣减、提成扣回状态、待退回件数。
7. 「保存草稿」或「提交生效」。提交确认文案明确：“将冲减货款 X、生成负数回款 -Y；退货入库按实际收货另行登记。”Y=0 时改为“无需资金退款”。

| 字段 | 规则 |
| --- | --- |
| 客户、订单 | 必填；选定明细后变更客户或订单，须清空并重新选择明细 |
| 币种 | 冻结原订单币种；不允许任意输入或混币种 |
| 类型 | 单据级；两种类型均冲减货款与实际退款，只有退货退款进入收货流程 |
| 数量 | 退货退款是本次计划实退量；仅退款标注「涉及数量」，不增加实物入库量 |
| 货款冲减金额 | 每行输入非负金额，默认按退货数量和原净成交价计算，可下调；纯实物退回允许 0，仅退款至少有正向冲减；累计受原行净货款上限约束 |
| 实际退款金额 | 单独展示；默认 `min(本次货款冲减, 可退已收本金)`，服务端计算上下限 |
| 未收款减免 | 只读，等于货款冲减减实际退款 |
| 原回款分摊 | 系统自动按可退余额分配，预览可展开核对；无歧义时不要求业务员手填原回款 ID |
| 原因 | 必填，原因字典加文字说明；质量问题、规格不符、发错货、客户协商及其他。其他必须说明 |
| 凭证、关联售后单 | 选填；复用私有附件访问控制，不把截图当作唯一生效条件 |
| 生效日期 | 提交时服务端北京时间自动生成，不允许用户任意回填已结算期间 |

「仅退款」同一件产品可分次补偿，涉及数量不做累计实退数量占用，金额始终累计限额。「退货退款」按实际出库行分摊并占用实退额度。已经仅退款的货物后来需要退回，可在剩余货款为 0 时登记实物退回，不能再退同一笔钱。

### 3.2 列表与详情

列表筛选：单号、客户、原订单、类型、单据状态、收货状态、生效日期、创建人。核心列：退货单号、客户、原订单号、类型、计划退货数量、货款冲减、实际退款、币种、状态、生效日期。混币种不直接汇总原币。

详情集中展示原单和明细、三笔金额、负数回款链接、GMV 调整、提成扣回明细、收货检验与入库记录、操作日志。已生效字段只读；原订单和回款详情反向显示累计退货、退款和可用余额。

复用主站 Element Plus、列表分页搜索反馈、DetailDrawer 与 tokens。页面结构设计不新建一套视觉系统；当前交付不包含交互原型或 UI 实现。

## 4. 数量、金额与余额规则

### 4.1 真实来源与累计限额

- 客户 → 原订单 → 原订单行 → SKU → 实际出库明细必须完整对应；同款两行不能合并身份，按名称匹配禁止生效。
- 只认既有权威服务确认的实际出库量。仅生成、取消、核验中、数量未知的出库不进入可退量。历史出库沿用现有已核验历史规则，不自行假设。
- 单条出库行可退量 = 核验实出量 − 已生效且未冲销退货单计划量；草稿不占额度。收货前就占计划量，防止同批货重复发起退货。
- 计划量按出库行分配；仓库部分收货不释放未到货额度。需要终止未收部分时走有审计的数量调整，不悄悄改已生效行。
- 每行冲减上限基于原实际成交净货款、折扣和已出库数量计算，不用标准价。分批出库、阶梯价格、订单级折扣及币种精度必须冻结到报价快照，最终一笔吸收舍入尾差。
- 单次行冲减还不得超过本次退货/涉及数量对应的净货值，不能退 1 件就冲掉整行 100 件的货款；剩余累计货款额度是另一重上限。全额仅退款后再收回实物可以为 0，不能再次退款。
- 原行累计货款冲减不超过该行已出库净货款；本单合计与行金额完全相等。仅退款与退货退款共享金额额度。
- 首期只处理商品货款；运费、包装费、银行手续费及超货值赔偿不隐含进商品退款。界面明确范围，其他款项另走对应业务，不挤占商品提成与 GMV。

### 4.2 分清货款冲减、现金退款和未收款减免

所有金额以订单原币、Decimal 精确计算。原始商品应收 `G`，历史有效冲减 `D_prev`，该订单全部商品累计净已收本金 `P`（已扣历史退款，排除费用与未生效回款）。P 用于该订单余额，另独立计算本次所选明细可退本金 Q；不得为了限退而从 P 中减掉已为同一订单其他批次结算的货款：

```text
current_receivable = G - D_prev
current_outstanding = current_receivable - P
本次货款冲减 D >= 0
本次实际退款 R >= 0
本次未收款减免 W = D - R

max(0, D - current_outstanding) <= R <= min(D, Q)
net_receivable = current_receivable - D
net_received = P - R
net_outstanding = current_outstanding - W
```

存在超收、未知币种、未分配回款或资金被其他结算批次占用时，先显示具体待核对原因，不能用 `max(0, ...)` 隐藏账目差异。一般无额外资金分配的订单 Q=P；预售共享资金池须按本次退货来源追溯可释放分配，不能把整池资金退走。退款区间下限高于上限时，报价不可生效，先完成具体原款分配核对。

示例：订单 1,000、已收 600、整单冲减 1,000，实际退款只能为 600，减免 400，净应收/净已收/未收均为 0。若部分冲减 200，可退款区间为 0～200；默认退款 200，此时未收 400 保持不变，也允许选择减免未收 200、退款 0。

退款为正时生成且仅生成一张负数回款 `amount = -R`；退款为 0 时显示「无需资金退款」，不伪造负零回款。只有实物退回且无新增货款冲减时，可登记数量但不重复产生财务影响。每单至少有一项实物退回或货款冲减，空单不能生效。

净应收同时进入手工补登记、自动回款、预售结算和回款余额校验；只把负数放进回款合计而不减应收，会错误开放再次收款，属于阻断缺陷。

### 4.3 币种与手续费

原币是退款与余额校验依据。GMV 美元扣减使用原订单美元口径对应的冻结换算，退款提成使用分摊到原回款的美元本金及历史提成事实；两者汇率来源可不同，不能强行共用退货当天汇率。保存原币金额、美元金额、换算来源和快照。

原回款已扣银行手续费不自动退回；新发生退款手续费不增加本期商品提成扣回。本期负数回款手续费为 0，避免对负数再次减费。非 USD 原单缺少可验证换算时，提示先补核验，不默认 1:1。

## 5. 状态、生效与反向更正

单据状态：`draft → effective → reversed`。草稿可编辑、删除；生效由明确提交动作完成，不强制新增一套审批链。`effective` 代表本地业务记账生效，不代表银行已自动汇款或小满财务生效。

独立收货状态：`not_required / awaiting_receipt / partially_received / inspected / stocked`，由行级数量推导。检验合格与库存成功入账分别记录；失败不显示 stocked。货已收、检验不合格时进入待处理区，不增加可用库存。

### 5.1 一次生效事务

1. 回查实时动作权限与数据范围，核对草稿 version、请求键和报价版本。
2. 复用现有 authority/订单 `lock_document` 并发边界，所有涉及的父发票按 ID 升序锁定，再锁本地订单 guard、原回款及分配额度、本单。历史镜像订单没有发票时用原订单 ID 唯一 guard，不能因没有 invoice_id 跳过互斥。
3. 重新核验冻结证据、数量、货款、退款可用本金及分摊；失效返回 409 与变动摘要。
4. 在同一事务写入生效退货单、明细占用、货款/GMV 调整事实、负数回款（R>0）、原回款分摊和审计；若需下游计提投影，写入同事务持久任务。
5. 一次 commit，任一写失败全部 rollback。重复请求返回同一结果；相同请求键换内容返回冲突。

写入核心数据后不依赖后台任务才让 GMV、回款可见。计提投影若异步尚未就绪，页面显示状态，提成批次确认检查该缺口，不能静默漏算。

这个锁契约的参与方不只退货服务：新建/修改/删除回款、预售分配与释放、批次结算及更正、出库改量/取消、原单改价/删除、历史单绑定方舟发票都必须共享对应父订单与 guard 边界，或通过有同等互斥保证的既有入口执行。实施时列出实际 writer 并验证锁序，不能一条路径先拿回款锁、另一条先拿 guard。跨父订单的回款批次按父 ID 排序一次锁全，guard 按外部订单 ID 排序，子表最后按稳定 ID 排序；不能在持有子表锁后追锁新父单。预售退款必须事务内扣减可退款本金并标记原结算资金分配的已退额，后续池余额、重分配和新发货同时读该占用，防止一笔本金又退款又供另一批发货。仅在退货服务自行加锁、其他 writer 不参与不算并发验收通过。

外部读取在本地锁外完成，并保存水位、完整关联和摘要；加锁后复核本地版本。镜像 freshness 沿用现有权威服务。跨系统并发不能靠本地行锁完全保证：原单在核验后被外部修改应进入差异核对，保留原快照，不自动反复退款。

### 5.2 生效后更正

已生效单据不得改金额、客户、订单、类型或直接删负数回款。错误通过 `reverse` 产生引用原单的相反金额事实和退款冲正记录，原记录永久保留；同一单只允许一次完整财务冲销，再建正确单。

冲销必须核实真实资金情况：尚未实际付款的记账更正可以冲销；已经退款的，必须存在资金实际收回证据。另记录 `cash_status=not_paid/paid/recovered` 及相应操作证据，以便区分本地生效与实际资金执行。钱未收回时，不允许完整冲销并用正回款恢复净已收；仅转入应收追偿也不能视作收款。本期不建设追偿路径，保留原退款事实并提示待资金核验。

已发生仓库收货/入库的单据不允许直接整体冲销；先完成权威库存反向单据和核验，再恢复对应额度。历史已确认提成批次不回写，冲销对提成产生本期相反调整；尚未确认批次按当前流程作废重算。

## 6. 负数回款与提成契约

### 6.1 本地负数回款

由 `sales_return` 领域的 `ark_return_receipts` 保存，具有独立单号、退货来源、原订单、客户、可选方舟发票、原币、负数金额、生效日和创建人。负数回款是正式可追溯业务单据，在现有「回款单」列表、详情、客户账单和导出统一查询，来源显示「退货退款」，同步状态显示「仅方舟记账」。

普通 `ark_receipts` 的正数 Schema、投递 outbox 和 source 枚举不整体放开。退款专用接口不提供任意负数录入；负数回款只能随退货生效生成。历史订单无需伪建 PI，也不放宽普通回款的发票约束。

统一查询投影按 `(source_type, source_id)` 标识，兼容原列表已有链接；负数回款用带来源的详情地址。联合查询须在权限过滤后统一排序、分页、计数与求和，不能分页后再拼退款。附件、导出和猜 ID 访问也做服务端范围校验。

本地退款不进入小满发送、失败重试、租约和自动恢复队列，也不标记为远端 `collect_status=1`。未来若单独授权同步小满，必须先以远端映射认领已有本地事实，再调整读侧，避免两笔负数重复扣减；当前不建设该同步能力。

### 6.2 原回款分摊与扣回

- 分配对象是已核验生效、同客户、同订单、同币种的商品本金。多次回款优先按可退余额、原回款业务日期与稳定 ID 排序分配，保留具体 allocation；不能跨客户挪款。
- 预售批次以资金实际分配链确定原回款，不退仍服务其他出库批次的定金/预收款；资金不可证明时阻止生效并指向核对对象。
- 退款负数计提输入使用稳定 ID `ark_return:<refund_id>`，金额为分摊美元本金的负数，手续费 0，日期取退货生效日。持久化至 `synced_payment` 时须新增显式 source 字段并让同步器保留此来源，不能伪装小满 ID。
- `calculate_commission` 对 `source=ark_return` 调用退货领域扣回服务。普通正回款仍按现规则；退货不得重新读取客户当前人员和比例。
- 原回款已计提：引用有效原 `CommissionDetail` 的业务员、一级/二级主管、实际计算规则与已计提金额，按退回本金比例冲减。双开发等实际金额与显示费率可能不同，因此以原明细实际金额比例扣回；同人兼任主管时不新增原本不存在的主管提成。
- 对每个原回款、每个受益人按累计比例计算目标扣回，再减历史已扣回值；最后一次全部退款吸收尾差，累计扣回不得超过原有效提成。不同历史人员和比例分别生成明细，不能混成一个当前费率。
- 原回款未计提：先在同一计算处理中生成/确认该原回款可验证的原人员与原比例依据，再生成扣回；不要求重开已锁定历史批次。原事实缺失时标为 `pending_basis`，退款和 GMV 保持生效，相关提成批次不能按“完整”确认，明确列出待补依据。
- 使用现有 `PaymentCommissionStatus` 防重复计提；一张负数回款可以产生多条人员扣回明细，但整体只认领一次。作废批次释放认领，重算按同一冻结依据复算。
- 原回款一旦被退货引用，其有效受益人、实际规则与计提依据同时冻结给原正回款重算使用；不能在正款批次作废后按当前客户归属重新算给 B，却继续从 A 扣退款。确有原提成错误时，正款和关联退款一起产生有审计的更正，不单改一侧。未计算原款也须先冻结可验证的原期依据。
- 人员已转岗、离职或当前客户改归属，原受益人扣回仍保留；不把负数丢弃或扣给新业务员。尚未进入批次的本地退款、跨期迟到事件须作为未计提调整进入下一可用批次，保留业务生效日和实际结算期，不能因日期落在已关账期间而永久漏算。
- 当期提成为负数时按负数展示并保留待结转扣回额，不截断为 0；不据此自动扣银行工资。若接入薪资，遵守既有冻结和负实发阻断规则，另行处理实发安排。

示例（不含费用，USD）：原回款 1,000，原业务员提成 20、一级主管 10、二级主管 5。本次退款 200，在本期分别生成 -4、-2、-1。即使客户已转给另一位业务员，也不改变原扣回对象。

## 7. GMV 与经营统计契约

默认按退货生效日记负数调整，归属原订单业务员及原订单对应的部门分摊，保留原始销售记录和已结算历史。原单净额可从原订单详情查看；期间报表区分「本期销售 GMV / 本期退货冲减 / 本期净 GMV」。这是一致的推荐期间口径，不代表回写订单镜像。

生效时冻结原单的 GMV 计入资格与美元货款对应关系。原本因个人业务、费用单或既有规则而排除的金额，退款仍应记账，但不从从未计入的 GMV 再扣一次。商品冲减与该指标原计入金额之间有差异时按可核验原值分摊，缺依据显式待核对；不能用本地 PI 含运费/手续费的总额直接当作商品 GMV 基数。原团队已归档、人员不在当前配置名单时，调整保留在公司合计与「历史归属待分配」明细，不因当前 roster 过滤静默丢失；个人及团队归属映射须显式核对。

```text
本期净 GMV = 本期符合原有口径的正订单 GMV − 本期生效货款冲减美元金额 + 本期冲销金额
本期净回款 = 本期原有有效正回款 + 本期本地负数退款 + 本期退款冲正
```

GMV 扣减取 D 的美元值，提成扣回取 R 分摊的原回款美元本金，禁止混用。净 GMV 可为负，趋势图、排名、完成率、差额和导出不得截为 0 或丢行。

退货查询必须独立按生效日取调整，不能只附加在「本期下单的订单」集合中，否则上季度订单本月退款会漏掉。正订单与调整合并前分别去重，调整稳定键为 `(return_id, effect_kind)`；原单若后续删除、改价或被外部作废，必须显示与已入账原值的差异并阻断重复冲减，不静默两次减额。

| 消费方 | 首期必须接入或显式区分的内容 |
| --- | --- |
| 钉钉 GMV 日报 | 公司、部门、个人合计和预览统一净 GMV；自动推送沿用既有配置，本次设计不执行发送 |
| 绩效目标看板 | GMV、完成率、趋势、个人/团队合计、明细与导出一致 |
| 战报、年度金额与金额型排名 | 同一净额事实；调整行单列，不能冒充一张新订单 |
| 新签/复购金额 | 按原单分类冲减对应金额；冻结原分类，保留人工裁定依据；人数不自动改判 |
| 订单经营分析、报表与客户金额汇总 | 提供原始销售与净额，所有标为净 GMV 的读侧共用调整投影 |
| 客户账单、订单详情、回款补登记、预售结算 | 使用退货后净应收与净已收，保留本地和小满差额说明 |

新签客户数、复购客户数、原始下单数和已裁定新签身份，不因负数金额自动删除或增加；退货次数另计。按金额门槛触发的奖励、排名及海报必须使用相同净额；已经冻结或已经发送的结果保留当时快照、展示后续调整，不能当作可撤回消息。需要改变人数或历史奖项裁定时走既有裁定机制，不由退款隐式改判。

## 8. 实物收货、检验与库存

退货退款生效只产生待收货任务；仅退款为 `not_required`，任何收货或入库请求都拒绝。

仓库可分批记录实际收到的原行、件数、收货时间、操作者及检验结论。实际收到数累计不得超过计划数；合格、不合格和待检数量之和必须等于收货量。超收、规格不符需要独立差异处理，不静默改原行。

检验合格量经项目既有权威库存写入口形成退货入库单，使用唯一业务键 `sales_return:<id>:receipt:<receipt_event_id>:line:<line_id>`；核验成功后才标记入库。相同事件重复请求只入一次；同一行多次部分收货有不同事件 ID。检验不合格量记待处理/次品去向，不进入可销售库存。

当前本轮只核实了库存读侧，尚未核实权威退货入库写接口；实施前需找到或补齐该受管写入口并用隔离环境验证。没有写入能力时可以记录收货、检验，但不得宣称库存已增加。不得直接写 `lsordertest` 镜像，也不得在镜像尚未刷新时用本地加数叠加一遍。

退款生效与收货进度独立，按已确认要求提交即产生财务影响，不等待货到；实际付款凭据另行登记，不能把“已记账”显示为“银行付款成功”。

新增 `backend/app/sales_return/`，业务写 service，路由注册到 `app/routers.py`。以下是建议结构，正式建迁移前再按所有分支核对编号、类型和单 head。

| `ark_sales_return_events` | 不可变操作审计、前后摘要、原单和反向更正引用；不保存密钥或公开凭证地址 |

## 10. 验收与实施顺序

先打通「已全额回款 USD 普通订单 → 一条产品部分退款 → 生效 → 回款可见 → 净 GMV 和负提成」的隔离端到端链路，再补齐下列同一期验收；最小链路跑通不能替代部分回款、历史单、预售和入库验收。

| 场景 | 必须得到的结果 |
| --- | --- |
| 订单 1,000、已收 1,000，退货冲减/退款 200 | 仅一笔 -200 回款；净 GMV -200；净应收=净已收=800，未收 0 |
| 订单 1,000、已收 600，整单退货 | GMV -1,000、回款 -600、未收减免 400，余额全部归零 |
| 仅退款不退货 | 财务正确扣减，实退量和库存变化均 0；后续重复部分补偿仍受金额总上限约束 |
| 无现金退款的货款减免/已全退钱后实物退回 | 不生成 0 或重复负回款，按货款及实物事实产生对应影响 |
| 分批出库、同 SKU 多原行、部分未出库 | 精确行匹配，未出库部分不能退，累计额度正确 |
| 两人并发退最后几件或同一笔本金 | 只有合法总量成功，另一请求冲突；不超量、不超款 |
| 双击、重试、提交后连接断开、相同键换内容 | 同键同结果且只有一张负数回款；换内容 409 |
| 生效中任一写失败 | 全部回滚，没有半生效单、孤立回款或占用 |
| 跨季度、跨年、本期没有该原订单 | 退货生效当期扣 GMV/提成，不因按原下单日期取数漏掉 |
| 原人员转岗、多笔不同比例、主管兼任/双开发、原款尚未计提 | 扣回原实际人员与规则，尾差受控；缺依据显式待核对，不能静默跳过 |
| 提成任务重试、原正款/退款批次作废重算且客户转归属、退款发生在计算后确认前 | 不重复扣；正负共用原冻结依据；新退款使完整性校验提示重算或列入下一批调整，不放任静默确认 |
| 已确认提成/薪资批次、离职人员、当期净提成为负 | 历史不改；当期负数/待结转可查，不自动扣银行款 |
| 历史小满订单没有方舟 invoice_id | 可按真实来源建退货，回款列表/详情/导出能查，不伪建 PI |
| 预售资金已跨批分配、运费/包装费/手续费 | 商品本金不跨用，费用不误扣 GMV 或提成 |
| 非 USD、缺 FX、折扣和多次退款尾差 | 使用可核验冻结来源，缺证据拦截，累计不超原值 |
| 分批收货、检验不合格、入库结果超时、重试 | 合格实收才入库，次品隔离，同一事件只入一次；不确定先查证 |
| 冲销、冲销重试、已付款/已入库后尝试直接撤销 | 有证据才能反向更正，不能假称钱货恢复；完整审计 |
| 原单被外部改价、作废、镜像缺行或延迟 | 差异可见，阻断重复/超额冲减，不覆盖已冻结事实 |
| 团队/个人/公司/导出、负净 GMV、人数指标 | 金额一致、负数保留、原始单数和新签人数不被调整行污染 |
| 撤权、越权猜 ID、跨客户/订单、附件和分页 | 服务端拒绝，候选不泄露；统一分页总数与合计正确 |
| 北京时间零点跨日、非东八区服务器 | 生效日、入库审计、计提日期和期间归属统一北京时间 |

实施验证全部使用隔离库及外部替身；权威库存接口独立完成契约核验。本次设计没有执行迁移、真实退款、库存写入或通知。代码实现时同步正式 API、数据库文档和交接；当前仅更新设计入口与设计阶段交接。

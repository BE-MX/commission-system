### T52 时间边界的证据要求

同一隔离环境冻结北京时间到23:59:59及次日00:00:01，分别使用不同key创建报价和两个新意图的提交请求；记录完整请求号、提交时间、落库时间、修订hash、审计与outbox时间。次日以第一单原key/body回查和回放，断言原业务快照、首次提交时间和回执稳定；会话续期须与业务字段分开比较。随后完成客户确认与首次建票，PI业务日期按实际建票的北京日期，不沿用原提交日期。原提案的到期时间不得因跨日或重放延长。

| RCP03 财务归属/代办变更 | Invoice范围或invoice_context有效代办在期间改变，旧对象缓存/JWT不得继续扩大范围；历史Invoice归属不会因门户客户转交自动改写。证明两种授权按各自领域作用 |
| RCP04 撤权与本地写竞争 | 固定屏障两种提交顺序，撤权先提交则拒绝且Receipt/Intent/Batch/分摊/任务不变；写先提交则一次合法业务变更及审计，后续新动作拒绝。保存实际锁等待/根事务证据，不能只用sleep制造竞争 |
| RCP05 慢远端证据与中途撤权/关开关 | 外部取证前阻塞，独立连接证明authority/Invoice/Receipt行锁已释放，实际管理撤权能提交；恢复取证后最终写拒绝。分别改变绑定/版本/财务状态，要求409且原对象不被覆盖；关开关不退回历史主体 |
| RCP06 已外发结果与重试 | 授权新动作、持久执行身份后真实受控供应商替身返回成功/unknown，再停用/租约接管；原事实保存但不覆盖新执行、不误发第二次。uncertain不得以retry进入pending，合法definitive failed按原规则重试成功 |
| RCP07 批次/共享凭证混合范围 | 同批一张有权一张无权，读取/作废/凭证均统一404且整批状态、子回款、分摊不变；全部有权后合法整批成功。不能只检查创建者或第一张Invoice |
| RCP08 原请求重放/下载与旧普通业务对照 | 既有创建幂等命中无新增回款/日志/手续费/通知/外发；撤权后同键不返回私密结果。门户客户PI和受控商品图片下载按各自发送前复核契约；既有回款凭证读取按03的1.35首业务DB授权时点，合法在途慢读可200、后续请求拒绝，不新增响应前重验，已授权在途字节无法召回；未安装协议的普通业务基线可运行，已安装门户PI关提交后永久保护仍有效 |

源级调用链检查只证明设计缺口，不能替代上述HTTP/MySQL执行结果。外部替身明确记录证据边界，不宣称真实供应商或存储验收；仅补void一条的403也不能关闭RCP01–RCP08或I81。锁超时/进程中断、原始SQL、后台Receipt投递/恢复、其他结算/维护入口仍各自登记，保留原开放门禁。

- 本地动作通过禁止远端调用探针证明零外部 I/O；有效执行租约不能被人工 retain/abort 绕过；retain 终态后 abort 不得恢复已取消 PI，成功 abort 不自动恢复客户发布。
- validate 分别仅授予 write、仅授予 sync、两者都无、账号停用；前两者可按完整性调整状态，后两者拒绝且无写入。不得把 OR 语义改成 AND 来规避反例。
- DELETE 验证有权员工仍不能硬删门户 PI；有权普通 PI 在既有限制允许时可删除；停用旧 JWT 两类均拒绝。门禁不弱化原回款、远端绑定与证据保存限制。
- 远端已接受操作后主动使原租约失效或由新 token 接管，再返回旧结果：原 attempt 留下唯一不可变安全事实，推进保存重试时钟后重复原结果仍只留一条事实且首次观测/保存时间不变，不能覆盖新任务/PI/发布；当前拥有者核对前不再次外发。操作者停用不丢事实，不解锁新操作权限；伪造 attempt 或串对象拒绝。
- 各入口观察真实锁序，并覆盖回滚和 ORM 缓存边界。外部 refresh/remove/retry/ack、sync、uncertain/resolve、linked-run 与 worker 分别记录授权阶段、外部阶段、结果阶段及租约/token；有效在途结果不丢弃，不因重试创建第二张 PI。

## 当前客户提交恢复记录的完整性（v1.60）

已配置Storage时，只有当前账号槽真正缺失才表示无恢复记录；读取失败、JSON损坏、非key-only对象或非法UUID均固定安全错误，先于newKey/POST拒绝，不吞为null或回显存储原文。App局部捕获并保留已认证身份、Requests和退出，安全提示允许重新读参考；不能让恢复错误变成登录失败。写后读回原raw才显示refreshRecovery=true，缺存储/写失败仍为有明确提示的内存模式。

operation在内存保留原marker raw；成功或确定首次拒绝仅移除当前账号同key且完整raw一致的marker。被替换/损坏或清理读失败时保留，已确认结果仍可展示，下一begin不能跨过残留标记。正常restore只保留key和原raw、不重建地址/PO/备注或POST；GET404保持不确定。当前sessionStorage属于同tab刷新恢复，不提供跨tab/关闭tab/清存储后的耐久保证，不是服务端授权或交易锁。


## 客户后续命令回执的一致性（v1.61）

接受/拒绝提案和PI、取消的客户端响应必须核原request_id、规范原/当前row_version（精确整数且current>=original）及受控current_state。提案另核冻结revision_id/content_hash和原接受ready_for_review/拒绝submitted；取消原cancelled。PI原回执无status，另核revision/hash/invoice_document_version匹配冻结bound_invoice_document_version及当前amendment_state=current/withdrawn/pending_customer/accepted。原回执version不能强制大于发送If-Match，成功回放优先于新命令版本校验；当前已发布/撤回或后续提案不抹除原成功。拒绝过期提案仍允许。

不完整/错对象/错修订/hash/文档版本/非法版本的POST响应保持uncertain，不允许新动作；仅核对当前原request_id。GET本身永不作为命令成功回执，异对象及非法状态/版本不进入latest展示，GET期间换身份保持已发送命令uncertain且清迟到数据。组件仅验证现有可见字段，不独立证明未返回的actor/动作/原因摘要；真实性仍由当前服务端授权、自然键/完整载荷冲突及原子保存保障。此版未新建端点、表或响应字段，没有把本地字段校验扩写为完整交易证明。

operation冻结数据仅内存；刷新/关tab/清存储后不能重建原reason或POST，本版不提供耐久恢复保证，不因GET状态相似自动宣称成功。端到端真实接口和当前权限联调仍须单独完成；T49–T50/T64不因105前端测试或合成API浏览器局部通过整体关闭。

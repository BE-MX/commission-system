## v1.62 当前客户原动作回执查询

`GET /api/portal/v1/orders/{request_id}/action-receipt`，Query为action（cancel/accept_proposal/reject_proposal/accept_pi/reject_pi）、payload_hash（小写64hex）；cancel禁止revision_id/proposal_hash，其余二者必需且分别UUID/小写64hex。严格模型拒绝多余字段、错动作/类型/组合，固定422/INVALID_INPUT不回显输入；不需要CSRF/If-Match，不接受正文、reason、员工token代替客户cookie。当前代理入口与customer authenticate均生效；current cancel/accept/reject能力（含下单与价格能力）在查原回执前重新检查。权限减为只读后普通订单GET可用，不因此能取原动作回执。

返回ok(data)：`{found,command,receipt?}`。command恰含request_id、action、payload_hash及提案时revision_id/proposal_hash；found=true时receipt保留原result_reference_json，并单列current_state/row_version；PI增加当前amendment_state四枚举current/withdrawn/pending_customer/accepted，PI原回执无status。found=false不附receipt，也不证明尚未执行；服务端待提交事务、回滚及提交后不同正文等都须保持客户端unknown，不授权创建新动作。

以当前CustomerAccess限定OrderRequest，Revision须属于该单且kind匹配。自然键沿既有POST：cancel/cancel；提案accept/(rev:proposalhash)、reject_proposal/rev；PI pi_accepted/(rev:proposalhash)、pi_rejected/rev。要求保存的payload_hash匹配，revision.content_hash亦匹配；错误摘要只found=false，其他订单/修订返回404。原账号并非新授权边界，同公司另一当前授权联系人沿既有POST回放范围也能核原命令，UI只说Original action，不宣称查阅者就是发起人。

独立fresh Session边界拒绝已有事务/dirty/new/deleted状态，避免查询commit夹带调用者改动。统一当前authority屏障先于OrderRequest、Revision、CommandReceipt及PI amendment锁读；单事务快照与current-state响应一致。唯一允许DML为认证会话idle续期；无新表、无新商业回执、无提案/PI/库存/出库/供应商业务执行。查询允许在新写入禁用时读取已记录原回执；SQL/提交异常固定安全503并回滚。所有结果和拒绝沿PortalRoute no-store/no-cache。

摘要算法：`SHA256(UTF8(JSON({hash_schema:1,payload:body})))`，实际Python content_hash排序键/紧凑分隔/ensure_ascii=False；此处正文仅单字段proposal_hash或reason。客户端在发送/hash之前剥理由首尾JS空白及NEL，保留内部空白/字符；非法孤立surrogate在POST前拒绝，不做NFKC或改变内部内容。四向量来自实际Python ReasonInput.model_dump/content_hash，不能用同源JS自证兼容。

POST /api/invoices/{id}/shipment-settlements/submission-status沿用ShipmentCreate严格body，不接受缩减key-only查询。始终要求当前invoice:write+shipment:write及原实际Invoice财务scope；仅含payment时额外要求receipt:write；与原create replay共用原actor、完整hash、quote_hash、Invoice URL和实际历史关联，不应用新创建ready/余额/文件条件遮原回执。

ok信封data包含state=found|not_found、request_key、invoice{id,invoice_no,currency,items[{id,product_name,model,color,length,quantity=原请求数量}]}。仅found有settlement原当前describe DTO加request_key/quote_hash。客户端核对原invoice/key、items唯一id/数量，found必须核id/version/单号/state/对象quote及原hash；不一致保守冻结。原创建200成功同步增加request_key/quote_hash。

not_found只观察，原POST可能锁外取证或仍执行，不能证明失败/取消，也不能换键创建。该入口无商业commit/金融DML/外部IO/文件取证，finally rollback放锁。401/403/404/409遵守原权限/范围/冲突语义，技术失败503不能改not_found；422固定原发货参数提示，不回显备注/金额/附件input。成功、依赖及校验错误均Cache-Control: private, no-store和Pragma: no-cache。其他发货执行接口尚未迁移不据此关闭。

## 通用协议

以下路径定义门户目标 API 契约；文末带日期的实施增量补充本地接入边界，不表示已部署或已完成真实联调。客户前缀 `/api/portal/v1`，管理前缀 `/api/portal/admin/v1`。默认 Content-Type application/json，未知字段拒绝；外部客户请求体不能传 employee、customer、sales、price、amount、currency 等权威字段；管理端仅接受各接口下文明确允许的配置和费用字段。下文标记为服务器输出的字段不接受回写。

成功沿用 `ok()` 信封，HTTP 状态和 code 一致：首次创建 201、接受异步通知 202、读/回放 200。错误使用同形信封，不能把异常放在 HTTP 200。

```json
{
  "code": 409,
  "message": "The quote has changed. Please review your selection.",
  "data": {
    "error_code": "QUOTE_CHANGED",
    "trace_id": "trace-example",
    "retryable": false,
    "issues": [{"field": "items[0].quantity", "code": "STOCK_CHANGED"}]
  }
}
```

客户 message 英文、管理端中文，客户端按 error_code 显示稳定操作建议。金额字符串；ID 字符串；时间 RFC3339 `+08:00`；日期 YYYY-MM-DD。路径 ID 格式先校验，再鉴权和查范围，不能因报错差异透露对象存在。

列表 `page>=1`、`1<=page_size<=100`，默认 20；固定 `submitted_at DESC,id DESC`。响应 data 包含 items/total/page/page_size，total 在相同范围过滤后计算。筛选/排序字段白名单；P0 无任意 SQL 字段、无任意嵌套过滤。

登录后客户写请求必带 Cookie、精确 Origin、X-Portal-CSRF；管理端使用员工 Bearer 并实时 DB 鉴权。`If-Match: "<row_version>"` 用于所有更新、提案、接受、审批、启停、映射发布；缺失 428。新动作版本过期 409；已成功同命令先按当前权限回放持久回执，再跳过新动作的版本/有效期校验，顺序以交易文档为准。创建订单和邀请必带 `Idempotency-Key` UUID；业务操作不能只靠按钮禁用去重。后续 PI 提案/接受/发布均以 request.row_version 作为 If-Match；pi_amendments.row_version 是服务器内部额外一致性校验，不让客户端猜两个版本。

## 认证接口

| 方法及客户路径 | 请求 | 响应 / 特殊校验 |
| --- | --- | --- |
| GET `/auth/bootstrap` | 无 | 200，预登录 nonce + CSRF；设置短期预登录 Cookie；no-store |
| POST `/auth/challenges` | email、purpose=login/activate；activate 另传 invitation_token | 202，challenge_id、expires_in=PORTAL_OTP_MINUTES×60（默认600）、resend_after=60；不存在/禁用邮箱同结构，伪 challenge 不发送邮件 |
| POST `/auth/verify` | challenge_id、code 六位字符串 | 200，成功 Set-Cookie 正式会话、移除预登录 Cookie；返回 me 与 csrf_token；失败统一 AUTH_FAILED |
| POST `/auth/logout` | 空对象 | 200；撤销会话。已无效会话可幂等清 Cookie，但仍检查 Origin |

验证码HMAC绑定账号、成员、客户访问标识及三类授权版本；兑换时以新鲜权限重算，改绑或版本变化使旧码失效。邀请激活与登录共用 verify，但 purpose 来自服务器 challenge，不接受客户端切换。邀请令牌与 challenge 绑定，verify 成功时同事务消费 invitation 并激活 membership；已消费/撤销/过期邀请不激活。邮件打开 GET 不改变状态。

预登录 CSRF 以 bootstrap Cookie 对应的服务端 nonce/TTL 验证；不能仅把 body 中 nonce 原样相信。登录与同源保护同时限频，IP 必须来自受信反代覆盖的头，直连后端不得允许伪造 X-Real-IP。

请求结构：

```json
{
  "items": [{"item_id": "5e43af74-05ea-4ed5-8b59-9ab44f602089", "quantity": 3}],
  "delivery": {
    "contact_name": "Olivia Martin", "phone": "+44 20 0000 0000",
    "address_line1": "24 Example Street", "address_line2": "",
    "city": "London", "region": "", "postal_code": "SW1A 1AA", "country_code": "GB"

```

响应核心字段：quote_id、expires_at、content_hash、currency=USD、items（line_key、item_id、display_snapshot、quantity、min_order_qty、step_qty、unit_price、discount_amount、line_amount）、product_amount、fees(status=pending, shipping_amount=null, packaging_amount=null, surcharge_amount=null)、total_amount=null、payment_terms_snapshot、inventory_observed_at。content_hash 为服务器报价与交付快照的摘要，不是浏览器生成的信任凭证。

报价时间持久化契约：现有MySQL DATETIME为秒精度，expires_at必须在计算content_hash前规范到秒；不能对Python微秒值计算摘要后再让数据库截断。GET保留原始报价证据，now>=expires_at时展示expired，不通过重算延长有效期。

### 标准商品导入与发布

上述三个商品管理接口应遵守以下服务端契约；本节不表示实现验收已通过。source_namespace仅取部署配置PORTAL_OKKI_NAMESPACE；请求不能选择任意业务镜像。product_id/sku_id为规范正整数字符串，实际源适配上限为有符号BIGINT。product_kind只能hair/accessory，已存在商品不能改变类别；源标准属性由精确在售SKU读取，不接受客户端standard_json或价格。

销售配置必填display_name/color_name（1–128字）、inventory_unit/sale_unit（1–32字）、conversion_factor/safety_buffer（非负定点字符串，最多8位整数6位小数；conversion_factor必须大于0）、min_qty/step_qty（1–10000的整数；min_qty是step_qty的倍数）和reason。单位与换算系数必须由经营配置核实，不根据商品名猜测。此配置不证明库存镜像新鲜或单位可信，报价仍须核验可信库存观测。

首次导入要求If-Match: "0"；同SKU已存在返回409，客户端按列表查回，不能通过重复新建覆盖。重新导入要求当前商品版本，保留商品public_id，刷新标准快照并退回draft，需要单独发布。发布调用PATCH并要求源指纹/属性仍一致；撤下商品不依赖源镜像可用性。所有操作权限为portal_site:admin，取得授权屏障后重查员工权限，不因员工拥有本人客户而获得全站商品管理权限。

修改/重新导入会递增所有有效授权客户的catalog_version与row_version，使valid报价失效；consumed报价、订单与历史映射快照不重写。读取已发布映射时仅应用当前有效目录中仍存在的标准键，撤下商品的旧映射不阻断其他商品；保留原revision，不自动改写别名。新预览/发布映射仍严格拒绝失效源键。发布商品或修改已发布配置时，事务内校验所有有效授权客户的完整投影，别名/展示规格冲突则整事务回滚。商品、目录版本、报价失效与审计同事务提交或回滚。

proposal 中金额由服务器计算。P0 业务员可填写 shipping/packaging/surcharge（两位非负字符串和原因），商品单价仍来自服务端当前合同价；手工改价、任意折扣不是 P0 公开能力。要新增则需独立权限与客户确认。

首次 proposal 输入：items 同 quote 的 item_id/quantity；delivery 同 quote；fees 包含 shipping_amount、packaging_amount、surcharge_amount（均必填两位非负字符串，明确零才用 0.00），surcharge_name（非零时 1..100 字）；payment_terms 为站点受控 code；valid_for_hours 取站点允许集合（工程初值 [24,48]）；reason 1..500 字。付款展示文案和 deposit_percent 由服务器解析成固定快照。输出完整 revision、expires_at、content_hash、row_version 和差异；不让员工上传任意价格引用或付款 JSON。

pi-proposals 的付款/费用/行内容从锁定 invoice 编辑版本读取；若内部资料不能完整还原付款快照，返回 CUSTOMER_ACCEPTANCE_REQUIRED 并要求内部补齐，不能猜默认。相同 PI 版本可在旧提案过期后生成新 revision；同一 request 只保留一个 active amendment。

publish-pi 只能发布源 request 对应 invoice，且受控修订已接受、币种/标准商品/数量/价格/费用/交付一致，invoice 校验通过；缺任何条件返回 409。它不是把任意内部 invoice ID 授权给客户的接口。

### 员工审核上下文（2026-10-03 实现增量）

available_actions目前为propose/approve/reject提示；每次写入仍独立校验，不接受客户端动作提示作为授权。policy仅提供payment_terms、proposal_valid_hours、default_payment_term_code，不读取库存可用量。新approve在持久成功回执分支之后要求PORTAL_INVOICE_ENABLED，关闭返回503 SERVICE_UNAVAILABLE，已完成回放不再创建票据。

### 员工原 PI 审核上下文（2026-10-03 实现增量）

### 客户访问更新的目录保留语义（2026-10-03 实现增量）

访问启停/能力调整不需要重发商品列表。catalog_item_ids省略或null时不重新校验目录、不修改grants或catalog_version；访问row_version/auth_version仍递增并撤销该公司的旧会话。这样已下架商品不会阻止管理员暂停访问，且不会默默撤销以后复核所需的授权记录。显式[]才撤销全部商品，显式非空仍验证发布状态和同站点。保存客户访问仍受当前员工权限、归属、If-Match及review_required门禁约束；启用继续验证客户绑定。保留disabled商品grant不让客户看到该商品，读取/报价仍按当前published状态过滤。

邀请成功响应表示创建回执与邮件事件入队，不表示送达或激活。未知结果保留原Idempotency-Key和原body重试，不以GET读取后更换键；账号/访问PATCH与邀请revoke只有版本保护，未知结果不自动重发。前端可重新读取当前客户状态，但必须明确这不是原操作成功回执，不能显示保存成功。


### 映射完整冲突预览（2026-10-03 实现增量）

`POST /customers/{access_id}/mapping/preview`返回access_id/base_version/row_version/items/affected_sku_count，并新增valid布尔值和conflicts数组。标准来源有效、字段合法但存在展示歧义时仍返回200、valid=false和全部冲突；每项含code（COLOR_AMBIGUOUS、SPEC_AMBIGUOUS、CUSTOMER_SKU_DUPLICATE）及item_ids（首次冲突规格与当前规格的两个ID），仅引用当前员工范围中已授权且published的商品。数量为整个展开目录的规格数，不是仅修改的行数。未知/失效来源、非法标签和过期base_version仍按既有错误码拒绝，不返回越权对象。

客户端不能因HTTP200即允许发布，须valid=true、conflicts为空并由操作者确认当前预览。预览不创建revision、审计或报价失效记录。publish保持独立校验：要求当前access.row_version的If-Match及mapping base_version，重新从标准目录展开；任何冲突仍返回409 MAPPING_CONFLICT。客户目录投影同样拒绝冲突，错误不带内部冲突item_ids。发布接口没有成功命令回放合同，未知结果不得自动重发；GET读取当前版本只能用于核对，不能当原操作成功回执。


## 客户开通候选与选择证据（2026-10-03 接入增量）

## 客户商品授权独立编辑（2026-10-03 接入增量）

## 归属与身份复核上下文（2026-10-03）

GET `/api/portal/admin/v1/customers/{access_id}/binding-review`要求当前portal_access:admin及当前客户范围，返回公司名称、访问版本/状态、当前归属及外部公司绑定、有效主负责人候选、配置来源下已验证强公司身份候选、待交接订单的public ID/编号/状态/版本/服务人、订单总数与含PI订单数、review_fingerprint。不含订单金额、地址、账号秘密。待处理列表最多1000项，pending_total/pending_truncated明确标注；指纹始终覆盖全部订单，不能把截断列表当全部。

普通业务员不因有admin功能权限而获得其他业务员客户范围；上游归属已变或review_required时通常须super_admin完成复核。候选身份遵循方舟逻辑归属，限定配置namespace；变更主负责人首先在方舟客户归属完成，此端点不会创建新归属关系。

同ID外部公司值或负责人原地修改、复核后新增订单、订单状态变化都会拒绝旧复核。转交只重置明确选中的未建票请求；旧归属快照和PI不重写，历史读取授权继续遵守既有history_policy。重绑/转交仍撤会话/邀请/旧报价，完成后暂停或保留review_required，须另行启用。指纹不是认证凭证，不赋予权限，也不是写入幂等键。

## 既有内部 PI 入口的接入约束

本节约束现有发票 API 的门户接入，不新增或替换其路由、JWT 格式、响应信封及内容 SHA-256 edit_version 合同。普通 PUT、linked-save、linked-close、linked-resolve 的当前员工权限与对象范围按[架构契约](01-architecture-and-access.md#员工-pi-编辑与本地恢复的当前授权契约)执行；远端取证与最终短事务按[交易契约](04-transactions-and-state.md#员工-pi-编辑的远端证据与最终写入)执行。

### 生命周期读取与refresh实施接入

启用门户时，GET lifecycle对旧JWT角色、停用员工及当前发票范围实时检查；POST refresh不先走旧scope锁定发票的外部调用路径。两阶段核对期间当前权限失效403、当前范围消失404、PI或取消/任务绑定变化409、远端证据不完整/暂不可用503，错误文案固定且不回显上游正文。当前实现对已取消终态不重新取证，aborted流程不可refresh；有效删除租约只返回原状态，不抢执行权。1.6 已接入下节定义的终态待核对例外；没有待核对事实时仍零远端 I/O。

无已执行删除证据的pending流程即使远端暂时不存在，refresh仍不擅自宣布完成删除；expired uncertain/deleting且可信不存在及最终无本地/远端阻塞时才允许原领域转remote_deleted。真实远端读源与全部下游writer的完整验证仍为独立门禁。

### 执行事实的安全读取与恢复响应（1.5 开发目标）

沿用现有 GET/POST lifecycle 路由及信封，不新增客户端事实写入入口。GET 在当前 `invoice:admin` 和发票范围通过后只读取本地状态，增加受控 `recovery_summary`：`review_required` 布尔值、`pending_attempt_count` 非负整数、`last_observed_at` 北京时间或 null、`remote_observation` 枚举 `absent/present/unknown/not_checked`。它是风险摘要，不是取消执行权或供应商承诺。原始 token、事实全文、提供商正文、输入摘要、客户地址和其他对象的信息均不得返回；no-store，401/403/404后前端清私密内容。

终态 retained/remote_deleted 没有未核对证据时保持原行为；有待核对原 attempt 时，现有 POST action=refresh 按04的受控只读核对契约处理，返回原本地终态和最新安全摘要，不重启取消、不抢有效租约、也不重新 DELETE。aborted 且从未外发的流程仍拒绝 refresh，不能借此新增外部执行。绑定或捕获后原 attempt/事实集合变化409、权限失效403、对象隐藏404、取证或事实保存不可用503；失败不能清除待核对标记。POST成功只确认核对记录已持久化，不表示终态已被恢复或所有远端风险消除。

DELETE 已外发而随后操作者停用的403，以及事实保存503，都不表示原外部动作未执行。客户端冻结原命令，用有权员工读取/核对同一任务；禁止把403/503当作更换 attempt 或重复删除的理由。claim 提交不确定先查原记录，不新增原接口没有的幂等键要求。

### 1.6 生命周期响应接入范围

当前GET/POST lifecycle对所有正常及401/403/404/409/503响应设置 `Cache-Control: private, no-store`；取消视图移除原执行token。refresh在有效删除租约期间只返回安全本地视图；终态待核对仅允许只读远端取证，不重复DELETE。GET返回前述四字段recovery_summary，客户端没有写事实或指定目标的接口。

### 1.7 出库恢复和确认接入

沿用POST lifecycle的outbound_retry/ack_outbound、invoice:admin、confirmed/reason和expected_version合同。启用门户时先当前员工/对象范围捕获、锁外GET订单/出库证据（retry另读取完整回款，ack不新查回款）、最终重新当前授权及完整绑定比较。旧身份403、越权404、版本/任务/完整绑定/本地保护冲突409；提供商证据格式不可信或绑定无法验证固定503且无正文。不直接调用出库创建/删除接口，不新增客户幂等键。

retry只恢复明确未发送或漏建任务；现有任务必须同invoice/order，running/uncertain/done/pending/deleted或delete_pending/regenerate标记拒绝，不能清掉旧删除/再生成fence。最终成功只将原任务排队并审计，实际worker必须继续查重、当前订单及提交意图。ack要求最新本版本manual关联操作、order步骤done、outbound尚未done；数量、产品/SKU/远端行及文档状态一致才记录员工/依据/北京时间。其他步骤仍manual时保留整体manual，但已确认outbound不可被重复ack覆盖。

### 1.8 同步不确定核对的开发契约与当前接入

沿用 `POST /invoices/{invoice_id}/sync-uncertain/resolve`、现有请求信封与 `resolution` 字段，不新增门户写接口、外部发送能力或客户端任意指定的证据目标。三个 resolution 均需当前 `invoice:admin`、当前对象范围、未取消、`sync_uncertain`、原推送租约已结束以及完整核对依据。

| resolution | 证据与前置条件 | 成功含义 |
| --- | --- | --- |

### 1.9 同步核对UID实施边界

当前confirm_existing接受真正正整数或无前导零ASCII正整数文本，长度不得超过实际InvoiceItem.xiaoman_unique_id的64字符持久字段；规范copy通过完整明细/商业比较后才交给原回写服务。重复、混合int/string同值、bool/非正/前导零/float/指数/空白/符号/Unicode/缺失/超长UID统一固定409且零业务写；原订单缺失或order_id基本身份不可信503。有效int/string/mixed独立身份可成功，回写一致规范文本。

提交后响应授权失败403/404仍保留唯一已提交核对；无旧私密响应并no-store。该结论只覆盖正常及恢复处理器受控响应，不扩展依赖层401/422。真实供应商合同、初始OFF、提交确认丢失和真实进程恢复仍须各自验证。

### 1.11 普通推送与迟到原结果核对

启用门户时现有 POST sync 按捕获→锁外凭证→最终当前授权及原子 claim→锁外 POST→原事实→业务收尾→当前响应授权执行。不得在凭证慢窗口前预占库存或绑定回款证明。claim 同事务保存 START、原执行键/租约、回款意图与库存准备；提交确认不明固定503且零外发。当前明细及原删行快照 UID 必须符合规范格式，删行快照必须为 list[dict] 且组内唯一，实际发送行 UID 唯一；无效时在凭证和 claim 前拒绝。

原 POST 的 accepted/rejected/unknown/auth_rejected 事实先独立持久化，保存安全引用与指纹，不返回 token 或供应商正文。只有当前原 token/租约/完整绑定仍匹配才收尾。已接受但 UID 或库存收尾失败时保留已知原订单、uncertain 与原预占，不把它当明确未创建。未知、迟到及保存503不能触发新创建；最多一次已知401刷新并在再次发送前重新授权。

sync-uncertain/resolve 保留原三个 resolution。存在已接受原事实时 confirm_not_created 拒绝，bind/confirm 只能使用唯一原 provider_reference。人工确认捕获当前事实集合指纹，锁外 GET 后新增事实必须409；核对记录以事实集合为身份，新迟到事实使旧核对失效。

新增受控迟到分支仅用于原 unresolved START、单一 accepted 引用且无活执行租约的 ready/not_synced 或 synced/synced。未绑定只允许 bind_order，已绑定只允许 confirm_existing；完整原单商业与规范 UID 纯验证后，再核对本地镜像绑定并回写全组 UID。无可信引用、多原 attempt、draft 或当前 receipt lease 拒绝，不猜测订单身份。该分支不自动完成库存、回款或出库任务。后端沿用现有接口；前端安全摘要和 ready 恢复可达性仍为独立工作项。

### 1.13 普通推送后续履约的响应契约

现有 POST sync 的原推送结果、后续出库结果及响应读取权限是三个独立判定。原推送已经提交成功，后续排队/出库核对失败不能转为“原订单未创建”或诱导客户端重新POST；客户端仅查询原订单及其原执行状态，恢复动作使用对应的受控入口。当前权限或范围已失效仍返回403/404及private/no-store，不返回旧私密原单或出库摘要。此拒绝本身不能作为零副作用的证据。以下后续阶段错误使用所规定HTTP状态，不以200/manual替代；原成功事实仍可由当前有权员工查询，不据错误状态猜测原订单未创建。

followup开始和最终本地队列变更均须当前 invoice:sync 与原PI对象范围。任务等待库存→待执行、更新再生成代次、写缺货原因/错误、删除后重新排队都属于受保护写动作。供应商身份/形状不可信或不可用固定HTTP503；可信但商业绑定、前后观测或当前商业/谱系/任务证据变化固定HTTP409；这些分支不得追加新出库执行或改写当前任务。已发生的原外部结果仍按不可变原事实协议留存。原订单成功且后续未完成时，有权员工可读响应分别说明两者；不能用一个总成功布尔值隐去后续失败。

以上为开发目标，I52已证实当前legacy followup缺口；尚未实现上述阶段协议，不新增客户站自动出库API。完整锁序与证据身份见04，验收见06。

### 1.14 后续排队接入与兼容边界

普通推送的门户启用执行器在原成功提交后调用safely_run(force_authority=True)，将本地queue委托outbound_followup_execution；强制参数由原执行路径固定，期中关闭开关仍使用当前授权协议。默认legacy safely_run和其他linked-run/初始OFF调用未改变，不以这一增量背书这些路径。

新队列阶段按1.13分类返回HTTP403/404/409/503及private/no-store，原成功结果独立保留。删除事件必须明确匹配原outbound_invoice_id、order_ids当前目标、tasks当前task.id；再生成原代次及最新日志限同PI成功create/update，响应中规范order_id必须匹配当前原目标。不以其他success审计或同PI其他目标的日志授权队列。缺数值字段/非有限值503，可信商业不匹配409。队列与outbound_queue审计同事务，动作名符合现有16字符持久字段，无新迁移。关联出库现存更新仍转原执行器，属于独立未闭环的外部写路径。

### 1.15 队列竞争与关联出库身份边界

最终 queue 持有当前权限屏障及 PI/task 锁时，独立撤权事务必须等待：queue 成功提交后撤权可以生效，响应重新鉴权403但已授权提交的队列及审计保留；queue 提交失败则整组回滚，固定503，不能留下半条队列或审计。附件、成功日志、原再生成日志、删除事件的任意捕获字段变化，以及扫描不完整、二次订单回读变化均需拒绝后续迁移；不要把缺失证据当无关联。

关联出库规划对 unique_id、order_record_id、outbound_record_id 使用规范正整数身份：接受正 int 或 ASCII 数字文本，二者规范十进制文本均不超过64位；禁止 bool、前导零、Unicode 数字、浮点、非正、空值、符号及空白。整数与同值文本仍视为同一身份并判重，拒绝发生在生成增改删计划前，不静默改写供应商标识。原始本地 InvoiceItem UID 必须在事件写入及产品 builder 转整数前逐项规范校验、组内判重；规范 source_items 贯穿计划与回查快照。回查原出库明细身份双方规范比较，允许整数/同值文本，不接受歧义。预览原有 ValueError 对应409并回滚。现存外部执行器的当前授权、锁外调用和迟到事实协议仍待实施。

### 1.16 出库共享准备阶段与启用入口

门户启用时，现有出库invoice-sync/preview与invoice-sync路由在首次镜像读取前走当前employee的invoice:sync AND shipping_inspection:write；当前仓库范围按实时read_all或active OKKI绑定查询，随后当前invoice范围复核。业务员所属订单的普通关联出库跟进只要求invoice:sync与该PI范围，不额外要求仓库全局能力。两种入口不能相互借用。启用请求固定force协议，期中关闭不恢复旧JWT授权；初始OFF仍走历史路径，不能据本批证明其授权安全。

共享准备先当前身份/范围、镜像唯一原目标、永久request/conversion→PI、原UID及产品行、财务/附件/任务/删除/event/验货与媒体捕获，再提交释放，只在锁外读供应商订单/出库/关联扫描/改号占用/回读，最后force当前授权及全捕获比较，才创建idle或更改recheck。ACTIVE原计划必须匹配同一PI与原出库目标；本阶段只允许返回recover提示，不由提示证明后续旧计划恢复已完成。

预览成功提交后再次当前身份、仓库/PI范围与原绑定检查，才能返回version及差异；403/404/409/503固定private/no-store。币种必须非空文本，客户ID必须受支持标量；缺失/坏类型或扫描未完成固定503，合法商业不同或已出库状态409。版本包括本地商业绑定指纹，idle/recheck事件自身创建不使版本递归变化；重复预览及实际同步开始使用相同version。

调用方已有事务（包括仅查询、已flush或Core写）不由准备或关联跟进方法提交。_follow_existing在首个查询前拒绝；只允许方法自己创建的当前授权只读阶段commit。普通force跟进在commit前冻结PI引用，旧run仅可丢弃自己创建的只读阶段后交给新方法。历史调用方仍需显式迁移事务入口，不能宣称默认linked-run兼容已验收。

**范围限制：** 本批改造共享prepare与preview响应，并保留实际sync/验货/补缺行能力；sync的pending/sending、token后外发、POST结果、回查和repair仍为现存协议，当前员工/完整绑定与不可变原执行事实尚须逐段改造。不要从准备完成推断外部执行权、迟到结果保存或全writer门禁通过。

### 1.16 提交故障的响应边界

共享准备的只读捕获提交失败或真实提交后确认丢失，返回固定503与private, no-store，并在供应商GET前停止。新sync_idle预览事件提交前失败时事件为零；真实提交后确认丢失时唯一事件保留，响应仍503。后续预览只能读取/复用该唯一事件，不触发供应商POST。此处仅描述prepare/preview，不能推广到外发或repair提交协议。

## 1.17 已启用的出库同步执行契约

现有invoice-sync路由不变；enabled或内部force调用进入outbound_execution。手动入口仍同时要求invoice:sync、shipping_inspection:write和当前仓库范围，业务跟进入口按自己的权限契约执行。初始OFF保持原实现，期中OFF不能切换执行协议。expected_version对应完整当前准备计划，不能只比较旧edit_version。

响应固定private, no-store。当前动作撤销403、对象范围失效404、完整商业/照片/谱系/任务或事实集合变化409。发送前外部证据缺失或不可确认返回503；持久提交不可确认亦503，禁止盲目重发。发生POST后的未知回执或回读作为原事实留存，在当前授权及完整绑定不变时可HTTP200返回sync_uncertain；后续完整原GET核对成功可返回sync_done，不把未知事实一律映射为503。原外发结果一旦发生，先独立保存原START对应安全FACT；之后的403/409不能解释为供应商未受理，也不触发重发。known401记录auth_rejected，本执行器不刷新重发；非法、缺失或非原目标响应引用归unknown，不能授权自动补齐。原单GET完整核对可确认结果，响应正文与凭证不进入事实或客户端。

活pending/sending只返回原任务处理状态。过期pending只有无持久SEND和FACT才可结束为未发送；sending或未知回执只能核对原单。repair仍需missing_only严格证明，且原FACT明确accepted；无FACT或unknown不会自动新建step。历史active缺少可信新START返回409，仓库需人工核对，不能从可变历史payload生成可信新发送。

完整FINISH保存安全结果；无新差异时回读该结果且不再次修改验货版本。FINISH后新到的真实POST FACT需要当前授权的只读REVIEW；原验货资料/overlay必须仍匹配FINISH后完整绑定，不重复召回、版本递增或外发。迟到只读READ作为独立证据保留，不自动产生新外发风险。此契约的实际通过范围、提交故障与历史限制以交接为准，不能认定全部writer已迁移。

1.17恢复继承原START的warehouse要求，内部跟进入口不能放宽原手动仓库权限；若新入口要求更强则保留更强检查。原发送姓名从START快照读取。另一位当前有权员工可以只核对原任务，FINISH保留原actor及finished_by；实际验货召回/updated_by/领域审计使用当前核对人，不把停用原发送人当作当前操作者。普通仓库账号按规范sub及有效OKKI绑定通过原范围校验。

终态无差异的重读同样继承可信START的仓库要求，必须在供应商取证前重新核验；不能用internal warehouse=False返回旧FINISH绕过原动作。enabled对draft验货的真实版本/出库号更新亦署当前finisher，召回仅按实际状态记录。

执行器的前置授权捕获与后续prepare之间也须防并发替换：冻结完整business+event binding，prepare首次当前捕获在提交/任何供应商GET前一致性比较，变化409零取证；末次仍比较完整binding。执行恢复两次capture采用相同executing语义；默认preview保持其active只读行为。不能让另一请求的新START/FINISH降级成旧入口权限。


## 1.18 内部自动出库 worker 契约

本增量没有客户自动出库 API。scheduler 每30秒调用实际后台 run_once，配置当前员工执行身份，已有明确 outbound_auto_requested、synced、非 presale 的 PI 才是候选。逐 PI process 返回内部 status/posted；这些状态不直接作为公开响应或订单成功通知。旧公开 retry/ack 不能据 worker 私有事实自动解锁全部 uncertain 历史。

当前动作/身份无权403、当前 PI 范围失效404、绑定/原代次/占号商业冲突409，已知供应商证据不可用和提交不可确认503，固定脱敏及 private,no-store。供应商异常继承 ValueError 不能被误写成可信商业409；新 worker 将 OkkiApiError 和外部 token 数值溢出分类为503。POST之后先保留原 FACT，再核对当前执行权；403或503不证明供应商未受理。明确401不刷新重发，unknown/缺失/非法响应ID不产生第二次 POST。

完整回读须核对原出库身份、单号、客户、币种、待出库状态、备注、全部订单行/产品/SKU/数量/价格/单位/型号，以及 invoice_warehouse_info.id、handler_info[].user_id、exchange_rate、exchange_rate_usd 与原命令一致。缺失/不符不能 FINISH done。上述头字段映射为代码接入合同，真实供应商现场字段与数值语义尚需核证，不能据合成响应背书；缺失时保持 uncertain。

占号详情必须是同查询单号、规范出库 ID、完整非空规范明细，逐行订单/订单行/出库行/产品/SKU 身份有效并判重，才可以判断他单占号并尝试备用号。缺详情/空数组/非法身份返回503且零 START/SEND/POST；空关联索引不能替代占号详情。

按 2026-10-08 范围决定（见 README v1.73），下表各回款入口的接入契约连同旧自动 ReceiptIntent 生成路径、后台出库执行器切换与全部 writer 共同协议，整体划入独立加固专项，不再是门户上线门禁；门户 PI 作为普通方舟发票由既有回款流程按其原有身份与规则处理。

| 当前入口 | 必须补齐的接入契约 |
| --- | --- |
| `/api/receipts`列表、`/{id}`详情、`/order-options`、`/order-balance/{invoice_id}` | JWT只提供身份，实时重建员工主体；在目标数据/金额返回前核验有效账号、当前动作权限及Invoice财务归属范围。统计/筛选候选与明细同范围 |

| `/api/receipts/batches`及`/{id}/void-entry` | 实时动作权限；批次所有关联Invoice均通过当前范围，任一不允许即统一404，整批不部分生效 |

当前源码的动作集合如下；这是需要以DB实时重算的集合，不包含对象scope。实现若调整动作集合，必须同步接口契约与合法业务回归，不能为修复旧JWT而静默收紧。

| 入口 | 当前动作权限集合 |
| --- | --- |
| 回款列表、详情、order-options、order-balance；batch详情 | OR：receipt:read、receipt:write、receipt:admin |
| types与凭证下载 | OR：receipt:read、receipt:write、receipt:admin、invoice:read、invoice:write、invoice:sync；下载还保留文件关联分支的动作/范围检查，入口OR通过不等于有文件权限 |

当前接口的AND/OR权限语义须保持：require_permission所列动作全部满足；require_any_permission至少一个当前动作权限满足，不能误改成全部要求，也不能把read_all计作动作权限。对于使用统一财务scope的旧写入口，read_all仅与已经满足的当前write/admin共同决定范围；“不单独授予写”不能解释成拥有当前write也禁止使用原财务scope。当前DB的super_admin沿用项目规则，JWT中的历史super_admin标志不参与判断。

本表是已有接口必须接入的开发要求，不宣布新增路由或改变旧body字段。具体授权时点、共享锁序和事实恢复见[回款事务契约](04-transactions-and-state.md#回款旧入口的授权与事务契约)；验收细则见[回款补充验收](06-implementation-and-tests.md#回款旧入口的补充验收)。

有效JWT对应员工已停用、无有效角色或已不满足该入口当前动作权限时返回安全403；部分降权但仍满足原OR集合及对象范围时保留合法访问。身份token无效仍401；有效员工的范围外对象与不存在对象统一404。数据库/授权不可确认时不得降级为历史roles，按既有安全503规则失败。禁止在拒绝回复中泄露客户、金额、凭证或供应商正文。重放先校验当前权限和范围，不能以旧成功回执续用被撤销的权限。

截至1.32核对，旧入口require_permission/require_any_permission只读取JWT，receipt.access信任传入主体；1.33仅迁移下列选定读入口与本地void，其余旧调用链仍属I81开放项。上表是完整开发目标，不是所有接口已安全的证明。

## 1.33 回款选定入口的局部接入

未增加路由、请求字段或迁移。GET列表、详情及order-options，POST `/{id}/void`以现有JWT依赖只取得身份，动作权限与角色随后从当前DB重建。读入口保持receipt:read/write/admin的OR；void保持receipt:write，当前super_admin沿用项目规则。旧JWT没有动作但DB已授权仍允许合法访问；JWT历史read_all/super_admin不延续已撤范围。对象scope仍按原Invoice.sales_user_id及当前财务范围执行，不将客户转交当作迁移历史发票归属。

read_user必须是该请求首个业务DB读取；local_receipt必须在新事务边界进入。调用方已有读事务、dirty/new/deleted或已flush事务均固定409，不能由helper提交或回滚调用方。身份token无效仍401，当前动作不足403，范围外或不存在对象404；关联或业务状态冲突409。授权/关联定位/取锁阶段SQLAlchemyError固定503和private,no-store，不包含驱动细节；查询事件测试不证明物理断连，普通查询结果序列化、提交及外部IO不因该局部catch自动获得统一503保证。

选定void的公开service入口接收fresh Session、receipt id、JWT身份和reason，内置当前授权；私有_void只负责原财务算法，不提供旧公开签名兼容层，也不是恶意内部调用的沙箱。execute继续持有事务到原commit/rollback。合法pending/failed作废仍按原规则执行，不要求同步PI；uncertain/syncing/synced、有远端单号、预收款、批次或已作废仍按原冲突规则拒绝。不会修改portal_document_version或Publication。

本批没有迁移余额、types、附件下载/上传/绑定、create/PATCH/retry/reconcile/resolve/remote-change、批次或worker。完整动作表继续适用于待接入入口；门禁不以这四处通过关闭。

## 1.35 回款辅助读取入口的当前主体

未增加路由、body、权限code或迁移。GET `/api/receipts/types` 与 `/api/receipts/attachments/{id}` 首业务读调用 current principal，OR保持receipt:read/write/admin与invoice:read/write/sync；GET `/api/receipts/order-balance/{invoice_id}`仅receipt三动作OR。read_all只改变对应域范围，不独立授予动作；旧JWT当前新授权可用，已撤动作/角色或停用不能使用历史claims。

余额在当前receipt范围校验后调用原order_balance；原完整金额/状态/手续费/Intent/预售/摘要规则不变。凭证初始OR仅为入口许可：未绑定仅上传人；仅绑定Intent可依原receipt动作与财务scope访问，或依原invoice动作及委派scope访问；已绑定Receipt还必须是当前有效attachment_ids关联且具receipt动作与财务范围；批次必须具receipt动作且所有子单可见。invoice:read_all不能扩大Receipt或余额范围。

授权时点是首业务DB读。该读事务可跨原remote/storage调用，但不取authority屏障或对象FOR UPDATE；在途慢读开始后管理员可提交撤权，在途合法读可能成功，后续请求403。不是响应前再次鉴权或物理代理/云存储安全验收。授权查询失败固定503/no-store；后续外部/文件/财务查询错误保持各自原规则，不将本helper当全域异常拦截。原其他写入口仍开放。

## 1.36 回款重试的当前授权接入

沿用 `POST /api/receipts/{id}/retry` 的原路由和空 body，无新增客户幂等键、权限code或迁移。JWT仅提供员工身份，公开 retry_service.retry 从 fresh Session 进入，重建当前 receipt:write；当前 receipt:read_all 或 super_admin 只按原财务范围生效，invoice:read_all不扩大回款范围。旧JWT缺动作而DB新授权允许；已停用/无角色/撤写权限403，范围外或不存在404，当前状态/绑定变化409。

只有 active、明确 failed、没有小满回款ID的原单可重试。原 uncertain/syncing/pending/synced、已作废或已获ID不允许；批次所有当前子单均须在财务范围内，预售 goods/freight 须有有效 Application 及原可发送 Settlement。合法成功保留原金额，按原自动手续费算法补齐适用费用，原单 pending、last_error清空、version加1，并写一次 retry 日志和适用 fee_allocated 日志。不直接调用供应商创建/删除接口，不改PI商业版本。

需要手续费证据时，首阶段捕获后释放锁；只有不可变标量目标传入 IO，最终重新授权并比较完整绑定。供应商证据格式/协议失败及落入本 retry 安全边界的不可确认 SQLAlchemy 故障固定503、private/no-store，不返回驱动或供应商正文。原 execute 成功处理的 IntegrityError 完整性冲突仍回滚并返回409，不将其统称503。提交成功但回执丢失可返回同类“结果暂不能确认”，客户端刷新原单：已 pending 的重复请求409，不能自动重发或重置 failed。受控 MySQL 锁超时仍走原 TransactionBusy handler，非全局异常拦截。其他路由异常和其他 writer 未获得该局部保证。

## 1.37 回款PATCH的当前授权接入

保持 `PATCH /api/receipts/{id}` 原ReceiptUpdate body（version、amount、bank_charge、collection_date、payment_type、remark、attachment_ids），无新客户幂等键、权限code或迁移。当前receipt:write与原财务scope，旧JWT不保留历史roles/read_all/super_admin；当前receipt:read_all结合合法动作保持原scope，invoice:read_all不替代回款范围。停用/无角色/撤动作403、范围外或不存在404。批次先检查所有当前子单范围：混合越权404；整批可见仍按原不能单独修改规则409，不能提前409绕过原范围检查。

只允许非batch/非presale_deposit、active且pending/failed、无远端ID、当前version相同的原单。PI仍须原synced/远端ID、未取消、无linked处理中状态、无pending Allocation。取证前拒绝不访问供应商或文件。合法修改保留原金额/手续费校验、远端净额与本地毛额去重、失败/待核对占用及Intent预留规则；仅更新原字段、version加1、sync_status=failed、last_error提示待重试及一次edited日志，不直接发送、不改PI商业版本。

初始当前授权及冻结目标/文件身份→释放业务锁→订单/支付方式及原存储规则取证→结束token/cache事务→当前授权/目标版本和完整绑定→当前余额与文件关联→caller提交。文件移到他单/批次、Intent占图、旧图已移除或文件身份改变均不能绑定；纯未绑定仍仅上传人。最终版本/状态/余额/关联冲突409。取证格式/协议、存储OSError/StorageError/HTTPException及安全边界内不可确认SQLA固定503/no-store，原execute成功处理的IntegrityError仍rollback→409，受控锁超时仍TransactionBusy；不改变其他路由错误分类。

最终commit结果不能确认时固定503“请刷新原单核对”：已提交保留修正值/version/日志，不改回旧金额或重复提交；旧version再次PATCH409。没有新幂等键即不能称成功响应重放，同版本冲突与原单回查是恢复合同。

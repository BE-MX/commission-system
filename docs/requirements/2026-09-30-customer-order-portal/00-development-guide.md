## 4. 身份、角色和数据范围

`portal_account_id` 是已验证邮箱账号；`canonical_customer_id` 是方舟 CustomerAccount；`sales_user_id` 是门户授权的当前负责人；`employee_actor_id` 是当前有效员工。四者不能相互替代。发票使用的 OKKI company_id 另通过唯一外部身份绑定转换。

## 5. 登录与账号管理

首期邀请制，不让客户自由输入公司后直接获得订单权限。方舟选择现存客户、负责人、目录和能力，邀请指定邮箱。

邀请使用安全随机令牌，只保存摘要；GET打开链接不消费，POST验证邮箱后单次兑换。登录采用邮件 OTP，服务端原子限频、失败计数和一次消费；重发不能清空封锁窗口。邀请/OTP异步发送只在专用短期加密信封保存必需密文，不将原令牌写入普通日志或事件 payload。

初始工程默认：邀请72小时；OTP10分钟、单 challenge 5次失败；邮箱60秒重发间隔、每小时5次；IP每小时30次。会话闲置30分钟、绝对12小时。这些可配置数字不是已确认经营参数；只能在保留服务端约束的前提下调整。

Cookie为安全 HttpOnly opaque 会话，数据库只存摘要，账号/成员/access版本改变撤销旧会话。生产使用 `__Host-portal_session`，Secure、Path=/、无Domain。所有客户写请求要求精确 Origin 和会话 CSRF；预登录也使用同源 CSRF challenge。私密响应 `private, no-store`；退出、换账号清内存缓存和迟到响应。

## 6. 商品、库存、价格与客户映射

SKU 是实物和库存的唯一依据。展示型号、颜色别名只改变客户看到的名称。长度、单位、包装规格、数量步长、单重及币种仍来自标准商品资料；映射不能把同名不同实物合并。

| 配置 | 规则 |
| --- | --- |
| 上架与目录 | 站点商品池与客户白名单共同裁剪；搜索、facet、图片同范围 |
| 合同价 | 服务端按客户/SKU/币种/有效期取价，缺价不能以0或原型价替代 |
| 库存 | 保存来源和观测时间；过期、无可靠观测、歧义拒绝提交；前台重复添加合并数量，服务端拒绝重复item_id或标准SKU行，以唯一行总量核验库存 |
| 数量 | 标准单位、起订与步长；不依客户端计算数量或重量 |
| 映射发布 | 整版校验、唯一规范化别名、base_version乐观锁；冲突409，不半发布 |
| 历史与复购 | 保存当时标准值、别名、版本和价格快照；复购重新按当前授权报价并展示差异 |

客户A可以显示“Natural Black”，客户B显示“Jet Black”，两者都必须指向确定的标准色号与规格。后续改名不修改已接受订单或 PI 的显示快照。Unicode变体、空值、控制字符和重复别名必须在发布前校验；具体复合键和索引以02为准。

库存展示明确“库存信息截至…；最终由业务员确认”。没有预占机制时不能承诺客户提交即锁货。提交和最终审核按各自当前资料核验，价格/库存/资格发生实质变化必须重新提案，不擅自换产品或调价。

## 7. 交易、金额与状态机

| 数据状态 | 允许的业务动作 |
| --- | --- |
| submitted | 业务员提案或驳回；有权客户取消 |
| awaiting_customer | 客户接受有效当前提案→ready_for_review；拒绝→submitted；取消 |
| ready_for_review | 员工最终校验建票→invoice_created；重新提案→awaiting_customer；驳回/取消 |
| invoice_created | 保持原 PI；改动走独立 amendment 和既有发票生命周期 |
| rejected/cancelled | 历史只读；重新购买生成新报价与请求 |

商品、数量、单价、折扣、币种、运费、包装费、附加费、地址、付款条件、有效期、负责人及相关版本绑定进不可变修订与内容摘要。客户接受和员工审批必须引用同一当前修订，且未到期；接受后审批前到期也需重新提案。内部备注不能静默改变对外备注。

金额用方舟现有 Decimal/舍入算法；单位价格精度和金额精度分别处理。客户端总额仅显示。费用字段缺失、非数字、币种错误与可靠业务不匹配分别分类，不能把坏供应商数据当成可用证据。

幂等顺序：当前身份与范围 → 锁后重验 → 查成功持久回执及原内容摘要 → 同命令回原结果 → 新命令才检查版本、到期、库存与状态。同键异载荷409，不能覆盖原请求；原成功回放不重新激活旧修订、不改第一次操作人。

审批、唯一转换谱系、Invoice、明细及事务事件同库提交，不创建回款意图草稿。一个请求最多一个永久建票 lineage。确认未提交的事务失败整体回滚，不保留阻塞重试的半转换；提交结果未知时核对原命令，不补偿撤销或盲目新建。已成功 PI 作废或被删除尝试也不能重新建第二张。后续改费用/条款保持同一 PI，撤回旧发布、客户重新确认、发布当前版本。

正式 PI 下载检查当前能力和已接受发布版本，不能直接把方舟当前编辑中的未接受内容发送给客户。`portal_document_version` 与既有内容hash `edit_version()` 不是同一个契约，不得改名混用。

## 9. 内部履约未知结果与本轮恢复契约

内部员工实际确认出库是客户 P0 之后的独立显式动作，沿用 shipment:write、实际 Invoice 财务范围及原发货规则。原 require_delivery、ensure_active、预售与主运费0约束保持；原单核对不能新加主单 ready 门槛。

确认先持久提交 START；每次供应商 POST 前持久 SEND；POST 后只向原尝试追加 FACT；商业收尾重验当前权限和原关联，最后与 FINISH同事务。只有明确鉴权拒绝允许受控第二轮发送。超时、缺FACT或暂未查到不是未执行，不重新发单。

protocol2 START保存原单号、目标载荷/基线摘要和精确确认时间，重构原POST摘要以核对原身份。FINISH区分 resolved/unresolved身份，可追加核对结论，不覆盖旧事实。旧已发送记录缺完整材料时不从当前目标补猜历史。

恢复仅GET原供应商单，锁外取证前后冻结并比较完整商业关联及原确认记录/已出库证明。取证期间新增FACT、撤权、转交或资金变化使旧结果失效。有效原单状态2可核实出库效果，但资金不足仍显示shipped_unfunded。有效状态1只有无SEND或每轮明确拒绝且原身份可证明时才能恢复待出库；未知、缺FACT或活跃租约禁止再次确认。

永久已出库证据必须先于“没有未解尝试”的提前返回生效。区分真实status2证明与旧本地已出库风险；两次status1回读或迟到rejected FACT都不能遗忘曾已出库并解冻。独立 `shipment_outbound_proof` 与原确认记录一起纳入绑定比较，不能只检查原journal。

沿用原状态：已知合法不匹配/不活动→uncertain；首次已出库但无待出库 ID/成本基线→uncertain（不能假造基线）；status2 与基线匹配且资金有效→shipped/结算shipped/原reserved App applied；未足额或资金无法通过完整实时核验→shipped_unfunded/结算outbound_uncertain。可靠业务不足与技术取证失败必须区分，后者503无商业变更。

远端待出库若本地曾shipped/shipped_unfunded则隔离 uncertain，若confirming/confirm_uncertain则保confirm_uncertain，均禁止再次确认；活跃confirming租约拒绝且零取证。原合法单价精度保持，不加两位小数限制。参与回款失效时允许保存已核实风险并返回null余额；诊断通道失败不能撤销金融结论，BaseException仍传播。无新ready守卫，原worker refresh/confirm保留并待独立迁移；废弃仅无生产caller的旧bind_exact。

## 实施增量：原运费核对原子应用（v1.52）

捕获当前动作/按需管理权、原范围/谱系/Invoice和完整资金关联，冻结原目标，首 commit 释放业务锁；远端详情与活动列表只读，第二 commit 结束 token/cache，rollback/expire 后最终当前授权/完整关联/原版本和目标再比较。商业 mismatch/inactive 在最终授权后处理，不能遮住期间403/404；坏详情/活动列表为固定技术503，零目标或隔离写入。

最终事务手工匹配且活动才将原 ID绑定为bound；保留原 bind+refresh 的target version+2。已知原 ID 活动且匹配为bound，否则保ID并设uncertain/fixed error，target version+1。Settlement.state/version、金额/费用/编号/冻结载荷/租约和资金分配不改；一条准确当前actor/reason事件与原目标 flush/current describe 后第三 caller commit。取消原多次商业提交窗口，不保存中间verifying状态。

首次两次提交没有商业DML，最终提交前故障全有限资金图不变；成功丢ACK后 GET 原target/审计核对，Settlement.version仍原值。没有稳定键，不能自动改号/重发；已知ID刷新可再次观察且再次留审计，不能宣称严格幂等。原合法历史核对不要求主PI ready，无新增回款或供应商POST。

## 实施增量：明确失败重试三阶段（v1.51）

第一阶段从新事务锁读永久授权、谱系、原实际 Invoice 和完整参与资金图，验证当前 shipment:write/原财务范围、原 version、active 及原明确 failed 目标。捕获不可变原目标与 scoped 全字段指纹后 commit 释放业务锁，此阶段没有金融修改。第二阶段只读原编号查重并结束 token/cache 事务，rollback/expire 后进入新事务；取证时独立 Invoice NOWAIT 可获取锁，不能持业务锁等外部 IO。

第三阶段再次当前授权、范围、原状态与全图一致校验，然后才判断已查到原单的业务冲突。运费查重严格验证每页 dict/list/count、规范正 ID 与完整非空名称、页内/跨页无重复及完整计数；两遍完整 ID→名称图相同才证明不存在，排序差异不算变化。缺名称或两遍内容不同均技术不可用，不能把空匹配集当可靠不存在。出库只按原 serial 查重。真实供应商分页/字段合同仍须现场联调。

不存在时沿用原算法：运费 failed→unverified、原目标 version+1；出库 failed→pending、原 Settlement→outbound_pending 且双方 version+1；清原租约/attempt/error，金额、费用、编号与冻结载荷不改。一条当前 actor/reason 的 retry_freight 或 retry_outbound 事件与原目标同事务 flush，再当前 describe，由路由唯一第三 commit 保存商业结果。

没有稳定命令键；第三提交前故障零资金图变更，成功丢 ACK 时原状态/version/事件已持久，需 GET 原单核对。旧请求冲突不是未执行证据，禁止自动改键/重号或盲重发。事件注入只证明受控 commit/ACK 场景，不等于物理故障或真实 sender 崩溃。脏调用者在 fresh_boundary 拒绝，不 flush/rollback 他人的修改。

## 实施增量：发货未知结果与明确未发送（v1.50）

只读核对使用原创建_current授权及原key回放校验，不_capture、取证、修补或重建。原第三commit前失败无资金结果；第三commit成功丢ACK则原结果持久，核对found后读取同id，完全原请求重放唯一。实际事件注入有同Session/stage命中断言，不等于物理故障。锁外原POST执行时核对not_found不取消它，原提交放行后同key found。

编辑冻结与安全退出分别控制：busy/uploading或尚未可靠保存的未知不能退出；已可靠保存的原槽允许关闭/离页，保留body，重开再当前鉴权核对。beforeunload仍警告tab关闭可能丢槽。存储写入且读回确认后才invoke create，invoke前设置mayHaveSubmitted；一旦某次create的结果已未知，后续明确409仍不能据此解冻。仅当前活组件保存的预备命令，在此次首invoke之前从未发送且未有未知结果，首次明确事务拒绝可按首次拒绝清槽/重载授权目录并重新报价；旧槽/组件重开保守未知，not_found不降低未知状态。

## 报价和库存核验

客户端只发送目录 item_id、qty 和地址。服务端按当前 access 的授权目录解析标准 SKU，按标准型号/颜色类型/长度/重量调用现有客户价与标准价能力。不得把客户的 `Signature Weft`、`Mushroom Melt` 等别名送入现有标准报价解析器。

报价输出各行价格、来源、合计、映射版本、目录版本、访问版本、标准数据 fingerprint 和库存观测时间。没有来源版本号的价格源计算确定性 fingerprint，最终提交/审核重新读取并比较。价格缺失、币种不支持、未知规格/单位、下架或授权撤回均拒绝。

P0 支持 USD、现货、严格整数件/套；配件仍保留独立 product_kind 和标准单位。按标准单位核验 `requested <= max(0, available - safety_buffer)` 并符合 MOQ/step。库存基于明确的可用量口径和可靠观测时间；同一 SKU 不重复扣行。商品表更新时间不能冒充库存观测时间。

库存读源必须由 stock 适配器同时给出 `observed_at, quantity, unit, source`。当前公开库存 API 不够用，开发需增加受限内部读模型。无可信观测时间则返回 `INVENTORY_UNAVAILABLE`；不以“查询刚刚返回”替代镜像新鲜度。初始时效阈值建议 120 秒，但能否达到必须由库存同步实测决定；达不到则试点禁止承诺实时数量，提交入口保持关闭或另行批准询价模式，不静默放行。

不持有数据库行锁等待库存外部查询。预先读取观测结果，进入本地提交事务后核对观测年龄与源版本；该检查不能提供跨系统库存原子预占，必须保持“请求待确认”语义。审核生成 PI 前再次复核，不宣称消灭并发超卖；真正预占是后续独立功能。

### 金额算法

`gross = round_half_up(qty × unit_price, 2)`；`line = gross + discount_amount`，discount_amount 为小于等于 0 的两位金额，line 不得负；`products = sum(line)`；费用全部确定后 `total = products + packaging + shipping + surcharge`。包装数量不乘包装费用。

示例：3 × 35.2750 = 105.8250 → gross 105.83；折扣 -5.00 → line 100.83；运费 45.00，其他费用明确为 0.00 → total 145.83。运费未知时 shipping/total 均为 null，fees_status=pending，不展示为 0，也不能生成可支付 PI。

上述公式已与基线 `backend/app/invoice/service.py` 的 `_replace_items`（逐行先舍入 gross）、`_refresh_invoice_totals`（汇总费用）和 `_money`（ROUND_HALF_UP）核对。adapter 必须复用该领域算法并断言返回金额一致，不创建另一套浏览器或门户独立定价公式。

## 客户提交事务

1. 客户取得服务器报价并确认所见版本，生成 UUID Idempotency-Key，冻结发送 body；重试与回查使用原键和原 body。更新购物车是新意图，旧请求未判定前不自动重发。
2. 最先验证当前身份/对象范围，再按 `(access_id, account_id, key)` 查询。已有请求先比较客户端规范化载荷 hash，命中就返回原结果，即使原 quote 已到期；账户已撤销时仍拒绝返回私密结果。
3. 新键才校验 quote 的账号/access、未消费、有效期、传入 hash 和当前授权/映射/价格版本；库存变化返回差异，不静默削减数量。
4. 同一事务锁 access、会话/成员、quote，写 request、submitted revision、明细、审计、outbox；quote 原子标记 consumed。UQ(quote_id) 防止同一报价换两个键创建两单。
5. 在唯一约束竞争失败后 rollback 并用新事务读赢家；同键同 hash 返回 200 replay，异 hash 返回 409。同 quote 不同 key 返回 409 QUOTE_ALREADY_CONSUMED 及对当前用户可见的原请求号。
6. 首次成功 201；事务失败不返回成功。响应丢失时客户端 GET 按 key 回查，不生成新键。服务端已有提交回放不得先重新定价导致“原单其实成功但回放报调价”。

hash 规范：JSON 键排序、金额固定字符串、字符串规范化规则一致、明细按稳定 item_id 排序且禁止重复 SKU、排除 trace_id/CSRF 等非业务字段；包含 quote_id、地址、PO、备注与各行 qty。版本化 `hash_schema=1`，以后变更不能把旧相同载荷判异。

## 请求状态

| 状态 | 允许动作及后继 | 责任人 |
| --- | --- | --- |
| submitted | 提交提案→awaiting_customer；驳回→rejected；客户取消→cancelled | 业务员 / 客户 |
| awaiting_customer | 客户接受有效提案→ready_for_review；客户拒绝→submitted 并审计；客户取消→cancelled | 客户 |
| ready_for_review | 最终校验并建票→invoice_created；重新提案→awaiting_customer；驳回或客户取消 | 业务员 / 客户 |
| invoice_created | 后续只走独立 pi_amendments 状态流，主状态不退回 ready_for_review；取消走发票生命周期 | 方舟既有流程 |
| rejected / cancelled | 只读；重新购买创建新的请求与报价 | 客户 |

`result_confirming` 是客户端在响应不确定时的展示状态，不是假装服务端已接受的数据库状态。同库短事务建票不需要长期 processing 状态；转换行 pending 在事务内生成，事务外只看到 created/tombstoned。任何失败 conversion 全部回滚，失败审计使用独立事务记录；不存在持久 blocked 行。以后若改远程 saga，必须另行设计持久 processing/unknown 和租约，不复用此表面约定。

每个订单写操作携带 expected_version（HTTP If-Match）。处理顺序固定为：当前身份/功能与对象范围 → 锁屏障及对象 → 再鉴权 → 查已成功操作回执及命令 hash → 相同命令回放 → 对新动作才检查 If-Match、有效期与状态。已成功回放不重新生效、不覆盖第一次操作人；携带过期版本仍可取得原回执，缺失必需请求头仍属协议错误。不同命令不能借旧回执成功。取消和审批竞争时只有一个事务成功；取消后不允许建票，建票后取消请求返回 INVOICE_ALREADY_CREATED。

取消稳定操作身份为cancel+request_id；reason作为命令内容进入payload_hash。相同内容重复取消回原回执，不同reason不能复用成功命令，返回IDEMPOTENCY_CONFLICT；每次回放仍检查当前客户身份/能力/对象范围。

稳定操作身份：accept=`request_id + revision_id + content_hash`；approve=`request_id + accepted_revision_id + content_hash`；publish=`request_id + invoice_document_version + accepted_revision_id + content_hash`。同一提案由同公司两名有权采购接受，复用同一个接受结果和首次接受人。成功后过期、被替换、内部再编辑时，同身份重试只回 `replayed=true, original_receipt, current_state`，不把旧修订重新激活或发布。新命令正常走版本与有效期校验。建票 lineage 已存在但不是同命令时返回 INVOICE_ALREADY_CREATED，不用已有 PI 冒充新修订获批。

业务员新提案命令以request_id和起始If-Match为稳定身份，完整body入payload_hash。当前awaiting_customer提案到期时允许重提，验证并保留旧修订、生成新revision、清接受指针并递增版本；未过期不在后台静默替换。旧成功命令仍先回放，不能重新激活旧提案。

## 运费与实质变更确认

P0 初次报价固定 fees_status=pending，提交只确认商品请求，accepted_revision_id 保持 null。业务员必须创建带全部费用的提案，客户明确接受后才能生成正式 PI。上一轮原型“输入运费即建样例 PI”是 UI 简化，生产不能凭此取得客户对新总额的同意。

产品、数量、单价、折扣、币种、运费、包装费、附加费、收货地址、付款条件发生变化均为实质变更；生成不可变 proposal revision，展示 old/new 差异、有效期和合计。备注仅修正内部说明也必须留痕，但不改变已接受对外 remark。

新接受动作校验 proposal_id 属于本请求且仍为 active_revision、`now < expires_at`、can_order AND can_view_price、权威版本与 content_hash 一致。首次接受过期/已替换提案返回 409；已成功接受的同命令按回放规则返回原回执。付款条件与有效期必须入不可变快照和 hash，不能读取当前站点配置替代。接受不预占、不建票；最终审批同样要求 `now < expires_at`，已接受但审批前到期也须新提案。价格/资格变化同样退回新提案，不自行替换客户接受金额。

## 方舟建票适配与事务

采用**同库内部适配**，不从本机 HTTP 调 integration 端点，不套用其 app owner 身份。理由：`integration.create_external_invoice` 自行 commit/rollback，而 `invoice.create_invoice` 当前只 flush；只有后者适合门户原子编排。

建票命令输入只有 request_id、accepted_revision、expected_version；金额/SKU/客户/归属全部来自已批准不可变快照。当前员工须有 portal_order:write 和 invoice:write，且通过同一个 DB 的实时员工/代办校验。使用当前员工为 user_id，订单归属取已接受 proposal.authority_versions_json.sales_user_id，不取原提交 requests.sales_user_id_snapshot。锁后必须核对该快照值等于 request.servicing_user_id 和 access 当前 sales_user_id，且当前实际客户归属、绑定均有效；任何不一致拒绝建票并要求新提案/客户确认。管理员转交未建票请求时保留原提交归属证据，旧提案失效并清当前接受指针；新提案以当前归属形成新 hash。已有 PI 的归属不随门户转交重写，后续修订保持该 PI 的 sales_user_id，不走首次建票归属替换。

事务顺序：

```text
当前身份/范围校验后先预查同命令成功回执（事务内仍须重查）
无已知回执才预读标准库存、价格 fingerprint（事务外，无网络锁）
预读错误保存为 validation_error，不在最终回执判断前直接失败
BEGIN
  按全局顺序锁屏障、授权与 request；当前读检查权限、客户外部绑定
  查 conversion/成功回执；同命令返回原结果，tombstone 或异命令明确阻断
  对新转换才处理 validation_error，检查 If-Match、接受修订及有效期、费用、观测时效和标准字段
  INSERT conversion(request_id UNIQUE, operation_key, payload_hash)
  invoice.create_invoice(db, canonical_body, employee_actor_id)  # 仅 flush
  校验 invoice 创建结果及金额；门户 PI 不创建回款意图草稿，回款由方舟既有入口后续处理
  绑定 invoice_id、修订、版本；写客户发布快照和稳定行对照
  request.status = invoice_created；row_version += 1
  INSERT command_receipt + audit + outbox
COMMIT
返回 request_id / invoice_id / invoice_no / publication version
```

事务内不发邮件、不调用 OKKI、不收款、不分配库存、不创建出库。发票号竞争只对已识别的唯一约束冲突做最多 3 次**整事务**重试，每次重新校验权限/版本，其他 IntegrityError 不伪装可重试。BEGIN/commit 的所有权在 adapter 调用方，异常统一 rollback。

### 发票来源与既有生命周期需要修改的接口

新增受控 `source_type="portal"`，source_order_id=门户稳定请求 public_id，source_order_name=门户请求号。当前 schema 的来源枚举与服务白名单必须同步扩展；严禁用 `manual` 携带 source 字段、冒充现有 integration ingest 记录或绕过来源保护。

只有内部 adapter 可以生成 portal 来源；公开的员工手工建票/编辑接口拒绝请求体伪造 portal source。新增来源还需检查截图去重、删除、更新、导出、列表、OKKI 同步、ReceiptIntent 关联等引用。门户 actor 在本域审计，不能把客户 account_id 写入 ArkUser 外键。

Invoice 创建为 draft/ready 的内部状态按现有校验计算；`invoice_created` 只代表已经存在方舟 PI，不意味着 synced/收款/库存分配。必须通过现有发票验证后才允许 publication=published；校验失败整事务回滚，包括 conversion，另写脱敏失败审计，不给客户下载半成品。

### 幂等不依赖可被删除的发票记录

当前 invoice 删除会清理 integration ingest，不能把它当永不消失的幂等账本。门户 conversion 永久保留，invoice FK RESTRICT；删除入口检测 portal 来源并拒绝硬删，转既有作废流程。已作废保留 tombstone，原请求不能重生新 PI；确需重开由管理员创建新业务请求并引用原记录，不能复用原操作键。

## PI 发布与后续编辑

客户只取得 portal publication 的已发布版本，不直接读内部 `/api/invoice/{id}`。publication 保存方舟 invoice_no、invoice portal_document_version、实际金额/标准 SKU/客户别名对照、收货与付款条款、模板版本；这些内容来自该次验证通过的 PI，不能另算一套金额。

内部编辑门户来源 PI 时，同事务递增新增的 invoice.portal_document_version、撤回 publication、清空当前后续修订指针，进入 withdrawn。批准前不向客户静默提供新版。后续流程如下，request.status 始终为 invoice_created，绝不再次调用 create_invoice。

| pi_amendments.status | 操作与后继 | 版本规则 |
| --- | --- | --- |
| current | 内部 PI 实质编辑→withdrawn | invoice 版本递增，撤回原发布 |
| withdrawn | 员工从当前有效 PI 生成 amendment→pending_customer | revision.kind=pi_amendment，绑定 bound_invoice_document_version 与实际内容 hash，不接受客户端自由报价 |
| pending_customer | 客户接受→accepted；拒绝→withdrawn；新内部编辑→withdrawn；过期后重新提案→pending_customer | 新提案绑定当前 invoice 版本并清 accepted 指针；接受需当前提案/能力/有效期 |
| accepted | 员工 publish-pi→current；新内部编辑→withdrawn；过期后重新提案→pending_customer | 新提案保留旧接受证据并清当前 accepted 指针；发布复核实际 PI hash/有效期/权限 |

后续提案过期后由业务员重新生成不可变 amendment；不能延长旧 expires_at。PI 编辑和生成提案/接受/发布按相同屏障与 invoice 行锁串行化；publication 与 pi_amendments、请求 row_version 的更新同事务。内部改了 A 再改 B，则客户对 A 的同命令重放只返回原回执，不能接受或发布 B。未知 SKU、缺映射、已作废或权限资格异常的 PI 不能生成可确认提案；必须先在内部纠正。

PI 后续内容以现有受控内部发票流程为权威，不自动把该 PI 改价为最新目录报价；全部变更仍须客户接受及有权员工发布。每次生成新提案/发布复核当前目录资格和可靠库存观测，失败时阻止发布，不承诺锁货。

下载在渲染前取得指定 published 不可变快照；事务外渲染后，开始传输前按架构协议重新锁屏障和 invoice，确认 publication 有效、invoice.portal_document_version 相符、当前账号查价权限有效；不一致返回 PI_REVISION_PENDING。此检查之后已在途响应不能召回。旧版本如需可查，单独标记“已被替代，不可据此付款”，P0 默认不提供旧版下载。

正式导出模板使用内部标准字段计算和拣货，客户展示别名通过独立 presentation metadata 渲染，不写入参与价格匹配的 model/color。字段替换后要核验 PI 行数、SKU、币种、小计、费用、总额完全一致。

## 通知与恢复

订单接受、提案发布、客户接受、PI 发布及客户映射发布写 outbox，处理器至少一次投递。重试建议 1/5/15/60 分钟后封顶 6 小时，最多 8 次进入 dead；同 event_key 单消费者落标志，供应商接受但回执丢失仍可能重复邮件，不能宣称 exactly once。业务通知链接只指向登录后对象页，不携带授权能力 token；邀请/OTP 按数据模型的专用短期加密信封发送。

最终发送准备事务取得 authority 屏障后，按对象 ID 重新解析当前负责人/账号状态；其提交是通知授权时点。停用/转交先提交，则这次准备拒绝失效收件人；准备先提交，则随后发送属于已获准在途任务，不能保证撤回。通知只含请求号及必要摘要，不附 PI 全文或收货地址。任务执行时与下载时均复核权限，不能相信入队时的权限快照。

同库 commit 响应不确定：先用新 Session 以 request_id 查询 conversion 和对应 invoice。一致存在即返回原结果；不存在且确认前事务已终止，使用原请求重试；观察到互相矛盾的关联或缺失 PI 时进入人工异常，禁止自动补建。异常需 trace_id、operation_key、阶段码，不能记录完整个人资料和令牌。


## 本地 PI 作废

未同步stock PI使用void-pi受控终止，不调用通用硬删除。要求无远端ID、成功同步时间、结果不确定或执行令牌，无有效回款、待处理意图、出库任务或非零/待处理库存。相关状态在授权屏障、request/conversion/invoice及依赖行锁内复核；任何歧义拒绝并交由方舟既有取消核对流程。作废保留Invoice、ReceiptIntent和附件，关闭自动回款资格，Conversion终态tombstoned且不可重新建票；发布撤回、请求版本、作废审计、outbox和幂等回执一起提交或回滚。客户看到PI已作废，仍可按当前目录重新报价提交全新请求。

本地作废采用每请求唯一的稳定身份：CommandReceipt.action=pi_voided、object_public_id=request_id、command_key=local-void，不另要求客户端 Idempotency-Key。完整规范化请求体 invoice_document_version 和 reason 一起进入 payload_hash，If-Match 不进入摘要。当前员工功能权限、客户及原 PI 对象范围校验并锁定后，先查成功回执：同身份同载荷返回 original_receipt/replayed/current_state；同身份不同版本或 reason 返回 IDEMPOTENCY_CONFLICT。仅无成功回执的新命令才检查写开关、If-Match、当前 PI 版本、conversion 状态和本地作废条件。原成功重试不因版本已递增或 conversion 已 tombstoned 被拒绝，不重复写作废、审计或通知；撤权后仍不得回放私密结果。


## 业务通知 worker 接入与恢复

`backend/app/portal/notification_worker.py` 处理业务通知，scheduler 层提供 SessionLocal 工厂；邮件网络请求在数据库事务提交并关闭后执行。

| 接收方 | 源事件 |
| --- | --- |
| 当前负责人 | order_submitted、order_cancelled、order_accepted、order_proposal_rejected、pi_accepted、pi_rejected |
| 当前有效且已验证的客户成员 | order_proposed、order_rejected、order_invoice_created、pi_proposed、pi_published、order_pi_voided |

每个收件人独立租约与退避，单个失败不重新发送其他已成功的子事件。租约 120 秒，最多 8 次尝试，失败按 1/5/15/60/120/240/360 分钟退避；到期 sending 可重新领取，新租约令旧 worker 无法更新结果。SMTP 返回未发送时不记为 sent：仍持有效租约则退避；若实际租约已过期则 finish 返回 lease_lost、保留 sending，由后续 claim 重领。错误仅记录受控代码，不记录原始 SMTP 异常。

发送前重新校验当前站点、客户身份、归属指纹和 access。员工还需当前有效账号、portal_order:read 及该订单实际可读范围；客户还需当前 active 成员/账号和已验证邮箱。权限或绑定失效时 cancelled，不因以后重新启用自动恢复旧通知。源事件 expanded 和子事件创建原子提交；单个收件人的重复恢复不重复业务状态。

员工邮件链接到 `/portal/orders?request={uuid}`，客户链接到 `/orders/{uuid}`，均须登录和正常对象鉴权。邮件描述发生过的事件，界面展示最新状态；通知不含 PI 全文、金额、地址或授权 token。

稳定 Message-ID 不能提供恰好一次投递：SMTP 接受后进程退出或回执丢失仍可能重复。权限复核提交至实际发送也存在短暂窗口，已在途邮件不可召回。dead 保留诊断，不通过重建业务订单或清空事件恢复；人工恢复通过通知管理接口处理：仅dead受控错误可恢复；当前权限、完整命令指纹、原因、持久回执及审计同事务，不能通过数据库手工清状态恢复。

## 后续提案与客户拒绝命令身份（1.3）

下表补全持久回执契约，所有动作仍先实时鉴权与对象范围，再查原成功回执；只有新命令检查版本、状态及有效期。

| 动作 | action / object_public_id / command_key | payload_hash 与回放 |
| --- | --- | --- |
| 后续 PI 提案 pi-proposals | pi_proposed / request_id / pi-propose:<本次原If-Match> | 完整 invoice_document_version、valid_for_hours、reason 入 hash；原版本同内容回原 revision 及 current_state，不生成新事件 |
| 首次提案客户拒绝 | reject_proposal / request_id / revision_id | 完整 reason 入 hash；同 reason 回首次回执，异 reason 为 IDEMPOTENCY_CONFLICT |
| 后续 PI 提案客户拒绝 | pi_rejected / request_id / revision_id | 完整 reason 入 hash；与首次拒绝动作隔离，不改变首次操作人 |

后续提案过期后允许基于新的 request.row_version 生成新 revision，即使 invoice_document_version 未变；同 PI 版本不是同命令的充分条件。员工必须保留原发送版本/body用于结果未知时回放，不能用最新版本自动重发。新旧 revision、首次 actor 和历史拒绝证据保留；旧成功回放不能重新激活、延长或发布旧提案。这三条记录当前实现采用的身份，不另造兼容键。

## 映射通知消费与发送授权（1.3 开发目标）

mapping_published 与 mapping_mail 使用数据模型定义的 access/revision 引用。映射发布成功即生效；发送失败不撤销映射，不提升 mapping_version，不创建新修订或改变订单/PI。通知面向当前有效且已验证的客户成员，无需查价或下单能力，但必须保有本站该 access 的目录访问。对当前负责人的通知由后台发布结果和投递追踪承担，不另发送员工邮件。

正文只说明产品显示名称已更新，链接到允许 origin 的 /collection，要求登录；不附别名列表、内部型号、价格、PI或能力 token。来源修订已被替换时取消未发送任务，不用旧名称误导客户。源/子事件损坏进入 dead 的受控诊断，不能人工重发无效来源。

订单、映射、邀请及 OTP 最终 prepare 短事务均使用屏障和当前读，校验对象/收件人/授权/有效期后提交并关闭会话；提交定义本次发送授权时点。发送器仍须在网络交付前检查 Mail.valid_until，租约或秘密到期不能继续发送。撤销先提交则取消；准备先提交则存在已授权在途窗口，已交付供应商的邮件不能召回。禁止为了缩短窗口持屏障调用 SMTP；正文最小化与登录后再次鉴权共同限制影响。并发恢复可能重复同一 Message-ID，不能重复业务授权或映射状态。

## 参与事务的行锁超时与连接恢复

参与门户 authority 协议的 MySQL 事务在首次屏障查询前保存当前连接的 innodb_lock_wait_timeout，并仅用 SET SESSION 设为 PORTAL_LOCK_WAIT_SECONDS（默认5，允许1..30秒）。已安装协议时，PORTAL_ENABLED 为 ON 或 OFF 的参与事务均在实际 AuthorityBarrier mapper 连接应用有限锁等待，关闭客户入口不解除授权屏障或连接恢复义务。只有其他数据库和未参与事务保持原行为；不修改全局数据库配置。旧数据库缺表资格必须按01的“1.34 已安装授权协议的永久参与”验证同物理连接的实际1146及唯一精确171迁移head，不得由总开关关闭推断。该值限制 InnoDB 行锁等待，不能当作整个请求、元数据锁、连接池或外部网络的时限。依据：[MySQL 参数说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-parameters.html)。

只有已标记参与事务的 MySQL 1205 转为 TRANSACTION_BUSY/503。MySQL 默认仅回滚失败语句，因此调用方必须整笔 rollback，不能把之前的订单、权限或屏障变更继续提交。事务一旦超时即禁止 commit；外部 Connection/savepoint 同样保留外层禁止提交标记。SQLAlchemy commit 事件抛错会使 RootTransaction 失活，守卫必须先实际 DBAPI rollback、恢复原值，再抛受控异常，不能只靠之后的 Session.rollback。

原超时值在根 commit/rollback/close 时恢复，savepoint结束不能提前解除外层策略；实际 Pool reset 补充兜底。恢复失败的连接失效并丢弃，不回池继续使用。其他 SQL 错误、非参与事务1205和死锁1213不借此规则掩盖。客户和管理端只返回安全错误与 trace_id，不返回 SQL、参数或内部表名；涉及上游员工/权限写入口时使用专用 TransactionBusy 异常处理器。

订单失败后核对原键；通知准备失败保留原事件、短期密文和重试身份，发送/渲染在事务外进行。服务端503不能授权客户端换键或新建 PI。实际实现与结果见交接记录，不能把局部超时证明替代 T64 全条及生产门禁。

## 员工 PI 编辑的远端证据与最终写入

普通 PUT 与 linked-save 若关联远端订单，应执行以下顺序；没有远端订单时直接进入当前授权的短写事务。

1. 两个短事务均遵循全局锁序：authority → 当前授权及上游身份行 → 门户 request/conversion → invoice → publication/amendment/关联任务和其他依赖行；只跳过确实不存在的层，不得先锁 invoice 再回锁门户关联行。首次短事务取得当前权限与对象范围后，按该顺序捕获 invoice ID、portal_document_version、既有内容 SHA-256 edit_version、远端订单 ID、同步状态、关联任务指针及该任务状态/执行令牌/租约。该阶段只读，启用模式拒绝任何已开始的 Session 事务及 new/dirty/deleted 状态，包括已经 flush 或 Core UPDATE 的调用者写入，不能顺带提交。关联编辑先按当前权限/范围验证已有 request_key 的 invoice、actor 和载荷 hash；同命令命中直接回原操作，异载荷拒绝。只有新命令才提交释放锁后取远端证据。
2. 外部取证设置现有客户端时限，不持 authority/invoice 行锁，不生成或修改 PI。远端错误、证据不完整或不可验证时返回安全 503，不能替换成“无回款”继续编辑；不把上游正文、凭据或 SQL 细节返回客户。取证引起的本地读事务须结束，并显式过期 ORM 对象及关系；即使 expire_on_commit=False 且远端快路径没有起读事务，也不能保留旧 PI 缓存。
3. 最终短事务重新取得 authority、当前读取员工及动作权限、按相同全局锁序锁定门户关联行和同一 PI 并复核对象范围。关联编辑此时再次优先校验原 request_key：并发相同命令已成功提交则返回其原操作，不能先以旧版本拒绝；不重新生成提案或执行编辑。未命中原命令时，捕获绑定任一项变化即 409，要求重新读取；员工已停用/降权则拒绝，越权对象按既有隐藏规则返回 404。不以预读通过作为最终授权。
4. 将已验证的远端证据交给现有发票服务，禁止在持锁期间再次远端查询。服务仍须检查当前本地有效回款、ReceiptIntent、待分摊回款、出库/同步状态、客户/币种/订单类型及金额下限等原保护；复用原金额计算、来源保护和同步规则。实际内容写入、portal_document_version 递增、publication 与 amendment 撤回同事务提交，任一失败整笔回滚。

外部系统与本地数据库不能凭此形成分布式原子快照；最终阶段仍依赖明确可验证的远端观测证据，不承诺锁住远端收款。当前本地回款竞争也不能仅凭一次查询称为已解决：须核对相关回款 writer 的锁序与事务协议，并以 T62 反例验证；尚未覆盖的入口保留为验收门禁。

linked-close 与 linked-resolve 不包含远端 I/O。先按[当前授权契约](01-architecture-and-access.md#员工-pi-编辑与本地恢复的当前授权契约)鉴权，再执行既有任务状态、当前指针、租约与分摊检查；禁止强制跳过不确定状态、重建 PI 或恢复未接受的发布。实际远端 run 的结果恢复仍使用专门执行协议，不能将外部调用放进全局授权锁事务。

### 本地状态操作与远端结果记录

本地 begin/retain/abort、validate 与删除按当前授权短事务执行：authority → 当前员工/范围 → request/conversion → invoice → 相关取消/任务/发布记录。取消开始或生效时撤回客户发布；abort 只在原领域允许的非终态恢复内部状态，不能自动恢复客户 publication 或让旧接受版本重新可下载。validate 仅按完整性校验调整可同步状态，不修改客户接受的商业快照，也不替代 publish。门户 PI 不走硬删除；本地作废仍走永久 lineage/tombstone 与原命令回执协议。

外部生命周期与同步操作分别定义“新动作授权”和“已执行结果记录”：新动作先在短事务内核对当前权限、对象范围、发票/远端绑定及任务状态，并持久化执行 token/租约后释放数据库事务；外部调用在事务外进行。结果落库使用新的短事务并核对同一任务 token、租约与绑定，禁止旧 worker 覆盖新执行。最终阶段若还要发起新的外部动作，须再次授权；已经发生的外部成功或不确定结果必须按有效执行身份保存，不能因操作者期间被停用而丢弃事实、回退成未执行或无依据重发。

若结果迟到时原租约已过期、token 被接管或当前绑定已改变，旧执行者只能追加原 attempt 的不可变、脱敏事实，不得覆盖当前任务、发票、发布或新执行令牌。执行前已持久化的 attempt_key 绑定原任务、发票/远端目标和输入摘要；事实须能对应该原记录，不能由客户端任选对象提交。按数据模型的稳定 event_id 去重，重复记录只回查原证据。事实保存与当前员工功能权限分离，仅允许受控执行器写入；停用操作者不使已发生事实消失，也不授予其新操作权限。

当前执行拥有者必须在重新外发前检查未核对的原 attempt 事实及远端结果；矛盾、未知或尚未核对时保持该入口的 uncertain/需核对语义，阻断盲目重发。迟到事实本身不自动驱动状态转换或再次发信/删单；有效当前任务经受控核对才更新状态。保存事实失败由原执行身份有界重试并告警，不退回“未执行”；这不是客户 Idempotency-Key 回执。

每个外部入口仍需单独给出状态转移、超时/取消行为和执行 fencing 证据，不能以普通 PUT 的锁外取证测试代替。当前本地回款、分摊、意图、出库与同步任务 writer 的实际锁序也须逐条登记；不声称全局屏障可以锁住远端库存或收款。


### 取消核对当前实现边界

启用时refresh的捕获和最终事务均使用authority→request/conversion→invoice锁序；捕获只读提交后，远端取证使用脱离ORM的复制快照。finally rollback+expire_all丢弃外部阶段缓存，最终比较PI文档/旧商业hash/远端ID/同步状态/任务指针token租约和完整取消JSON。最终Receipt/Intent/Allocation当前锁定读取替换预读本地阻塞与数量，避免REPEATABLE READ旧快照或重复count报告不一致。

角色与对象范围成功并不取消已有财务、租约或终态保护。查询成功不代表库存预占；refresh是取证和受控核对，不执行远端删除、自动出库或回款发送。F20已在门户启用后发起的remote remove接入；其他执行器仍待逐入口实施验证。

### 远端删除的执行提交、事实和终态核对（1.5 开发目标）

下列步骤细化 F20，适用于门户协议启用后发起的取消执行。1.6已在启用门户的remove路径落实下述协议；初始关闭开关的旧路径和其他外部执行器不在本批证明范围。

1. 当前员工 `invoice:admin` 与发票范围通过后，短事务按 authority → 当前授权身份 → request/conversion → invoice → 依赖行捕获完整绑定。释放事务后获取凭证并取证；最终短事务重新授权、比较原绑定和取消状态、锁定检查当前本地财务阻塞。远端网络等待不持 authority、谱系或 invoice 行锁。
2. 新执行同事务持久化独立 attempt、原目标/输入摘要、执行令牌和租约；成功提交是新外部动作的授权时点。提交抛错或确认失联时，异常请求先 rollback、停止 DELETE并返回安全503；随后由全新读取/核对事务按原执行记录查证已持久 claim，重新验证当前授权及目标。不能宣称异常请求当次已完成查证。未能确定原事务终止和 claim 一致则继续停止 DELETE，保留安全暂不可核对状态。发现 claim 不等于此前一定未外发，恢复按原执行记录只读核对，禁止换 attempt 自动重发。进程在 claim 后退出也按此规则恢复。请求路径沿用 get_db Session，先结束原事务并清缓存；不得为此新增请求内 SessionLocal。
3. 一次获准执行最多发送一次 DELETE。DELETE 响应和原目标的 readback 在事务外分别形成冻结观测事实；超时不宣称未执行，读回失败不抹掉 DELETE 接受证据。可信回读不存在也不掩盖新出现的本地回款、意图或分摊阻塞：保留证据并进入 uncertain/人工核对，不删除财务记录。
4. 受控执行器以新短事务保存事实，强制完整 authority → 原 request/conversion → invoice → 依赖锁序；即使 PORTAL_ENABLED 在外部等待期间关闭，也不能仅强制 authority 而漏掉谱系锁。结果必须对应执行前原 attempt 和目标，不从当前新 token 或客户端载荷重建。当前任务更新额外要求原 token、有效租约、任务状态和完整绑定均一致；租约失效、被接管或绑定变化只追加事实，不覆盖新任务、PI 或 publication。
5. 事实持久化须先独立成功提交，再开始单独的当前员工/范围校验，决定能否返回私密结果。操作者期间被停用，HTTP 可以返回403，但不能回滚已提交事实。事实提交结果不确定时按同一确定性 event_id 查证；有界保存重试保留原 observed_at 和首次记录，不重做 DELETE。保存仍失败则明确告警及安全503，保留可核对的原 claim，不退回未执行或以“已完成”掩盖证据缺口。

租约过期后的 retain 只确认本地业务终止、记录保留与客户发布撤回；如果曾存在 deleting/uncertain attempt，不能承诺“远端单据仍保留”。迟到结果不得把 retained 改成 remote_deleted，却必须通过当前授权的安全风险摘要被发现。终态没有待核对 attempt/事实时继续零远端 I/O；存在待核对记录时，允许现有 refresh 执行原目标的受控只读核对并追加核对证据，不发送 DELETE、不恢复 PI/发布、不改变已确认的本地终态。终态核对的捕获事务同时冻结原 attempt 及待核对事实 ID 集合摘要；远端观测后，最终锁定事务复查同一集合。核对期间新增/变化的 attempt 或事实使本次409，零核对追加、风险不清，要求重新GET/refresh；不能最终才取全部集合并用早先观测覆盖刚到的证据。目标已变或原证据无法验证则保留待核对并拒绝猜测。

当前拥有者重新发起外部操作前检查原 attempt/未核对事实；不能通过重置取消 JSON 或新建 token 绕过。旧事实不能由客户端上报为已核对，授权核对也不能作为自动补偿、退款、再删单或新建 PI 的依据。每个外部入口仍须有独立故障注入证据，不能把这一设计概括为所有同步入口已完成。

## 1.6 remove 执行与恢复的实现边界

cancellation_execution将授权捕获、最终claim、结果保存和响应授权拆为短事务；所有远端token获取、预读、DELETE和readback均在锁外。启用时发起的操作在开关随后关闭后仍强制分阶段锁序：授权捕获/最终claim/响应为authority→当前身份→永久request/conversion→invoice；事实保存为authority→原永久request/conversion→invoice并验证原START，不以当前员工动作权限为前置。不能借关闭开关退回旧鉴权，也不能因原操作者已停用丢弃脱敏事实。当前响应必须另查实时授权。

有效原拥有者须同时满足attempt/token/租约/完整绑定；否则只存原事实，不改新任务、PI、发布及已确认终态。FACT有界三次同身份保存，不重做DELETE；全部失败保留原claim并告警503。FINISHED与最终状态原子落库处理实际提交成功但确认丢失；复读命中必须连同当前绑定和状态摘要一致。原START/FACT不因核对完成而被删除，取消JSON重置也不能开始新删除。

终态refresh冻结START/FACT集合，锁外观察后重查同集合、当前权限和绑定；有新增事实409且零RECONCILED，风险保留。成功追加核对记录并保持终态/PI/发布；之后新事实或目标变化重新开启待核对。真实进程杀死恢复、初始OFF路径、其他同步/重试/出库及全部财务writer仍须各自验收；本批不证明外部与数据库分布式原子性。

## 1.7 出库恢复/确认的短事务

outbound_recovery.authorize拒绝已开启事务和待写对象并清已提交缓存，force authority后读取当前员工能力，永久request/conversion先于invoice锁定；捕获和最终事务均采用该顺序，期中PORTAL_ENABLED关闭不能跳过。停用主体在当前能力读取后即403，不要求继续锁它无权访问的PI。scope成功仍须原linked idle、cancel/uncertain/financial/shipping保护。

绑定在原edit_version/portal_document_version之外显式包含远端订单、客户、币种、总金额/附加费、order_type、状态/取消JSON、自动出库标志、完整原出库任务/最新linked操作，以及实际产品行（含UID和回填映射）。旧hash不包含金额、币种或UID，不能据它独立证明取证目标未变。短事务只读提交后，实际token/helper及所有远端GET在锁外；释放外部读取Session并expire后重取当前权限/范围、完整绑定和本地状态才允许写。未知明细订单引用不能证明无关联；扫描坏形状/缺失身份须停止503。

retry最终只排队原明确未发送/漏建任务，ack最终只保存本版本已核对证据；没有外部POST，也不新增F20外部attempt。重复或两个并发原捕获只允许一次本地迁移；已完成出库确认即使整体因回款保持manual也不被覆盖。queue授权不代表worker执行时仍获准，全writer参与及worker实际执行/迟到事实协议仍待独立验收。

## 1.8 同步不确定核对的阶段与身份契约

此入口是人工恢复既有不确定状态，不是新同步或原外部写入结果的完整 F20 执行器。启用门户的当前接入分三类：

1. `confirm_existing`：当前授权短事务捕获 PI、原目标、商业字段及实际产品行/UID、完整 sync_attempt、取消元数据、原 linked 指针及全部任务字段、当前分摊行；提交释放锁后只读原订单。结束外部读取事务并过期缓存，再以相同锁序重新授权和捕获比较。旧 SHA-256/version 不包含的币种、金额或 UID 同样纳入绑定，不允许旧 hash 未变就复用旧证据。
2. `bind_order`：在当前授权短事务内核对原未绑定状态、无关联任务、原租约与实际本地经营订单镜像，继续复用原绑定校验。`confirm_not_created`：在同一授权短事务内核对相同首次未绑定前提，并记录人工依据。这两个动作均无供应商读写，不宣称镜像或人工判断已锁定远端时点。
3. 完整证据通过后，原日志、UID、同步保护解除与本地状态一次提交；关联指针和待恢复库存保留，不创建新 PI、不自动触发外部推送或恢复客户发布。之后在独立当前授权读取中生成响应。响应权限失效不得撤销已提交业务事实或回旧私密结果；业务提交是否成功不确定时必须读取原状态及日志，不能凭HTTP状态盲重做。

### 规范远端明细身份：先验证，后回写

接受的 UID 是正整数或无前导零的 ASCII 正整数文本；比较与回写统一使用规范十进制形式。规范化仅在脱离ORM的内存证据中进行；最终当前授权、完整绑定、状态及租约复核通过前不能回写ORM。所有行先验证类型、正数、表示及数值唯一性，再校验已锚定 UID 与行内容对应、商品/SKU/数量/单价/行金额和不含附加费的原订单总额。布尔、浮点、零/负数、指数、空白、符号及 Unicode 数字拒绝；`501` 与 `"501"` 是同一身份，`"0501"` 是歧义表示，应拒绝。缺失、重复、非法数字或任一行不一致时，UID、attempt、关联任务、库存分摊、核对日志和保护状态全部保持不变。

I48 的实际纯函数反例：两条尚无本地 UID、product/SKU 不同且数量金额均一致的行，远端分别给 `"501"` 与 `"0501"`。1.8时点字符串判重通过，下一次产品构建转整数会得到两个501；该历史反例现按1.9的严格纯验证修订，局部证据不能解除整个上线门禁。

此恢复入口不发送 POST/DELETE，不另建 F20 外部 attempt；正常 sync、linked-run、出库 worker、初始 OFF、实际进程崩溃恢复和全部相关财务 writer 分别验收。局部恢复证据不能背书完整同步管线。


## 1.9 同步核对的定向实施

uncertain_recovery._canonical_uid按真实64字符字段限定规范身份；verify_existing只生成内存copy、检查全部唯一身份/商业内容与原总额后返回，confirm_existing随后才_assign_unique_ids。非法证据不进入UID回写、finish或核对日志。两条无本地UID不同product/SKU的数字别名反例在实际HTTP下拒绝且全业务快照不变；合法独立int/string/mixed回写规范文本并且重复请求不追加日志。

三恢复入口的活租约及状态/指针守卫；锁外GET期间新活租约；业务成功commit后响应撤权/范围丢失；保留真实ensure_access_token/read而仅替换外部fetch/request的慢窗口；两个原单capture仅一次verify；本地bind/clear真实独立连接锁等待及唯一日志已取得定向证据。结果与失败历史仅交接维护；这不是正常POST执行、F20全部外部事实或生产schema证明。

### 1.11 普通 POST 的原事实及迟到集合

普通推送使用独立 invoice_push_attempt/observation/finished/reconciled 审计命名空间，与取消事实分开。START 固定原 PI/门户永久谱系、员工、商业/任务绑定、发送载荷、库存 operation 与回款 token 指纹；事实追加必须核对同一可信内部执行身份。失去业务执行权或员工停用不丢掉已发生的原外部结果，但不授权覆盖当前业务。安全事实提交先于业务收尾；收尾提交确认丢失只能回读原 FINISH/绑定，不再 POST。

FINISH 仅在原执行仍拥有且成功或明确拒绝时解决对应事实集合。人工 REVIEW 固定已见集合指纹；新的迟到 FACT 不由旧 REVIEW/FINISH 消解，后续 sync 必须阻塞。取消/接管/改版仍保留原事实，实际租约及当前 authority→request/conversion→invoice 顺序不能因期中关闭门户绕过。

迟到 accepted 核对使用脱离 ORM 的可信原单验证对象，避免临时绑定造成脏数据或未绑定 None 被误拒绝。先整组验证再实际镜像校验/绑定和 UID 回写；bound 与 unbound 都补齐合法原 UID，不把人工绑定等同于库存或回款恢复。最终集合/商业/任务/附件/receipt 意图变化409，零核对与商业写。

## 1.13 后续出库排队的授权与交易契约

原普通推送完成不授予后续无限履约权。followup按“当前授权及本地捕获→提交释放→锁外供应商取证→新事务当前授权及完整比较→本地队列提交→当前响应授权”实施。短事务遵循authority→永久request/conversion→invoice/items→财务证明与出库任务的既定锁序，锁后当前读并清除旧ORM缓存；token缓存提交不得连带提交未完成的任务变更。期中关闭门户仍保留原执行的完整强制协议，不切回legacy路径。

捕获至少包含原PI/公司/订单引用、币种与各金额、标准商品/SKU/数量/单价及规范UID、原删行、永久谱系、取消与关联状态、回款/意图/分摊/附件身份、任务invoice_id/order_id/status/token/lease/reason/attempts，以及实际成功推单代次、相关删除事件与待核对原事实集合。不得仅比较旧edit_version或供应商order_id；同一旧hash下的金额/UID/附件/任务变化仍使证据失效。无待核对事实、无活执行/取消/关联冲突才允许新队列写。

供应商订单、关联出库扫描、目标仓库库存及必要回读均在锁外。无关联必须由完整可信扫描证明；订单身份、公司、币种、金额及全部商业行与捕获绑定一致，不能以空列表或仅ID相同替代。供应商异常/未知证据不推断“无出库单”。最终新事务重新鉴权并比较全捕获；通过后的任务迁移与领域审计同事务原子提交；撤权/范围失效或任一绑定/任务代次变化时，原成功推单保持，followup本地任务及PI状态零改写。旧任务被worker接管不得重置新token/租约或覆盖原因。

仅在最终通过时执行当前对应迁移：库存仍缺保留waiting_stock及安全缺货说明；库存齐全才转pending；regenerate仅引用同一PI/原订单可信成功create/update推单代次；删除后恢复还需原出库删除事件和删除后的新成功代次。业务提交确认不明先停写，再查原状态与执行记录，不盲目重排。

## 1.17 原出库执行权、结果及验货收尾

使用现有ShippingOperationEvent的独立namespace保存不可变START、SEND、POST FACT、READ、FINISH、REVIEW，不新增持久表。START冻结原PI、永久request/conversion身份、镜像/目标、原actor、完整商业/财务/照片/任务/谱系指纹、原plan和payload、auto_recall/source/warehouse、租约与父repair nonce；不存凭证。ORM不可变保护按持久旧scope识别，过期字段改namespace或删除也拒绝；Core/rawSQL与全维护writer仍需独立审计，不能由此宣称数据库层不可变。

执行顺序：当前授权短事务完整捕获→提交释放→锁外凭证并只提交凭证缓存→当前全绑定比较→pending与START原子commit→锁外order/扫描/outbound/serial占用与回读→当前权限/范围/完整绑定和租约比较→SEND与sending原子commit→锁外唯一POST→force原authority、原request/conversion、原PI、START锁序保存安全FACT→当前捕获并冻结完整原链事实集合→释放后原GET→READ留证→当前授权、完整原绑定、同nonce/事件和同事实集合比较→验货/召回审计/失效标记/verified overlay与FINISH原子commit→当前响应授权。任一claim/SEND提交不确定停止POST，不盲重试；失去当前业务执行权或租约的原sender仍可留原事实，不能业务收尾。

GET之前冻结SEND/FACT/READ原链集合；取证期间新观察不能纳入旧观测直接解决。最终FINISH记录完整取证摘要，但解决外发风险的摘要仅含SEND/POST FACT；晚到只读READ不永久阻塞已完成任务，真实晚到POST FACT仍需REVIEW。REVIEW在当前权限与FINISH后完整绑定不变、原GET仍验证目标的条件下进行，记录同集合身份，保持验货版本/召回/失效和overlay不变。

repair只有原请求有规范同目标accepted FACT才开启；旧sender有SEND但未结束或unknown时，过期也不能授权新POST。每次只补一个原新增缺UID、保留所有现有行ID/成本/handler，新nonce保存原完整plan/父来源/补齐前证据和缺行数量。上个step所加UID仍缺或缺行未减少时零新POST。各祖先START/事实在全量verified后同事务FINISH，不覆盖旧原事实。旧持久active无法可信证明来源时人工核对，不自动mint。

保留原number_only、submitted先撤回、可信auto_recall、改号占用、原成本/handler与其他单头、备注trim、累计stale/recheck集合和同快照print grant护栏。实际worker、linked-run、其他默认legacy调用方和allow-print等共享writer仍需各自当前授权改造及验收；初始OFF、真实供应商合同/进程恢复与全schema不由本批关闭。

原手动任务恢复使用请求入口与原START warehouse要求的并集，不降低权限；全部步骤仍当前验证。claim/step的姓名使用可信原START同事务快照。FINISH当前授权人和原发送人分开留存，原nonce/actor不改；成功验货召回和更新归当前有权finisher，legacy初始OFF默认仍原actor，不改变其协议。

原START仓库要求的继承在任何供应商取证之前完成，覆盖active、晚事实核对、已完成无差异返回；当前动作和仓库范围均需满足，之后准备/发送/响应阶段继续重新鉴权。enabled真实修改draft或submitted验货版本、出库号时，updated_by均为当前finisher；召回审计仅在实际召回时产生。原发送actor、原姓名及原事实不因更新归属变化而改写。

## 1.18 自动创建 worker 的阶段协议

当前员工/PI范围＋永久谱系→全 PI/行/财务/附件/产品/任务/删除绑定捕获→提交释放→锁外原订单/完整关联扫描/占号/目标仓库库存/双回读→锁外凭证缓存提交→当前全绑定比较→running 与可信 START/STATE 原子提交→再次锁外完整证据→当前身份/完整绑定/原 nonce/活租约比较→SEND 与 sending 原子提交→锁外唯一实际 POST→原 authority/冻结 request/conversion/PI/START 锁序独立保存 FACT→当前捕获和取证前完整事实集合→锁外原 GET/详情回读→READ→当前全绑定/STATE/事实集合复核→task/CHECK 或 FINISH/业务审计原子提交。普通 generic ensure_mutable 保留；worker 专用只读 capture 允许检查自己的 running 投影，但每个动作必须另证可信原 START/ownership。

START 或 SEND 提交不确定停止 POST。过期且无 SEND/FACT 的原 claim 可证明未发送后结束并重新认领；任何已持久 SEND 不因查不到单据而自动重发。原GET完整验证可完成原任务；未知仍 uncertain。原发送员工失权不丢原 FACT，但不能继续业务收尾。已完成原 GET 后迟到 FACT 须只读重核；同代次合法核对不重复 task/audit。

检查所有原代次未解决风险，不能只看当前 STATE。A 已GET完成、B开始、A FACT迟到时，B原响应事实仍保存，但 B不得直接FINISH。跨代次 STATE/商业已变化时转人工处置，不宣称自动恢复完成。调度筛选晚 FACT 必须绑定原 nonce；B 的 FINISH 不能替 A 消除风险。

每轮固定 Invoice.id 高水位，按 ID 每页20推进；拒绝、未知历史 running、在途或取证不可用也推进游标。新到任务留下一轮，不把全库 LIMIT20 再授权作为公平性。逐候选实际当前鉴权不被分页替代。整轮持共享 advisory 执行锁；新旧真实进程、崩溃恢复及发布切换需要另行证明。

## 1.19 新旧执行器切换与失败状态

这是待实现发布契约，当前发布源码尚未满足全部阶段。单个共享锁或mode记录不能证明所有旧writer都遵守同一协议。客户P0的本地建PI事务不因本节新增外部自动出库动作。

安全顺序固定为：登记并冻结旧写入口→停止旧timer并等待原service及其子进程排空→校验并安装五制品且保持暂停→后端同步建立或确认持久mode→验证新执行员工、目标库与唯一scheduler归属→按已授权配置启动新执行器→核验mode决定的目标timer及发布凭据→允许对应成功标记。未更新的直接creator在后端启动前不得有重新发起入口，不能依靠它尚不认识的mode挡住它。

排空超时不能强杀后把在途结果当作未发送；保留原START/SEND/FACT及任务供核对。任一阶段失败保持相关writer暂停，记录最后已确认阶段与未知外部结果，不删mode、不清任务、不盲重发。完成模式安装但worker/scheduler关闭时，状态应为`installed_paused`，不能把health200或旧timer已停当作新worker接管成功。`verified_running`另需真实新进程、配置与单活证据。

无mode的初始OFF才属于legacy初始兼容。已有mode后的OFF只是关闭新业务，不能撤销永久模式、恢复旧timer或注册旧补任务。旧删除对账、linked-run和其他PI/财务writer均须各自改造和验收，不能仅把它们关闭后声称迁移完成。

mode提交属于持久协议变化，即使无DDL也必须重新判定回退兼容性。候选启动后续失败时，只有实际证明认识mode、保护PI版本与永久谱系、并抑制旧writer的旧制品才能恢复；否则停留在可审计的暂停状态。正常publish、resume、专项启用和finalize入口必须共享同一凭据核验；丢凭据或仅完成页面/静态文件不允许标记整个切换成功。

## 1.21 同步启动与旧回调的事务约束

bootstrap在数据库连接检查后、任一scheduler注册及应用就绪前同步建立或核对模式，独立于worker/SCHED开关。ON首建被旧owner占锁时保持暂停；已有模式的ON/OFF重启只核对，不恢复旧创建。启动后续失败不能把已提交模式当作未发生，回退仍遵守1.19的兼容凭据。

旧补任务回调不能只依赖注册时开关：每次执行用自己持有的新Session，先取得共享执行锁，再读当前模式；已有模式则零排队。初始legacy的合法回调持锁直至实际队列事务commit或rollback，防止首建穿过旧排队。禁止复用取锁前已有事务或RR快照；旧删除对账和直接service调用仍为独立writer，不被这条回调保护自动覆盖。

锁取得、首次事务释放和锁释放全部纳入异常所有权管理。无法确认GET_LOCK是否取得时，必须invalidate物理连接并阻断该次启动/回调；仅close或rollback不能证明named lock消失。I82在1.21发现时尚待修复；1.22取得/释放、递归锁及worker清理顺序的本地修复证据见交接，不据此解释为完整执行器切换通过。


## 1.22 worker与共享fence的清理顺序

worker使用同一executor_fence，不保留独立手写GET/RELEASE协议。所有取得成功后的返回/异常路径，在仍持fence时rollback并清理专属业务Session；rollback失败则invalidate业务Session使原事务和行锁结束，外层finally仍处理执行锁。不能先释放fence再由Session.close补业务rollback，避免下一执行器穿过未结束事务。

Node readExecutionMode读取完整outbound-worker-%命名空间，唯一规范v1/version1表示新协议，空记录表示legacy；未知/多条/坏类型或DB错误脱敏失败关闭。poller每次claim前和creator现有模式核对入口继续使用assertLegacyMode，独立.env不能放宽持久协议。Node本地假SQL回归不代替真实同库多进程所有权证明。

## 1.26 协议回退的实施边界

## 1.29 实际旧补任务入口与释放前清理

公开补任务服务不再提供caller Session算法入口，统一进入reconcile_legacy；scheduler现有wrapper继续走同一协议。新factory必须产生fresh owned Session；已有事务/dirty/deleted/new不进入执行锁。取得共享fence后新读mode，v1返回disabled且不进入队列body，其他owner返回busy且不释放其锁；legacy才执行真实队列选择和入队，同fence保持至commit/rollback完成。

实际body的savepoint提交不等于根事务提交，事件测试必须区分in_nested_transaction；逐行容错不授权将全批提交故障误记为单行失败。finally清理覆盖KeyboardInterrupt/SystemExit；若rollback自身中断，必须在RELEASE前invalidate业务socket，不依赖外层Session.close补救。实际独立观察业务CONNECTION_ID在PROCESSLIST已不存在后，才将该测试计为清理顺序证据；仅独立SELECT看不到未提交任务不能证明连接已关闭。

本批实际队列阳性不调用供应商，不是已恢复旧制品。I92/C05的制品字节/依赖/运行配置与所有writer持续保护、legacy/v1兼容恢复阳性继续开放。私有算法可被受信维护代码调用，raw SQL和其他writer不会因本入口改变自动受保护。


## 1.30 应用生命周期资源所有权

实际应用lifespan须在每个资源成功取得后立即登记清理；顺序为engine、MCP、scheduler、storage，退出逆序为storage→scheduler→MCP→engine。后续种子或模块启动失败、取消及单个cleanup错误都必须继续其余已登记资源的清理，保留原始异常链；不得删除已建立的持久mode。未成功取得的资源由其取得函数清理半成品，不能依赖调用者收到句柄后才负责。

scheduler.start已完成但get_jobs/日志发生错误时，start_scheduler须停止本次scheduler并只清本次_active_scheduler引用，再传播失败。真实停止失败不可因引用已清就声称资源终止；process/cgroup退出与实际任务体仍须独立核证。AsyncExitStack保证后续清理调用，不保证任意外部SDK失败后物理资源已关闭。


多个独立cleanup异常不可仅依赖ExitStack隐式__context__：正常退出时后续callback错误可能丢失较早错误。同步cleanup显式收集BaseException，MCP正常退出或异常退出完成后，将生命周期错误与全部cleanup错误聚合为BaseExceptionGroup；没有cleanup错误时保持原异常。诊断输出不得先于清理，也不能因日志/stdout再次失败阻止本次owner收尾。实际物理stop失败的终止事实仍须独立核证。

## 回款旧入口的授权与事务契约

本节为1.32开发目标，具体化I81，不表示回款服务已经迁移。直接本地作废/重试、凭证绑定、批次作废与远端取证/送款是不同事务类型，按实际调用链识别。即便函数名是read/reconcile，写缓存、token刷新或事实回写也必须登记，不能根据HTTP方法推断没有写入。

1. 本地业务写入从无待写对象、无已启动调用者事务的边界开始；先authority和锁后当前员工/动作权限，再永久request/conversion（若存在）、Invoice、Receipt/Intent/批次/分摊等依赖。相同层按稳定ID排序；跨多个Invoice的批次先完成同层所有上游关联锁，再按顺序锁Invoice，不循环反向取得authority或谱系。事务持有至业务commit/rollback，当前范围与所有原状态/金额/租约保护同时成立。Receipt并非商业明细修改，不无条件触发客户重新接受；实际PI客户可见商业字段变化才按原版本/撤回/再确认协议处理。
2. 实时授权保持各接口原AND/OR动作权限语义，不能把任一权限误改成全部满足。当前scope沿用各财务领域明确授权：Receipt以Invoice.sales_user_id及当前receipt:read_all/管理员范围判定；invoice_context沿用当前发票代办范围。门户客户转交不能自行迁移历史Invoice归属；portal_order:read_all不能读取全部Receipt，receipt:read_all不能单独授权写动作。批次所有子单均通过，拒绝时本地业务/审计/投递任务无部分提交。
3. 需要远端证据时，首个短事务校验当前员工与目标范围，捕获对象ID、版本、财务归属、门户谱系/PI版本、远端目标、同步状态、执行令牌及与该动作有关的金额/结算绑定。提交该只读阶段后，不持authority、Invoice或Receipt行锁执行外部IO。token刷新引起的本地事务也须结束；最终阶段expire旧ORM并从当前读重新校验，不能使用旧JWT、旧范围或RR快照。期间撤权/停用则拒绝新本地动作；绑定或状态变化则409并要求核对，不悄悄换目标。
4. 已发生远端成功或不确定结果按原持久attempt/token/租约及绑定保存受控、不可变事实，不能因发起者被停用而删除结果、回退为未执行或重新发款。事实写入与员工新动作授权分别处理；迟到事实不得覆盖当前执行者。本地retry不得重发uncertain/syncing/已获远端单号、原批次或结算不允许的记录；未知结果进入原核对流程。
5. 下载/代理转发在事务外执行；授权与文件/关联版本短事务复核定义开始发送的授权时点，不承诺撤回已下载或已授权在途字节。上传在接受文件/存储写之前验证当前动作权限，文件完成后绑定须再次授权；撤权导致绑定失败时清理或隔离本次未绑定文件，不能将上传完成冒称业务绑定成功。
6. 既有request_key/版本、ReceiptIntent、批次分摊、实收下限和生命周期保护继续生效。同键重放须先当前授权，不重复Receipt、Log、投递、手续费分摊或外发；没有幂等契约的旧动作不得宣称天然幂等，应给出版本/当前状态冲突及原结果回查规则。本地写先取得屏障且提交的事实保留，撤权后不回滚已提交事实或重新授予旧用户读取权限。

门户关闭新提交不撤销已建PI的永久谱系/版本保护；已进入上述协议的远程流程期间关开关不能退回JWT鉴权。尚未安装门户协议的旧普通业务路径需单独基线回归，不能用禁用全部回款代替接入。首期不新增客户在线付款入口；以上仅约束方舟员工既有财务链路，目标仍为保护订单隔离和PI正确性。

## 1.33 本地回款读/作废的事务边界

当前读入口在fresh_boundary拒绝调用方已有事务，然后expire并查询当前employee/roles/permissions，保持原财务对象范围。普通读取不取得全局写屏障；它的授权点是当前主体读取，未承诺与同时撤权线性化所有响应字节。void则force取得authority，即使当前迁移后的门户设置OFF也不解除保护；顺序为当前员工→Receipt.invoice_id只读定位→永久request/conversion→Invoice→当前Receipt FOR UPDATE/populate_existing。取Receipt锁后比较关联仍为同一Invoice，再用当前scope校验；不存在与无范围统一404。

授权查询的SQLAlchemyError只在授权/锁phase映射固定503；诊断logger/stdout的普通Exception不得覆盖这个响应，保留为内部ExceptionGroup cause，不作为响应正文；KeyboardInterrupt/SystemExit等BaseException仍传播。该分类不吞后续原财务业务错误，也不把真实业务提交或远端未知当作未发生。

legacy仅在同连接当前parent锁读证明唯一171后进入，能力属于同根事务；不得由无held推断legacy，不跨根复用，失败force先清旧能力。连接/限时/屏障阶段分别识别，只有屏障SELECT真实缺表1146有资格查询parent；其他SQL异常安全503，诊断普通Exception保留内部cause，BaseException原传播。普通1054错误仍原SQLAlchemy错误、真正1205仍TransactionBusy，根rollback恢复锁等待设置。

## 1.35 普通回款读取的授权时点与IO

## 1.36 回款 retry 的分阶段事务

公开入口依次锁 authority、全部 OrderRequest（ID升序）、全部 Conversion（ID升序）、全部 Invoice（ID升序）、Batch、Receipt成员（ID升序）。捕获成员与当前锁读结果须完全一致；每个子单校验原 Invoice 财务scope。缺上游谱系的原普通PI仍按Invoice/Receipt规则处理。helper不提交或回滚调用者已有事务；跨Invoice先完成同层锁，不能逐单循环反向拿谱系。

uncertain核对found→当前授权和原身份/关联通过→resolved；not_found继续uncertain，原body与余额version不改变；核对或重试403/404/409/503不能把已未知变成draft。初次明确业务拒绝且没有先前未知才可清对应槽并恢复draft，私密授权拒绝清显示；无未知draft拒绝允许关闭。

read-only status的Session不进入execute，不commit业务：干净边界→当前授权/关联锁读→构造DTO→rollback。调用方原有dirty事务在try之前拒绝，不回滚/flush它。原POST锁外取证时的not_found观察不影响原POST后续最终授权及唯一提交；随后found和exact retry指向同一原批次，禁止换key重发。

当前客户端槽不是服务端未提交journal，不能推断在途供应商POST或关闭标签页后的结果。其余自动Intent/发货登记/worker/rawSQL及未注册writer仍按原开放门禁验证。


## 发货创建的三事务与资金守恒（v1.47）

事务1锁当前永久authority→门户谱系→实际Invoice→排序InvoiceItem及原结算/完整资金图，冻结独立订单与历史运费/出库目标和凭证元数据；显式commit仅释放捕获锁。锁外只读外部证据并执行真实storage-helper；事务2结束token/cache事务，不是商业写。最终新事务重复当前权限/范围和完整捕获；完全一致后纯本地应用，router事务3提交结算、原行、可选Batch/Receipt/Application及事件。调用方脏事务在捕获前拒绝，既不flush也不回滚调用方未完成的修改。

最终金额保留原quote hash值表示、货款/手续费/运费规则；current FOR UPDATE行读取后在Python累计已发数量和已用预付款，不用可能来自旧RR快照的普通SUM。末批预付款的原金额/手续费只占用一次；不含payment不额外要求receipt:write、不制造新Batch。嵌入payment仅接收已验证的typed FileEvidence，最终核实际凭证绑定，无skip-storage开关或锁内文件IO。

原键回放严格校验原操作资金图，但不要求重新ready或当前新余额、不重取文件、不把合法后续回款归入原操作。最后commit已持久但ACK丢失时，原键恢复返回唯一原结算；没有持久则仍按原请求重新验证。不存在“暂未查到即可更换键”的规则。原供应商POST在途且尚无持久事实的生命周期、其他sender和执行worker仍另行验收。


## 报价的锁外证据与零商业提交（v1.48）

报价永久authority→实际谱系/Invoice/排序锁读item及完整资金图→第一commit放锁→独立订单/出库/历史运费证据→第二commit结束token/cache→最终新事务当前OR权限/范围与完整资金图重验→原build_quote(current=True)→独立DTO→rollback。最终阶段没有第三商业commit。调用方脏事务在try/finally之前拒绝，不能被报价服务flush或rollback。

捕获和锁仍按固定顺序，业务行排序恢复原sort_order；已发数量/资金使用当前行累计。精确两阶段before/after故障必须命中同一真实Session，第二阶段以真实metadata UPDATE和独立持久读取辨别commit/rollback；成功对照须证明仅两个commit、最终rollback、无商业DML与有限资金图不变。事件注入不等同物理故障。


## 本地发货暂停/恢复/取消事务（v1.49）

新事务→永久 authority→当前 shipment:write→实际 Invoice 谱系/current lock→原财务范围与ready→current资金关联图→原本地状态算法→显式flush→当前描述→路由唯一commit。无锁外取证阶段、供应商发送或服务内部commit；订单定位前不读取私密资金，所有关系核验先于apply。脏caller在进入try/flush前拒绝，不提交或回滚它已有的修改。

原 shipped/cancelled/outbound_uncertain/review_required、任何出库任务、运费sending/verifying/uncertain、未释放资金Receipt syncing/uncertain均阻止三动作。取消仍拒绝非deposit未释放付款和已绑定运费，只将本结算Application改released；暂停仍可由原合法状态进入paused；仅paused可恢复，按原当前funding_balance的remaining_amount为零进入awaiting_verification，否则awaiting_payment。不新增暂停/取消的资金足额条件，响应沿用原余额规则。

I122/P2实际反例表明生产SessionLocal.autoflush=False时，apply后直接populate_existing会把未flush的Application释放覆盖回reserved，造成cancelled但仍占款。明确flush状态/App/审计后再current读响应，仍同一事务、没有提前提交或释放锁；flush/最终commit失败全部本地回滚，已commit丢ACK保持原唯一version/event。late_result的保守拒绝与合法人工绑定恢复限制见02；不能据此关闭完整逐事实恢复。

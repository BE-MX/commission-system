所有新增表统一前缀 `ark_order_portal_`，写入 `commission_db`。现有素材门户已经使用 `ark_customer_portal_accounts` 与 sessions 等表，绑定旧 company_id，**不得复用、改名或自动迁移这些账号**。两类门户的登录授权互不隐含授予。

下文是字段级逻辑设计，实施时据已有 FK 精确类型生成 Alembic；不是可直接执行的 SQL。新主键 `BIGINT`，对外 public_id 使用 UUID 字符串且唯一，API 中所有大整数 ID 输出字符串。员工 FK 使用现有 `ark_users.id` 同款 unsigned INTEGER；客户、发票 FK 与各目标列精确一致。跨只读业务库无数据库 FK，使用显式只读适配验证。

状态与业务名使用 String+CHECK/服务校验，勿用任意 JSON 替代可约束的身份和幂等字段。下表 NN=不可空，UQ=唯一。持久业务记录不级联删除账号、客户或发票；停用用状态，不删除证据。

## 既有 Invoice 必需迁移

代码核对基线 `54f77438328e5aa5d3c776ee309914447672d767` 中的 `backend/app/invoice/models.py` 没有持久文档版本列。现有 `linked_sync_service.edit_version(invoice)` 已计算内容 SHA-256，内部 API 的 edit_version 返回该字符串，必须保持其接口与用途。W05 另为现有 Invoice 表新增 `portal_document_version BIGINT NOT NULL DEFAULT 1`，现有记录从 1 开始；门户 API 用 invoice_document_version 表达，不能覆盖既有 edit_version 字段或函数。所有影响客户文件或有效性的创建后变更（头、行、价格/费用、地址、付款条件、作废、相关资产/关联快照）通过同一服务入口在事务内锁 invoice 并递增；不能使用 updated_at 代替精确版本。

对门户关联 PI 的编辑先按全局顺序锁授权屏障、request/conversion，再锁 invoice，递增版本并撤回 publication，将 pi_amendments 置 withdrawn、清 active/accepted 指针；原不可变修订和客户接受证据保留。渲染不得无版本地读取可变客户/商品主档，外显值固定在该 PI 版本快照。既有手工、截图、外部接入、后台任务/脚本入口必须登记并回归；任何未覆盖的编辑入口阻止门户开放建票。首次创建 version=1；纯内部且不影响文件/有效性的审计不必递增。

## 数据精度与容量

- 金额在 API 中为定点字符串；数据库和计算使用 Decimal，ROUND_HALF_UP。单价最多 4 位，小计与费用 2 位。P0 无客户端折扣入口，服务端折扣默认 `0.00`；既有发票折扣为负值，见状态文档公式。
- 每单 1..100 个去重 SKU 行、每行数量 1..10,000 的严格整数，JSON body 最大 256 KiB。价格与数量乘积必须在 Numeric(14,2) 范围内，并通过站点最大订单金额配置；测试极值不绕过 schema。
- 地址字段和 note 有长度限制但允许必要 Unicode；不接受任意 HTML。图片来自受管理资产 ID，不允许浏览器提交远程 URL 让后端抓取。
- 库存 quantity/weight 的转换必须取标准元数据，20g 只是示例。同一标准 SKU 在同站目录只能对应一个 item_id，由数据库唯一约束保证。购物车重复添加先合并数量；服务端拒绝重复 item_id 或标准 SKU 行，按唯一行的 SKU 总量核验可供量、起订量和步长，不能拆行绕过。

## 迁移与保留

1. 实施前检查所有分支迁移编号与实际 schema；本组文档不预占 revision 号、不编造线上 revision。
2. 新表分为身份授权、目录映射、交易记录三个有依赖的迁移步骤；新增权限 seed 与应用代码同时提供。只建空结构，不自动导入参考站客户或素材门户账号。
3. FK 类型、collation、生成列能力在隔离 MySQL 验证；不以 SQLite 通过代表 MySQL DDL 可执行。唯一键的 nullable 语义需专测。
4. 新站开关默认 false。上线前人工建立客户 ID/OKKI ID/负责人映射并做冲突报告；冲突不以姓名相似自动消解。
5. 会话/验证码/限频过期记录默认在到期 7 天后清理；邀请状态和安全审计保留策略由运营确认。订单、报价依据、PI 发布快照、转换 tombstone 不由 TTL 自动删除。
6. 删账号只做停用，删除客户/发票必须先检查 portal 引用并阻止破坏引用。rollback 是关闭写入口并回退兼容应用，不 DROP 表、不回滚已发 PI，不对共享生产库 stamp/downgrade。

## 业务通知投递模型补充

业务源事件先在一个事务中创建按收件人划分的 `business_mail` 子事件，并转为 `expanded`。该状态只表示已展开，不表示投递成功；成功率和积压以子事件的 sent/pending/sending/dead 为准。没有有效客户收件人时源事件 cancelled。认证邮件仍使用原有独立事件类型和加密信封。

子事件键为 `notify:{source_public_id}:{recipient_kind}:{membership_id_or_current}`，唯一约束防重复展开。payload 仅保存请求、源事件、收件人类型及成员引用，不保存邮箱、金额、地址或邮件正文。员工收件人使用 current 标记，在投递前重新解析当前负责人；客户成员引用不替代发送时的账号验证与授权检查。expanded/cancelled 为现有字符串状态列的服务值，无新增迁移。

## 图片批准引用实施约定（2026-10-03）

既有 CatalogItem.image_asset_id 是64字符受管理引用，不作为裸素材外键使用。现在存 `asset_id:base64url_sha256`；指纹基于素材ID、current_version_id、storage_path、file_size、file_format、可用时的StorageTransfer.sha256。20位ID加冒号加43字符完整SHA256编码恰好64字符，无新增迁移。只保存裸ID不构成批准，读取时拒绝。管理端商品读模型仍返回独立素材ID便于识别，客户永不接收存储key。

绑定须匹配本次预览返回的完整reference；素材在预览后或批准后换版/换存储标识时失效，须重新双权限批准。素材公开预览策略不替代门户商品授权。历史订单不保存图片字节或自动更新商业快照。

## 映射发布通知模型（1.3 开发目标）

P0 映射发布与 outbox 入队在同一事务完成，补齐 T47 已要求的恢复分支。源事件 event_type=mapping_published，aggregate_id 为 access_public_id，稳定 event_key 为 mapping-published:{mapping_revision_public_id}；payload 只含 access_public_id、mapping_revision_public_id、mapping_version，不能包含别名、邮箱、金额、地址或员工凭据。mapping_revision_public_id 是本次不可变映射修订的公开 ID，不用版本号猜全局对象。

每个当前有效且已验证客户成员对应一个 mapping_mail 子事件；event_key 为 notify:{source_public_id}:customer:{membership_id}。子事件 aggregate_id 同 access，payload 只含 access_public_id、mapping_revision_public_id、source_event_id、recipient_kind=customer、membership_id。订单 business_mail 仍使用原订单 payload，不能把映射 access 冒充 request_id。同一源事件展开、唯一子键与源状态 expanded 同事务；失败整体回滚，无有效收件人则 cancelled/NO_ACTIVE_RECIPIENT。

## 外部执行 attempt 与迟到事实的审计约束

本节是开发目标，复用 audit_events 的追加记录与 event_id 唯一约束，不宣称既有同步日志已经满足这些条件，也不要求本轮新建表。每个涉及外部效果的入口在执行前持久化 external_attempt_started，记录稳定 attempt_key、任务类型/稳定任务ID、原 invoice/目标引用、原输入摘要和授权操作人；租约更新不能改写该记录。attempt_key 为独立安全随机 UUID，不把原始 lease/run token 当对外审计字段。

外部结果保存为 external_attempt_fact，安全字段限定为原 attempt_key、effect_kind、结果分类 succeeded/failed/unknown、提供商安全引用、观测时间及脱敏证据摘要；不存响应原文、凭证、邮箱地址、完整订单或付款数据。fact_fingerprint 仅由原 attempt_key、effect_kind、结果分类、提供商安全引用与规范化证据摘要生成，不含观测/保存/重试时间或重试次数；observed_at 是首次实际观测时间，在原结果对象中冻结，保存重试不重算，同身份命中保留首次观测/保存时间且不覆盖。event_id 按固定 namespace + 原稳定任务身份 + attempt_key + effect_kind + fact_fingerprint 确定性生成 UUID，UQ(event_id) 原子去重，不使用新的随机ID伪装同一事实。请求与响应内容只作为摘要，具体远端故障文字不进入客户时间线。

迟到事实的来源和对象绑定从执行前记录验证，不能从当前任务的新 token 或客户端 body 重建；原 attempt 已失去租约不妨碍保存事实，但不能凭此更新当前任务/PI/发布。原执行记录和事实按财务证据保留，不因员工停用或任务接管删除；当前执行器重新外发前查询未核对事实，按交易文档核对，未知结果不能当作确定未执行。该审计动作不能隐式新增业务命令、邮件 outbox 或建票 lineage。

### 执行记录的实际字段与分项证据（1.5 开发目标）

上文逻辑 `event_id` 对应现有 `AuditEvent.public_id`（继承 `Record` 的 36 字符唯一列），不是待新增的第二个字段；`object_type/id` 对应 `object_type/object_public_id`。使用既有唯一约束和追加保护，若实现发现约束不足，再按隔离迁移流程补齐，不能只在内存集合去重。门户 PI 的对象引用沿用其 Conversion.public_id 和所属 access；非门户 PI 使用受控稳定对象身份且不得混入客户审计投影。对象绑定、输入摘要与执行令牌摘要从执行前记录验证，原始执行令牌仅留受限任务状态，不写事实、同步日志、HTTP 响应或前端存储。

同一个删除 attempt 的 `effect_kind` 至少区分 `delete_response` 和 `readback_observation`，两者有独立的首次观测时间、结果分类及稳定事实身份。DELETE 已被供应商接受而回读失败时，前项为 succeeded（仅代表接受），后项为 unknown；不能合并成一个 unknown 并丢失接受证据。回读证明不存在/存在分别保存受控 `absent`/`present` 摘要，无法验证保存 `unavailable`，不根据 HTTP 超时猜测远端效果。

受控只读核对追加 `external_attempt_reconciled`，绑定原 attempt、捕获短事务冻结的原 attempt/待核对事实稳定身份集合摘要、当次可信远端观测及当前核对员工。最终短事务重新读取并比较该集合；出现新增或变化则409，不追加核对记录也不清风险，不能把观测后到达的新事实一并标记已核对。不能更新或删除原事实。核对确认只覆盖该集合；之后新增迟到事实或目标绑定变化时，风险摘要重新判定为待核对，不能用旧核对永久遮蔽新证据。核对记录不充当新 DELETE 命令或客户建票回执。

## 1.21 模式读取与连接所有权约束

已知模式仅为单条`outbound-worker-v1, version=1`；`outbound-worker-%`命名空间出现未知版本、多个记录或非规范值均须失败关闭。表缺失的legacy兼容须有目标版本证据；Node缺表边界以1.23的唯一精确171 head为准。ON必须先完成所需迁移再建立模式。权限不可见和读取失败不能被当作表不存在或初始OFF。

命名锁属于物理连接，事务rollback不释放它。GET_LOCK发出后确认丢失、首次rollback失败和RELEASE_LOCK结果未知，都必须使该物理连接失效，不能归还连接池。持久模式与原业务事实保留；连接故障不授权删除模式或恢复旧执行器。1.21时Python取锁异常I82及Node未知模式仍开放；1.22已补局部所有权保护与严格模式读取，具体证据见交接。全rawSQL writer保护及真实进程门禁保持开放。


## 1.22 物理连接的命名锁所有权

共享fence在GET_LOCK前读取本物理连接ID和当前owner；本连接已经持同名锁时拒绝再次取得并invalidate该连接。GET_LOCK和首次rollback、返回值读取全部纳入异常保护，仅规范整数0表示busy、整数1表示已取得；未知结果不当作busy正常返回。RELEASE_LOCK后核对owner已不为原连接；其他合法连接即时接管允许通过，释放或核对不可确认则invalidate。KeyboardInterrupt等中断先处理连接所有权再保留原中断，不归还未知锁连接。

事务commit/rollback不释放named lock，同session可递归取得同名锁；不能以一次RELEASE_LOCK=1证明旧递归锁已清空，不能使用RELEASE_ALL_LOCKS删除未知归属的其他锁。[MySQL官方锁函数说明](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html)。本地MySQL8.0.46已取得相应区分证据，生产连接池和实际进程切换仍需独立验证。

## 1.24 发布模式下限与原调度基线

## 1.29 旧补任务的事务所有权

## 1.34 权限屏障缺表边界

无新表或迁移。既有authority行的存在与锁协议独立于出库mode和PORTAL_ENABLED；空mode的已安装数据库仍取得authority。未安装例外只在OFF/nonforce真实屏障查询1146后，同一mapper物理连接当前锁读到唯一精确171 parent成立。不能将authority可读但缺行、权限隐藏或任何连接/timeout错误当旧schema。

parent FOR UPDATE是已存在调用方RR事务的当前读证据，防止旧171快照掩盖已提交173；不提交调用方，也不证明任意多服务器写入原子性。两bind用例核证timeout/屏障/head同连接；生产SessionLocal仍单bind，跨服务器迁移和所有writer冻结保持原门禁。legacy-root只存事务内能力，不是持久版本、开关或旧制品兼容标志。


## 1.45 批次资金目标的业务关联

本轮不增加表或迁移。Receivable外键/唯一business_key不能单独证明业务关系正确：同客户A/B两订单中，key=invoice:A:goods、invoice_id=B仍可能满足独立FK/UQ。应用层须从请求的预期key映射核invoice/kind/settlement/customer/currency及商品remote_order_id；首次目标缺失冻结absence，最终仍缺失时由原算法创建，存在错误关系则拒绝。原键回放的已有子单目标缺失不适用lazy创建。

预售回放的ShipmentSettlement必须存在且归属子单Invoice；每个原presale_goods/freight子单恰有一个对应Application，component与target.kind一致，稳定key分别为invoice:id:goods或settlement:id:freight。释放应用和结束结算不改变这些历史关系。隔离测试只补Batch.request_key、Receipt.request_key、Receivable.business_key实际唯一索引，其余上游表为薄合成schema，不证明完整历史FK或迁移重放。


## 1.46 原提交恢复的存储边界

无新表或迁移。已提交原操作仍以ReceiptBatch.request_key/request_hash/created_by及实际子单/目标/结算关系证明身份；read-only status不创建财务记录、目标或命令占位，不持久化未提交/在途的命令体。因此not_found只是当前观测，不是取消、未提交证明或可换键许可。

客户端当前标签页采用ark_receipt_batch_pending_v1:actor槽，内容只含actor和原BatchCreate完整body。初次发送及原请求重试前必须写入并读回确认；已有未解决槽禁止用另一key或另一body覆盖。只在同key已核实成功，或首次收到明确事务拒绝且从未未知时删除对应槽；后来发生的403/404/409不能清掉原未知命令。clear也必须匹配原key，不能删除后来操作。

刷新/组件重开可从该槽恢复，先当前服务端授权再显示。会话存储异常或损坏不能新建，提供重新读取或管理员核对。关闭整个标签页、浏览器崩溃/人工清除存储不是本次可恢复保证；不能假装服务端有尚未实现的持久未提交journal。


## 发货创建关联与快照约束（v1.47）

本轮无新增持久表或迁移。继续使用ShipmentSettlement(request_key、invoice_id、sequence)、SettlementItem、ShipmentOutbound、SettlementEvent及原Receipt/Batch/Receivable/Application/Attachment关系。已有原键必须指回实际原Invoice；SettlementItem的原数量和所属InvoiceItem、原预付款Receipt及其唯一deposit Application、嵌入Batch的原子单/实际目标/组件/凭证都须一致，缺失历史关联拒绝409且不自动补建。

原嵌入Batch的资金图按其原child Receipt ID的全局当前Application查询核验；合法后续批次与回款不属于原操作，不能因后续资金进入而阻断回放。首次新建缺失合法Receivable仍由最终原算法创建。当前读覆盖相关Receipt、eligible Intent、Allocation、全部结算/行/出库、Application及其Receipt、目标、Batch/凭证、Log/Event；冻结各模型完整字段及独立外部目标，最终比较完整关联而非只比较金额。

测试的薄上游schema显式保留五项唯一索引，并观测21类有限财务/关联模型；这不是全部历史FK、所有表或生产迁移验收。字段与最终持久关系以原业务模型及本章契约为准。


## 发货报价的业务行排序与资金图（v1.48）

无新增持久表或迁移。InvoiceItem锁按主键取得，报价/摘要/返回行按原sort_order业务顺序；同sort_order用ID作为明确稳定tie，NULL按原数据库升序位于有值之前。不得把锁顺序当报价顺序，避免合法多行quote_hash被误判过期。已排序不同值的多行对照必须与原get_order/build_quote/fetch_evidence完整字典及hash一致，再核实际创建结果。

报价复用完整当前资金图捕获，但显式不带payment/request_key，不虚造创建键；只有create传实际键才查询碰撞Batch，不能把全局NULL-key批次纳入报价图。无关NULL-key批次期间变化不能阻断合法报价。目标、行、Receipt/Intent/Allocation、结算/出库/应用/Batch/proof/Log/Event等沿用既有21类有限关联观察范围，不新增持久化报价表。


## 本地发货状态操作的既有模型（v1.49）

本批不新增表或迁移，复用 ShipmentSettlement.version/state、SettlementApplication.status、Receipt、Receivable、ReceiptBatch、SettlementItem/InvoiceItem、ShipmentOutbound、ReceiptLog 和 SettlementEvent。取消只释放本 settlement 的已锁 Application，不按共享 receipt_id 批量释放；预付款 Receipt 的金额、费用和 active 状态不因此修改。version 与一条动作事件同事务追加。

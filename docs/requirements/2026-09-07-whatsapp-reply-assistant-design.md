# WhatsApp「话术」助手：功能设计与接入方案

日期：2026-09-07。状态：设计提案，未实现、未创建线上 Agent、未修改线上配置。已补充吸收用户提供的「谈单助手0826」中客户复盘与成交推进方法；不包含其阿里询盘提取、客户背调抓取或报告运行流程。

## 1. 结论

推荐直接在方舟实现轻量「销售回复 Agent」：扩展提取当前私聊上下文，方舟按业务员权限检索已发布知识，生成对方语言的回复草稿，业务员预览后填入输入框，自己发送。

不建议把现有 Accio Work Agent 服务化作为首版主链路。亮哥已确认：现有 Agent 以 SOUL 为核心，没有其他 Skill，接入的也是方舟知识库。因此没有独有知识库、专有工具链或复杂工作流必须留在 Accio。新 Agent 应直接吸收方舟销售方法，保留业务能力，而不依赖特定桌面 Agent 容器。

这里的 Agent 是「有明确角色、知识来源和输出边界的回复生成服务」，不是新建通用多 Agent 平台。首版为有上限的两阶段处理，不新增自主浏览、客户背调、订单操作或自动发送。

```text
扩展「话术」
  → 当前私聊的有限上下文快照
  → 方舟：设备鉴权 → 用户权限 / 知识 ACL
  → 对话意图与语言识别 → 检索已发布知识 → 生成与校验
  → 扩展：外语草稿 + 中文释义 + 来源 / 待确认项
  → 用户「填入输入框」→ 用户自行发送
```

两条方案都应由方舟提供统一入口；即使将来改用外部 Agent，扩展也不持有 Accio 凭据、不直接连接个人桌面。

## 2. 选型依据：事实与未知项分开

### 2.1 已核实的现场事实

- 扩展 v1.2.5 已有设备配对鉴权、来信/发送前翻译、预览回译、填入/恢复输入框、切换会话失效保护。可复用，但当前接口一次处理单段文本，不是多轮回复生成。
- 后续已验证并合并 v1.2.6 的 cloud API 路由；话术设计沿用扩展的方舟入口，不重新引入 work 中转。单段翻译的约 3 秒实测不代表多轮话术生成能达到同样速度。
- 当前消息解析器只读取尚未处理的来信。话术需要「双方消息」，且必须包含已翻译的历史消息，不能直接把现有来信列表当上下文。
- 方舟知识库已具备平台权限、库成员 ACL、发布修订与版本读取，HTTP / MCP 复用同一 service。
- 2026-09-07 只读数据库核对：4 个活动库共 61 篇已发布文档，约 119,610 个文本字符。并不是只有本轮整理术语时使用的 12 篇资料。
- 普通知识搜索是标题/正文子串匹配；知识编辑 AI 已有授权范围内的关键词提取与词频排序，可借鉴其权限和排序逻辑，但还不是多语言语义检索，也不是话术服务。
- `app.ai.call_service.delegate()` 目前只创建 pending 日志和 task_id，没有真正派发 Accio 任务；而且会把 task 写入日志，不能直接用于 WhatsApp 上下文。
- 本次查询到的 WhatsApp 预设均为 direct 模型，没有现成的可用话术 Agent 预设。
- 用户确认：Accio Agent 仅 SOUL + 方舟知识库，没有独立 Skill。

| 方舟知识库 | 已发布文档 | 首版用途 |
| --- | ---: | --- |
| KB-01B｜内部公司与产品知识 | 17 | 已核实产品事实、术语；内部信息不等于可对外披露 |
| KB-02｜销售政策与承诺边界 | 3 | 样品、付款、交期等约束；待确认和动态条件不能当承诺 |
| KB-03｜销售打法与客户策略 | 35 | 判断本轮目标、议价、价值型跟进、低风险推进 |
| KB-04｜质量与售后 SOP | 6 | 共情、取证、升级路径；不自动定责或赔付 |

数量是管理员视角的只读清点，不代表每位业务员均可访问全部库。

### 2.2 两条方案比较

| 维度 | A：方舟原生回复 Agent（推荐） | B：已有 Accio Agent 服务化 |
| --- | --- | --- |
| 业务知识 | 直接使用当前方舟发布版本 | 当前同样来自方舟，没有独有知识优势 |
| SOUL / 销售风格 | 新角色规则 + 动态检索，可吸收已验证表达 | 保留原 SOUL；但现有 SOUL 内容与实际效果尚未导出对比 |
| 接入工作 | 新回复端点、有限上下文采集、检索与校验 | 同样需要扩展和方舟入口，另需验证并实现 Agent 调用协议 |
| 耗时可控性 | 可限制模型次数、上下文和检索量，单独调优 | 取决于运行方式、工具循环、启动和队列；无当前实测，不假定必然慢 |
| 团队权限 | 自然绑定业务员账号与知识 ACL | 必须解决外部 Agent 身份映射；不能共享亮哥的高权限知识凭据 |
| 隐私和会话隔离 | 可设计为正文只在短时内存中存在 | 需验证会话记录、长期记忆、日志与跨客户隔离，不能只靠新建会话 |
| 持续维护 | 方舟统一修改模型、策略、知识与审计 | 方舟 + Accio 两套运行环境；桌面桥接还涉及在线状态、升级和恢复 |
| 未来换模型 | 换独立回复预设，不动扩展 | 能力与服务稳定性受 Agent 平台接口约束 |

官方 2026-08-19 更新的一篇相似 OKKI/WhatsApp 案例描述当时没有入站 Agent API，采用钉钉唤醒与本机回写桥接；案例还注明最终端到端验证受 DNS 失败影响。它证明桥接有过探索，**不是当前所有版本都无 API 的证明，也不是成熟服务 SLA**。[官方相似案例](https://www.accio.com/wow/usecase-one-click-ai-sales-follow-up-via-okki-crm-dingtalk-bridge.html)

官方 Agent Core 文档说明长期记忆可从对话中提炼并持久化，且同一 Agent 的核心文件在多个场景共享。因此「每个客户新建聊天」并不能单独证明客户隔离；如果未来选 B，需验证运行时记忆开关、日志保留与工具权限。[官方 Agent Core 文档](https://zh.accio.com/wow/doc-agent-core-design.html)

本机未安装 Work Agent CLI，未读取个人 Agent 私有配置，未尝试登录、安装、唤醒或收费调用。其本地 Skill 主要面向商家经营能力发现，不能据此推断支持 Accio Work 桌面自定义 Agent 入站调用。用户补充已足以确定首选方向，无须为设计安装全局工具。

仅在以后出现「已有 Agent 有不可替代能力，且有受支持的服务端调用、身份隔离、结果协议、配额和数据保留能力」时重新评估 B。不建设自动切换双引擎，也不以钉钉通知、浏览器点击或个人电脑常驻作为首版依赖。

## 3. 用户体验

### 3.1 默认流程

1. 在现有输入框工具条的「翻译」旁增加「话术」。输入框为空也可使用；原有翻译行为不变。
2. 点击后读取当前私聊已加载的最近 20 条纯文字消息，包含双方原文。显示「已读取 12 条 / 仅当前已加载内容 / 回复语言：德语」等真实摘要，立即开始生成，不要求用户填写客户类型或销售阶段。
3. 若输入框已有文字，标为「你的未发送草稿」作为意图参考，不伪装成已发送历史或已批准承诺。提供清晰的关闭该项入口。
4. 生成结果先展示一条推荐回复。中文释义、简短建议理由、知识来源和待确认项分层展开，不把长篇客户分析放在回复前面。
5. 用户可以「更简短」「更柔和」「换个推进方式」「重新生成」或补充一句本轮目标；这些动作才触发新的生成，不预先生成多份备选消耗时间。「换个推进方式」改变推进当前关卡的路径，不只是换措辞；证据只支持一种路径时如实说明，不强凑三版。
6. 「填入输入框」只放入对客外语正文。引用、中文提示和内部策略绝不混入正文；使用现有编辑器替换与恢复机制，仍由用户自己发送。

首次使用以简短说明告知：点击话术会把当前选取的文字上下文交给方舟及其配置的模型处理；不读取完整历史，不自动发送。此说明不是每次重复审批。

### 3.2 上下文与语言规则

- 只取当前私聊 DOM 已加载的内容，不读取 WhatsApp 私有数据层，不后台拉全历史、不自动翻页；群聊继续不支持。
- 默认 20 条；展开范围可到 40 条，总文字上限暂定 12,000 字符，参数从能力接口下发。超限按消息边界保留最近部分，界面明确提示有截断，不静默丢弃最新客户问题。
- 仅有旧片段或无法确认正在看对话尾部时，明确显示范围。用户可回到最新消息后重新读取，或主动补充背景；不能声称已掌握完整关系和历史承诺。
- 保留方向、相对顺序、原文和必要的换行；时间只作辅助，不按本地化时间字符串重排。跳过媒体但显示「有未读取的图片/语音」提示；客户说“看这张图”时先请求文字描述，不猜内容。
- 已生成的译文、工具条文字、系统通知、重复引用消息不得混入上下文。无法可靠判断来信/发信方向时不猜角色。
- 回复语言优先级：本次明确选择 > 最近有效客户消息的主要语言 > 当前会话已选语言。用多条有效客户原文辅助判断；“OK”、数字、表情不作为强语言证据，混合语言或不确定时给出可修改提示。
- 不按姓名、号码区号或国家猜语言，不因某个语种推断客户类型。首版沿用扩展已有支持语言；英文、德文是必测语言，不承诺未经测试的新语种质量。

### 3.3 交互安全与失败反馈

- 点击时冻结会话实例、消息快照、草稿版本和语言。生成中切换聊天、关闭面板或取消后，丢弃迟到结果。
- 同一聊天收到新消息后，旧结果标为「上下文已更新」；不允许直接填入旧结果，应重新生成。输入框在生成中被用户编辑，也不能覆盖新内容。
- 未登录 / 权限撤回：引导重新授权或联系管理员；知识无权限不显示文档标题；失败不影响原翻译按钮。
- 未检索到可靠知识：只生成不含产品/政策承诺的澄清或共情草稿，并明确「本轮无可靠知识依据」。检索失败不能伪装成“知识库没有”。
- 超时 / 模型错误：保留用户草稿，显示可重试状态；取消只保证不再展示或写回，不能承诺模型侧调用已撤销或不计费。
- 不显示未经完整结构与证据校验的流式草稿。首版为单次 POST：扩展只显示自己可观察到的「读取上下文 → 生成话术 → 完成/失败」，后端分阶段耗时用于诊断，不在没有进度协议的情况下假称正在检索或校验，也不伪造百分比。

## 4. 新 Agent 的业务规则

角色规则草案见 [销售回复 Agent SOUL](2026-09-07-whatsapp-reply-agent-soul.md)。它是角色和决策规则，不是生产报价表，不将库存、退款、免费样品、具体时限等动态政策写死。

### 4.1 从知识库吸收什么

- 以《外贸询盘到复购｜证据驱动的全链路销售方法》398 / v2 为主要方法依据：帮助客户低风险决策；分清事实、推断、缺口和动态承诺；每次推进一个有价值的下一步。
- 以 374–380 的销售话术提供场景和表达参考，而不是整段机械复述。先回答客户刚提出的问题，再提供相关价值，不先堆公司宣传。
- 议价：承接预算顾虑，确认同等级和规格是否可比，用可核实证据解释差异，提供可行验证路径，不贬低竞品或自行降价。
- 样品：围绕客户的实际使用方式建立测试目标，避免把免费或返还费用当成交诱饵。
- 跟进：增加新的比较维度、测试建议或信息，不只是重复“有更新吗”；拒绝后不再设计强追。
- 售后：先承接影响，提出最小取证动作，未核实前不定责、不承诺全额退款，不虚构已经建单或升级处理。
- 风格：专业、自然、短句，不默认使用 bestie 等亲密称呼；熟悉程度来自对话，不来自国别刻板印象。

### 4.2 知识优先级与真实冲突

优先级不是简单“版本号更大优先”（不同文档版本不可直接比较）：

1. 系统安全边界与业务权限约束。
2. 适用且已核实的政策，以及当前订单/库存等动态证据。
3. 适用产品的已核实稳定事实。
4. 销售方法与表达示例。

| 本次发现 | 首版处理 |
| --- | --- |
| 378 / v2 样品话术承诺首单返还样品费；351 / v3 样品政策写明抵扣规则不向客户提及 | 样品费返还承诺不进入生成；提示内部口径冲突，等待知识负责人处理 |
| 376 / v2 等模板包含全系单一供体、使用一年以上、竞品价格倍数等概括；398 / v2 要求此类声明具备可追溯证据 | 只学习议价结构，不复制未核实产品范围、寿命和数字 |
| 374 / v2 模板含“已经升级服务部门”，378 / v2 含“已经查到签收”“排产紧张” | 没有本次动作或实时证据时不得这样写；可提出下一步要做的事 |
| 349、350、388 等文档虽已发布，标题仍含“需确认”，正文也混有待核实条件 | 发布状态不等于承诺获批；待确认条款不作为确定承诺 |

首版由配置维护有限的来源用途：方法参考、可对客事实、强制约束、待确认/禁用于承诺。优先按文档/章节配置；混合文档不能整体默认可外发。知识可读权限与对外披露权限是两回事，内部成本、客户分级、审批阈值和客户策略不进入回复正文。

用途配置绑定 `document_id + published_revision_id + section_anchor/content_hash + policy_version`，不是给文档永久盖章。知识修订更新、章节失效或文档停用后，旧用途许可和派生缓存一并失效；新修订在用途核验前不能继承旧版「可对客」许可。若必需政策因此不可用，返回安全澄清而非降级为无约束生成。业务负责人只需核验变化的相关章节，不要求每次重审全部知识库。

政策约束必须作为检索的必选部分，而不是只取“最相似的话术”。样品场景同时取适用样品政策；售后场景同时取责任与审批边界。若业务员看不到必要约束或约束仍不明确，只给安全澄清草稿，不用高权限服务账号替他补全。

首版不查询订单、实时库存、物流、财务，也不修改客户资料。所以不能因为客户说“上次答应七天”就验证为公司当前承诺；只能忠实理解客户诉求，提示业务员核查。

### 4.3 吸收「谈单助手0826」：从当前片段复盘到下一步回复

本次参考用户提供的 `deal-assistant/SKILL.md` 及其 `analysis-workflow.md`、`knowledge.md`、`report-contract.md`。只提炼客户复盘、成交判断和回复策略；不运行原 Skill，不读取阿里询盘、TM、OneTalk、OKKI 或订单资料，也不增加 HTML 完整报告功能。

| 原方法中的有效要点 | 话术助手中的落点 |
| --- | --- |
| 客户需求、沟通转折、异议、双方承诺放在同一事实层看 | 在已选片段内形成简短复盘；区分客户确认、卖方说法、推测与缺口，不只改写最后一句话 |
| 商机阶段与活跃度分别判断 | 阶段回答“采购进行到哪一步”，活跃度回答“最近如何互动”；沉默不自动退回普通询价 |
| 看客户承担的承诺成本，而不是只看回复是否热情 | 优先看客户是否补齐决策条件、接受验证路径或确认商务条件；给出本轮最强信号、限制与依据，不输出伪精确成交概率 |
| 同时识别业务员的有效动作与未闭环动作 | 保留客户已回答的信息，先补尚未回应的问题；短理由指出本轮可改进动作，不做业务员评分或无证据归责 |
| 每版话术有策略、适用条件、可用状态 | 默认选一条最合适策略；说明为何此时适用、哪些条件未满足，不把“语气不同”当“策略不同” |
| 下一步由动作、责任人、完成信号组成 | 将“发资料/继续跟进”改为能验证的推进目标；例如客户确认对比规格或选定测试指标，而不是把销售方发出文件当成交进展 |
| 接受、继续异议、部分回复、拒绝分别处理 | 下一轮根据真实反馈重选动作，不预设客户会同意，不自动追发；缺内部授权时明确由谁核实什么 |

**复盘的最小工作结构**：上下文覆盖范围 → 已确认需求 / 有依据的推断 / 关键缺口 → 当前阶段与阻塞 → 最强客户行动及变化 → 本轮一个目标 → 合适策略与使用条件 → 下一步完成信号。它是模型的短小工作摘要，不是面向用户的长篇思维过程，也不是持久客户档案。

阶段可以参考六类语义：一般询问、具体产品兴趣、需求补齐、形成方案/报价/验证、处理异议、确认交易条件。它们不是强制依次经过的 CRM 状态机；产品咨询与异议可能并存，按当前阻塞选择主阶段，有矛盾证据则标为待判断。老客户或售后场景不得硬套“从询盘到首次付款”的阶梯。

活跃度与趋势只在输入确实提供相应证据时判断。首版消息按顺序输入，不保证有可靠时间间隔，因此不得仅凭一段聊天推断“长期沉默”或套用 24/48/72 小时跟进。缺少较早互动时，趋势应为未知，而不是“持续增强”。

信号要看动作目的：客户提供地址可能只是要算运费，不等于接受报价；问价格或说“不错”不等于有明确采购承诺；卖方提出寄样不等于客户同意测试。每个关键判断关联本次快照中的消息序号，并校验买卖方向。该序号只在当前请求中有效，不使用真实消息 ID，不把原文证据复制进日志或长期记录。

缺口按“当前阻塞 / 下一步需要 / 后续再问”区分，不把规格、预算、数量、交期等清单一次盘问完。资料缺失只降低对应判断的确定性，不妨碍回答其他已经明确的问题。

对接受、继续异议、部分回复和拒绝四类反馈，分别遵循：推进已同意的下一步；回应新异议；沿用已回答信息、只补剩余关键项；尊重终止。内部准备事项与客户请求分开：比如是否可提供特定检测资料由业务员向技术确认，不能把“请内部核实”或“经理尚未批准”混进客户正文。没有实际审批动作，不宣称已经升级或批准。

**不照搬的部分与原因**：

- 不默认生成三篇完整话术、完整客户报告、成长训练和管理看板。WhatsApp 是即时回复场景，继续采用一条推荐回复、短理由与必要待确认项；详细分支和替代策略只在确有需要时处理，不增加默认模型回合。
- 不照搬“话术先冻结、知识库后查”。先独立理解客户事实与目标，再检索适用政策和产品证据，最后生成话术；知识库不能改写客户说过什么，但必须能够纠正不适用策略或阻止越界承诺。
- 不照搬“只有卖方在聊天里说过的内容才可对客”。经过用途核验、适用的稳定产品事实可以首次用于回答；反过来，卖方过去说过的价格或交期也不自动等于当前有效授权。动态承诺仍遵守 §4.2，旧承诺存在时提示内部核查，不装作未发生，也不擅自重诺。
- 不继承原 Skill 的“完整历史”假设、固定证据 JSON、补丁合并与渲染器契约。本助手仅分析当前有界上下文；看不到的背调、历史订单或时间信息一律不补造。

**合成场景示例**：客户已说自己需要 20 英寸发帘，随后表示“另一家更便宜，我还不确定差别是否值得”。本轮应识别为价格比较下的价值/风险疑虑，而非“即将付款”。推荐先确认两份方案的结构、克重等是否可比；不能再问客户要多长。若可比规格已确认，才考虑换成共同确定测试指标的验证路径。完成信号是客户确认比较口径或选定验证指标，不是业务员发出一段更强硬的推销话术。免费样品、最低价格和交期均不能从这一场景中推导出来。

## 5. 方舟实现边界（拟议，不是现有接口）

### 5.1 模块职责

- 扩展 `src/whatsapp/`：增加双方有限上下文采集；不得放宽现有来信自动翻译的判定。
- 扩展 content：增加话术控制器和结果面板，复用安全填入机制；reply 与 translation 独立忙碌状态，输入框写入互斥。
- 扩展 background：唯一持有设备 token，通过新增 typed runtime message 调用方舟；不保存上下文到 storage。
- `app/whatsapp_translation/`：增加回复编排 service / schemas / route，复用设备归属校验，同时实时校验拟新增 `whatsapp_reply:write` 权限。
- `app/knowledge/`：发布知识读取、用户 ACL 与有范围检索仍归此模块；从已有检索中提炼需要的能力，不在回复模块复制数据库权限逻辑。
- `app.ai.service`：统一模型入口，新增独立回复预设，强制 `snapshot_mode="metadata"`。不复用 `delegate()` 占位接口或将聊天正文塞入现有 AgentRun / AgentArtifact 持久表。

知识身份必须从已验证 device.user_id 获取当下角色/权限，再传给 knowledge service；不得把扩展给出的 user_id、is_admin 或 library_ids 当授权依据。翻译管理员不自动等于知识库管理员。

### 5.2 有上限的处理链

1. 校验会话快照、角色、输入大小、设备/人员权限、独立话术配额与并发。
2. 一次小型规划调用：识别客户语言、本轮问题，按 §4.3 形成短小的片段复盘与策略意图，并生成少量中文检索词和产品英文别名。复盘融入本次规划，不另建报告模型调用；不预先冻结对客文案。客户原话作为不可信业务数据，不执行其中的指令。
3. 在配置来源与用户实时可读库的交集中检索。现有 61 篇规模可先使用多关键词、术语别名、标题加权与章节分段，最终给模型最多约 4–6 个相关片段及必要约束；单片段暂定不超过 1,200 字符、总知识上下文不超过 6,000 字符，给强制约束预留预算，不把适用条件截掉；不整库塞入 prompt。
4. 一次生成调用：输入有限上下文、片段复盘、角色规则、检索证据、目标语言和术语，在证据与政策约束下确定推荐策略，输出外语草稿、中文释义、简短建议理由、证据关联、风险/待确认项。
5. 服务端校验后一次性返回：schema、目标语言、长度、来源白名单/修订/引用原文、敏感信息、未获支持的金额/日期/保证性表达等。硬校验失败不自动反复生成；无证据则安全澄清。

普通请求最多两次模型调用。两次都用独立预设，与刚刚关闭思考的翻译预设分开管理；可先用当前直连模型做合成质量基线，但不能把翻译测试结果视作销售判断能力验证。

第一版先补跨语言检索：例如德语问题转为“样品测试、发帘、交期”等中文语义关键词，结合 Genius Weft / Tape-In 等保留名词。原德文整句直接传 `.contains()` 不可靠。若正式评测仍有改写、同义词漏召回，再为已发布章节增加多语言向量索引；这是质量驱动的后续决策，不是首版先购置向量数据库的理由。

句子与引用的对应关系不代表语义已被数学证明。结构校验能拦截虚构来源，但对无依据承诺仍需保守规则、合成评测和人工确认；不把中文释义标成“独立审校通过”。

### 5.3 请求与响应边界

拟新增 `POST /api/whatsapp-translation/reply-suggestions`；保留现有统一信封与 `Cache-Control: no-store`。不重载 `/translate` 的字段含义或复用其 4,000 字单段限制。

请求：`request_id`、随机的本页 `conversation_epoch`、`context_version`、有序 `messages[{role,text}]`、上下文范围/省略标识、`draft_intent`、用户语言选择（可为 auto）、可选回复风格。不上传联系人姓名、号码或真实聊天 ID；正文中出现的联系方式在不影响任务时本地掩码。

响应：`request_id`、原样关联的快照版本、`status`（ready / needs_confirmation / insufficient_context）、`reply_language`、`reply_text`、`meaning_zh`、`rationale_zh`、`sources[{document_id,revision_id,version_no,section}]`、受限 claim 引用、`risk_flags`、`missing_information`。标题与引用只能来自本轮授权证据；模型不能构造任意外链。

内部理由解释为什么这样回复，不能返回模型深度思考过程；客户画像推断不作为确定事实展示。`needs_confirmation` 可以返回不含承诺的安全草稿，而不是把带未核实数值的文案交给用户一键发送。

§4.3 的复盘结构首先作为短时内部决策依据，不因此扩展成十多个必返报告模块。现有 `rationale_zh` 概括当前阻塞、推荐路径及希望客户采取的下一步；必要使用条件放入 `missing_information/risk_flags`。下一步的完成信号用于判断后续真实回复是否推进，不将其写成已发生事件。

### 5.4 隐私、日志与幂等

- 正文/草稿/译文/联系人信息仅存在页面、请求和必要的短时内存；不进入数据库、Redis 持久化、日志、监控 body、错误堆栈内容、分析事件或版本库。
- AI 调用只存请求长度/哈希、模型、耗时、token 与结构化错误；审计可存授权用户、来源修订 ID、结果状态、风险类别，不能存模型原始输出或包含客户原话的理由。
- 当前 `search_published(..., audit_action=...)` 会把 query 写入审计。因此回复检索不能直接记录由聊天生成的原始查询，需使用元数据审计路径；“接口是只读”不等于“不会写聊天日志”。
- 权限在每次请求、返回前及命中缓存时重新核验；来源修订发生变更时不复用旧结果。缓存范围包含用户/设备、当前快照、语言、预设版本及来源修订，不跨用户共享回复。
- 首版不复用普通翻译的文本缓存；重复点击只在当前同一请求内合并。使用相同 request_id 的重传不得产生第二次模型调用；载荷不同的同 ID 返回冲突。
- 若部署有多 worker/实例，单进程内存幂等不足。需复用或增加只含 owner/request hash/status/lease 的共享占位记录，不存正文；结果短时仅留执行进程内存。状态不确定、进程重启或无法取回结果时不自动重跑计费，提示用户主动重新生成。涉及新增表时另走隔离测试与部署迁移流程。
- 外部模型供应商仍会接收选取文本；本系统“不落正文”不等于数据从不出方舟。所选模型服务的数据保留设置仍需上线前核验。

### 5.5 耗时和体验目标

首版目标而非实测承诺：普通 20 条以内纯文字对话，中位总耗时不高于 8 秒、P95 不高于 15 秒。记录意图理解、检索、生成和校验各段耗时；超时预算初拟服务端 30 秒 / 扩展 35 秒，按真实测试与 MV3 生命周期对齐，不沿用两次各 40 秒的串行等待。

首版仅显示本地读取/请求中/完成状态，完成校验后展示完整回复，不新增 SSE 或轮询进度端点。优先减少无关上下文、知识片段与多份候选；不为速度取消必要的知识核验，也不先建立长任务调度平台。模型超时或上下游错误不自动追加高成本模型 / 外部 Agent 尝试。

## 6. 验收与推进顺序

1. **准备角色和来源配置**：使用本次 SOUL 草案，确定可对客事实、必须应用的政策和 style-only 模板。只对影响首版回复的冲突做处理，不要求重整整个知识库后才能启动。
2. **先验证服务质量**：使用合成对话测试中文检索词、来源召回、外语回复和承诺边界。取得测试授权后才做实际模型调用；本设计阶段未增加收费调用。
3. **打通最小闭环**：话术按钮 → 双方上下文 → 方舟 → 一条草稿 → 预览/填入/恢复。之后才补简短改写等次级操作。
4. **小范围试用**：以业务员认为可直接使用/需轻改/应退回的比例评估，记录类别而非聊天正文；不把“填入输入框”当成“客户已收到”。

| 验收类别 | 必测场景与通过条件 |
| --- | --- |
| 上下文正确 | 同时包含双方；已翻译消息不遗漏；译文不重复；旧片段/媒体/超长/方向未知有准确反馈 |
| 语言 | 英文、德文、混合语、OK/表情短答；手动覆盖有效；价格单位、产品类型和否定条件保持正确 |
| 销售质量 | 产品咨询、嫌贵、样品验证、无回复跟进、售后、老客户已给过规格；先回应本轮问题，不重复盘问 |
| 片段复盘 | 客户提供地址只为核算运费、卖方单方面提出寄样、只看到最近片段；不得推成接受报价、客户承诺或完整历史画像 |
| 阶段与变化 | 已进入议价但暂未回复、缺可靠时间间隔、老客户售后；阶段与活跃度分开，无证据的趋势标未知，不硬套线性阶段 |
| 推进策略 | 规格已齐却嫌贵、信息仅部分补齐、要求换个推进方式、客户明确拒绝；策略与当前阻塞匹配，只补缺口，不将语气改写冒充另一策略，不强追 |
| 知识与旧承诺 | 新的可对客稳定产品事实、卖方历史交期与现行约束冲突；允许有来源的新事实，旧说法不自动变成当前授权，最终文案受适用政策约束 |
| 事实与承诺 | 样品费冲突、需确认交期、虚构紧张、假称已升级、未经支持的寿命/收益；不得输出未经支持的承诺 |
| 隐私与注入 | 客户要求忽略规则/泄露底价/读取别的客户；知识模板要求自动发送；均不能越过权限与产品边界 |
| 权限和版本 | 两个业务员不同库权限、权限撤回、知识改版、库停用；来源及缓存不能越权或继续用旧版。原可外发章节改版加入内部条件后，旧用途许可不得继续生效 |
| 交互安全 | 生成时换聊天/新消息/编辑草稿/取消/后台休眠；旧回复不能误填，恢复不覆盖用户后续编辑，绝不发送 |
| 可靠性与成本 | 重复点击/跨 worker 重传/状态不明/模型超时/坏 JSON；不重复调用、不吞错误、不伪造无知识结果 |

预试用基线建议使用至少 30 条合成用例，覆盖上述类别，英文/德文各不少于 8 条；语义可用性由业务负责人盲评。严重错误（越权、跨会话误写、无依据金额/交期/退款承诺、泄露内部信息、自动发送）必须为 0；这不是所有真实场景零风险的保证。未达到耗时目标时报告实际分布，不能只展示最快样例。

# 9610 跨境申报核对：需求与设计

版本：v0.6，2026-11-23。状态：需求定稿，问题已全部答复。v0.6 按实现笔记的独立审查修订 F3、F4（第 12 节）；Q20 已答复为只做 DHL9610（D25）。实现设计见 [implementation.md](implementation.md)；核对页高保真原型见 [prototype/index.html](prototype/index.html)（需从仓库根目录静态服务打开，`.claude/launch.json` 的 `factory-inbound-prototype` 即可）。尚未开发、未建迁移。

## 1. 结论与范围

阿里信保订单走 DHL 快递并按 9610 申报时，业务员目前要做三件事：在 DHL 网站建运单、在 DHL 网站填跨境申报、在公司 Excel 再登记一遍。专员每天从 DHL 导出申报的订单和收款单，逐项和 Excel 比对后，上传「报关订单」和「报关收款单」两份文件。

本需求让方舟取代这份 Excel：

- **业务员**：建运单、填申报仍在 DHL 网站做（不变）。在方舟里只多一项：付款方式为「便捷发货」的订单发票，创建时必须填阿里信保订单号。验货单上传物流单照旧只输运单号。
- **系统**：把 DHL 导出的每一条申报，和同一阿里订单号下金额相等的「票」一一配对（一票 = 同一运单发出的货），再核对物流状态，自动标出漏申报、金额对不上、未揽收等异常。
- **专员**：定时从 DHL 导出订单和收款单两份文件，导入方舟 → 只处理异常 → 一键导出核对通过的「报关订单」「报关收款单」，上传报关。

不做：

- 不调用 DHL 建运单接口（`POST /shipments`），接口没有 9610 申报字段（第 3.3 节）。
- 不替专员在 DHL 侧提交或撤回申报。
- 不录入净重（D17）。
- 不改 OKKI 推单逻辑。

## 3. 现状事实（2026-11-20 至 11-23 实测）

### 3.1 公司 Excel 登记表

样本 `跨境申报记录.xlsx`（11-19，10 单），18 列：发货图、日期、运单号码、阿里信保订单号、平台、国家、真实货值USD、单价USD、尺寸/条数、净重、毛重、运费、保费、业务员、收货人姓名、电话、地址、邮编。上线后不再需要。

### 3.2 DHL 跨境申报导出：订单

样本 `订单1795398200619.xls`（导出于 11-23，37 条订单头）。海关跨境电商**电子订单**报文格式，三张表：

| 表 | 字段（英文名） | 说明 |
| --- | --- | --- |
| OrderHead | appType, appTime, appStatus, orderType, **orderNo**, ebpCode, ebpName, ebcCode, ebcName, **goodsValue**, **freight**, currency, note | 第 1 行中文表头、第 2 行英文字段名、第 3 行起数据。样本中 appType=1、appStatus=2、orderType=E、currency=502（美元），ebp/ebc 均为鄄城莱莎（3716961731） |
| OrderList | orderNo, gnum, itemNo, itemName, itemDescribe, barCode, **unit**, currency, **qty**, **price**, **totalPrice**, note | 只靠 orderNo 关联订单头。品名都是「100% 人发假发」，货号 2025001；unit 015=条、007=个 |
| BaseTransfer | copCode, copName, dxpMode, dxpId, note | DHL 导出中 dxpMode、dxpId 为空 |

关键事实：

- 不含运单号、国家、净毛重、收件人、店铺。
- **导出是累计范围**：11-23 的文件包含 11-19、11-20 的订单。
- appTime 是导出时刻（所有行同一秒），每次导出都会变。
- 同一 orderNo 可有多条订单头（D9 分批申报）。样本中订单尾号 `029078` 有两条相同的订单头，明细两行单位分别为 015、007。
- **OrderList 与 OrderHead 逐行对应**：两份订单样本中，明细第 i 行的 orderNo 与订单头第 i 行相同，且明细 totalPrice = 订单头 goodsValue（每票一行明细）。所以同号多头时可以按行号把明细归到各自的订单头，`029078` 能分开。
- 与 11-19 Excel 逐单对照：10 单全部在导出中，货值、单价、条数、运费 10/10 一致。
- **申报的「条」与发票的「件」不是同一单位**：SHT261131 的发票是 65 件 20g 发帘，对应申报 13 条（第 3.5 节）。条数不能和发票数量直接比。

### 3.3 DHL 接口能力

- 方舟已接 MyDHL API 物流查询并自动轮询，事件表保存原始事件码。
- 按运单号查询可得：目的国家、件数、DHL 实称重量、事件；收件人姓名为空，无货值、条数、参考号。
- `GET /shipments/{运单号}/get-image` 返回 `403 / 8032`，需 DHL 开通；本需求不依赖它。
- MyDHL API 3.4.1 没有 9610 申报字段，也没有列出账号下全部运单的接口。
- `shipped_at` 在首次轮询到非 `pending` 状态时写入当前时间，`SM` 等预约事件被映射为 `in_transit`，二者都不能当「已揽收」。

### 3.4 报关上传文件与收款单

样本 `报关上传用订单.xls`、`报关上传用收款单.xls`（11-20，10 单）：

| 文件 | 表 | 内容 |
| --- | --- | --- |
| 报关订单 | OrderHead、OrderList、BaseTransfer | 与 DHL 订单导出**结构完全相同**，10 单取值都能在 11-23 DHL 导出中逐字找到。appTime 为生成时刻。BaseTransfer 带 `dxpMode=DXP`、`dxpId=DXPENT0000480486` |
| 报关收款单 | ReceiptsHead、BaseTransfer | ReceiptsHead 字段：appType, appTime, appStatus, ebpName, ebpCode, ebcCode, ebcName, **orderNo**, payCode, payName, payNo, **charge**, currency, **accountingDate**, note。样本中 `charge = goodsValue`（不含运费），payCode/payName 为鄄城莱莎，payNo、note 为空，accountingDate 为到账时间（精确到秒） |

DHL 原始收款单样本 `收款单1795405261021.xls`（导出于 11-23 11:41，10 条）实测：

- 表结构、两行表头、字段与报关上传样本完全一致；accountingDate 已填好；payNo、note 为空；BaseTransfer 的 dxpMode、dxpId 为空（与订单导出相同，导出时由方舟补上）。
- **订单和收款单的导出范围不一样**：同一天的订单导出有 37 条，收款单只有 10 条。其中 9 条能在订单导出里找到同号同额的订单；1 条（尾号 `023624`，到账 11-23 09:56）晚于订单导出时刻，所以订单导出里还没有。
- 11-20 报关样本的 10 条收款中，8 条出现在这份收款单导出里，到账时间一致。
- 结论：订单与收款单要各自累积导入、按订单号和金额配对，不能要求两份文件一次导入、条目一一对应。

### 3.5 方舟发票现状（生产库只读查询，2026-11-23）

- 付款方式在 `ark_invoices.internal_payment_method`。2026-09 起包含「便捷发货」的取值只有三种：`大莱莎信保（便捷发货）`、`小莱莎信保（便捷发货）`、`新莱莎信保（便捷发货）`。另有 `…信保（报关）` 三种，不属于 9610。
- 「应付合计」即 `total_amount`（产品净额 + 包装费 + 运费 + 附加费/手续费）。
- **金额口径实测**：11-23 导出的 37 条申报中，按 `total_amount = goodsValue` 能找到发票的只有 13 条，21 条在任何金额口径下都找不到。
- **抽查 SHT261131**（大莱莎信保（便捷发货），草稿状态）：对应申报订单尾号 `044850`。发票：产品 2817.75 + 运费 50.00 + 附加费 86.03 = 应付合计 **2953.78**；明细 3 行共 65 件。申报：货值 **3013.92**、运费 80、13 条。相差 **60.14**。亮哥确认原因是业务员漏加了手续费，这正是本系统要拦下的「金额对不上」。
- 推论：现有发票里金额不准的情况不少。上线时只核对上线日之后创建的便捷发货发票，历史数据不进核对（F4）。

### 3.6 方舟现有链路

- 验货单 → OKKI 出库单（`outbound_record_id`）→ OKKI 订单 ID（一个出库单可含多个订单）→ `Invoice.xiaoman_order_id` → 订单发票。
- 出库明细有 `product_id`、`sku`、`qty`，没有价格（`outbound_service.list_outbound_items`）。发票明细有 `product_id`、`sku_id`、`price_per_piece`。所以一票的产品金额可以按「出库数量 × 发票单价」算出来。
- 上传物流单时，`shipment_link_service.create_and_bind` 建物流跟踪并回填 `shipment_tracking_id`；一个运单可被多张验货单关联。
- 发票有 `sales_user_id`、`commerce_status`（draft/confirmed/cancelled/closed）；已推 OKKI 的发票编辑受 `app/invoice/edit_authority` 管控。

## 5. 功能需求

### F1 发票录入阿里信保订单号

- 订单发票增加「阿里信保订单号」。付款方式包含「便捷发货」时**必填**，否则隐藏。
- 一张发票填一个阿里订单号；一个阿里订单号可以出现在多张发票上（D9）。
- 只允许数字，长度 15~20 位（样本为 17~18 位），保存时去空格。
- 发票改成便捷发货付款方式而没有阿里订单号时，保存被拒。上线前的历史便捷发货发票不强制补录。
- 已推 OKKI 的发票补录或修改阿里订单号，按 `edit_authority` 现行口径执行；字段不推送 OKKI。
- 店铺 = 付款方式中「信保」前的部分（大莱莎 / 小莱莎 / 新莱莎），不另设字段。

### F2 上传物流单时的提示

- 验货单「上传物流单」弹框：关联发票中有便捷发货发票时，只读显示阿里订单号和店铺，提示「本单走 9610，请确认已在 DHL 填写跨境申报」。不增加任何录入项。
- 关联的便捷发货发票没有阿里订单号时（历史数据），提示去发票补录，不阻断上传。

### F3 导入 DHL 申报文件

- 专员上传 DHL 导出文件，订单文件（OrderHead、OrderList、BaseTransfer）和收款单文件（ReceiptsHead、BaseTransfer）可以一起传，也可以单独传。系统按表名自动识别文件类型。支持 `.xls`（用现有 xlrd）和 `.xlsx`。按第 2 行英文字段名定位列。
- 某个文件表或字段缺失、数字非法：只拒绝这个文件，并指出文件、表名与行号。
- 一条订单条目 = 订单头第 i 行 + 明细第 i 行（第 3.2 节逐行对应）。导入时校验两表行数相同、同行 orderNo 相同，否则拒绝该文件。
- 订单条目的身份是内容哈希：orderNo + 本行订单头内容 + 本行明细内容 + 同内容出现序号。收款条目的身份是：orderNo + 收款单内容 + 同内容出现序号。
  - **排除 appTime**：DHL 每次导出都会改成导出时刻，不排除的话放行和「已导出」标记每天都会失效。
  - **只含本行明细**，不含同号其他票的明细：同一订单第二票后来申报时，第一票的身份不变。
  - 同号同内容（如 `029078` 两条同额）按出现顺序加序号 1、2…。
- 每个条目记录首次出现的导入批次和行号，作为配对时的先后顺序。
- 导入是**累积**的：以往导入过的订单和收款条目都保留，新文件里相同身份的条目只更新「最近出现时间」。
- 某个 orderNo 在新的订单文件里出现了，但以前导入的某条该号条目没在新文件里出现：标「可能已被修改」提醒（业务员可能在 DHL 改过申报，也可能只是导出时间范围没覆盖到）。导出包含这类订单号时要求专员确认，可把旧条目作废。
- 同一个文件重复导入（文件哈希相同）提示「已导入过」，不重复处理。

### F4 申报与「票」配对

核对范围：快递渠道为 `DHL9610` 的便捷发货发票（D25）。`FEDEX9610` 的单不在 DHL 导出里，不参与核对。

配对单位是**票**：同一个阿里订单号下、经验货单关联到同一个运单的便捷发货发票（未取消、币种 USD、上线日后创建）。

票金额：

- **整发**：发票的全部明细数量都在这一票的出库里（本票出库数量 = 发票明细数量），计入它的 `total_amount`。
- **分票**（D22）：发票只有一部分在这票出库，包括另一部分还没出库或还没上传运单的情况。费用「各票各算各的」（D23），系统算不出每票的精确金额，改为两步校验：
  - **逐票下限**：本票出库产品金额 = Σ 本票出库数量 × 发票明细净单价（`total_price / quantity`，已含行折扣）。申报 goodsValue 不得低于它。
  - **合计**：把共用运单的分票发票连成一组（A、B 两张发票都分在运单 1、2 上，就是一组）。组内发票全部发完后，组内各票申报 goodsValue 之和必须等于组内发票 `total_amount` 之和。

配对规则：

1. 整发票：申报 goodsValue 四舍五入（ROUND_HALF_UP）保留 2 位后，**必须等于**票金额（D13）。样本 goodsValue 有 3 位小数（如 `2196.282`），所以取整规则写死。
2. 分票票：同一阿里订单号内按「运单关联时间 ↔ 申报首次出现顺序」配对，再做逐票下限校验。
3. 同一阿里订单号下，一条申报既能按金额配给整发票、又可能属于分票票时，不自动配，标「配对歧义」由专员指定。
4. 同额的多票与多条申报，按运单关联时间与申报首次出现顺序依次配对。
5. 每条申报最多配一票，每票最多配一条申报。

核对规则：

| 异常 | 判定 | 级别 |
| --- | --- | --- |
| 申报无发票 | 申报的 orderNo 下没有任何便捷发货发票 | 阻断 |
| 申报无运单 | orderNo 下有便捷发货发票，但都还没上传运单 | 阻断 |
| 金额对不上 | orderNo 下有已上传运单的票，但没有票金额与申报 goodsValue 相等的未配对票；核对页显示差额（如 SHT261131 差 60.14） | 阻断 |
| 分票低于产品金额 | 分票的某票申报 goodsValue 低于本票出库产品金额 | 阻断 |
| 分票合计不符 | 分票组已全部发完，各票申报之和不等于组内应付合计之和；显示差额 | 阻断 |
| 分票未发完 | 分票组还没全部发完，合计暂无法校验 | 提醒（不挡本票导出） |
| 分票产品金额无法计算 | 本票出库明细对不上发票明细 | 阻断（专员核对后放行） |
| 配对歧义 | 见配对规则 3 | 阻断（专员指定后放行） |
| 缺收款单 | 订单条目没有收款条目对应：同一（orderNo，金额）下，收款条目数少于订单条目数 | 阻断 |
| 收款单无订单 | 同一（orderNo，金额）下，收款条目数多于订单条目数（通常是订单还没导入） | 提醒 |
| 可能已被修改 | 见 F3 | 提醒（导出时需专员确认） |
| 未揽收 | 运单没有 PU 及其后的运输、清关、派送原始事件（SM 等预约事件不算） | 阻断（专员可「确认已发」放行） |
| 发票已取消 | 申报对应的发票已取消（`commerce_status = cancelled`） | 阻断，提示专员不要在 DHL 侧提交 |
| 票无申报 | 便捷发货的票已揽收，但没有配对上任何申报 | 提醒 |
| 单位不统一 | 明细 unit 不是 015（条） | 提醒 |
| 非 DHL 承运 | 便捷发货发票的运单承运商不是 DHL | 提醒 |

v0.3 的「条数不符」规则删除：申报「条」与发票「件」单位不同（第 3.2 节）。

### F5 跨境申报核对页

- 入口：主站新页面「跨境申报核对」，在 `navigation.js` 登记。
- 默认视图：「未导出且有阻断异常」的申报；可切换「全部 / 仅异常 / 可报关 / 已导出」。
- 筛选：导入批次、上传物流单日期（「当天」的口径）、业务员、店铺（大/小/新莱莎）、物流状态、异常类型。
- 每行一条申报：阿里订单号、店铺、发票号（可多张）、业务员、运单号、物流状态、申报金额/运费/条数、票金额、差额、到账时间、异常标签。
- 行操作（均填写原因，留审计）：
  - 「确认已发」：未揽收但确认已交给 DHL，放行。
  - 「指定配对」：配对歧义或分票产品金额无法计算时，专员指定这条申报对应哪一票，放行。
  - 「作废旧条目」：「可能已被修改」确认是 DHL 侧改过申报时，作废旧条目。
  - 「本单不报」：退款、撤单、改走其他渠道等，排除出本次报关。
  - 跳转发票、验货单、物流跟踪详情。
- 放行记录绑定申报条目的内容哈希；申报内容变了，放行失效。
- 列表与分页照 `views/expo/ExpoLeads.vue` 标杆（宪法 14）。

### F6 导出报关上传文件

专员勾选「可报关」的申报（默认全选），一次导出两份 `.xlsx`，结构与第 3.4 节样本一致：

- **报关订单**：OrderHead、OrderList 取所选申报的原始值（数值保留源文件写法，如 `2331.04000`）；appTime 为导出时刻（北京时间，`YYYYMMDDHHmmss`）；BaseTransfer 每个订单头一行，copCode/copName 取 DHL 导出原值，dxpMode=`DXP`，dxpId 取配置项。
- **报关收款单**：ReceiptsHead 取所选申报对应收款单的原始值（含 accountingDate）；appTime 为导出时刻；BaseTransfer 同上。
- 表顺序与样本相同；每张表保留两行表头（第 1 行中文、第 2 行英文字段名）。
- 单元格类型照样本：订单头、收款单、BaseTransfer 为文本；OrderList 的 qty、price、totalPrice 为数值，其余为文本。
- 行顺序按申报在 DHL 导出中的顺序；同一阿里订单号的多票可在同一份文件里（D21）。
- dxpMode、dxpId 放在 `config.py` Settings 中，不写死在业务代码里。
- 每次导出记录导出人、时间、包含的申报条目和两份文件。已导出的条目标「已导出」；再次导出需确认。

## 10. 验收场景

测试只在隔离库运行。夹具：用 11-19 Excel 与 11-20 报关样本中的 20 单，造对应的便捷发货发票（`total_amount` = 申报 goodsValue 四舍五入到 2 位，创建时间在上线日之后）、出库单、验货单和 DHL 运单（其中 2 条只有 SM 事件、其余有 PU 事件）。导入文件用 11-23 订单与收款单样本的脱敏副本，以及从订单派生出的、覆盖夹具 20 单的收款单。夹具只验证规则；真实金额口径已由 SHT261131 抽查确认。

1. 创建付款方式为「新莱莎信保（便捷发货）」的发票，不填阿里订单号，保存被拒；改为 PayPal 后可保存，阿里订单号字段隐藏。
2. 便捷发货发票的验货单上传物流单：弹框只读显示阿里订单号和店铺，没有新增录入项。
3. 导入 11-23 样本：夹具中的 20 单全部配对成功，其中 2 单标「未揽收」；样本中其余 17 条申报全部标「申报无发票」。
4. 两张便捷发货发票（同一阿里订单号，100 + 50）拼一个运单，申报 150：配对成功；申报改为 100：标「金额对不上」，差额 50。
5. 按 SHT261131 造发票（应付合计 2953.78）与申报（3013.92）：标「金额对不上」，差额 60.14；发票补上 60.14 手续费后重新打开核对页，配对成功。
6. 申报 goodsValue `2196.282` 与票金额 `2196.28` 配对成功；`2196.285` 与 `2196.28` 不配对。
7. 一张发票（产品 1000、应付合计 1100）分两票发出，出库产品金额 600、400：
   - 第一票申报 650、第二票还没发：第一票可导出，标「分票未发完」。
   - 第二票申报 450：合计 1100，通过。改成申报 430：标「分票合计不符」，差额 20。
   - 第一票申报改为 590：标「分票低于产品金额」。
8. 订单尾号 `029078`（两条同额订单头）配两票同额：两条都配对成功，各自带本行明细（一条单位 015、一条 007），后者标「单位不统一」。
8a. 同一阿里订单号第一票已导出，第二票的申报在后来的导出文件中出现：第一票身份不变、仍为「已导出」，第二票正常核对。
8b. 发票 65 件，第一票出库 40 件且已上传运单，剩余 25 件还没出库：第一票按分票处理（逐票下限），不报「金额对不上」。
9. 「未揽收」条目专员「确认已发」后可导出；修改该条申报金额再导入：放行失效。
10. 第二天导入同一范围的新导出（appTime 不同、内容相同）：放行和「已导出」标记保持不变。
11. 先导入 11-23 订单文件、再单独导入 11-23 收款单文件：9 条收款配上订单；尾号 `023624` 标「收款单无订单」；夹具中缺收款的订单标「缺收款单」，补导收款后消失。
11a. 某订单在 DHL 改了金额后再导出：旧条目标「可能已被修改」提醒，新条目正常核对；导出该订单号时要求专员确认，可作废旧条目。
11b. 同一（orderNo，金额）有两条订单、两条收款，到账时间不同：两条都配上收款，不报「缺收款单」。
12. 导出的两份 `.xlsx`：除 appTime 外，与 `报关上传用订单.xls`、`报关上传用收款单.xls` 逐表、逐列、逐单元格取值和类型一致，BaseTransfer 带 `DXP` 与 dxpId。
13. 同一组文件导入两次：第二次提示「已导入过」。删掉 OrderList 表后导入：整批拒绝并提示缺表。
14. 发票取消后其申报标「发票已取消」并阻断。
15. 上线日之前创建的便捷发货发票不参与配对，其申报标「申报无发票」。
16. 服务器时区设为 UTC，在北京时间 23:59 与 00:01 各导出一次：appTime 与「当天」筛选按北京时间（宪法 23）。

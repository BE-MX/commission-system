# 方舟接管交易业务、小满仅保留客户维护：分析与设计

日期：2026-09-30

## 1. 结论与分析边界

**方案可行。建议将方舟从“小满业务的操作入口和分析平台”，升级为订单、产品、库存、出入库和回款的权威业务系统。小满继续维护外贸客户资料，方舟通过单向同步取得客户与联系人。**

这不是补几个页面即可完成的改动。现有方舟已经积累了订单制单、定价、预售分批结算、回款登记、生产报工、半成品库存、检验与物流等能力；真正欠缺的是成品库存账、完整本地出入库、本地资金生效与对账，以及让所有业务从方舟本地事实取数。

推荐复用现有模块，优先补齐以下五项：

1. 方舟产品与 SKU 主档，解除产品身份对小满的依赖。
2. 成品库存余额、预占、不可变流水与出入库单据。
3. 订单的独立业务状态，以及订单、生产、出库、回款之间的明细关联。
4. 本地收款确认、应收核销、退款冲销与提成数据来源。
5. 历史数据和未结业务的切换规则，以及全部下游取数的迁移。

**依据与限制。** 本分析核查了当前工作区 main、HEAD 5d0c1449 的源代码、路由、模型、同步器及项目文档；相关文档存在其他任务的未提交修改。本次未连接生产数据库、未实时核验小满租户权限和服务器调度，也未修改业务代码或数据。因此，“已有”首先指源码中已实现；上线信息单独引用最新交接记录。不能从代码推断现有库存准确率、历史数据完整率或实际业务覆盖率。

9 月 28 日交接记录已报告预售主单、回款、独立运费、分批出库执行链路完成联调并发布；部分旧设计稿、数据库文档仍写“未部署”，本分析不以这些旧标签否定已有能力。[E1]

本方案默认先接管目前依赖小满的外贸交易链路。已在方舟内完成的内贸客户、内贸订单、充值和生产流程保留，并接入统一产品/库存等基础能力；不要求先将内贸所有历史表并入外贸表。现有发票主要承担商业单据功能，本项目也不自动扩大为税务开票、总账或完整会计系统。

## 2. 当前真实的数据链路

现状有三层，不能只关闭其中一个接口：

~~~mermaid
flowchart LR
    CRM["小满：客户、产品、订单、库存、出库、回款"]
    MIRROR["lsordertest：小满业务镜像"]
    ARK["方舟：制单、回款登记、预售结算、生产、检验"]
    READ["方舟：备货、报表、提成、售后、客户分析"]
    CRM -->|"外部同步任务"| MIRROR
    MIRROR -->|"跨库查询"| ARK
    MIRROR -->|"跨库查询"| READ
    ARK -->|"订单/回款/出库接口"| CRM
~~~

- **读镜像：** 标准产品、SKU、成品库存、历史订单、回款、出库单等仍由小满同步至 lsordertest，方舟跨库读取。
- **写小满：** 方舟订单通过 order/push 创建或编辑小满订单；回款通过 receipt/push 发送；普通自动出库及预售出库最终调用小满 outbound 接口。
- **本地台账：** 方舟保存制单与业务规则、回款凭证和发送状态、结算分配、生产与半成品库存、检验媒体等，但其中部分业务动作仍以“小满同步成功/远端回读”为完成条件。

目标应变为：

~~~mermaid
flowchart LR
    CRM["小满：客户维护"]
    SYNC["客户同步：客户、联系人、归属及必要用户映射"]
    C["方舟稳定客户身份"]
    P["方舟产品 / SKU"]
    O["方舟销售订单"]
    W["库存 / 预占 / 出入库"]
    F["应收 / 收款 / 分配 / 退款"]
    R["生产、检验、物流、售后、提成、报表"]
    CRM --> SYNC --> C --> O
    P --> O
    P --> W
    O --> W
    O --> F
    W --> R
    F --> R
    O --> R
~~~

小满同步中断时，已同步客户的本地订单、收款和出入库仍应运行；新增客户与归属更新显示同步状态，不能静默猜测新客户身份或扩大访问权限。

## 3. 功能差距：已有、欠缺与调整

| 回款 | 本地回款单、私有凭证、幂等、防重复、余额占用、同客户同币种多订单分配 | 本地财务生效、收款账户/银行流水核对、实际到账、汇率、未分配预收、退款及冲销、账期/账龄 | 已有基础，欠缺独立资金闭环 |
| 预售结算 | 首款、末批抵扣、按批分摊、货款/运费分离、分配占额、出库前资金核验 | 保留算法，用本地有效收款核验；本地运费应收直接记账；取消为小满适配而建的空商品运费订单 | 保留价值较高 |
| 售后 | 证据、责任判断、审批、处理方案和关闭流程 | 售后决策关联真实退货入库、补发出库、退款/贷项；“处理完成”不能仅靠文字代表资金和货物流转 | 补执行关联 |
| 提成与经营报表 | 提成批次、归属快照、经营决策台、采购节/战报、日报 | 把订单/回款/销量来源转到本地正式账；保留历史口径和已结算批次；退款生成调整 | 上线前同步迁移 |

上述结论不能换算成“方舟已经完成多少百分比”。现有页面复用率较高，但库存过账、资金核销、历史迁移的工作量由业务规则与数据质量决定。[E2–E10]

## 4. 数据结构调整

### 4.1 客户：小满 ID 留在映射层，业务表引用稳定的方舟 ID

已存在 ark_customer_accounts、ark_customer_external_identities、ark_customer_contacts、ark_customer_assignments 等统一客户模型。优先接通它们，不再另造第三套外贸客户表。[E3]

现有 ark_invoices.customer_id、ark_receipts.customer_id 等实际保存小满 company_id；内贸 customer_id 则指向 ark_domestic_customers.id。**同名不代表同一身份，不能直接改列类型或用数值相等自动关联。**

建议分步处理：

- 新增明确的 customer_account_id 外键，通过 source_system + source_account_key + company_id 的身份映射回填；无法唯一对应的记录进入人工核对。
- 历史小满 ID 保留为外部身份，不能覆盖或伪造成本地 ID。外部标识带来源和租户命名空间，订单、产品、出库、回款同样如此。
- 业务单据保留客户名称、联系人、收货地址、订单业务员等当时快照；客户改名、转移或合并不重写旧交易事实。
- 客户当前负责人、订单成交业务员、提成归属快照是三个概念，分别保存。客户转交不应自动改变历史提成，也不应自动给予全部历史交易修改权。
- 小满负责其维护的基础档案和 CRM 归属；方舟负责客户价格、交易条件、信用控制、交易统计、AI 分析等本地字段。同步不得覆盖方舟衍生字段。
- 方舟已有内贸客户及自主获客线索保留原来源，逐步通过身份关系接入；本次不要求将它们强制写回小满。

统一客户投影服务接收“已抓取并标准化”的数据，本身不证明生产已持续抓取所有客户/联系人。上线前必须验证来源覆盖、负责人映射、增量游标、删除/合并与停用事件。[E3]

### 4.2 产品：新增本地产品/SKU，保留价格能力

建议新增的核心实体：

| 实体 | 关键字段/责任 |
| --- | --- |
| ark_products | 产品编码、名称、产品类别、系列/等级、是否可销售/可采购/可生产、启停状态 |
| ark_product_skus | product_id、独立 SKU 编码、型号、颜色、长度、卷度、净重、基本计量单位、条码及规格状态 |
| 产品外部映射 | source + tenant + external_product_id + external_sku_id → 本地 product_id/sku_id；唯一约束并记录迁移依据 |

具体字段名在实现时结合既有字典确定，不要求一期建设复杂商品平台。

- 现有 ark_std_prices、ark_customer_price_rules、ark_price_color_types 保留；配件价格与相关产品引用迁到本地 SKU。
- ark_invoice_items 新增本地 SKU 外键，已有 product_id/sku_id 暂明确为 legacy external ID，按验证过的映射迁移后退出正常业务逻辑。
- 安全库存、生产购物车、生产明细、产品工序路线、半成品组成、售后、色块图和外部接入也需迁移，不能只改订单页面。
- 成品“件”与净重“20g”必须分字段；半成品使用克数及对应精度。净重不能直接当库存计量单位。
- 非标产品保留每一行实际规格和数量，形成可追踪的配置 SKU 或生产规格快照。现有小满适配器会把未匹配非标行合并成一条通用商品，历史导入不能依靠这条通用商品反推完整明细，应优先使用方舟原明细。[E11]
- 不以名字相同自动合并 SKU；停用产品不删除历史引用。批次是否成为库存维度，按现有实物追溯要求决定。

### 4.3 订单：复用 ark_invoices，而不是再建一套平行交易主表

推荐在现有 ark_invoices / ark_invoice_items 上演进销售订单核心；短期保留表名、API 和商业发票导出，以减少接口与历史关联搬迁。业务服务明确区分“订单”和“导出的单据版本”。

| 当前字段/结构 | 建议调整 |
| --- | --- |
| status 含 draft/ready/synced 等，sync_status 参与业务判断 | 拆出 order_status、履约汇总状态、收款汇总状态；同步状态仅记录历史集成 |
| customer_id 是小满客户 ID | 增加稳定本地客户外键及外部映射 |
| product_id / sku_id / xiaoman_unique_id | 本地 SKU 与 InvoiceItem.id 成为业务关联主键；旧外部行 ID 仅追溯 |
| internal_received / internal_balance 可由制单内容形成 | 正式已收/未收由有效款项分配计算；录入意图与已生效资金严格分开 |
| order_type 同时表达库存/生产/预售 | 界面先保留三类模板；底层区分履约来源与结算策略，避免以后把“预售生产单”塞进互斥枚举 |
| xiaoman_order_id / source_order_id | 拆清来源、历史外部绑定与当前权威系统；不能把“有小满 ID”继续当允许收款/取消的前提 |
| 日期、业务员、金额快照 | 增加确认日、要求交期、版本号及确认快照；保留历史业务日期和成交责任人 |

订单状态可采用 draft → confirmed → closed，另有取消/部分取消处理；发货和付款状态由各自明细事实汇总。不要用一个“已完成”同时表示钱收齐、货出完、生产做完。

确认后的订单变更需检查已生产、已预占、已出库、已开应收、已核销部分。已履约数量和已经入账金额不能被直接编辑覆盖；通过变更单、补差或冲销承接。尚未发生的部分可按权限调整。

ark_customer_orders 目前是小满订单的客户分析投影，不是另一套可编辑销售订单。它应消费方舟订单事件/稳定查询结果，为客户价值、复购与机会分析服务，不能升格为第二个交易写入口。[E3]

### 4.4 库存与出入库：新增事实账，余额由过账维护

建议新增以下实体，统一放在独立库存领域，而不是把 lsordertest 的只读镜像改为写库：

| 实体 | 最小责任 |
| --- | --- |
| 仓库 | 本地仓库编码、名称、启停；库位按实际管理需要启用 |
| 库存单据头/行 | 类型、来源、仓库、SKU、数量、业务日期、状态、操作人、审核人、行级来源和版本 |
| 库存流水 | 每次过账的有符号数量、单据行、前后余额或核对信息、幂等键、冲销引用 |
| 库存余额 | 仓库 + SKU + 库存状态的余额与版本；需批次管理时再纳入批次维度 |
| 库存预占 | 销售订单行/出库行占用量、仓库/SKU、状态、释放/消耗原因 |

首批单据类型至少覆盖：期初、生产入库、销售出库、销售退回、盘盈盘亏、调整；有多个实际仓库则覆盖调拨，有外购则覆盖采购到货/退供。领料/退料优先复用现有半成品账，避免同一物料双重过账。

数量规则：

- 可用库存 = 已验收且可销售的实存 − 有效预占。待验、次品、冻结库存不进入可售实存。
- 生产在途是预计补货量，不能计入当前可拣货数量。当前备货分析把可用和在途相加的口径只用于补货判断。[E4]
- 确认现货订单时按实际可供量分配库存；缺货部分明确进入缺货/待生产状态，不能靠负库存掩盖。
- 新建出库单/预占不代表实际出库。正式过账在同一数据库事务内扣实存、消耗预占、写流水和回写履约数量。
- 单据未过账可取消；已过账需反向凭证。售后退货是新的实物入库，不是删除原出库单。
- 同一业务事件唯一幂等键，锁定余额/预占/单据的顺序一致，防并发超卖和重复过账。

本地出库头行是货物流转依据；现有 ark_shipment_outbounds 当前主要保存远端投递数据，应增加本地出库关联。普通单、生产单、预售单最终都进入同一套库存过账服务，保留各自放行与结算规则。

检验单、照片/视频、扫描会话、打印与操作日志继续使用，增加 local_outbound_id/local_outbound_line_id，并保存旧关联。小满镜像行 ID 与 API 返回行 ID 不保证相同，不能简单把字符串列转整数列。[E7]

### 4.5 生产与半成品：补上实际耗用和成品入库

现有生产订单收到货时只改 received_qty；末道报工完成和收货数量达到订单量都可能把同一 status 设为完成。在途统计又排除了完成状态。[E5]

需要拆分：

- production_status / produced_qty：工序完成了多少。
- receipt_status / accepted_qty / received_qty：仓库验收合格多少、已过账入库多少。
- 原生产单与销售订单行的数量分配：支持一张生产单为多张销售订单供货，或同一销售行分批生产。备货生产也允许没有销售来源。

成品入库必须通过库存单据过账；received_qty 改为已过账入库的汇总结果，禁止旧 setter、报工接口和入库接口分别加库存。

半成品已有真实本地余额和流水，应保留。把现有“准备推小满时预占、同步成功后扣料”改为：生产释放/领料计划预占，实际领料或投料时扣料，退料与报废有独立记录。若业务选择按标准用量自动倒冲，也应绑定一个明确的生产事件并与手工领料互斥，不能把扣料简单挪到销售发货时。[E6]

既有已扣半成品量和 pending 分配须逐项承接，不能随着产品 ID 转换再次扣料。半成品账与成品账一期可以分开，统一查询和来源关联即可；不为“统一表结构”强行混合整数件与小数克。

### 4.6 回款：把本地登记升级为正式资金事实

目前普通回款要求订单已同步小满；余额核验读取远端订单/回款；有效金额取决于小满 collect_status。payment_type 和汇率也依赖小满接口。关闭发送开关只能停止发送，不能让这条链路自动改为本地运行。[E8]

优先复用现有台账，建议的职责如下：

| 现有表 | 目标职责 |
| --- | --- |
| ark_receipt_batches | 提升为每一笔客户付款的主记录，所有单笔收款也生成主记录；保存客户、币种、原始付款额、实际净到账、账户、日期、凭证、状态及幂等信息 |
| ark_receipts | 承接这笔付款向订单/应收的分配明细；不再把每个分配行同时当成独立银行来款；旧远端回款 ID 作为历史事实保留 |
| ark_receivables | 从预售商品/运费目标扩展为正式应收目标，补业务日期、到期日、状态、来源及必要的分期关系 |
| ark_settlement_applications | 只表示已分配款项在发货批次上的资金占用/应用，不额外生成现金或再次核销同一应收 |
| 凭证与日志表 | 保留权限、文件、哈希及审计；扩展为付款主记录也能稳定持有的凭证 |

具体改造必须有明确的数据版本和受控迁移，不能在原接口不变的情况下悄悄重解释历史金额。无 batch 的历史回款不能直接复制一遍作为“新收入”；核验唯一经济来款后再归入对应付款主记录。

付款主记录提升为独立实体后，必须同时改现有权限逻辑：当前批次访问通过子回款关联订单推导，没有分配明细的纯预收会被现有逻辑视为不存在。新增以客户/财务职责为边界的付款主记录权限，分配时再逐一验证目标订单权限，不能为解决预收问题放开全部订单数据。

应新增退款单及退款分配明细、应收调整凭证/明细，记录原付款/分配、金额币种、原因、审批、生效日期和冲销关系。分配修改不覆盖原生效金额：保留原分配，追加释放/冲销，再建立新分配。履约资金占用也必须同时释放或阻断，否则会出现已退回的钱仍能放行出库。

现有 ark_receipts 的 batch_id + receivable_id 唯一约束只适合一次分配。若允许冲销后重新分配到同一应收，需增加分配事件/版本身份并调整此唯一约束；不能为绕过唯一键删除旧收款行。一个付款主记录可先有零个分配，分配行仍应明确关联其订单和应收。

应收目标总额与付款分配是一层关系，分期到期计划和发货批次占款是另一层关系。分期/批次只拆分同一应收责任，不能把整单商品应收与每批商品应收一起求和。新增运费等合同外确定费用可形成独立应收，必须有明确来源。

需新增或补齐的规则：

1. 本地资金状态：登记/待核对 → 已确认入账 → 冲销或退款。订单上的“已收”只计算有效分配，凭证上传或自动意图本身不是到账证据。
2. 收款方式、收款账户和汇率由方舟维护。保存原币、账户币、折算币的金额、汇率方向/日期/来源，不能继续从小满订单读取汇率。
3. 一笔来款可以分配多笔订单，一笔订单可以多次收款；允许保留未分配预收，之后再分配。不能为了存预收虚构订单。
4. 默认先保持现有“同客户同币种”分配边界；如有跨币种核销，必须增加显式换汇/兑换事实及差额处理，不能自动混加币种。
5. 退款出款、应收减少、取消核销是不同事件。退款不是删除原回款，也不是把订单改回未收。
6. 财务确认、核销、退款、调账分权并记录操作者；审核层级沿用业务需要，不强制给所有日常收款叠加多级审批。
7. 补对账单、应收账龄、未分配款查询和期间锁定；已结账期间用新期间调整记录处理。

**金额口径尤其需要清理：** 当前本地回款 amount 含费、bank_charge 保存分摊费用，推小满的 amount/real_amount 则是扣费净额且远端 bank_charge 为零。这是现有接口适配结果，不能导入后把本地和小满两份金额相加。[E8]

客户承担的交易附加费、银行实际扣费、公司承担的费用是不同概念。未来分别记录；历史只有一种混合费用时保留其原口径和来源，不自动推断出不存在的银行费用数据。

新增 actual_bank_fee、customer_surcharge 等清晰字段时，不把现有 bank_charge 直接改名当作实际银行扣费。付款主记录只有经过资金确认后才可分配为有效核销；同币种下，累计有效分配不得超过该笔款项的可分配额，单个应收累计核销不得超过应收净额。并发分配时同时锁付款主记录和目标应收，单靠订单锁不足以阻止同一笔预收在两个订单被重复使用。

银行去重优先使用收款账户与银行流水号等真实身份；附件哈希、同日同金额只能提示疑似重复，不能单独定义一笔经济来款。旧远端同步失败/待核对状态也不能批量改成“已确认”，必须先核实其真实资金结果。

示例：应收为 1,000 美元，客户支付 1,000 美元，银行扣 20 美元，公司承担此费用，则净到账 980、费用 20、核销应收 1,000。若客户承担手续费，则应由合同明确应收附加费或剩余欠款，不能直接套用上一种结果。

### 4.7 预售：保留分批算法，移除远端适配负担

保留 ark_shipment_settlements、明细、应收和资金占用，以及现有累计分摊、末批抵扣、数量上限和幂等规则。[E9]

- 小满无商品运费订单是当前接口适配方式。接管后运费直接作为本地应收组成，与商品 GMV 和商品提成分别统计，不再生成一张伪销售订单。
- 出库放行读取本地有效收款、信用批准及库存分配事实；不再需要远端 order/info、receipt/info 和 outbound/info 才能决定是否放行。
- 预售付款规则继续明确首款留到末批抵扣。若业务未来改变规则，必须版本化，而不是修改历史批次算法。
- 对历史单，原来的独立运费订单通过映射关联原预售批次并归类为运费，不能导入成第二次商品销售。

示例：商品 10 件，每件 100 美元，定金 200，暂不计运费/包装/手续费。首批 4 件应付 400、定金仍保留；末批 6 件应付 600−200=400。实际现金合计为 200+400+400=1,000，商品销售额也是 1,000，不能再把定金应用额算成新回款。

静态搜索已看到这些依赖分布在多个业务域，不能只改 invoice、stock、receipt 三个模块。[E10]

提成导入还需解决两个具体契约：当前 synced_payment 的 payment_id 是外部回款 ID，改源后应以“来源命名空间 + 唯一回款分配/调整事件”去重，并承认已经消费过的历史事件；当前计算公式是 payment_amount − service_fee，新的适配层必须明确传入含费金额还是净额，防止银行费用或交易附加费被再扣一次。先做同样本新旧结果对照，再切换日常数据来源，不借此次技术迁移改变业务提成政策。

客户订单投影应增加 ark 来源及本地订单关联，按统一交易映射处理历史 okki 投影和迁入订单，不能让两条来源记录同时进入客户价值统计。工作台当前“订单数据截至”也以 okki 游标判断，需随交易来源一起调整，避免本地已有新订单却仍显示旧数据水位。

## 6. 小满接口和调度如何收缩

### 保留

- 客户基础资料、联系人、所属公司、客户归属、公海/私海及必要字典。
- 为解析客户负责人所需的小满用户标识与方舟账号映射。
- 客户鉴权、分页、增量游标、数据新鲜度、失败重试、同步日志和人工补同步。
- 合并、停用、删除的确定性事件处理。未出现在某一页或一次接口失败不能解释为客户已删除。

“只同步客户”应明确包括联系人和归属，否则当前客户选择、发货通知与数据范围会缺少必要信息。跟进记录、附件是否同步只影响客户维护体验，可按使用需求选择，不应把订单金额继续作为小满同步字段隐式保留。

### 退役或改为历史只读

- 商品、SKU、库存、订单、回款、出库等持续同步；订单/回款/出库 push；普通自动出库 poller；远端变更核对和回款日期镜像修复。
- 小满订单枚举、付款方式、仓库 ID、远端状态等对本地业务的运行时依赖。
- 小满推单设置、同步成功按钮语义、远端缺失时冻结本地新业务等规则。

### 不能按进程名直接整服务停掉

部署清单包含北京 okki-index、OKKI/Shopify 配套 cron、独立 MCP，以及办公室 n8n。客户同步和交易同步可能共用进程或调度文件，本仓库不能证明每个外部任务的完整职责。应先列出“任务→读写表→游标→消费者”，保留客户任务，退役交易任务；Shopify 等独立渠道的订单导入若仍在使用，应重接方舟而不是被顺手关闭。[E12]

改用新业务模式后，后端交易入口和调度同时拒绝旧的远端交易动作，不能只隐藏前端按钮。部署器和启动脚本也不得复活旧任务。客户 token 和权限按保留功能缩减，但退役交易权限应在最后一次受控迁移与对账结束后进行。

小满账户降配后能否继续使用所需客户 API、额度、联系人和归属字段，需按实际合同/租户确认；本地代码不能证明商业授权。即使最终不再保留历史交易 API 权限，也必须在降配前完成历史资料与附件的可读归档。

实现继续使用现有 FastAPI 模块化单体和 MySQL。订单确认、库存过账、资金分配等一致性要求在本地数据库事务内完成；通知、统计投影、客户分析通过提交后的持久任务处理，失败可幂等重试。无需为此次接管先拆微服务或建设新的通用事件平台。客户原始同步区可继续保留在只读镜像层，交易领域不再依赖其订单/库存/回款表。

## 7. 历史迁移与切换设计

建议采用“影子核对 + 一次明确主账切换”，不长期双写两个交易主系统。新结构完成前继续沿用现有流程；影子阶段只导入/核对，不产生真实二次出入库或外发收款。

### 7.1 迁移对象分开处理

| 对象 | 处理方法 |
| --- | --- |
| 已完结历史订单/出库/回款 | 只读历史事实和外部映射，保留单据/凭证/媒体；不重新过账到当前余额 |
| 未结订单 | 导入完整合同快照和已履约/未履约明细；承接剩余数量、应收、预收及占用关系 |
| 当前库存 | 盘点或核实期初实存、可售/待验/不良、仓库、预占；生成一次期初凭证 |
| 在途生产/已完工待入库 | 保留生产进度与尚未验收入库数量；不能从 status=完成推导已经入库 |
| 已确认收款 | 按经济来款和分配关系去重；保留已核销、未分配、已退款及手续费/汇率的证据 |
| 既有半成品账 | 继续保留；仅迁映射与业务触发点，已扣料不重扣 |
| 已计提/已支付提成 | 保留原批次、回款身份和口径；迁移本身不得重新计提 |
| 待发送/失败/不确定任务 | 按远端是否真实发生逐笔处置；结果未核实不能直接重试或转成本地已完成 |

订单“未履约部分”不是一张新销售，应收“期初未收”也不是新增销售额。完整历史单用于查看，期初余额用于延续收付/履约，两者必须有唯一关联。

数量示例：切换时实存 100 件，其中 30 件已经为未出库订单预留，则导入实存 100、预占 30、可用 70。不能将可用 70 当作实存，再扣一遍 30；也不能给每个历史出库单重新扣库。

资金示例：历史订单应收 1,000，已有效核销 600，剩余 400。迁移后只延续 400 的未收责任；历史 600 可查询，但不能再增加一次银行余额或再生成一轮提成。

### 7.2 切换步骤

1. **盘点与预演。** 确认仓库/SKU映射、订单与小满重复关系、历史非标合并行、费用口径、出库单头行 ID、凭证文件和未结事项；在隔离环境反复导入，输出差异清单。
2. **影子核对。** 同一时点逐仓逐 SKU 对库存，逐客户逐币种对未收/预收，逐订单行对已发/待发，逐回款对已计提。差异必须有归因，不能只比较总金额。
3. **冻结交易写入。** 小满人工交易入口、API 写入、方舟旧推送器、外部定时任务及相关工作节点全部冻结，等待在途处理排空。客户维护/同步可保留，但身份映射导入须固定水位并处理随后客户变更。
4. **最后增量与核对。** 记录统一北京时间切换时点、同步水位、映射版本和每类导入回执。仍存在不确定资金/库存动作的范围不得开启新写入。
5. **切换方舟为唯一交易写入口。** 启用本地库存/资金过账；停止旧交易同步与远端发单；更新报表、MCP、接入方和部署任务。
6. **切换后核对。** 逐笔验证首批真实业务，检查库存、资金、提成、检验及通知的一致性；交易数据日结、余额和流水重算结果要能核对。

同一可销售库存池不能让一部分订单仍在小满扣库、另一部分在方舟扣库而无统一占用服务。若必须分批业务试点，先物理/逻辑隔离仓库与库存池，并明确未结订单归属；否则采用完整库存池的一次切换。

所有迁入记录携带 migration_batch_id、原始身份、导入时间、核验状态，以及“只读历史/期初承接/新业务”的明确角色。历史归档、余额承接和新单创建走不同入口，导入不得触发自动出库、通知客户、自动回款或重复计提。正常交易记录使用内部稳定键；已过账记录及其上游身份采用禁止级联删除的约束。

### 7.3 回退边界

切换后尚无新过账，可关闭新入口、恢复旧系统并撤销未使用的切换结果。**一旦方舟已经发生新出入库/资金核销，不能恢复旧数据库备份或重新打开小满写入当作回滚。** 应冻结相关业务，保留新增事实，受控修复或按明确映射补录后再选择唯一主系统。

数据库迁移遵守现有 Alembic 单 head、字段类型匹配、生产部署入口和全部相关写实例冻结规则；不得直接把小满镜像表纳入方舟写权限。

## 8. 建议实施顺序与验收门槛

| 阶段 | 交付范围 | 通过条件 |
| --- | --- | --- |
| A：基础与口径 | 字段权威矩阵、客户身份映射、产品/SKU、本地字典、仓库、历史外部映射 | 未结业务引用能唯一定位；单位/币种/归属/金额口径明确 |
| B：最小库存闭环 | 成品期初、生产/采购收货、预占、销售出库、取消释放、退货/调整；接检验与生产 | 无小满交易 API 时可完成一条真实形态的端到端链路；数量守恒与并发不超卖 |
| C：资金与预售 | 本地收款确认、应收/预收、分配、退款、汇率、预售结算；提成与报表改源 | 同客户多订单和分批发货不重复核销；账、款、订单、提成可对账 |
| D：迁移与整体验证 | 全量历史只读归档、未结业务承接、下游与外部调度调整、故障恢复演练 | 差异清单关闭、旧 writer 清单可证明停用、客户同步独立可运行 |
| E：受控切换 | 最后增量、主账切换、首批业务核验 | 全部退役门槛通过后再停用/降配小满交易能力 |

A/B/C 为开发分解，**不是做到 B 就可以先关小满**。具体工期应在未结单量、库存池、采购来源、付款币种和异常业务样本核查后估算，不能仅按页面数量承诺。

必须验证的场景：

1. 小满订单/产品/库存/回款/出库接口全部禁用，现有客户仍可完成本地制单→收款→出库→提成/报表。
2. 同一 SKU 被两个请求同时分配；可用不足时只能成功允许的数量。
3. 双击、网络重试、进程重启不会重复确认收款、扣库、入库或占用定金。
4. 最后一道工序完成但仓库未验收时，成品可售库存不增加，待入库仍可查询。
5. 部分生产、部分入库、部分出库、缺货补货、订单部分取消。
6. 一笔来款分两张订单，一张订单多次收款，超额来款留预收，退款后余额正确。
7. 两批预售、末批定金抵扣、运费独立、手续费与分摊尾差；商品 GMV 与现金不重复。
8. 单据修改后旧检验资料正确失效，旧出库/明细/二维码仍能追溯。
9. 退货入库、补发出库、退款/贷项可以独立组合，原始单据和流水不被覆盖。
10. 历史小满单和方舟单映射为同一交易；历史来款只计一次，已付提成不重复生成。
11. 客户改名、合并、转交、停用与联系人移动后，历史快照和当前权限都正确。
12. 半成品旧 pending/已扣料迁移后不会永久占用或重复扣料。
13. 库存流水重算=余额，有效资金分配+未分配预收可核对付款主记录，应收余额与明细一致。
14. 客户同步中断、报表消费者延迟、后台任务失败不会改变已过账业务事实；恢复后幂等追平。

本次为分析设计，未执行上述业务验收；这些是实施的完成条件。

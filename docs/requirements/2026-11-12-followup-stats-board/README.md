## 结论先行

1. **看板回答三个问题，一个视图回答一个**：我跟得怎么样（个人数据）、团队跟得怎么样（团队数据）、接下来该怎么做（AI 建议）。三个视图用底部悬浮切换条切换，长看板滚到哪都够得着。
2. **数字和判断分两层，来源不同**。数字（次数、覆盖率、按时率）全部是 SQL 确定性统计，秒开、可下钻、可对账。判断（谁可能成交、哪里出了共性问题）才交给 AI，而且**每条结论必须挂着原始跟进记录作证据，没有证据的不展示**。这样 AI 说错了一眼能核对，数字永远不会被 AI 改写。
3. **AI 建议必须能直接变成动作**。每条建议带「生成待办 / 记一条跟进 / 看证据」三个出口和「有用 / 不准」反馈。只能看不能做的洞见不上屏。
4. **「跟进质量」呈现为行为事实 + 改进建议，不出综合分、不排名次**。11-09 需求已定「不扩展到个人绩效打分」，本设计沿用。管理者能看到每个人的质量指标与团队均值的差距，但看板不会给人贴一个 72 分。AI 对个人做法的评语本人和管理者都能看，且是同一份（第九节 D2 已确认）。
5. **权限不新增 code**。业务员（`domestic_followup:read`）只看自己；管理者（`read_all`）看全部。业务员看不到「团队数据」视图，但在个人数据里能看到不带姓名的「团队均值」参考线。
6. **分三期**：P1 数据看板（无 AI，约占 60% 价值）→ P2 AI 建议 → P3 周报推送与策略闭环。P1 不依赖 P2，可单独上线。

## 一、要解决的问题

现有 5 个页签都是「清单」：客户清单、待办清单、记录清单、异常清单。能查到每一条，但回答不了这些问题：

| 谁 | 现在回答不了的问题 |
|---|---|
| 业务员 | 我这周跟得够不够？哪些该跟的客户漏了？我的客户里谁最可能成交、谁在变冷？ |
| 管理者 | 今天谁还没动？谁的节奏在掉？团队整体卡在哪种障碍上？客户普遍在抱怨什么？ |
| 两者 | 跟了这么多条，有没有规律——什么样的跟进方式真的带来了成交？ |

**设计准则**：每个图表都要能回答「看完之后我下一步做什么」。答不上来的图表不做。

## 二、信息架构

```
客户跟进
└─ 统计看板（新页签）
   ├─ 顶部：时间范围（本周 / 近30天 / 本季度 / 自定义）+ 业务员筛选（仅管理者）
   ├─ 视图 A 个人数据   每个指标按人分开展示
   ├─ 视图 B 团队数据   集成展示（仅 read_all）
   ├─ 视图 C AI 建议    个人层 + 公司层
   └─ 底部悬浮切换条    [个人数据 | 团队数据 | AI 建议]
```

### 悬浮切换条

- 位置：内容区底部居中悬浮的玻璃胶囊，和项目雷达原型的底部切换条同一形态。看板很长，放在页面顶部滚下去就够不着了。
- 选中项是一块滑动的金色底，切换时滑过去（transform，240ms）；各段等宽。键盘左右键可切换，键盘触发不播放滑动动画。
- 业务员没有「团队数据」时只显示两段，不出现灰掉的按钮。
- 只有它使用实时毛玻璃（`backdrop-filter`），符合 DESIGN.md「实时模糊只留给 ≤5 个小浮层」。

### 个人数据与团队数据的差别

| | 个人数据 | 团队数据 |
|---|---|---|
| 组织方式 | 一个人一块，块内指标相同（小多图） | 所有人合在一张图里 |
| 热力图 | 月历（周一~周日 × 周） | 人 × 日 矩阵（一行一个人） |
| 比较对象 | 自己的上一周期 + 团队均值线 | 团队上一周期 |
| 业务员看到 | 只有自己这一块，占满宽度 | 不可见 |
| 管理者看到 | 可选「全部并排」或单选某人 | 完整 |

## 三、视图 A：个人数据

业务员进来就是自己的一整页；管理者默认「全部并排」，点人名筛到单人。

### A1 四个关键数字

| 指标 | 口径 | 为什么放这个 |
|---|---|---|
| 跟进次数 | 周期内 `status=confirmed` 的记录数，按 `followup_date` | 最基本的量 |
| 触达客户数 | 去重 `customer_id` | 防止对同一客户刷记录 |
| 有效沟通率 | 分母 = 填了 `result_code` 的记录；分子 = 结果不是「未接通 / 未回复 / 客户拒绝」的记录（与 `followup_service` 判断有效推进时用的同一组负向值，抽成共享常量）。结果为空的旧记录不进分母 | 量之外看质 |
| 应跟未跟 | 负责客户中，距上次跟进超过等级频率（`frequency_days` 配置，键为「S级/A级/B级/C级」，默认 7/14/30/60 天）的客户数。负责客户的范围见第七节 | **唯一一个直接告诉你「该去做什么」的数字**，点击直接出名单 |

每个数字带与上一周期的差值，以及（业务员视角）团队均值。

### A2 跟进节奏（核心图表，两种视图可切换）

- **日历热力图**：一格一天，颜色深浅 = 当天跟进次数（单一金色由浅到深，0 次为空格）。今天有描边。悬停显示当天次数、触达客户数、有效沟通数；点击某天打开当天的记录列表。
- **曲线柱状图**：柱 = 每日跟进次数，线 = 7 日移动平均（不含周日；同一个 Y 轴、同一个单位，不做双轴）。虚线 = 团队人均（同样不含周日）。节奏下滑一眼可见。
- 「断档工作日」不把今天算进去——今天还没过完。
- 切换用卡片右上角的分段开关；切换时两张图交叉淡入，不位移。
- 周日和未来日期用斜纹底标出，不计入「未提交」。

### A3 今日未提交提示（节奏卡片下方）

- **管理者**：列出今天（北京时间）还没有任何已确认跟进记录的业务员，带头像、上次提交日期、连续未提交天数。全员已提交时显示一行绿色的「今天全员已提交」，不留空白。
- **业务员**：只提示自己——「你今天还没有记录跟进」+「记一条跟进」按钮；已提交则显示今天的条数。
- 名单范围 = 「跟进统计名单」里的人（设置项，默认取有 `domestic_followup:write` 且名下有负责客户的在职用户），避免把管理员、财务算成没提交。
- 周日不提示（沿用钉钉日报周日不推的既有规则）；法定节假日由管理员在「跟进设置」维护一份非工作日名单，名单内的日期不提示、不算断档；请假暂不识别，见 D5。
- 口径：按 `followup_date = 今天` 判断。补录昨天的记录不算今天提交。

### A4 客户覆盖

按客户等级 S/A/B/C 各一条进度条：按频率跟上的客户数 / 负责客户数。右侧直接列出「应跟未跟」前 5 名（店名、等级、已超期天数），点击打开该客户时间线并可直接记跟进。

### A5 跟进结果与障碍

- **结果分布**：未接通 / 未回复 / 有效沟通 / 已报价 / 已寄样 / 客户拒绝，横向条形，按 `result_code` 字典。
- **推进障碍**：价格 / 产品适配 / 采购时机 / 决策人 / 已有供应商 / 信任不足，按 `obstacles` 多选展开计数。
- 两张图并排，点击任一条筛出对应记录。

### A6 跟进质量（行为事实，不打分）

三条横条，每条标出团队均值刻度：

| 指标 | 口径 | 说明什么 |
|---|---|---|
| 留下一步 | 全部已确认跟进记录中，填了 `next_date` 的占比；不要求填写本次结果，也不排除未接通、未回复、客户拒绝 | 有没有安排下一次跟进 |
| 约定兑现 | 分母 = 周期内已到期的全部 `plan` 任务（含至今没做的）；分子 = 没有顺延过（`snooze_count = 0`）且在到期日当天或之前完成的。顺延会直接改写到期日，所以顺延过的一律不算按时 | 说了跟有没有跟 |
| 有效推进 | 分母 = 填了 `result_code` 的记录；分子 = `effective_progress = true`。该字段非空默认 0，旧记录和「否」分不开，所以只能用「填了结果」来圈定分母 | 是不是真的往前走了 |

2026-11-13 调整「留下一步」：按选定周期、记录作者统计全部已确认记录，重复跟进分别计数；只有 `next_plan` 而无 `next_date` 不计入分子。无记录显示「—」，有记录但无下次日期显示 0%；下钻展示同口径的已填日期记录。有效沟通率、约定兑现与有效推进口径不变。

「录入及时」不做：历史补录的记录没有落库标记，分不出来，而 D8 已确认不为此加列。

另附两个辅助数字：未回复后平均隔几天再跟、平均顺延次数（`snooze_count`）。

### A7 待办纪律

收货回访闭环率（done ÷ (done + expired)）、未处理异常/意见数与最长挂起天数。和现有「待办」页签的计数同源。

## 五、视图 C：AI 建议

### 5.1 页面结构

```
┌ 本周要点 ───────────────────────────────────────────┐
│ 三张摘要卡（最值得马上处理的 3 件事） 生成时间 · 依据 N 条记录 │
├ [我的客户]  [公司层面]（仅管理者可见完整版）──────────────┤
│ 我的客户：                                             │
│   ① 可能成交      客户卡：信号、证据原话、建议动作与时间   │
│   ② 正在变冷      客户卡：变冷依据、建议                 │
│   ③ 节奏调整      2~4 条具体到客户等级/客户的建议         │
│   ④ 跟进方式      2~3 条针对本人记录的改进建议            │
│ 公司层面：                                             │
│   ⑤ 共性问题      聚类卡：N 家客户提到同一件事 + 建议策略  │
│   ⑥ 个别问题      单个客户的特殊情况，值得单独处理         │
│   ⑦ 有效做法      从已成交客户的跟进过程里复盘出的共同点    │
│   ⑧ 节奏建议      是否调整某等级的跟进频率等              │
└──────────────────────────────────────────────────────┘
```

### 5.2 八类建议各自看什么

| 类别 | AI 读什么 | 输出 | 举例 |
|---|---|---|---|
| ① 可能成交 | 近 30 天记录里的积极信号：问价、要样、问交期、谈数量、状态变化「开始买高端款」等 | 客户 + 信号 + 证据原话 + 建议动作和时间 | 「新理想：两次问到 35cm 头套交期，上次寄样后说'质量可以'。建议本周三前报批量价。」 |
| ② 正在变冷 | 连续未回复、间隔拉长、状态变化「订单减少/竞争品牌增加」，并对照系统订单数据 | 客户 + 依据 + 建议 | 「德师傅：连续 2 次未回复，近 3 月订单金额下降。建议换电话联系并带新品。」 |
| ③ 节奏调整 | 该业务员各等级客户的实际间隔 vs 配置频率；约定兑现情况 | 具体建议 | 「你的 A 级客户平均 21 天跟一次（标准 14 天），其中 4 家超过 30 天。」 |
| ④ 跟进方式 | 本人记录的结构：是否留下一步、未回复后的再跟间隔、记录是否只有结论没有客户原话 | 改进建议 | 「未回复之后你平均隔 9 天再跟，团队里隔 3 天内再跟的回复率高出一截。」 |
| ⑤ 共性问题 | 全部异常/意见条目 + 障碍 + 跟进要点，做主题聚类 | 主题 + 涉及家数 + 代表原话 + 建议策略 | 「7 家客户提到直播退货率高（集中在小发片）。建议：出一份直播选品建议给业务员。」 |
| ⑥ 个别问题 | 不成簇但严重度高或涉及 S/A 级客户的条目 | 客户 + 问题 + 建议 | 「爱黛儿：二店员工冒充亲戚拿货，建议核对授权拿货人名单。」 |
| ⑦ 有效做法 | 已成交客户在成交前的跟进序列（次数、间隔、是否寄样、障碍如何化解） | 可复用的做法 | 「近 90 天成交的 11 家里，9 家在首次报价后 3 天内有第二次跟进。」 |
| ⑧ 节奏建议 | 各等级覆盖率与成交/流失的关系 | 给管理者的配置建议 | 「B 级客户 30 天频率下，沉默转化主要发生在第 20~25 天，可考虑调到 21 天。」 |

①~④ 是个人层，⑤~⑧ 是公司层。这就是你说的「既分析业务员自己，也在公司层面分析；既找共性也找个性」。

### 5.3 让 AI 建议可信的五条硬规则

1. **证据绑定，读取时再验一次**：模型输出的每条结论必须带 `evidence_followup_ids`（1~5 条），生成时校验一次。快照里**只存记录 ID，不存原话**；每次打开页面按当前登录人的可见范围（`visibility.followup_filter`）重新取原文——记录被改、被作废、客户已交接给别人时，证据自动更新或消失，证据全部失效的建议整条不显示。
2. **数字不让模型写**：涉及次数、天数、占比的地方，模型只输出槽位（如 `{a_level_overdue}`），由后端把算好的数填进去再展示。不对自由文本做数字回查——日期、「35cm」这类也是数字，回查不可靠。
3. **宁缺毋滥**：某一类没有足够证据就整类不显示，写「本周期没有需要特别提醒的」。不凑数。（沿用培训速递「宁缺毋滥」的既有做法。）
4. **业务员隐私边界**：业务员看到的公司层建议是脱敏版——只有主题、家数和建议，不出现别人的客户名和原话；涉及不足 3 家的主题不给业务员看，输出再过一遍店名过滤。管理者看完整版。
   - 「正在变冷」里的订单对照只给有订单读权限的人显示，协作范围本身不带订单金额（11-09 第 6.1 节）。
   - ⑦⑧ 是小样本观察，不是因果结论：样本少于 10 家不出，界面标注样本数；「已成交」按 11-09 第 3.2 节的成交判定，不用跟进里勾选的状态变化。
5. **标明是 AI**：每张卡标「AI 分析 · 生成时间 · 依据 N 条记录」，并提供「有用 / 不准」反馈。P2 先把反馈存下来，P3 再把「不准」作为负例回灌。
6. **③④ 两类本人和管理者看到的是同一份**（D2）。管理者看不到本人看不到的评语，评语同样必须带证据、数字同样由后端填，界面上向本人注明「管理者也能看到」。

### 5.4 从建议到动作

每张客户类建议卡有三个按钮：

- **生成待办**：按建议的日期和内容生成一条 `plan` 任务（走现有 `task_service` 的建任务入口，来源键 `insight:<id>`，一条建议只能生成一次）。生成前可改日期和内容。需要 `domestic_followup:write` 且对该客户可写（`ensure_customer_writable`）；只有 `read_all` 的管理者看不到这个按钮——11-09 已定「读范围不带写权」。
- **记一条跟进**：带着客户打开现有的记跟进抽屉。
- **看证据**：展开引用的原始记录。

公司层建议的出口只有「标记已采纳 + 备注」。不生成待办：任务表要求必须挂客户、类型只有四种，一个「主题」挂不上去；为它新造一种事项不值得。

### 5.5 生成机制

- **定时批量生成，不是打开页面现算**。多图多记录的分析要几十秒，现算会让页面转圈。每周一 07:30 生成上周个人层 + 公司层快照；每天 07:30 只刷新 ①② 两类（成交/变冷信号变化快）。登记在 scheduler registry，只在办公室单活实例运行。
- 结果存快照表，页面读快照，秒开。页面显示生成时间。
- 提供「重新生成」按钮：每人每天限 2 次，前端轮询。**不和录入用的 AI 整理共用线程池**（那个池只有 3 个线程，被洞见生成占住会卡住业务员记跟进）；生成状态存在数据库里，进程重启后能续跑或标失败。
- 走 `app.ai.service.chat` facade + 后台可配 preset；字典值域（结果、障碍、状态变化、分类）运行时从 DB 注入（红线 7）。
- 生成失败：保留上一份快照并标注「上次生成于 X」，记 warning（红线 6）。不显示半成品。
- 输入控制：个人层取该人近 60 天已确认记录（摘要 + 要点 + 结果 + 障碍，不送截图）；公司层先由后端按主题预聚合再送，控制 token。

## 六、「跟进质量」怎么呈现

你提到要「分析出业务员的跟进质量」。两种做法：

**与旧决定的关系**：11-09 需求第 1 节排除了「自动判断员工能力」。D2 已确认：在本看板内，AI 可以对业务员的跟进做法给出评语，管理者也能看。范围限定如下，超出的仍按 11-09 执行：

- 客观指标（留下一步、约定兑现、有效推进）→ 本人和管理者都能看，有口径、可下钻。
- AI 对个人做法的评语和改进建议 → 本人和管理者看同一份，每条带证据。
- 仍然不做：综合分、排名、把评语或指标自动接入考核与提成。

| | A 行为事实 + 建议（本设计采用） | B 综合质量分 / 排名 |
|---|---|---|
| 呈现 | 「留下一步 62%，团队均值 78%」+ AI 给出具体改法 | 「跟进质量 72 分，排第 4」 |
| 业务员反应 | 知道差在哪、怎么改 | 盯着分数，倾向于刷指标（多记短记录、随手填下一步） |
| 可解释性 | 每个数字能点开看是哪些记录 | 权重是人为定的，容易被质疑 |
| 与既有决策 | 一致（11-09 第 1 节、9.1 节：不自动判断员工能力、不扩展到个人绩效打分） | 需要推翻既有决策 |

采用 A。管理者能在团队视图里把每个人的三项质量指标并排看，也能看 AI 对每个人的评语，只是不合成一个分数。

## 七、权限与数据范围

| 身份 | 个人数据 | 团队数据 | AI 建议 |
|---|---|---|---|
| 业务员（`domestic_followup:read`） | 仅自己；可见团队均值线（无姓名） | 视图不显示 | 个人层仅自己（注明管理者可见）；公司层脱敏版 |
| 管理者（`domestic_followup:read_all`） | 全部业务员，可并排或单选 | 完整 | 可切换看任一业务员的个人层（①~④，与本人所见相同）；公司层完整版 |
| 协调员（`coordinate`，无 `read_all`） | 同业务员 | 不显示 | 同业务员 |
| 配置管理员（`admin`） | 按其是否有 `read_all` | 同左 | 另可在「跟进设置」维护统计名单与 AI 生成开关 |

- **不新增权限 code**。`read_all` 本来就是 kind=data 的数据范围权限，语义正好。
- 「谁的数据」的归属口径：**次数类指标按记录作者 `author_user_id`**；**客户覆盖类指标按负责客户**。两者不混用——客户换了负责人，历史跟进次数仍算在当时写记录的人头上。
- 「负责客户」的范围（覆盖率、应跟未跟共用）：
  - 有跟进责任记录的客户，算在当前跟进负责人头上；没有责任记录的老客户，回退到客户归属人 `owner_user_id`。
  - 不计入：停止开发、待分配、已停用的客户。
  - 暂缓且约了未来日期的客户，到约定日之前不算超期。
  - 没有等级或等级不在频率配置里的客户，单列「未定级」，不算超期。
  - 从未跟进过的客户，从接手日（没有则建档日）起算。
- 所有统计接口在后端按身份裁剪，业务员传别人的 user_id 一律拒绝（不是前端隐藏）。团队均值由后端算好只返回一个数，不返回明细；统计名单少于 4 人时不返回（人太少能反推出别人）。
- AI 证据校验复用 `visibility.py` 的可见范围判断，保证业务员点开的证据都是自己本来就能看的记录。

## 十一、不做什么

## 十二、原型说明

[prototype/index.html](prototype/index.html) 是单文件静态原型，无需启动服务。

- 顶部深色条是**原型专用**的「视角切换」（管理者 / 业务员），用来演示权限差异，真实页面没有它。

- 所有人名沿用 10-30 文档里的 5 位业务员，客户名与数字均为演示数据，不代表真实业务情况。
- 图表在原型里用手写 SVG，实现时换成 ECharts，视觉以原型为准。

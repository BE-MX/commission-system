# 方舟交易双路线过渡：功能设计优化方案

版本：v1.1，2026-10-27。状态：设计及对抗审查修订完成，建议用于后续开发拆解；审查覆盖和限制见[审查报告](../reports/2026-10-27-commerce-dual-route-adversarial-review.md)。本设计已获开发授权；当前分支的实现、验证和限制见[开发验收报告](../reports/2026-10-28-commerce-dual-route-implementation.md)。本文件保留设计依据，不代替实现证据；未合并或发布。

## 1. 结论与适用范围

采用“一份订单合同、两个处理入口、唯一正式办理路线、独立对比结果”。复用已有页面组件、纯计算及本地业务服务，补齐订单级办理权和双路线协调。不能靠复制导航、替换查询SQL实现安全过渡。

小满继续维护客户档案、公海/私海、联系人及归属；方舟保留客户同步。过渡期小满交易功能继续服务旧路线订单；最终停止其交易写入，不停止客户维护。独立路线的交易办理只依赖本地已核验身份、目录及账本，不能实时查询小满作为必需条件。

本文只交付功能/技术边界、复用清单、阶段范围、验收和审查依据。设计交付时未改业务代码、建迁移、发送真实请求或执行切换；后续开发以验收报告为准。旧设计的整体替换目标仍是终态，本文替代其“一次全局切换”的过渡方式。历史验收不被追认成双路线验收。

## 3. 用户看到的功能

### 3.1 导航与页面复用

保留既有“小满流程”入口与权限；增加明确标注的方舟入口。过渡期使用可理解的名称，不在业务界面暴露legacy/local等实现值。

| 页面/入口 | 使用方式 | 复用与差异 |
| --- | --- | --- |
| 订单发票管理 | 统一创建、修改、导出合同；详情显示正式办理路线、运行状态和对比入口 | 以main现有`InvoiceManage.vue`及编辑组件为基础；接候选本地服务，禁止另造第二张正式订单 |
| 出库管理（小满流程） | 原办理入口；仅可写归属该路线的订单 | 保留已核验的同步、恢复、删除/取消、检验及权限行为 |
| 出库管理（方舟独立） | 独立列表、报价/分批、资金就绪、检验、正式出库、取消及历史 | 复用`OutboundRecords.vue`展示部件与检验/媒体/打印；本地动作接`local_fulfillment`；新增独立导航，不能只藏在订单详情里 |
| 回款管理（小满流程） | 原登记/发送/恢复；只显示该路线正式办理数据 | 保留原流程，不偷偷改其款项用途/银行费含义 |
| 资金与应收（方舟独立） | 付款、确认、核销、预收、凭证、冲回、退款、贷项、账龄/对账 | 复用候选`finance/native`；保留本金、客户附加费、银行实际费的区别，不强行压入旧回款表单 |
| 验货、打印、扫码 | 一个真实发货批次只提交一次验货；自动解析路线 | 保留照片/视频权限、当前主线预览与取消请求能力；对比记录不能生成可用发货码 |
| 双路线核对 | 管理员/财务按订单、批次、资金查差异、缺项、事件滞后与关闭依据 | 新增功能；比较值与正式值并列，不能在此修改账本或“忽略后强制通过” |
| 历史责任承接 | 默认存量沿旧路线结清；例外按原候选承接协议办理 | 复用`MigrationWorkbench.vue`和强类型清单，不把承接入口当普通路线开关 |
| 本地目录/库存/生产 | 为独立交易提供实际基础；试点按资源门禁开放 | 复用候选目录、库存单据、生产、领料与供货能力；共享库存边界先解决 |

两个入口采用相同页面骨架和局部组件，查询/命令服务显式分开。只提取真实重复部分，不建设通用可插拔工作流引擎。UI按钮是否可用由服务端返回的能力与当前权限共同决定，提交时后端重验。

共用组件的KeepAlive草稿、列表缓存、下载请求和幂等请求身份必须按正式/对比用途、route、对象ID及epoch隔离。切导航时取消旧请求，晚到响应不能覆盖当前路线数据；服务端详情/扫码解析不能信任URL中的route。共用组件不等于共用可写状态。

操作语义不能随组件一起照搬：旧“删除小满出库/恢复删除”与本地“取消发货批次并释放资金/预占”使用不同命令及确认文案，不能共用旧composable的默认API；旧“允许补验前打印”只影响打印，绝不授予本地正式发货豁免。出库/结算/检验身份带对象类型与不可混淆的业务映射，本地批次ID恰与旧出库ID相等也不能误删旧单。查询适配可以统一显示字段，命令适配必须按服务端能力明确列出支持动作，不支持就不提供，禁止把未知动作回退到旧API。

### 3.2 三个容易混淆的状态分开显示

- 正式办理路线：小满流程 / 方舟独立。决定谁能产生正式业务事实。
- 业务状态：待发、部分发货、已收/未核销、已退款等。不能从远端同步成功推导实物已发。
- 对比状态：未启用、待处理、数据不完整、有差异、一致。只供验证，不改变前两项。

方舟独立入口可查看启用对比的旧路线订单，但显示“验证数据，不办理真实出库/退款”，按钮用“运行对比/查看差异”。正式模式的“确认出库/登记收款”不能复用为模糊的“提交”。默认列表区分正式和对比，导出也带来源标识。

### 3.3 一次录入与独立验证

日常用户只录一次真实业务输入；正式路径处理后，把不可变输入及结果凭证分别交给对比任务。对比路径读取同一合同版本、物料/SKU映射、原始付款和发货输入，独立计算状态、数量及金额，不直接复制正式路径输出当作自己的结果。

例如旧路线订单10件/1000美元，收600、首批发6：旧入口办理实际业务，本地入口展示同单验证数据及计算差异，实物只发6、正式款只记600。另一张新单进入本地正式试点后，由本地入口办理；旧入口显示其关联与只读状态，不再创建小满出库/回款。不能把旧订单的影子“已收600/已发6”直接提升为正式期初，真实转线仍走完整核验。

初期只自动比对已能可靠采集的动作。小满侧手工变更必须先形成带外部ID/版本的观察记录；采集不全显示“覆盖不足”，不能显示一致。不强迫业务员长期在两边重复填同一笔回款。独立路线特有能力可在明确的验证场景中演练，结果不混入正式账。

## 4. 正式办理权与平台阶段

### 4.1 两种维度各管一件事

平台阶段建议为`legacy_only / transition / local_only`，控制安装能力与可用worker；订单办理权建议为`legacy / local`，控制正式命令。`shadow`是执行用途，不能作为订单的第三种正式办理权。

订单草稿按试点策略自动推荐路线，确认前展示。合同正式生效时固化路线与`authority_epoch`，所有后续单据继承；没有路线记录的历史单，升级依据现有明确来源设为legacy并保留依据，不凭status/编号猜测。发生身份冲突则只读待核验。

生效后不提供通用“改路线”按钮。已生效订单即使尚未发货，也不在首期自由换线；先沿原路线完成。没有任何经济事实的草稿可经权限校验调整。已过账单只能走第9节的受控承接。

### 4.2 正式命令的统一校验

每个命令按以下条件办理：当前人员权限及业务范围有效；订单/付款归属明确；平台允许该路线；命令路线与服务端办理权一致；`authority_epoch`及业务版本相符；幂等键/正文摘要一致；相关库存/资金责任允许执行。客户端参数不授予办理权，super_admin也不绕过经济唯一性和冻结边界。

正式处理在同一数据库事务写入业务事实、结果凭证及待投递记录。对外调用采用持久请求身份和阶段记录，不持有数据库事务等待HTTP；使用有界重试和原结果核对。至少一次投递＋幂等消费实现一次经济效果，不宣称跨系统exactly-once。

旧路径存在running/uncertain或在途请求时不能移交、释放其预占或改为本地补做。同一操作先查询原结果；结果未知保留责任并阻断冲突动作。

对外发送前，worker与移交命令锁定同一办理权记录，在短事务内检查epoch并写入持久`sending_claim`（源命令/外部请求键、对象、epoch、正文摘要及库存/资金责任引用）。提交后才发HTTP，不能只有“检查后解锁再发送”。移交也在该锁下冻结并查询全部未终结claim；已认领进程尚未调用、正在调用或接收成功但未回写时，claim均阻止移交。claim不能因租约超时自动释放为可重发/可转线；恢复器只核对原请求，明确未发送或远端终局结果后才终结。epoch不能撤销已到达远端的请求，这个持久责任负责覆盖该窗口。晚到响应向原claim追加证据，不因当前epoch不同而丢弃；是否可再办理与历史结果是否须留存是两件事。

### 4.3 阶段、任务与部署兼容矩阵

| 平台阶段 | 旧交易worker | 本地正式worker | 验证worker | 恢复门禁 |
| --- | --- | --- | --- | --- |
| legacy_only | 仅legacy对象 | 不开放 | 独立实例可开 | 已有本地正式责任则拒绝启动 |
| transition | 仅当前epoch的legacy对象 | 仅当前epoch的local对象 | 独立实例可开 | 必须已安装办理权表、消费者过滤、银行/资源门禁与支持的全部worker版本 |
| local_only | 禁止交易写入；只读历史 | local对象 | 可留作审计 | 存在未完成legacy责任不能宣布完成切换；客户同步继续 |

阶段与最小兼容版本有持久记录，启动前校验配置及数据库事实，禁止有本地责任后退为legacy_only。transition不能由任意环境变量单独启用。全部writer（包括独立Node脚本、定时器、手工入口、第三方）未完成兼容/撤权时，不能开放正式试点。Scheduler同时注册两个任务仅意味着可扫描，认领、恢复、重试及实际发送前仍需核验route和epoch；错误或无法读取时拒绝发送，不能默认legacy。

混合来源报表分别获取两条正式路径的水位并输出覆盖区间；任一路径落后则相应报告显示滞后/阻止生成最终榜单，不能因另一条路径成功而宣布全量current。独立worker的受保护配置同样理解transition，现有“local文件不可被legacy进程覆盖”的防复活约束不得失效。生产发布继续走项目指定入口，不并行启动旧二进制解释新表。

## 5. 对比运行的隔离与恢复

推荐独立验证数据库/实例运行候选本地服务，同一订单ID只作为关联身份，使用`dataset_id + invoice_id + contract_revision`区分数据集。生产仍只有一份正式合同；验证库的重放副本不是第二份正式订单。对比worker不持有生产写凭据、真实小满交易/承运商/支付/通知凭据，也不能访问生产上传目录写入或生成可执行扫码令牌。

生产应用只负责已授权输入快照、待投递记录和只读差异展示；同事务保存可重试的outbox，后台worker增量导出必要字段到验证环境。真实客户/银行/媒体数据按权限最小化，不把完整凭证复制给无权的测试账号。照片可使用受控引用/摘要，对比库不提供绕过原权限的文件链接。

| 故障/操作 | 必须行为 |
| --- | --- |
| 验证环境不可用 | 正式交易不等待其HTTP；已提交outbox保留，界面显示滞后，不把正式成功说成双轨一致 |
| 正式事务回滚 | 没有可投递的成功业务事件；失败诊断不作为已发/已收凭证 |
| 重复/乱序/晚到事件 | 同经济事件去重；按合同/来源版本处理，缺前序暂停该对象，不能用墙钟覆盖新版本 |
| 源数据修改或取消 | 新版本或关联冲回事件；保留旧对比快照，旧版本一致不能覆盖当前差异 |
| 重建验证库 | 新dataset从明确检查点重放；生产账、媒体和正式办理权不受影响 |
| 人工核对关闭差异 | 记录事实依据、操作者和复核；原差异与数值保留，分类为已解释/已修复，不伪装为数值一致 |

每个比较样本需有覆盖清单：合同版本、最后观察/导出/应用水位、缺失依赖和最近核对时间。首期对比“事件结果与账本守恒”，不以异步镜像的暂时差异判定业务错误。尚未发生任何外部发送、也不存在未知外部结果的纯本地原子事务，若无法持久保存outbox，则该事务失败并可按原幂等键重试；外部请求一律按下一段恢复。只允许验证worker故障降级，不能吞掉未记录的事件。

外部已成功但本地事务失败不能被描述为业务回滚：持久claim仍为待核对，恢复后以原外部身份读回结果，在同一确认事务补不可变远端证据、正式凭证和outbox，不重发。同一次成功既由恢复又由回调观察到时关联同一经济事件。未能明确证明原请求未创建，一律unknown并保留责任；没有成功outbox不等于外部没有成功。可继承main现有回款attempt/迟到remote_id保留机制，再补办理权和outbox，不能换成简化的通用HTTP重试。

成功事务outbox不包含正式拒绝的命令，不能据此宣布拒绝逻辑已获验证。实时授权后先持久记录最小命令观察（可复用已有请求/发送阶段记录），结果分类accepted/rejected/unknown；拒绝原因、输入合同版本和独立候选执行结果用于对比。它是诊断输入，不生成经济过账，不把越权请求正文扩散到验证库。若该观察未覆盖某类拒绝，覆盖矩阵明确标为未观察，并以隔离合成反例补验；不能悄悄缩小一致率分母。

正式预期结果保存在只读证据区，不能导入候选`FinanceEvent/StockLedger/InvoiceCommerceEvent`或命令幂等表。候选使用独立`execution_event_id`及`dataset/run/request_key`命名空间，计算后由核对器关联源事件。重建检查点明确哪些已核验旧事实是初始状态、哪些待比动作必须重执行；不得导入该动作的正式结果后再调用候选，命中幂等短路就声称独立计算成功。初始责任也有单独守恒校验，检查点后一切输入必须完整。

涉及多单共用付款/库存/生产责任的样本，初始化使用同一一致检查点并保持跨对象因果顺序；不能分别复制不同时间的订单余额拼成一个“初始状态”。无法形成完整依赖的样本先标数据不完整，不拿来证明并发守恒。

## 6. 两条正式路线共存时的共享责任

这是从只读对比进入生产试点的硬前提；只按订单分路不能解决同仓库存和同笔银行款的竞争。

### 6.1 库存、半成品与生产

首期生产试点采用“可执行的排他资源范围”：明确仓库/库存桶及SKU或物料责任，只允许一种正式路线使用；另一条路线的可售查询、预占、出库、公开库存/MCP、调拨、退货、生产供货与人工小满操作必须排除该范围。镜像没有仓库/库存桶维度时，不能靠添加一个warehouse_id假装已隔离；该SKU/物料仍归旧路线，或扩大排他范围到所有相关实物。

每个试点范围需盘点、冻结旧在途责任、核清生产及半成品、建立唯一期初和明确释放边界，配置写入拒绝与可售排除并验证。任一旧writer或小满手工操作无法约束，禁止该范围的真实本地出库，仍可做隔离对比。单独UI标签、运营口头约定不算排他能力。

后续如需两条路线同时销售同一共享SKU，必须先建立共同的实物预占/扣减协调：旧路径也先取得持久责任，远端确认后关联同一经济事件结转；超时保留责任，不能自动释放。小满手工及第三方writer同样纳入或撤权。实现前不能把旧镜像余额与本地余额相加作为可售。共享半成品、同一生产批次供多订单亦遵守相同原则，不只管成品。

旧镜像扣减和方舟本地扣减若描述同一次实物事件，只形成一次本地责任及对照记录；不能以两个系统各有流水为由扣两遍。调拨跨资源范围等同移交，首期禁止无核验直接跨线调拨。退货追随原出库进入对应隔离桶，不能退到另一条路线扩大可售。

### 6.2 银行款项与应收

正式银行款须有跨路线唯一的经济身份登记：收款主体/银行账户＋银行交易唯一标识，关联币种、原币总额、付款人证据与正式路线。请求键只能防请求重试，不能替代银行款唯一性。银行流水号是否唯一需按实际账户/渠道核验，不将空值、凭证文件名或人工随机号作为事实。

首期同一真实付款只归一条正式路线；未分配预收也必须归属，双方登记/导入/退款入口共用同一身份登记及锁定规则。现有小满回款、银行导入和手工登记都需映射到该身份；缺少强身份的旧款进入差异队列，不向本地试点开放再次分配。

银行试点边界按收款主体/账户/渠道域封闭，而不是只标记已知的单款：该域的旧收款、未分配预收、退款及在途记录必须完成身份对照，并接管所有新增登记/远端手工入口；存在无法识别的旧款，就不能识别新导入是否与其重复，该域不得开放本地正式登记。可选择没有旧路线责任且能排他使用的既有账户/渠道先试点；不要求为技术方案强行新开银行账户。若无法隔离账户，先完成该账户的全量对照和统一登记门禁，再做真实试点。单张订单“没有历史回款”不足以解除整个账户的重复收款风险。

“同一银行款同时核销两条路线订单”暂不支持。不能拆两个虚构流水号避开限制；需等统一付款分配与跨路线守恒做成后再开放。历史已核销及已退款金额必须作为已消费责任保留；原汇率/客户附加费/实际银行费不能因重放重算。

### 6.3 提成、经营统计和客户

正式统计从“所有对象选一个全局来源”改成“按订单/付款的正式归属选择一次”。旧镜像经营记录与本地记录建立明确映射，迁移后保留原消费ID及有效边界。新旧来源不能简单UNION ALL，不能仅按订单号或金额相同去重。比较用的数量、现金、GMV、提成永不进入正式战报/日报/采购节/复购/客户画像或Agent上下文。

退款、退货、贷项按原正式事件关联调整，不能随当前平台阶段改投另一份提成。客户归属同步决定当前访问范围；合同、收款及提成原受益人快照继续保留，客户改名/合并不得重算历史归因。小满暂时不可用时，方舟对已核验客户正常交易；冲突/争议身份阻断新经济动作，不能猜客户映射。

## 8. 最小必要数据契约（建议，尚未建表）

复用现有业务表，不另建正式销售订单主账。首期需要以下职责，具体表拆分由实现时现有约束决定：

| 职责 | 最小信息与约束 |
| --- | --- |
| 订单办理权 | `invoice_id`唯一、正式route、epoch、状态active/frozen、来源/生效凭证；更新需版本检查，历史变更有不可变事件 |
| 合同与对照关联 | 稳定invoice/item ID、合同revision和摘要、原小满单/批次ID；一对多拆批有显式行映射，非标聚合行不能替代真实行 |
| 正式操作凭证 | 全局经济事件ID、route、epoch、命令幂等键与摘要、业务日、状态、关联单据；外部ID唯一映射，未知结果不生成第二个事件 |
| 待投递输入 | 源事件ID、对象/版本、输入快照引用、事件schema版本、投递状态/错误；与正式提交原子保存 |
| 对比结果 | dataset/run、计算器版本、源事件/合同版本、覆盖/水位、差异项/原值/结果、复核证据；无正式库存/资金外键入口可消费它 |
| 资源范围 | 仓库/SKU/质量桶或物料/生产责任的范围、独占路线、已盘点检查点、冻结和移交记录；不能存在冲突的活动范围 |
| 真实付款身份 | 主体/账户/渠道交易ID唯一、原币/总额、归属route、证据及已消费责任；跨路线也不能创建第二份可用本金 |

示意正式请求携带`request_key, expected_business_version, expected_authority_epoch, business_date`；后端从对象获取真实route。对比任务额外携带dataset、contract_revision、source_event_id，走独立受权服务，不允许客户端在正式API传`shadow=true`获得绕过校验的权限。

库存与资金采用原候选既有锁序基础，新增付款身份/办理权/资源锁必须在编码前形成完整锁序和真实MySQL对抗测试。旧请求、后台任务和移交不能各持不同锁序。设计不指定一条未经验证能覆盖门户屏障及HTTP的全局锁链。

## 9. 迁移、试点、停止与恢复

| 阶段 | 交付和范围 | 放行证据 |
| --- | --- | --- |
| A 当前主线整合 | 封存旧工作区清单/摘要与必要恢复材料；以main新任务分支整合领域能力、主线权限/门户/媒体变化；重新编排未发布迁移 | 原main回归不倒退；隔离MySQL完整链唯一head/历史数据保留；不重写已发布revision、不stamp跳过冲突 |
| B 独立页面与隔离对比 | 共用制单/检验部件；独立出库/资金入口；合同输入outbox、验证实例、差异工作台 | 正式路径外部行为不变；重试/断电可恢复；验证无生产写、无真实外发、无统计污染 |
| C 排他范围生产试点 | 仅新订单；明确实物资源范围与收款账户域；银行身份登记与旧入口排除；混合统计及worker办理权 | 资源无交叉暴露；账户旧款身份完整或能排他；同笔款拒绝双登记；旧单正常、本地单断开小满交易服务仍闭环；用户角色实际操作 |
| D 扩围与例外承接 | 按证据扩大新单范围；共享资源须先共同预占；确需转线的旧单用完整责任清单 | 金额/数量/身份无未解释差异；旧worker与远端手工边界可控制；按对象核验，无全局强制切换 |
| E 小满仅CRM | 旧交易单已结清或完成承接；全部交易writer停用及权限撤销；客户任务保留 | 全实例读回配置/权限/在途清零；正式新业务独立可用；保留历史查询与恢复证据 |

首批试点建议选择整单现货、单币种、单一正式付款、无存量首款占用且资源能排他的新订单。预售、共享半成品、跨单供货及售后均保留能力，首批未覆盖时明确禁止而非悄悄退回小满；扩围前逐类验收。试点按订单确认时规则固定，不以用户当前账号或“今天启用开关”重解释历史单。

少量存量移交顺序：冻结该对象新认领→排空/核清在途及unknown结果→以同一检查点核验合同/资金/履约/库存/生产/媒体/已付提成→先形成可重试的移交准备记录→原子固化本地期初与新epoch→验证两边按epoch拒绝旧任务→恢复新办理。跨系统无法一次原子切换时，保持冻结并可从持久检查点恢复，不出现两边都active的窗口；不能以超时自动解除冻结。

这里的“对象”是共享责任闭包，不一定是一张订单：同一付款及其全部分配/退款/贷项、同一在产供货或预占的关联订单、已付提成原消费身份及其调整，须一并枚举。若付款P已分配旧单A600＋B400，仅迁移A会造成跨线资金责任；首期拒绝单独移交A，选择整个闭包一起冻结/核验/承接，或都沿旧路线结清。生产批次/物料共享关系同理；不得把已消费金额另造为新可用期初。闭包扩展到无法核清的范围时，禁止强行截断关系后迁移。

暂停试点只停止新增本地试点订单和新worker认领；已发/已收事实保留，当前路线仍负责查询、纠错、售后及核对。恢复代码必须理解当前schema和办理权；禁止用旧整库覆盖、legacy配置重启或开启旧脚本来“回退”。新款未分配、未结售后/提成亦算存量责任，不因订单关闭忽略。

## 10. 对比指标、验收场景与完成判据

金额按各自原币与冻结汇率比较，整数件与0.001克分别核验，不凭总额接近判定一致。分币尾差按同一经确认规则解释，不能用任意容差吞差异。不能只选通过样本：测试清单与导出水位决定分母，缺项单独统计。

| 编号 | 攻击/验收场景 | 必须结果 |
| --- | --- | --- |
| T01 | 同单两个入口并发正式出库/核销 | 唯一办理路线生效；错路线拒绝，实物/本金只变化一次 |
| T02 | 验证库故障、生产重启、worker重复投递 | 正式结果正确、outbox可恢复；验证滞后可见；重放无经济新增 |
| T03 | worker检查epoch后暂停、移交并发；或小满已接收但本地回写失败 | 同锁持久sending_claim先落地，移交冻结等待；未知结果不超时释放，恢复只核对原请求并补同一凭证/outbox |
| T04 | 两路线购买同SKU或领同物料、同一生产批次供多单 | 首期排他门禁拒绝冲突；共享开放后真实MySQL证明共同预占不超卖 |
| T05 | 无银行标识旧款已存在，新银行导入不知它相同；两个入口/远端手工重复登记 | 账户域旧款未核清则本地登记整体不放行；完整身份后同款拒绝再生成本金，未分配款也不能双用 |
| T06 | 一笔款涉及两路线、退款与核销竞争 | 首期跨路线明确拒绝且无残留；同路线资金守恒，退款不会增加另一份可用款 |
| T07 | 预售首款300已抵100，历史发6，新发1+3，独立运费 | 末批仅抵剩余200，原资金不复用；分批商品/运费与合同及付款分别守恒 |
| T08 | 合同修改/取消、对比乱序晚到、重建dataset、正式拒绝未形成事件 | 当前版本/epoch不被旧事件覆盖；拒绝输入独立观察/反例；预期凭证不进入候选幂等账本，必须实际执行；不完整不能记一致 |
| T09 | 手工小满变更尚未观察、镜像延迟或缺外部版本 | 显示覆盖不足/滞后，不能闭差异后冒充一致；正式责任不被镜像覆盖 |
| T10 | 调拨/退货/生产供货跨排他范围，公开库存/MCP读取 | 冲突拒绝或经正式移交；另一条路线不暴露同一可售；退货不扩大错误桶 |
| T11 | 移交同时旧任务发送；同付款P跨A/B两单仅迁移A；共享生产供货跨路线 | 同锁claim阻断发送窗口，晚到结果留存；共享责任闭包不齐拒绝移交；旧二进制/凭据被部署门禁或撤权拦截 |
| T12 | 一个真实订单同时出现在镜像、本地、验证库，发生退款/已付提成 | 正式统计和提成只一次，调整关联原消费事件；验证数据零贡献 |
| T13 | 无权用户直调本地/验证API、换dataset或访问照片、门户授权撤销 | 实时权限及数据范围有效；不能绕过main屏障或获得他人凭证/真实扫码能力 |
| T14 | 客户改名、合并/转归属、小满暂时不可用 | 历史快照不改；当前范围及时生效；已核验本地交易独立，新冲突不猜映射 |
| T15 | 独立页面实际制单/收款/核销/检验/发货/售后 | 桌面/移动闭环、错误保留原请求可恢复；两入口各自可辨；不出现双填强制流程 |
| T16 | main→新head及旧候选合成数据承接，未知revision、多head | 正常完整链保留数据/约束；异常阻断，不运行生产迁移、不靠stamp绕过 |
| T17 | 北京时间零点、非东八区主机、原外币汇率/旧缩放值 | 明确北京时间和原历史口径；不能按今天或当前汇率重算 |
| T18 | 旧出库ID与本地批次ID相同，切入口后点击删除/恢复/先打印 | 按对象类型与服务端能力分派，不能误发旧API；本地取消保持释放/历史凭证；先打印不绕过检验发货门禁 |

进入下一阶段的条件是：该阶段适用场景有实际结果，所有阻断/高风险设计问题已闭合，未解释的资金/数量/办理权差异为0，覆盖清单完整，业务负责人能核验差异依据。具体试点样本数量由实际业务类别覆盖确定，不能仅按“运行一周没报错”放行。技术核验不代替真实盘点、银行证据、现场停写回执和发布授权。

## 11. 本方案的范围取舍

首期不做跨路线共享付款分配、不做已生效订单随意换线、不做两个正式订单主账、不要求长期人工双录、不建通用事件平台/流程引擎。先以现有数据库outbox、明确服务边界和独立验证实例落地，后续共享资源能力只有业务需要且能证明守恒时再开放。

对比一致只能证明已覆盖输入上的行为一致，不证明两边共享的算法一定正确。资金/库存仍须独立守恒式、人工核验原凭证及关键反例，防止共用错误算法一起算错。旧路线已知缺陷可以成为经证据解释的差异，不要求新路线复制错误。

# 方舟 AI 服务接入文档

版本：1.0 ｜ 日期：2026-09-14 ｜ 适用范围：自建网站调用方舟 AI 文本服务

本文可独立使用，不要求接入方访问方舟源代码。将本文作为附件交给你自己站点的 Codex，并告诉它：“按本文完成当前网站的 AI 服务接入”。

## 1. 使用前准备

请向方舟管理员领取以下信息。真实密钥由站点负责人自行填写到服务器或托管平台的密钥设置中，不粘贴到 Codex 对话、文档或源码。

| 配置项               | 含义                                              | 示例（均为占位符）                           |
| ----------------- | ----------------------------------------------- | ----------------------------------- |
| `ARK_AI_BASE_URL` | 管理员确认可访问的网关地址，包含 `/api/ai-gateway`，末尾不含 `/chat` | `https://<管理员提供的域名>/api/ai-gateway` |
| `ARK_AI_KEY`      | 专门分配给当前网站的站点密钥                                  | `ark_site_<由负责人在服务端配置>`             |
| `ARK_AI_PRESET`   | 已授权的文本能力名称，按管理员提供的值原样配置                         | `<管理员提供的能力名称>`                      |

同时告诉 Codex：AI 按钮在哪个页面、用户输入什么、期望显示什么结果。例如：“在产品页增加英文文案生成，输入产品特点，展示生成结果并允许复制。”

管理员需要确认：网关已经部署并可从站点服务器访问、站点已启用、能力已经授权，以及可用的每日次数、每分钟次数和并发上限。代码已合并不等于服务已经上线，不能根据本文猜测生产域名或上线状态。

## 2. 给 Codex 的开发任务

请在我的现有网站中完成方舟 AI 文本服务接入，遵循本文全部接口约定。

1. 先检查项目技术栈、页面结构、后端入口、现有登录与配置方式。沿用项目实现，不重建整个网站。
2. 实现调用链：**浏览器 → 本站受保护的后端接口 → 方舟 AI 网关 → 本站后端 → 浏览器**。
3. 如果项目只有静态前端，增加适合现有部署平台的最小服务端接口或函数；方舟密钥必须保存在服务端。平台无法提供足够执行时间时，说明需要的后端部署条件，不改成浏览器直连。
4. 从服务端配置读取第 1 节的三个变量。按项目原有方式创建 `.env.example` 占位配置，并确保真实 `.env` 不进入版本控制。不要求我把真实密钥发进对话。
5. 提供本站的 `POST /api/ai/generate` 或符合项目惯例的等价接口。最小请求为 `{"text":"用户输入"}`，最小成功返回为 `{"content":"生成结果","request_id":"请求编号"}`。
6. 本站后端先验证访问者身份、功能权限及访问频率，再调用方舟。复用现有登录；没有登录时先完成接口与 mock 验证，明确邀请制或登录接入条件，不发布无访问控制的付费调用接口。不要拿方舟站点密钥充当用户登录凭据。
7. 能力名称由服务端确定。浏览器不能指定任意 Preset、模型、供应商地址或供应商密钥。多个功能需要不同能力时，在服务端建立受控映射。
8. 每次新的业务操作生成一个 UUID，发往方舟的请求头为 `X-Request-ID`。服务端保留该编号，用于失败提示与排查。关闭本次外呼在 HTTP 客户端、代理和任务队列中的自动重试。
9. 页面提供输入、提交、加载、结果和错误状态；加载时防止重复提交，结果以纯文本或经过安全处理的 Markdown 展示，不直接插入未经处理的 HTML。
10. 校验请求及响应，按第 5、6 节处理失败。不要将方舟响应当成 OpenAI SDK 的响应结构。
11. 用 mock 完成验收；缺少凭据时完成其余实现并准确列出缺失配置。真实连通测试只在服务已就绪、负责人明确授权测试调用后进行一次短文本调用，不循环消耗额度。
12. 最后交付代码、改动说明、配置位置、运行方式、测试结果和待配置项。未经授权不发布网站。

## 3. 方舟接口协议

### 3.1 请求

```http
POST {ARK_AI_BASE_URL}/chat
Authorization: Bearer {ARK_AI_KEY}
Content-Type: application/json
X-Request-ID: {UUID}
```

请求体示例：

```json
{
  "preset": "<管理员提供的能力名称>",
  "messages": [
    {"role": "user", "content": "请将以下产品介绍翻译成英文：这是一款适合日常佩戴的假发。"}
  ]
}
```

所有大括号占位变量必须在服务端替换，不要把示例占位符当成真实配置。

| 项目         | 约定                                                                             |
| ---------- | ------------------------------------------------------------------------------ |
| `preset`   | 非空字符串，最长 64 字符，必须是本站已获授权的能力名称                                                  |
| `messages` | 1～20 条消息；如需多轮对话，每次显式携带必要历史，网关不替站点保存会话                                          |
| `role`     | 只允许 `user`、`assistant`，最后一条必须为 `user`                                          |
| `content`  | 非空纯文本，首尾空白会被去除；全部消息内容合计不超过 16,000 个 Unicode 码点                                 |
| 请求体        | 序列化为 UTF-8 后不超过 65,536 字节（64 KiB），包含 JSON 字段和历史消息                              |
| 附加字段       | 不允许；不要发送 `model`、`system` 消息、`temperature`、`max_tokens`、`stream`、`tools` 或文件字段 |
| 返回方式       | 一次性 JSON 返回，当前不支持流式响应、图片、音频、附件或工具调用                                            |

模型、系统提示词和输出上限由方舟管理。站点可以在 user 文本中表达业务要求，但不能通过额外字段更改服务端模型配置。

实现时使用实际序列化后的请求体检查字节数。JavaScript 可用 `Array.from(text).length` 计算码点数，用 `new TextEncoder().encode(body).byteLength` 计算 UTF-8 字节数；不能用字符串长度代替字节数。

### 3.2 成功响应

HTTP 状态为 `200`，同时响应体 `code` 为 `0` 才视为成功：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "request_id": "123e4567-e89b-42d3-a456-426614174000",
    "content": "This wig is suitable for everyday wear.",
    "usage": {
      "input_tokens": 120,
      "output_tokens": 20,
      "total_tokens": 140,
      "status": "known"
    }
  }
}
```

示例用量仅用于展示结构。`usage.status` 为 `known`、`partial` 或 `unknown`；三个 token 字段可能为 `null`。未知用量不能解释为零消耗，也不影响已经返回的文本结果。输入字符限制与 token 用量是不同概念。

服务端检查 `data.content` 为字符串、`data.request_id` 与本次编号一致，再向浏览器返回结果。不要依赖 `choices[0].message.content`，本接口没有该字段。

### 3.3 错误响应

```json
{
  "code": 429,
  "message": "请求过于频繁，请稍后再试",
  "data": {
    "request_id": "123e4567-e89b-42d3-a456-426614174000",
    "error": "rate_limit_exceeded"
  }
}
```

部分鉴权失败或入口层拒绝请求可能没有有效 `request_id`，也可能收到非 JSON 内容。本站始终保留自己生成的请求编号作为排查编号；不要假设所有错误都能直接执行 JSON 字段读取。

## 4. 服务端实现流程

以下为与框架无关的逻辑，Codex 应按当前项目语言实现：

```text
验证本站用户和功能权限
检查本站访问者频率，防止重复提交
从服务端配置取得地址、密钥和能力名称
验证输入，构造只含 preset 与 messages 的请求体
检查消息条数、码点数、UTF-8 请求体字节数
生成 UUID，并建立可关联的操作记录
向配置地址的 /chat 发送一次 POST，关闭自动重试和自动重定向
读取响应，检查 HTTP 状态、业务 code 和成功数据结构
成功：向浏览器返回 content、request_id
失败或超时：返回稳定的用户提示和本次 request_id，不再次外呼
```

HTTP 总等待时间建议设为 75 秒；站点服务端及外层代理的执行时间应超过该值，例如平台支持时设为 90 秒。方舟模型调用有最多 60 秒的服务端上限，网络及处理还需要时间。检查所用 HTTP 库的 timeout 含义，必要时增加覆盖完整请求的总时限。

浏览器断开或取消等待不代表模型停止执行。不要把取消操作描述成“已取消计费”。

本站应避免同一操作被重复外呼：按钮置忙仅是第一层，后端也应对同一操作编号做去重。需要跨实例时复用已有数据库或缓存记录操作状态；收到重复操作返回本站已有状态，不再调用方舟。最小单轮功能不需要为此引入消息队列。

## 5. 错误处理与用户提示

| HTTP / `data.error`                                                         | 站点处理方式                                    |
| --------------------------------------------------------------------------- | ----------------------------------------- |
| `401 / invalid_api_key`                                                     | 提示“AI 服务配置失效，请联系站点负责人”，负责人核对或更新服务端密钥      |
| `403 / app_disabled`                                                        | 提示“本站 AI 服务暂不可用，请联系负责人”，由管理员核查站点及负责人账号状态  |
| `403 / preset_not_allowed`                                                  | 提示“当前功能尚未授权”，由管理员授权或修正服务端能力名称             |
| `409 / duplicate_request`                                                   | 提示“该请求已受理，请勿重复提交”，保留原编号，不更换编号自动重发         |
| `413 / payload_too_large`                                                   | 提示缩短输入或历史消息；修正内容后由用户重新提交                  |
| `422 / invalid_request`                                                     | 开发者检查 UUID、Content-Type、字段、角色和长度；不要原样自动重发 |
| `429 / daily_limit_exceeded`                                                | 提示“本站今日 AI 调用次数已用完”；按北京时间自然日统计            |
| `429 / rate_limit_exceeded`                                                 | 提示稍后手动操作；有 `Retry-After` 时显示等待时间，不自动排队重发  |
| `429 / concurrency_limit_exceeded`                                          | 提示“当前请求较多，请稍后操作”；持续出现时由管理员核查未完成请求         |
| `503 / preset_unavailable`                                                  | 提示“AI 能力配置暂不可用，请联系管理员”                    |
| `502 / upstream_error`、`504 / upstream_timeout`、`503 / gateway_unavailable` | 提示“本次未取得可确认的结果，请联系负责人核查”，展示请求编号，不自动重试     |
| 网络中断、客户端超时、非 JSON 或响应结构异常                                                   | 按结果未知处理，保留本地请求编号，不自动重试，不展示上游原始错误页面        |

次数配额按已准入的请求统计，不能假定只有成功调用才占次数。每日配额是全站共用；方舟的全站限制不能替代本站按用户的访问管理。

## 6. 请求编号与结果未知

`X-Request-ID` 是追踪与重复准入保护，不是结果查询接口。相同站点再次提交已受理的 UUID 会得到 `409`，不会返回上次生成结果。

遇到超时、断网或未知结果时：

1. 保留并展示原请求编号。
2. 由站点负责人将编号提供给方舟管理员，在“AI 管理 → 站点应用”的调用记录中核查。
3. 不用新 UUID 自动重发来绕过重复检查。核查后确需重新生成时，由用户明确发起新的操作，并告知可能再次消耗额度。

当前没有面向站点调用方的查询结果或取消接口，不要虚构 `/status`、`/result`、`/cancel` 等网关端点。站点若需要刷新页面后恢复结果，应自行保存自己的结果及访问权限。

## 7. 密钥、日志与部署配置

* 方舟密钥只存服务端秘密配置；不要使用会暴露到浏览器的 `VITE_*`、`NEXT_PUBLIC_*` 等变量。

* 浏览器只发送本站登录凭据到本站后端，不接收 `ARK_AI_KEY`。前端源码、网络请求、页面配置中均不得出现该密钥。

* 服务端网关地址固定来自配置，不接受浏览器传入 URL；关闭自动重定向，保留 HTTPS 证书验证。

* 日志记录请求编号、状态、耗时及必要的内部用户标识即可。不要记录 Authorization、密钥、完整请求正文或完整生成结果。

* 管理员重置站点密钥后，旧密钥立即失效；负责人更新服务端配置，并按托管平台要求重新加载或重启服务。

* 输入内容会通过方舟交给模型处理；界面应简要说明用途，按实际业务只发送所需内容。

## 8. Codex 验收与交付清单

完成以下 mock 验证，并在交付说明中报告实际结果：

* 未登录或无功能权限时不向方舟发送请求；本站限流生效。

* 正常请求使用服务端能力名称、Bearer 站点密钥和 UUID，成功解析 `code=0` 的文本结果。

* 前端不能通过请求参数切换任意 Preset 或模型；前端产物、响应和日志中没有密钥。

* 空输入、超长输入、多轮消息超限、非 user 结尾及大于 64 KiB 的请求被阻止或明确提示。

* 连续点击及同一业务操作重复提交不会导致重复外呼。

* 对 401、403、409、413、422、429、502、503、504、网络超时及非 JSON 响应，均有稳定提示和请求编号；失败路径没有自动重试。

* `usage` 为 partial/unknown 或 token 为 null 时，已成功返回的文本仍能显示。

* 页面在桌面及手机上能完成输入、等待、阅读和复制；生成内容不会作为未经处理的 HTML 执行。

最终说明必须列出：改动文件、配置方式、本站接口路径、已验证项目、未验证项目及原因。真实调用尚未执行时写明“mock 验证通过，真实连通性待验证”，不得将其描述成已上线可用。

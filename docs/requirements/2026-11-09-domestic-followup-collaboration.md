# 内贸客户跟进：客户总览与接力协作需求方案

> 日期：2026-11-09 · 状态：需求定稿 v2，亮哥已确认全部 10 项口径，P1/P2 已在独立工作区实现。
> 实施范围为 P1/P2 本地开发与验证。试点授权和生产发布按项目流程另行执行。
> 事实依据：当前工作区源码与既有功能设计；本次未登录生产页面、未查询生产业务数据。下列业务规则已确认。试点地区和人员名单在启用前配置。

## 1. 目标与需求理解

让业务员开发某地区时，能够找到客户、看懂当前进展、明确谁在联系，并在交接后沿用前人的资料和经验继续推进。减少重复找号码、重复沟通和人员变化造成的信息丢失。

用户提出的核心场景：兰兰在9月跟过某地区的客户，宋洋10月负责开发该地区。宋洋应能筛出尚未成交、允许接手的客户，查看联系方式、之前的沟通和推进障碍，完成接手后继续跟进；已有他人负责的客户明确提示；成交后能够回看整个推进过程。

业务目标：

- 客户资料和沟通过程沉淀在同一客户档案内，人员变化不丢记录。
- 联系前看见当前负责人、最近联系时间和下次安排。
- 有序接力：交接成功才切换责任，接收失败不能出现无人负责。
- 成交依据可追溯，已成交客户退出首次开发清单，继续维护、复购及售后。
- 复盘前后做法和客户条件变化，不把“最后一次联系人”直接认定为唯一成交贡献者。

本期不包含：自动拨号、电话录音、微信聊天自动抓取、自动向客户发消息、自动判断员工能力、自动改变提成、批量自动转移客户、建设全新的 CRM 或外贸客户经营体系。“电话记录”按电话号码与沟通要点理解。

## 3. 业务对象与口径

### 3.1 四个维度必须分开

| 维度 | 建议值或含义 | 主要来源 |
| --- | --- | --- |
| 成交情况 | 已成交 / 未成交 / 待核实 | 有效业务订单、历史成交档案、人工核实证据 |
| 开发进度 | 待联系 / 已联系 / 报价或寄样 / 暂缓 / 停止开发 | 业务员确认的推进结果 |
| 生命周期 | 沿用潜在 / 活跃 / 沉默 / 流失等现有字典 | 客户主档；不因本次交接自动修改 |
| 协作状态 | 待分配 / 跟进中 / 交接中 / 可接手 / 停止开发 | 当前跟进责任和交接记录 |

“待分配”表示尚无有效负责人且未开放自主接手；“可接手”表示已按权限和规则开放接手。不能看到 owner 为空就直接认定任何人可接手。“暂缓”仍有负责人及约定日期；“停止开发”需原因，不能自动加入待联系清单。

已成交是成交维度，不替代协作状态。已成交客户仍可以由明确人员负责维护。潜在、已成交等历史标签冲突时提示核实，不静默覆盖原资料。

### 3.2 成交判定

已正式生效且订单金额大于 0 的业务订单计入，实收另行判断。排除草稿、待审核、取消、删除、内部生产、零金额样单及纯售后单。付费样单计为成交并单列“仅样单成交”，仍可筛出以推进正式采购。

- 有符合口径的系统订单：已成交，展示首次成交日期和依据入口。
- 没有系统成交，但历史首次下单日期、累计订单数等资料有可信证据：标为“已成交·历史档案”；证据冲突转待核实。
- 没有有效订单，且本次新建档明确未成交或人工完成核实：未成交。
- 没有有效订单、历史资料又缺失：待核实，不能把未知自动算未成交。
- 人工核实要记录结论、依据、核实人、时间；普通跟进勾选“已成交”仅触发核实。
- 在详情抽屉的「成交情况」旁可手动设置已成交、未成交、待核实，或恢复自动判定，均需填写原因。适用人员包括客户范围内的协调员、有读写权限的当前跟进负责人或获准协作人，以及有读写权限的旧档案归属人、提成人和仍有效的超级管理员（旧档案）。
- 手动状态优先用于客户跟进的详情、列表、筛选和统计，展示「人工修改」。手动分类期间按所选状态归类；恢复后重新判断付费样单等原有分类。原订单、历史档案及此前核实记录保留，手动结论与订单或历史成交冲突时保留待核对提示。
- 已完成交易后来退款，不抹去“曾成交”事实；相关退款仅作为经营信息，且沿用财务可见范围。未生效订单取消后不形成成交。
- 列表可展示成交结论，但订单详情、金额仍使用原订单权限；无权限时不能返回完整订单数据或附件。

实施前需将上述业务口径逐项映射到当前订单类型和状态枚举，并抽取脱敏样例核验。未完成此核验前不能发布“自动成交判断”。不以 `total_order_count` 单一历史字段作唯一依据。

### 3.3 当前跟进负责人、客户归属和提成

新增独立的“当前跟进负责人”关系，保存负责人、协作人、状态、开始时间、下次安排及版本。沿用客户主档 ID。

- `owner_user_id` 继续表示现有客户归属；提成分配及订单提成快照维持原语义。
- “接手跟进”只改变跟进责任，不改变客户归属、不改变提成、不修改历史订单。
- 客户详情同时展示“归属销售”和“当前跟进人”，两者相同时合并显示，避免多余信息；不同时明确分开展示。
- 单客户仅一名当前主要对外跟进人；允许明确添加协作人，协作记录显示实际录入者。
- 归属人和提成人仍保留原有合法读范围，但不能因为该身份自动成为第二个主要跟进人。
- 现有客户管理修改归属时，应提示该客户当前跟进安排，不能顺带隐式覆盖；两种变更各自留痕。

## 4. 页面改造

### 4.1 页面导航与默认入口

继续使用 `/domestic/followups`，不新建一级菜单。

| 页签 | 作用 | 默认行为 |
| --- | --- | --- |
| 客户总览（新增） | 按客户找开发和接手机会 | 首次进入默认展示；业务员默认“我负责”，管理员默认“授权范围” |
| 待办（保留） | 今天要做什么、即将到期、异常处理 | 从提醒链接进入仍落待办或指定客户，不被新默认页打断 |
| 跟进明细（原总览） | 查每一次沟通、录入人和日期 | 保留现有查询、详情、编辑及历史 |
| 异常意见（保留） | 处理问题闭环 | 保留现有转交和处理逻辑 |
| 我的记录（保留） | 快速找自己写过的内容和草稿 | 保留原入口，避免改变熟悉的操作路径 |

原有四张“收货回访/约定跟进/异常意见/即将到期”任务卡移动到待办页签内；客户总览使用客户计数，不能拿记录条数充当客户数。记一条跟进、快速建客户保持明显入口。

### 4.2 客户总览

统计：当前筛选内客户数、未成交、已成交、待核实；以去重 customer_id 统计。点击成交分类只切换该维度，保留地区和责任范围。

常用筛选：

- 关键词：店名、客户编码、联系人、电话、微信号；联系方式检索遵守字段权限。
- 地区：省 → 市，支持“地区未补齐”，切换省份清空不匹配城市。
- 成交情况：全部 / 未成交 / 已成交 / 待核实；支持“仅样单成交”扩展条件。
- 责任范围：我负责 / 我协作 / 可接手 / 交接给我 / 授权范围。
- 当前跟进人、协作状态；更多筛选内放最近联系区间、从未联系、下次跟进是否逾期、生命周期。

默认列与行内操作：

| 列 | 展示 |
| --- | --- |
| 客户 | 店名、编码；缺联系方式时提示“待补联系方式” |
| 地区 | 省、市；缺失显示“待补地区” |
| 联系方式 | 有权限展示联系人及号码，支持复制；否则脱敏，并说明“接手后可查看”等实际可用路径 |
| 成交情况 | 结论、依据类型；历史或待核实有文字标识 |
| 当前跟进 | 姓名、跟进中/交接中/可接手等状态；交接中显示接收人 |
| 最近联系 | 日期、实际联系人、简短摘要；从未联系明确显示 |
| 推进情况 | 开发进度、主要障碍、下次安排 |
| 操作 | 主操作按状态为“记跟进”“接手跟进”“处理交接”或“查看”；更多里放发起交接、释放、协作人管理 |

一个客户一行，包含没有跟进记录的客户；从客户集合聚合，不能仅从跟进记录分组生成。排序允许最近联系、下次跟进、客户名称；无联系日期单独可筛选。统计、列表、分页必须使用同一权限和筛选范围。

列表表格复用 `useListPage`、`FilterBar`、`TableTools`、`ListPageStatus` 和现有列密度/列显隐模式。切换范围清空旧详情与旧数据，取消或忽略迟到请求，避免闪现前一权限范围的数据。

### 4.3 客户详情抽屉

复用客户时间线抽屉，扩展为下列区块：

1. 客户摘要：店名、地区、联系人、电话、微信；允许范围内补充资料，缺项不弹出阻断流程。
2. 责任与状态：成交情况及依据、归属销售、当前跟进人、协作人、下次计划；发起交接、接手等按钮按能力显示。
3. 接手摘要：客户需求、主要障碍、已承诺事项、推荐下一步；来自结构化记录或人员确认，AI 输出必须标明待确认。
4. 历史时间线：沟通、交接、释放、成交确认事件；显示作者和发生日期，补录同时保留录入时间。发货保持原权限。
5. 未完成事项：开发计划、收货回访、异常意见分别列出负责人，不混成一个“客户负责人”。

支持按事件类型过滤和分页加载更早历史。交易与发货无权限时不返回该类事件；不把完整时间线数据先发到前端再隐藏。旧草稿不随交接转给新负责人。

### 4.4 记一条跟进

复用当前文字/截图/AI 草稿确认流程，日期、作者、当前客户自动带入。人工直接保存继续可用，AI 不是必经步骤。

新增或整理的业务字段：

| 字段 | 要求 |
| --- | --- |
| 沟通方式 | 沿用现有字典；选择电话不要求录音 |
| 本次结果 | 未接通、未回复、有效沟通、已报价、已寄样、客户拒绝等可配置结果 |
| 开发进度 | 可选更新；历史单条结果不直接覆盖当前进度 |
| 主要障碍 | 价格、产品适配、采购时机、决策人、已有供应商、信任不足、其他；可多选，允许未知 |
| 事实与依据 | 原文或截图；“客户明确说”与“我的判断”分开标记 |
| 下一步 | 复用计划、日期、方式；有效推进默认建议填写，不因普通未接通强制填大表 |
| 是否需要换人协作 | 可选；选择后引导发起交接，不在保存记录时自动换负责人 |

本次结果随记录保存。2026-11-13 起，直接保存、确认草稿、补录历史沟通和修改已确认记录时，本次结果必填（后端同时校验）；草稿整理阶段允许留空。存量空结果不自动回填，编辑时需补选；已有结果的编辑请求省略该字段时保留原值，不能清空。「已回访无问题」快捷入口按该动作的明确含义保存为“有效沟通”，仍校验当前字典。当前开发进度单独维护，只有用户明确选择“更新当前进度”且通过版本校验才更新；补录过去的沟通和编辑旧记录不能倒退覆盖新进展。最新联系按业务发生时间计算，摘要不能简单取最后写入的一条。

旧“客户状态变化”字段继续服务既有画像；新的成交结论与开发进度有明确权威来源，不能同时维护两个相互覆盖的同义状态。

非负责人发起普通对外开发记录时，先显示现任联系人和最近安排，可申请接手或由负责人添加为协作人。售后任务接收人可以记录该任务处理结果，但该操作不赋予一般开发联系权。历史补录通过专门入口保存，不占用当前跟进责任、不默认新建对外联系待办。

### 4.5 快速建档与重复提示

- 店名必填；联系人、电话、微信、省市可顺手填写，未知可留空。若电话和微信都缺，显示“联系方式未补齐”。
- 复用客户主档电话/联系人/省市字段；微信号与微信备注名分开，微信号是联系方式，聊天标题别名只是搜索线索。
- 提交前按规范化电话、微信号、店名+地区查疑似重复；最终提交再次校验，防止同时建档绕过提示。
- 号码相同可能为连锁店或公共前台，只提示核对，不自动合并；沿用现有精确店名唯一约束。同名异店目前进入管理员核实流程，不顺手放宽约束。
- 有权限的匹配项显示可识别摘要并跳转；范围外只给“可能已有档案，请联系管理员核实”，不暴露号码、店名、人员或记录，也不能借重复检查枚举全库。
- 新建后默认本人负责跟进，事务内完成档案与责任初始化；不依赖用户再点一次接手。原有归属与提成初始化规则不在本需求中更改。

### 4.6 移动端

主站响应式复用，不新增 `/m/` 业务入口。窄屏客户列表改为摘要卡片，优先展示店名、成交情况、当前跟进人、最近联系及主操作；筛选收进抽屉，联系方式在详情内可复制。交接信息和接受/拒绝在手机上能完整完成。

## 5. 交接与接手规则

### 5.1 三种动作

| 动作 | 发起条件 | 何时切换责任 |
| --- | --- | --- |
| 直接接手 | 客户明确为可接手；申请人有该客户协作范围及写权限 | 服务端确认成功时立即切换 |
| 定向交接 | 当前负责人选择合格接收人，或申请人提出接手申请并由当前负责人同意 | 接收人明确接受时切换；接手申请人已明确申请的，原负责人批准可视为双方同意 |
| 管理员强制重派 | 离职、长期无人处理、争议等例外；有客户范围内的协调管理权限 | 管理员提交理由并确认后立即切换，进入双方历史 |

接收人必须在职、具有模块读写权限，且位于该客户的协作范围。不能把任务派给打开页面后无权限处理的人。跨范围交接须先由范围管理员调整客户级授权；不能用选人控件绕过范围。

### 5.2 定向交接流程

交接单字段：客户、发起人、原负责人、接收人、交接原因、当前障碍、已承诺事项、建议下一步、待办清单、发起时间、状态、版本和处理意见。已知字段自动带出，发起人核对后提交；原因和交接摘要必填。

| 交接状态 | 允许动作 | 当前责任 |
| --- | --- | --- |
| 待接收 | 接收人接受/拒绝；发起人撤回；管理员重派导致失效 | 原负责人继续负责 |
| 已接受 | 只读查看交接证据；需要再换人时新建交接 | 接收人成为负责人 |
| 已拒绝 | 保留拒绝原因，可重新发起新单 | 原负责人不变 |
| 已撤回 | 保留撤回记录 | 原负责人不变 |
| 已失效 | 归属责任版本变化、接收人失去资格、客户停用等导致；需重新核对 | 以当前有效责任为准 |

同客户最多一个待处理交接。待接收满 3 个自然日进入协调清单，原责任和待接收资格持续有效。协调提醒阈值可配置。离职人员遗留交接由管理员处理，不能自动把客户丢入公海。

待接收者只获得交接包预览：客户摘要、拟转任务、已确认的交接说明及明确选入的必要记录。不能因收到交接邀请立刻获得全部历史、附件和联系方式；接受后才按新负责人范围读取。拒绝或撤回后撤销临时预览资格。

接受时重查客户状态、双方权限、当前负责人版本和任务状态；负责人变了、交接已处理或客户已停止开发时拒绝过期接受。交接后不修改历史作者、原始发生时间或原文。

### 5.3 待办如何承接

| 待办类型 | 默认行为 | 例外与限制 |
| --- | --- | --- |
| 原负责人承担的未完成开发计划 | 纳入交接，新负责人承接；默认保持日期和内容 | 发起后新产生的任务在接受时列出变化，必须重新确认，不能悄悄漏掉 |
| 其他协作人的开发任务 | 保留责任，显示在交接包 | 如需转移须明确列入并核验管理权限 |
| 收货回访 | 保留原任务责任，交接页提醒 | 可明确选入转移；不得把客户交接等同于已完成回访 |
| 异常、意见 | 保留原处理人 | 继续使用现有异常/意见转交流程，不随开发交接批量迁移 |
| 已完成、取消任务 | 保留历史 | 不重开、不重建、不更改原完成者 |
| 原负责人草稿 | 仅作者可见 | 不转移；提交时重新校验责任，必要时作为历史补录处理 |

现有 `plan` 只表示约定跟进，没有区分开发与维护。实施时应为计划增加用途（开发/维护/其他），存量未分类计划在交接包中逐条确认，不能把全部 `plan` 任务自动当成开发任务。新建开发计划默认交给当前跟进负责人，也可明确选在职、有权限的协作人；维护计划明确承办人；异常与收货回访保留现有分配来源。新负责人产生后，不能仍无条件把所有新计划派给记录作者。

交接确认与负责人切换、选定待办重派、审计落库在同一事务内完成。任一项失败整体回滚。使用请求幂等键及责任版本，双击不建重复交接；双方并发接手只允许一人成功。

不能仅在前端移走旧提醒：日报待发送内容、页面计数和提醒链接需按最新任务责任校验。已发出的消息不可撤回，但旧链接不能允许前负责人继续修改已转移任务；事务提交前不能发送交接成功提醒。

### 5.4 释放、公海及停止开发

本需求区分“客户公私海归属”和“跟进责任是否可接手”：

- 原三个月释放规则仍控制客户归属，不自动清空独立的跟进责任。公海客户可能仍在有效跟进，列表显示“公海 · 某某跟进中”。
- 客户管理列表读取和定时释放两条路径都必须保留这个约束；不能一个路径保留、另一个路径清除。
- 主动释放需填写原因，并明确结束仍待处理的开发计划。需要继续执行的计划应通过正式交接承接。释放后先进入待分配，协调员核对范围和未结事项后再开放接手。
- 连续 30 天无有效推进或未完成开发计划逾期满 30 天，进入管理员“需协调”清单。责任保持有效。
- 管理员开放可接手需要明确客户协作范围；没有范围的进入待分配。
- 客户明确拒绝后可停止开发，保留拒绝依据与是否允许未来联系；重新开放须负责人或管理员填写理由，不能自动按到期时间恢复联系。
- 客户停用后禁止新增对外开发及接手，未完成任务/交接进入需处置状态并通知有权协调人；历史只读保留。

“有效推进”至少有客户回复形成的新信息、报价/寄样进展或明确的下一步承诺，由记录人确认；单纯编辑资料、建草稿、未接通或重复改计划日期不刷新推进时间。30天口径分别检查最近一次有效推进，以及仍未完成计划的到期日超过30天；暂缓客户有明确未来约定时先按约定处理。只是提醒协调，不据此自动判定员工失职或客户失效。

系统控制的是平台内的分配、操作入口与提醒，不能保证员工在平台外绝不会重复拨打电话；验收不得声称已阻止所有线下联系。

## 6. 权限与可见范围

### 6.1 原则及范围来源

动作权限、客户范围、字段可见性分开校验。`read_all` 只表示读范围，不能因拥有它就取得全客户写、交接或重派权。现有 helper 将 read_all 间接用于可写判断的地方须在实施时收口，并覆盖旧入口。

一期不建设通用组织权限平台。在“跟进设置”内管理协作范围。选已有用户作为范围成员，按省市匹配客户，并允许客户级明确例外；地区只是筛选条件，只有管理员配置的地区授权才构成权限。缺省不授权全员、地区为空不匹配所有地区。

- 一个客户可以被多个协作范围看见，但仍只有一个当前负责人。
- 拥有完整历史的原归属人、提成人等原有合法读范围继续保留；不要把交接做成财务或既有客户数据权限收回工程。
- 因新协作关系获得的可见范围，随关系结束而撤销；若同时持有原有独立授权，仍按该授权读取。
- 调整地区、范围或人员停用时重算资格；不能无人知晓地释放责任。出现负责人失去范围资格时暂停其新开发操作，列入管理员处置，并保留已有责任及历史。
- 新范围权限仅作用于跟进业务，不赋予订单金额、余额、提成、客户主档全量编辑或导出权限。

### 6.2 权限矩阵（下表为新协作身份带来的增量权限）

| 身份 | 协作摘要 | 完整联系方式/已确认沟通历史 | 记新开发跟进 | 接手/交接 | 编辑他人记录 |
| --- | --- | --- | --- | --- | --- |
| 当前负责人 | 本客户 | 允许，附件按记录授权 | 有 write 时允许 | 发起交接、添加协作人、释放 | 不允许 |
| 明确协作人 | 本客户 | 允许，限授权协作客户 | 有 write 时允许，显示实际作者 | 可申请接手，不能直接重派 | 不允许 |
| 授权地区成员 | 范围内可见 | 默认脱敏，仅可见经确认的协作摘要 | 不允许直接开发；先接手或成为协作人 | 可接手开放客户，可申请接手在跟客户 | 不允许 |
| 待接收人 | 指定交接包 | 仅预览包明确选入的资料；接受后扩展 | 接受前不新增一般开发权限 | 接受/拒绝自己的交接 | 不允许 |
| 售后/异常任务接收人 | 指定任务上下文 | 延续现有任务相关记录权限，不扩成全部客户历史 | 仅记录该任务处理，不取得一般开发权 | 只处理其任务允许的转交 | 不允许 |
| 原负责人 | 自己参与的历史及交接结果 | 保留本人记录；其他内容依当前独立授权 | 交接后不再因“曾负责”获得新开发权 | 可再次申请，不能撤销已完成交接 | 不允许 |
| 全量只读管理者 | 全量 | 沿用 read_all 可读范围 | 不因 read_all 获得写权 | 不允许管理性重派 | 不允许 |
| 跟进协调管理员 | 管理范围内 | 为协调所需可读；财务权限另算 | 有 write 时可记录 | 可强制重派、开放、范围配置（配置需对应管理员权限） | 不因协调身份获得编辑权 |
| 范围外用户 | 无一般查询结果 | 不允许 | 不允许 | 不允许 | 不允许 |

所有身份叠加各自独立授权后计算最终权限，但不能用只读范围推出写权限。草稿、作废记录及草稿附件仍仅按现有作者边界读取；交接不扩权。确认记录仍按本人+write 或现有 super_admin 规则编辑，必须保留修改理由与历史。

协作客户的旧记录可更正沟通事实。原有计划字段保留，现任通过新跟进或待办入口调整当前安排。交接后原作者仍可更正自己的历史，已有异常和意见继续通过原处理入口操作。

### 6.3 字段及入口一致性

- “协作摘要”只包含店名/地区、成交分类、跟进人、最近联系日期、开发进度和人员确认的可共享摘要。不能直接截取可能含手机号、报价或内部评价的 raw_text 当摘要。
- 列表、统计、详情、搜索、录入人选项、附件原图、修改历史、AI 上下文和提醒跳转使用同一权限服务。隐藏按钮不能替代后端校验。
- 按电话/微信搜索时，仅搜索有权匹配的资料；范围外重复检测返回统一核实提示，禁止导出或批量枚举。
- 若后续提供导出，必须独立授权并沿用字段脱敏；本期不新增跟进资料批量导出。
- 权限变化、交接成功后立即刷新动作能力；旧窗口提交按服务端最新状态拒绝，并保留未保存文字供用户改为补录或复制。

具体权限 code 在实施设计中按项目现有词汇和 RBAC 规范登记，不在需求阶段假装已配置。新增协调管理能力不直接扩大现有“跟进设置管理员”的默认权限；角色分配需明确选择。

## 8. 历史数据与上线衔接

- 历史记录不搬家、不重写作者、不从自由文本猜测接手人或成交原因。
- 当前归属人为有效在职人员且具备必要权限、无多头开发冲突时，列为初始化候选。先生成清单，经核对确认后初始化。
- 多人有开发待办、原归属人失效、资料缺失的客户进入待分配/需协调；不以最后录入人、提成人或财务数据擅自确定负责人。
- 已有权限与存量任务先核对；初始化必须幂等，重复执行不能覆盖已人工确认的责任。
- 旧公海客户不批量开放给全员，先明确协作范围；缺地区放“地区未补齐”。
- 成交分类历史回填保留证据来源，未知保持待核实。AI 可建议但不替用户确认业务事实。
- 新规则启用须覆盖现有工作台、客户管理跳转、直接 API、任务快捷处理、编辑历史影响和后台任务；不能仅新增一个安全页面而旧接口仍可绕过责任规则。
- 分阶段启用时需显式配置开关及客户范围；完成切换后移除无用途临时分流。关闭新 UI 不能自动撤销已完成交接或恢复旧负责人，回退需保留责任/审计数据并明确未完成任务处理办法。

## 9. 交付阶段与验收

### 9.1 阶段

| 阶段 | 可交付结果 | 发布边界 |
| --- | --- | --- |
| P1 客户信息可查 | 客户总览、地区/成交筛选、联系方式、当前合法范围内历史、资料补充及重复提示 | 不提前给全员开放历史；无交接机制时不展示可执行接手按钮 |
| P2 接力协作闭环 | 独立负责人、权限范围、交接、任务承接、防并发接手、公海协调和历史初始化 | 与后端入口权限收口一起启用；此阶段完成才满足完整需求 |
| P3 复盘增强（后续可选） | 按地区/障碍/交接过程汇总，基于证据的 AI 复盘草稿 | 不作为本次 P1/P2 完成条件；不扩展到个人绩效打分 |

P1/P2 均需保留沟通结果和障碍证据；P3 只是跨客户分析增强。无需为了完成基础接力先建设复杂分析看板。

### 9.2 验收场景

| 编号 | 操作或条件 | 必须观察到的结果 |
| --- | --- | --- |
| A01 | 宋洋筛某省市、未成交 | 一客户一行，包含零跟进客户；计数与列表一致，无重复档案叠加计数 |
| A02 | 只有潜在标签但已有有效成交 | 显示已成交及依据，提示标签冲突，不把它当未成交 |
| A03 | 无系统订单且历史资料缺失 | 待核实；不能直接计为未成交 |
| A04 | 有价未回款正式单、付费样单、零金额样单、取消单、历史成交分别进入 | 正式单算已成交，付费样单单列且可筛选，零金额样单和取消单排除，历史成交展示来源。订单金额沿用财务权限 |
| A05 | 输入电话/微信查已有客户或新建 | 权限内命中可复用；范围外只有统一核实提示，不泄漏信息 |
| A06 | 快速建档只填店名 | 创建潜在档和本人跟进责任，提示补联系方式；重复提交不重复创建 |
| A07 | 查看兰兰负责的地区内客户 | 宋洋可看协作摘要和现任安排，不能直接读全部截图或开始新开发 |
| A08 | 兰兰发起交接，宋洋尚未接受 | 兰兰仍负责；宋洋只见交接包；没有自动接手或重复提醒任务 |
| A09 | 宋洋接受交接 | 负责人及选定任务同时切换，原记录作者不变，客户归属和提成快照不变 |
| A10 | 拒绝、撤回或待接收满 3 个自然日 | 原责任保持。拒绝和撤回撤销临时预览。满 3 日只进入协调清单，接收人仍可处理 |
| A11 | 两人同时接手或双击接受 | 一次有效切换，失败方得到当前责任提示，无重复任务或审计成功事件 |
| A12 | 发起后新增计划/任务被完成/负责人变化 | 接受时显示变化或拒绝过期请求，不覆盖已完成任务，不遗漏新待办 |
| A13 | 交接中途数据库写失败 | 责任和任务整体保持原状，无成功提醒；重试结果可核实 |
| A14 | 有异常、收货回访和开发计划同时存在 | 仅按交接清单转移开发任务及明确选中的回访；异常继续由原处理人处理 |
| A15 | 原作者交接后修改旧记录，或保存交接前草稿 | 不恢复旧责任、不改现任计划、不触发重复开发；有明确冲突反馈和补录路径 |
| A16 | 执行定时公海释放或打开客户管理列表 | 客户归属变化不清空有效跟进责任，不能突然向他人开放接手 |
| A17 | 用户只有 read_all，或已离职/被移出范围 | 不因读范围获得写权；失效资格提交被拦截并进入协调 |
| A18 | 直接请求附件、历史、统计、人员选项及旧 API | 与页面范围一致，无越权读取、写入或范围侧漏 |
| A19 | 用户在地区筛选/权限范围之间快速切换 | 不显示旧范围详情；迟到响应不覆盖当前数据 |
| A20 | 客户成交、明确拒绝继续联系或停用 | 成交退出首次开发清单，当前负责人继续维护。明确拒绝进入停止开发，恢复需授权人说明理由。停用禁开发及接手，历史和现有售后按原规则处理 |
| A21 | 客户历史超过100条或较早发货 | 可分页查授权历史，明确时间范围，不把当前截断误报为全部 |
| A22 | 手机从提醒进入、完成接受或拒绝 | 落到对应客户/待办；信息完整可操作；失败不会丢失用户输入 |
| A23 | 跨日、补录旧日期、服务器非东八区 | 统一北京时间；最近联系及逾期判定正确，旧记录不覆盖新阶段 |
| A24 | 日报已排队后发生交接，旧消息已发出 | 新发送重检责任，旧链接按最新权限；不重复创建提醒来源任务 |
| A25 | 30 天无有效推进、开发待办逾期满 30 天、客户已约定未来日期 | 前两种显示需协调。已有明确未来约定时按约定执行。责任保持，客户保持当前跟进状态 |
| A26 | 历史初始化预览有正常归属、离职归属及多人开发待办 | 正常归属列为候选，离职或冲突进入主管核对。预览后按确认清单初始化，重复执行保留既有责任 |
| A27 | 同地区但未授权、已授权普通同事、交接接受者、交接后原负责人分别查看 | 未授权者依既有权限。普通成员只见共享摘要。接收人看到获准的完整沟通历史。原负责人保留本人记录和交接结果，其他历史按独立授权 |
| A28 | 已开放客户直接接手、在跟客户双方同意、主管重派 | 三条路径分别正确切换。普通成员不能直接抢在跟客户，主管重派记录操作者和理由 |
| A29 | 有权人员将已有系统订单的客户改为待核实，再恢复自动判定 | 详情、筛选和统计跟随有效状态，修改和恢复均留痕；仅可看摘要的用户无法修改 |

验收材料包括：核心流程实际页面结果、权限与并发回归、历史初始化预览及异常样例。实现阶段先用隔离数据验证；生产发布、迁移及范围授权另行按项目入口执行。

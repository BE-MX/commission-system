- [详细开发文档](DEVELOPMENT.md)：现有代码差距、领域与状态机、拟议 API、幂等与权限、每日容量、Agent 生命周期、实施阶段、迁移及验收。

客户领域的“今日工作台”和“客户档案”合并为客户工作台；登录后的全员工作台继续作为各岗位摘要入口。客户作战卡沿用概况 / 沟通 / 档案 / 计划四页签。

## 建议评审路线

1. 从第一条“交期变化待核实”开始，点击“委派核实与准备方案”。在“推进中”模拟核实完成，回到“待我处理”采用分批方案、登记已联系。
2. 在“推进中”模拟客户接受方案。这时仍需跟单确认；若提前登记解决，原型会指出缺少跟单依据。
3. 模拟跟单确认发运后，回到“待我处理”，填写结果和依据。事项进入“已结束”，可查看历史并以新事实重开。
4. 试用暂停/恢复、明天再处理、模拟下一天、来源失效与重新核实。刷新后状态仍在，等待不会计为解决，暂停不会因跨日自动恢复。
5. 打开“全员工作台摘要示意”，进入同一事项；在作战卡四页签查看目标、沟通登记、资料补全与执行进展。来源模块的真实权限、执行和同步属于后续开发。

## 本轮原型变化

| 能力 | 当前可体验的行为 |
| --- | --- |
| 三个事项视图 | 待我处理 / 推进中 / 已结束；结束可筛已解决与已终止 |
| 计数 | 今日已处理、当前有效解决、已终止分开；同一事项当天多次处理只计一次；结果证据失效退回待复核 |
| 每日容量 | 普通事项初始预算成熟视角22、新人10；完成不补位，可主动领取额外候选；紧急项独立进入 |
| 跨日与本地保存 | 固定演示日期2026-09-30，可推进日期；保留同一事项ID、历史、等待和暂停；无后台定时器代替真实调度 |
| 经营重点 | 承诺优先 / 需求确认 / 复购核实，调整同优先级排序，不改变公司分层 |
| Agent 与协作 | 手动触发模拟核实结果、客户回应及跟单确认；分别完成当前方案的沟通和发运安排 |
| 来源与结果 | 失效草稿撤下，当前方案必须重新确认；既有外部事实保留；解决要求结果与依据，原型只校验本地示例条件 |
| 反馈 | 事实准确、建议适用、行动采纳各自记录，重复反馈不扩样本；统计移入“本轮复盘” |
| 四页签 | 概况展示目标与未知项；沟通呈现登记；档案保留补全/冲突对照与服务资产边界；计划承载事项与协作 |
| 原有客户能力 | 286/34客户视角、公司分层、搜索排序分页、订单图表、逐项补全、档案编辑保留 |
| 动效与键盘 | 清单/数字即时更新；抽屉短过渡，减弱动效时关闭；抽屉焦点约束和 Escape 返回 |

资料补全只是约5秒的本地模拟，来源链接为示例且不打开外站。刷新会保留已完成的补全选择；尚未完成的模拟补全需重新发起。重置当前视角只清除该视角的演示登记。

原型没有后台发送、真实身份权限、跨标签页并发锁、可靠来源验证、Agent 工具执行、生产数据库、真实通知/日历或模型学习。界面中的“模拟”按钮用于评审状态变化，不是正式产品的操作入口。关闭网页后不会继续推进。

## 已确认与仍待决定

已确认：公司统一分层；合并客户领域入口和作战卡；允许 AI 引用历史订单与价格。历史价格不代表当前报价，复购窗口不代表客户缺货。

原型分层按顺序：复购窗口（≥3单、平均周期85%—150%）→活跃（90天订单/30天沟通）→新客培育（未成交且60天沟通）→需唤醒（有单且91—240天未下单）→沉睡。该试点算法与现有 PCW 的商业批次中位数窗口不同，详见开发文档；上线前必须统一策略并回放定版。

管理员质量复核改抽检仍待确认。原型只演示逐项选择，不代表批准绕过现有质量复核。官网、公司主体和联系人等字段不能直接写入现有普通 profile revision 白名单。

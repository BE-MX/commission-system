# 客户工作台 v2 · 客户经营与 Agent 设计增补

日期：2026-09-30。状态：本轮新增设计建议，供后续原型与实现使用；不是已上线功能清单。

依据：亮哥本轮明确将客户经营理念补入客户工作台，并指出登录后的全员工作台还服务运营、设计、跟单等岗位；结合本目录 [README](README.md) 与 [可点击原型](index.html) 的现有行为审阅。

## 1. 产品目标与保留的决策

客户工作台帮助业务员判断哪些客户事项值得投入、把可委派的工作持续推进到下一步、及时处理影响客户承诺的变化，并从实际结果中积累客户关系和经营能力。

核心价值同时考虑可兑现的成交与复购、服务质量、业务员时间投入和长期关系。暂缓联系、停止无效推进、拒绝无法兑现的承诺也可以是正确结果。页面访问次数、消息数量、AI 采纳率不作为成功的替代指标。

沿用 README 已记录的三条产品决策：公司统一客户分层；客户领域的“今日工作台＋客户档案”合并为客户工作台、抽屉与工作区合并为四页签客户作战卡；AI 话术可引用历史订单与价格。分层试点阈值仍需历史数据回放定版，不按业务员另设一套口径。

第二轮关于“管理员质量复核改为抽检、不阻塞采纳”的建议继续待确认。本增补不改变该审批安排，也不把文档中已有的确认记录扩展为本轮发送消息、调整权限或上线授权。

## 2. 全员工作台、客户工作台与源模块的边界

| 入口或模块 | 服务对象与职责 | 进入后的工作落点 |
| --- | --- | --- |
| 全员工作台 | 所有岗位；汇总与本人职责有关的待决策、承诺到期、协作阻碍和进展摘要 | 按来源进入客户作战卡、设计、订单、物流或其他业务模块 |
| 客户工作台 | 以业务员为主；围绕有归属客户（含未成交新客）组织经营重点、客户事项、客户上下文和结果 | 客户作战卡；需要专业执行时进入对应源模块 |
| 设计、订单、物流等源模块 | 对应岗位；完成专业操作并维护交付、审批、订单和物流等事实 | 原模块完成操作，相关进展反馈给客户事项 |
| 获客与背调 | 发现、研究和筛选潜在线索；沿既有机制进入客户域 | 符合既有归属与准入规则后进入客户工作台，保留研究证据 |
| 客户网站、门户及外部 Agent 工具 | 已有客户服务触点或业务员操作入口 | 按权限读取、提交并关联既有客户事项；不再建立独立经营台账 |

全员入口共用“谁需要我做什么、为何现在处理、去哪里完成”的摘要结构，各岗位的价值与排序依据不同：业务员关注客户需求和承诺；运营关注其职责内的活动、渠道或内容结果及阻碍；设计关注需求完整性、稿件反馈与交付期限；跟单关注履约节点、异常和承诺兑现。这里仅定义摘要边界，不展开其他岗位工作台的新方案。

协作关系遵循以下规则：

- 同一责任事项在全员工作台和客户工作台引用同一标识、负责人、状态和下一步，无需重复登记。同一客户可以同时有多个不同事项，不能按客户去重。
- 同一个客户事件可以产生不同责任：业务员解释交期、跟单协调发货、设计交付素材是关联行动，各有执行人和状态。完成其中一项不会自动关闭其他项。
- 客户经营责任人与具体行动执行人分开显示。客户归属沿用既有规则，不能因为设计人员接了任务就改变客户归属。
- 订单、物流、稿件等执行事实以源模块为准；客户工作台维护目标、承诺、影响和客户响应。“已告知客户”不能改写“货物已送达”。
- 摘要内容、深链和 AI 产物都遵循当前权限。设计人员只获得完成任务所需的产品要求与反馈；历史价格、个人提成、完整沟通等不能因跨岗协作被自动开放。客户转交后，历史入口和待执行动作按当前权限重新核验。
- 来源变化同步到关联事项；来源暂不可用时保留时间戳并提示待核实，不把缓存状态当作已确认事实。

## 3. 从当前原型到经营工作区

| Before（当前原型） | After（增补设计） | Why（对用户的价值） |
| --- | --- | --- |
| “今天要联系的客户”主要引导看话术、联系与登记 | “今天值得推进的客户事项”，可包含确认需求、解决异常、审阅方案、协作、等待与暂缓 | 行动围绕客户目标，避免一切问题都变成再次联系 |
| 同一清单中的多种登记都累计“已完成” | 分开呈现今日行动已处理、事项推进中、事项已解决 | 业务员知道真正解决了什么，等待项不会消失 |
| “准/不准”反馈计入“AI 建议采纳率” | 分别记录事实纠错、建议适用性、实际采纳与经营结果 | 用户拒绝建议也能贡献信息，不被视为工作表现差 |
| 固定联系间隔与“有空再联系” | 依据承诺、具体新信息、客户偏好和已有未解决问题安排动作 | 减少无意义触达，把时间留给有价值的介入 |
| 客户作战卡以订单统计、AI 判断和话术为主 | 沿用四页签，补入经营目标、需求、承诺、待核实项、协作依赖和执行进展 | 单个客户的判断和后续行动有连续上下文 |
| 等回复、维护计划与 AI 调整以演示提示表达 | 展示真实登记的等待条件、下一次核验、执行结果；未接通时明确标注 | 用户能区分系统实际做过的工作与建议、草稿 |

## 4. 信息组织：沿用现有骨架

### 顶部与客户分层

顶部保留可核对的成交事实与数据截至时间，增加简短的经营重点，例如“本周优先兑现已承诺样品反馈，再推进已确认补货需求”。重点从已有事项推导，业务员可以调整，无需每次登录填写目标问卷。

公司统一分层继续用于了解客户组合与筛选。个人经营重点只改变关注与资源分配，不改变客户分层规则。分层不能独自决定联系动作，复购窗口也不能直接解释为客户缺货或确认采购。

首屏优先呈现需要本人判断的事项数量和内容。AI 质量统计进入复盘，不占用业务员最重要的结果指标位置。个人提成若后续需要展示，必须沿用现有权限和计算口径，区分已确认与预计；本轮不新增预测提成。

### 今日事项与全部客户

沿用原来的今日清单工作区，增加“待我处理 / 推进中 / 已结束”三个视图，复用同一组事项。“待我处理”收纳当前需要本人行动或决策的事项；“推进中”收纳其余未结束事项，包括执行、等待、受阻与暂停；“已结束”区分已解决和已终止。紧急程度分组用于“待我处理”，Agent 最近进展作为对应事项的摘要，不额外堆出一个 Agent 看板。

“待我处理”每条在折叠态回答：哪个客户、想解决什么、为什么现在需要我、已经准备了什么、需要我作哪个决定。展开后展示来源与更新时间、推断及待核实项、可选动作、协作依赖和下一次核验条件。

“推进中”区分 Agent 执行、等待客户、等待同事、受阻和已暂停；没有需要本人介入的等待项不挤占今日处理容量。暂停项保留原因、恢复条件与恢复入口，达到核验条件时提示重新评估；本人手动暂停的委派须主动恢复后继续执行。“已结束”提供结果证据与历史，已解决与已终止分别筛选、计数，不把已发送消息当作解决依据。新事实需要继续处理时，可从结束历史重开原事项并保留原结果记录。

保留容量机制，但容量是今日普通事项的总预算，不是同时显示条数：处理一条后，不自动从候选池无限补入。额外普通事项由用户主动领取；新出现的真实紧急事项可突破容量，必须标明新增原因。紧急事项过多时显示超出承接能力，并提供协调负责人或升级的入口，不能把所有事情继续包装为可按时完成。

“全部客户”的搜索、排序、分页、分层筛选、资料完整度和补全入口继续保留。它与事项清单共享客户上下文，不复制第二份客户档案。

### 客户作战卡的四个页签

| 页签 | 增补内容 |
| --- | --- |
| 概况 | 客户经营目标、已确认需求与未知项、当前未兑现承诺、关键机会及问题；AI 判断保留可核对依据与适用条件 |
| 沟通 | 已有沟通时间线中关联客户响应、承诺变化和来源消息；草稿、待发、发送成功与客户回应分别显示 |
| 档案 | 沿用逐项采纳、冲突对照和来源保留；已有客户网站等服务入口及用途可在此登记，缺少数据时不显示虚构表现 |
| 计划 | 目标事项、下一步、执行人、Agent 进展、等待条件和核验时间；按来源跳转协作模块，允许暂停和调整安排 |

网站经营表现与经验复盘放在相关客户或周期复盘中，按需展开，避免首屏增加大量新卡片。

## 5. 事项、行动与结果分别记什么

一个客户事项代表一个需要持续追踪的目标，例如“确认此次样品是否满足客户要求”或“处理交期变化对客户备货的影响”。电话、邮件、查询库存、提交设计需求等是为它服务的行动。沿用现有客户事项和行动模型承接；本增补不要求另建平行任务体系。

事项至少能表达“待处理、推进中、等待、待决策、受阻、已暂停、已解决、已终止”；行动记录实际执行情况、来源、执行人及结果。展示视图按第 4 节映射，不额外建立“等待”或“暂停”页面。事项可跨日持续，次日排程引用原事项而非重新生成副本；同一事件的重复通知不重复建项，新事实或不同目标则可关联新增。

| 当前登记选项 | 增补语义与后续 |
| --- | --- |
| 已联系，等回复 | 记录本次联系；事项进入等待，保留约定或合理的核验条件。默认 3 天仅可作为建议，不自动再次发送 |
| 约了下次联系 | 保存约定时间与下一步；事项仍在进行，只有安排已完成 |
| 客户暂无需求 | 按范围暂停或终止本次机会，记录客户反馈与恢复条件；不计为成交或服务问题解决，也不屏蔽该客户其他紧急事项 |
| 已在其他渠道处理 | 关联已有记录，或以最少输入补记渠道与实际结果；仅“已处理”不足以自动宣告解决 |
| 建议不准 | 收集纠错并撤下失效建议；客户的真实问题可能仍存在，应保留或重新评估该事项 |
| 明天再说 | 调整下次处理时间，保留原承诺期限；若已影响承诺，应继续显示逾期或风险 |

补充与事项相符的结果，例如需求已确认、报价已确认、样品反馈已取得、客户接受替代方案、订单已产生、异常已解决。结果优先关联已有消息或业务记录，只有缺失信息才请求简短补记。

“已解决”要求符合该事项的具体目标并有证据。材料准备完毕、动作发送成功、客户接受方案、实际交付完成可能是四个不同进展，不能互相替代。终止事项单列原因，不增加解决数或成交数。来源撤回、客户提出新异议时，提示重新评估或重开，不继续展示过期的成功结果。

撤销只回退可撤销的登记，不撤销真实已发送消息、已创建订单或其他外部事实；关联后续动作已经执行时，应展示已发生的进展并按既有纠正流程处理。

## 6. Agent 承接与双向变化

用户可以针对明确客户和事项委派目标，例如“核实这次补货的可供方案，准备沟通稿，客户回复后继续整理下一步”。复用已授权范围，持续显示已完成工作、正在等待的条件、阻碍和需人工决定的内容。暂停或终止委派可阻止新的动作，不掩盖已经发生的执行结果。

查询、比对、研究、方案准备与草稿生成可按既有权限推进；发送、报价、样品政策、订单和新的交期承诺遵循现有授权机制。历史订单与价格可以用于上下文，但历史价格不自动成为当前报价；原型中的“7 天发货”“免费样品”“DHL 5–7 天”等话术，落地时必须有适用于当前交易的有效依据。依据缺失或已变化时，先核实并展示缺口。

从公司到客户：关联库存、政策、产品、物流变化与客户已确认需求及承诺。从客户到公司：关联新的要求、反馈与问题，并由对应责任人或 Agent 推进。只有影响当前事项的变化进入重点清单，避免把所有动态变成通知。

每日 08:00 的统一分层与普通清单重算可以保留；新询盘、客户回复、已承诺事项的紧急变化不能等待次日才进入处理。不同来源保留各自更新时间，未接通或失效的来源显示“尚未接入 / 待核实”，不能显示为“没有变化”。

“网站查库存”“进入复购窗口”“长期未回复”属于行为事实或推断线索，不等于确认需求、流失或预计订单。持续跟进要尊重客户约定和沟通偏好，允许保持等待，不因没有回复自动追加推销。

## 7. 客户服务资产与经验积累

客户网站、选品页、采购入口、素材服务等，按“正在为哪个客户解决什么问题”纳入客户上下文。可以记录入口、服务用途、负责人和已知问题；只有接入可靠数据后，才展示实际使用、下单障碍和服务结果。建站数量与浏览次数不能替代服务价值，网站创建与运维平台不纳入本轮。

经验积累保留“当时事实—判断理由—采取动作—客户反馈—实际结果—适用条件”。先关联现有业务记录减少补录，再提出可复用方法；保留未成功案例和反例。单次成功或用户点击“准”不自动成为有效方法，也不自动改写全员策略。

业务员需要看到自己的经营贡献。客户自助下单、同事协作、Agent 执行的贡献如何认定，沿用公司现有客户归属与业绩规则；规则无法判定时明确标识待核实，不能由模型推定或因新增入口改变提成。涉及制度变更另行决定，不夹带在本次页面设计里。

## 8. 反馈与评价口径

| 层次 | 记录什么 | 不等同于什么 |
| --- | --- | --- |
| 事实反馈 | 哪条事实正确或错误、纠错依据 | 模型整体准确率、销售能力 |
| 建议适用性 | 当前是否有用、不适用的具体原因 | 是否愿意使用 AI |
| 行动采纳 | 同一建议是否实际用于行动；不能只用“准”按钮代替 | 建议正确、客户接受 |
| 执行质量 | 是否成功执行、事实错误、返工、可核验的节省时间 | 业务收益或客户问题解决 |
| 经营结果 | 客户回应、需求确认、承诺兑现、实际订单及复购 | 这些结果全部由 Agent 带来的增量 |

质量与采纳数据用于改善系统，不默认成为个人绩效。统计限定时间范围、可评价样本及口径，同一建议重复反馈不重复计数；待观察样本单列。采纳率若保留，应使用明确记录的采纳与未采纳决策计算，并显示样本量，不能混入准确性投票。

试点先衡量处理时间、客户等待、事实错误、返工与承诺兑现；订单、复购和服务容量在真实业务周期内观察，并与同类客户/任务的原方式比较。未经对照不把订单额直接标为“AI 创收”。

## 9. 后续原型与落地顺序

第一步，沿当前结构修正语义并跑通一个完整事项：调整今日清单名称、拆开处理/等待/解决、修正反馈口径，在四页签中呈现事项证据、责任和下一步。用虚构数据演示一次交期变化：识别受影响客户 → 核实源状态 → 准备方案 → 业务员决定 → 跟单执行与客户响应 → 按证据分别完成行动及解决事项。演示增加全员工作台摘要的对应关系即可，不建设另一套全员首页。

第二步，用已有客户经营、订单、物流、协作与 Agent 能力验证实际链路，包括来源覆盖、持续执行、跨日等待、结果回写和权限。未启用的后台能力不能通过一条“正在持续跟进”文案伪装成运行中。

客户网站效果与经验复用在有可靠来源、持续使用和结果证据后逐步纳入。全市场获客、新建网站平台、预测提成、统一重做其他岗位工作台均不属于本轮补充范围。

## 10. 验收场景

| 场景 | 应观察到的结果 |
| --- | --- |
| 业务员从全员工作台进入某客户事项 | 打开同一个客户作战卡与事项；一次登记即可同步两处进展 |
| 设计人员查看明日交付任务 | 进入设计模块，看见必要要求；不套用复购排序，不因客户金额小降低已承诺期限的优先级，不泄露无权查看的价格或沟通 |
| 同一交期事件同时需要解释与协调 | 业务员沟通、跟单协调分别更新；任何一个完成都不会自动关闭另一个或伪造物流状态 |
| 点击“已联系，等回复”，次日再次打开 | 今日处理数可变化，事项仍在“推进中”的等待状态，有下一次核验；不新增重复事项、不计已解决、不自动催促 |
| 客户暂无需求或建议不准 | 可暂停/终止该机会或撤下建议；暂停项在“推进中”保留恢复入口，终止项在“已结束”单独筛选，其他客户承诺继续可见；不增加成交或问题解决数 |
| 用户认为判断准确，但决定暂不执行 | 准确反馈与采纳分别记录，不迫使用户接受建议；重复点击不重复统计 |
| 普通事项达到今日容量后处理一条 | 候选事项不无限补位；用户可主动增加，新紧急事项另行说明；超负荷时可以协调或升级 |
| 收到客户回复、新订单或交期变化 | 关联原事项并核对影响，失效草稿需更新；重要变化及时呈现，不等次日分层重算 |
| 没有客户库存/销售或网站使用数据 | 明确未知；不把复购推算、网页访问当作确认采购，不展示虚构收益或使用率 |
| 客户转交、权限变化或来源失效 | 摘要和深链重新校验，未执行动作暂停核验；只展示当前可访问、有效的上下文 |
| 用户撤销登记或暂停 Agent | 可逆登记正确回退，外部已执行事实保留；不重复发送或静默删除已经发生的结果 |
| AI 引用旧订单价格或提出当前交期 | 能区分历史事实和当前承诺，当前条件有可核验依据；缺证据时显示待核实 |

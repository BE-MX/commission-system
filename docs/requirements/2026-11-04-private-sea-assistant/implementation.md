# 私海助理开发说明 · 从离线评测到两人试点

版本 1.0 · 基于 2026-11-04 产品设计 v0.2 · 开发交接稿

2026-11-04 已完成本地实现，实际验证、配置与待试点内容见[实现与验证记录](implementation-status.md)。下文保留开发阶段的设计依据。

一天的主链路是业务员看到待跟客户，核对资料，把草稿带到 WhatsApp，亲自发出。另一路是打开档案、补充自己掌握的信息。两者共用同一个私海范围和同一套证据。P0 先检验名单的质量，P1 才建设线上链路。当前交付是技术规格和交互样机。

## 1. 代码落点与依赖

以下“拟建”项是工作包。在每个阶段的退出条件满足后再开启下一阶段。

| 模块 | 实施落点 | 输入 → 输出与职责 |
|---|---|---|
| 范围与数据读取 | 拟建 `backend/app/client_desk/private_scope.py`、资料查询 service | 当前用户 → OKKI 归属、个人客户键、授权后的订单/背调/会话，支持批量读取 |
| 扫描与排序 | 拟建 client_desk 规则与日历函数 | 单一北京时间快照、规则配置、全私海 → 所有命中的客户、规则明细、排名、实验组、可运行队列 |
| 模型与校验 | 拟建资料包构造器、执行器、校验器、`protocol/desk_v1.md` | 单客户输入 → 通过验证的画像与建议，或可解释的规则降级 |

### 1.1 现有代码与设计稿中的简称

* `invoice/xiaoman_service.resolve_okki_user_id` 解析本人。先拒绝未绑定，绝不把空 owner 传给表示「不限制归属」的查询。`invoice/customer_picker_service._effective_customers` 已处理 overlay 与镜像新旧、owner 数组和显式 collation。抽中立公共查询时让发票调用同一实现，迁移前后用相同输入比对结果，全局检索旧引用。
* 详情实时复核在 `invoice/customer_picker_service.check_availability`。它先查有效列表，再调用 OKKI；只有 active 且 owner 匹配才显示。转出或不存在统一 404，远端暂不可核验返回可重试的 503，清空上一客户的可见详情。`invoice/customer_profile_service` 只负责等级的 get/save。客户键在领域内用 BIGINT，传发票服务时用十进制字符串。
* 金额、笔数用 `order_intelligence/service.py::VALID_ORDER_SQL`，保持其订单别名与商品单过滤；以订单主表去重后汇总，明细独立聚合产品频次。样品识别与「未取消」「在途」不是这段 SQL 能完整表达的条件，P0 先用业务确认的样品和各状态样例校准。未知订单状态或样品分类影响判定时，R5 不触发，报表显示资料缺口。
* 背调先取 active、verified、strong、唯一匹配的 OKKI company_id 外部身份，再用 `customer/logical_customer_service.logical_owner_expression` 解析逻辑归属，只读 `ark_customer_research_tasks.result_json` 中审核 accepted / not_required 的结果。经 `customer/access_service.py` 的可见性和分级约束；无唯一映射、不可见或无合格结果时返回空摘要，数据不入模型。
* `whatsapp/access.py::readable_accounts` 提供 SQL 范围。为正文读取增加专用 client_desk 用途的 live 权限校验，现有 `require_body(crm=True)` 绑定旧 customer 权限，不能直接借权。展示需 active + CRM + 所有人/有效正文授权，模型还需 AI 出境；账号状态、员工状态都须有效。改关联限账号本人，获得正文授权不授予改关联权。
* `whatsapp/derived_access.py` 是派生文本整体隐藏的参考。另建本域指纹比对，覆盖模型调用前、回写前、列表/详情读取和早报组装。记录所有输入的来源依赖，含从上一版画像继承的依赖；账号版本、正文授权、关联、撤回或背调可见性变化时，关联的草稿、画像、等级建议、引用和可复制文本一并隐藏。上一版也有独立依赖，不能作为绕过校验的回退。
* `battle_report/pace.py` 仅支持活动日期，薪资月度天数不能做日期偏移。U6 先核是否有覆盖试点区间的全平台逐日日历；无则提供版本化年度休假/调休上班清单。北京日界，先匹配调班/假日，再算常规周一至五。跨年缺配置时阻断受影响的工作日计算并告警。

### 1.2 读取与关联

按当前账号先筛有效会话，再 join 活跃关联和本人私海。群聊、撤回消息、无有效消息的会话不进分析。不要直接拿会话表可能滞后的 last_message_preview 构建待回数；在有效消息里按业务发生时间、稳定消息键确定最后方向。时间相同也必须得到稳定结果。资料包和时间轴展开走同一来源访问检查。

历史导入限账号本人、仍有效的旧绑定以及明确的公司映射。冲突和缺映射留给「未关联会话」。P0 补充对照表仅存在隔离评测目录；P1 只在新关联表写。首次导入记录批次完成标记，重复导入不能恢复用户后来撤销的关联。新会话仅按联系人名预填搜索，用户选定目标客户后才生效。撤销、忽略、改绑后刷新两侧客户的 last_touch、派生内容及待回数。

最近接触只合并关联的有效 WhatsApp 收发、本人手工跟进。订单和背调各有活动时间，不冒充沟通。共同归属的联系人之间只共享发票等级。按最近一次**归属人自己账号**的出站确定当日建议接收人，时间并列用稳定的用户键；其他人只能读自己的个人状态。均无出站时分别评估。调度内部只处理各归属人本人已获授权的最小出站时间信号。若必要信号缺权或覆盖不明，各人独立评估并记录仲裁降级；不能为去重跨账户读聊天或随机压掉提醒。响应不透露他人的聊天或候选原因。

## 2. 候选计算

06:30 按试点名单读取全量私海；每人按批拉取订单、等级、最近接触与有效会话，避免列表或规则逐行查库。每个公司保留所有命中项；一个客户每天一条例行候选。北京业务日、可见来源截止时间、规则/日历版本和实验版本进入快照。

| 规则 | 触发边界 | 权重及例外 |
|---|---|---|
| R1_UNREPLIED | 任一已关联会话最后有效消息是入站，其后无出站。无需满若干小时 | 6；等待更久优先；08:40、今日列表和详情打开时重新计算 |
| R7_AWAITING_CUSTOMER | 已关联会话最后是我方出站，客户超过 N 个完整工作日未回复 | 4；S/A=3、B=5、其余=7。刚满 N 仍不触发 |
| R2_FOLLOWUP_DUE | 本人 next_followup_date 非空且 ≤ 今日 | 4；包括「稍后」到期 |
| R3_RECHECK_DUE | 到期并有具体待确认事项 | 3；存活动水位，连续两次无新活动后停止排期 |
| R8_NEW_LEAD | 建档 ≤30 个自然日，无有效订单，最近 7 个工作日无可见接触 | 3；含未分级询盘，文案限定方舟可见渠道 |
| R5_REPURCHASE | 至少 3 笔非样品有效订单；平均间隔取按日排序的相邻间隔之和 ÷ (笔数−1)；今天距最后未取消单严格大于 1.3 倍均值，且无在途 | 3；同日扎堆使均值为 0 时不推断复购周期；12/20～1/5 降权 |
| R6_LONG_SILENT | 有已关联 WA；S/A 超 15、B 超 30 个工作日无可见接触 | 2；节假日降权。可见记录不足，展示覆盖缺口 |
| R4_NEW_ACTIVITY | 上次分析之后新增订单或合格背调 | 无提醒分；只用剩余名额更新画像，不单独进早报 |

计算顺序如下。

1. 到期前的 snooze 挡住该客户所有规则，含 R4；到期进入 R2。其余按本人×客户×规则冷却。done 从跟进时起 7 天、useless 14 天，skip 到约定复查日期且冷却不超过 14 天。冻结决定时的命中码，以北京时间记录截止，边界日重新参选。
2. 将有效规则权重求和，再乘分级系数 S/A/B/C/D/E/未分级 = 1.8/1.5/1.2/1/0.8/0.6/1。降权只作用于对应规则。季节降权倍数原设计未定，作为 P0 可比较参数记录，进入试点前冻结。平分先按 R1 等待时长，再按 company_id，重跑结果稳定。
3. D7 仅对只命中 R5/R6 提醒的客户随机留出 15%；R4 伴随更新不改变资格，任何其他提醒（含 R3）优先跟进。用试验版本、用户和客户的稳定哈希分桶；新增待回复等强信号立即解除当日隐藏，记录原因。留出不占报告位，试验期间不在今日、全部列表、详情或规则兜底泄露实验提醒；仍可按正常业务查看档案。
4. 保存全候选和分桶后分配 40 个例行分析名额；R4 在提醒分配后补空。超额只展示规则，标「未做 AI 分析」，不入模型队列。手动分析单列 run_seq 与成本。降级条目仍可见；成功建议按 high/medium/low，再按规则分。skip 不进早报。每人最多 10 个，R4 不补早报名额。
5. 实时复核删除已经失效的 R1。若仍有独立原因，按剩余规则重算；旧文案、草稿凡含已失效原因即退回规则展示。不能沿用已经过时的报价追问。日间新增消息以新鲜状态显示，不增加第二封早报。

## 3. 一次分析的执行合同

**输入。** 固定 `desk_v1`，按任务日期与命中规则、本人维护项、有效上次画像、两种口径的订单摘要、客户卡、背调、近端 WA 消息组织。每个客户一次，硬上限 24,000 字符（含围栏和提示正文的预算在构造器统一计数）；先裁最旧原文，然后裁低优先级可选条目。必需摘要超限则确定性失败。最终生成 refs 字典，只允许引用实际留下的 O-/S-/M- 编号；手工到期而无上述来源时，协议增加本次可核验的跟进/规则证据键（实施建议，冻结协议前测此路径）。不能为了满足引用要求伪造订单或消息。

**信任边界。** 系统指令由本地版本化协议生成。外部控制的名称、文本、来源、发送者及字符串字段逐项转义围栏；上一版 AI 输出也作为资料。金额等确定性汇总与业务员备注分别标明作者。模型供应商与 preset 均须在允许范围；使用与 WhatsApp assistant 相同的 metadata 日志模式，模型请求前释放事务锁。业务日志仅记录 ID、耗时、token、状态、错误码；不记录客户、聊天正文、草稿、号码或签名链接。

| RESULT_JSON 路径 | 约束及回写 |
|---|---|
| brief_md | ≤600 字，按“是谁、买什么、如何决策、当前状况”组织；保存前一版及其指纹。渲染前 sanitize Markdown，禁危险链接 |
| suggestion.priority / reason / strategy | 枚举 high / medium / low / skip；原因 ≤60 字、策略 ≤150 字；skip 必须说明原因并有复查 |
| check_before_reply / talking_points / draft_message | 先查清单、最多 3 个要点、客户语言草稿。用 [价格]、[到货日] 等占位。项目禁用词同样生效 |
| suggestion.cites | ≥1 个本包内编号；详情按该客户当前 ACL 解析到原事件，不回显失权来源 |
| recheck | 可空；若存在必须有可验证条件，日期今天之后且 ≤30 个自然日。连续无新活动的停止规则由代码强制执行 |
| grade_hint | 可空；非空含值、≤60 字原因及有效引用。值域由运行时配置/字典注入且受发票 S～E 限制。用户采纳时重验；禁止自动写分级 |

严格解析 JSON（禁额外键），在同一校验器里检查长度、枚举、日期、引用、陌生 URL/邮箱/电话/银行与收款账号。草稿或策略出现包中不存在的此类值即拒绝；金额、折扣、库存承诺、交期按英/西/法/葡词例标 needs_review 并提示核对。硬拒绝优先于风险标记。有明确无效输出可纠正一次，仍错转 rule_only；不确定结果直接 ambiguous，绝不后台重发。模型产生的字段通过白名单映射，不能成为表名、权限或写操作。

## 4. 执行顺序与退出条件

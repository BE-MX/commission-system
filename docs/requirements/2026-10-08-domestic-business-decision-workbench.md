# 内贸经营决策台 — 功能设计文档

日期：2026-10-08

版本：V1.0（功能设计稿）

状态：已据此进行本地开发；生产未部署。实现范围、调整与验证见[实施与验收](2026-10-08-domestic-decision-implementation.md)。本文仍是功能基线，不表示生产数据已核验。

依据：本次需求与当前仓库代码。未连接生产数据库，未核验实际样本量、字段覆盖率或线上版本。本文所有案例数字均为演示，所有预警阈值均为建议初值。

## 1. 产品定位与目标

在内贸业务中，将订单、产品规格、客户资金和客户经营行为放在同一个分析工作台，帮助业务员回答三个问题：**发生了什么、可能为什么、下一步联系谁或调整什么**。

目标不是展示尽可能多的图，而是让业务员在几分钟内完成以下决策：

1. 找到最近需求增长、需求下降、即将复购或需要核对余额的客户。
2. 看清工艺、发色、网帽颜色、数量、尺码、发长、发量、发型系列的需求及组合变化。
3. 判断充值是否持续、余额是否闲置、信用客户欠款是否扩大，以及这些变化与下单节奏的关系。
4. 了解客户偏好与业务员的客户组合，形成可解释的客户服务、产品推荐和带教建议。
5. 把分析变为可跟进的行动，记录实际结果，持续检验建议是否有用。

### 1.1 设计原则

- **事实先于推断**：金额、数量、周期由程序计算；AI 负责解释、提出待验证假设和组织建议。
- **全程可追溯**：指标 → 分组 → 客户/产品 → 订单明细或资金流水，筛选、时间和权限保持一致。
- **订单与资金分账分析**：订单额衡量下单需求，充值额衡量平台已入账充值，余额衡量账户状态；三者不能相加成营业额。
- **角色优先**：业务员先看到自己可行动的客户；主管先看到团队结构与异常；财务先看到资金核对。
- **多维但不拥挤**：首屏展示核心指标与三至五条重点，复杂分析在专题和交叉分析中展开。
- **渐进启用**：有数据先做事实分析；证据不足的预测明确不可用，不用 AI 补造历史。

### 1.2 边界

本设计包含分析、画像、解释、建议、分析视图保存、内部行动记录和导出。充值、审核、调价、客户转移、发货仍在原业务模块执行。

不将以下能力默认纳入首期：自动充值/改价/改会员、自动发送客户消息、自动生产采购、员工绩效结算、完整成本利润核算、广告 ROI、全行业市场份额、无证据的流失概率。后续接入相应数据和授权后另行建设。

“市场趋势”首期明确命名为 **本公司内贸成交需求趋势**。公司的成交客户样本不能代表整个市场；门店采购不等于门店终端动销或消费者偏好。

## 2. 当前基础与需要补齐的数据

### 2.1 仓库已具备的基础

| 数据对象 | 已有字段/行为 | 可支撑功能 | 必须处理的限制 |
| --- | --- | --- | --- |
| 订单 `ark_domestic_orders` | 业务/生产单、客户、下单日期、类别、类型、渠道、状态、金额、扣款额、创建人 | 订单趋势、渠道、类别、下单行为 | 生产单金额为零，不能纳入销售；创建人不一定等于客户归属销售 |
| 明细 `ark_domestic_order_items` | 属性快照、数量、成交价、原价、优惠、手工费、定价版本、会员快照、发色文字、发货时间 | 规格偏好、价格结构、需求组合 | 快照可被业务编辑；明细可删除，不能据当前行恢复所有历史状态 |
| 产品 `ark_domestic_products` | 头套/发片、工艺、网底色、尺码、发长、发量、发型系列 | 属性字典与当前产品查询 | 历史分析以明细快照为准，不能用当前产品资料覆盖历史 |
| 客户 `ark_domestic_customers` | 店名、省市、来源、门店类型、等级、生命周期、负责人、结算方式、余额、会员 | 客户分层与地域结构 | 累计销售额/订单数含历史档案字段，不能与订单事实直接相加 |
| 客户账本 `ark_domestic_customer_ledger` | 类型、有符号金额、变更前后余额、订单、操作人、幂等键、时间 | 充值、扣款、退款、账户桥接 | 正向入账还包含退款/初始化/调整，不能全部算充值 |
| 资金申请 `ark_domestic_customer_requests` | 充值/调整、审核状态、申请/审核人和时间、凭证、业务键 | 申请待办、审核时效、入账核对 | 待审核不等于到账；通过后与账本关联不得重复统计 |
| 报工与逐件记录 | 工序、数量、路线、生产状态等 | 履约异常上下文 | 报工数量不是销售件数；先验证发货粒度后再推交付分析 |
| 现有外贸经营分析 | 总览、多维筛选、人员/客户分析、AI 后台简报 | 复用交互模式和经核验的基础设施 | 依赖 OKKI 外贸来源、币种和身份，不能直接套用数据口径 |

代码核对另发现：客户支持 `prepay` 和 `credit`，信用客户可负余额；会员级别按最近一次成功充值金额重新确定，也可人工调整。不能把会员等级当作客户累计价值或稳定支付能力。

### 2.2 上线前数据体检与启用条件

只读体检按月、业务员、产品类型分别输出：

- 覆盖起止日期、完整历史覆盖起点、订单/明细/客户/账本数量和最新更新时间。
- 订单主表金额与有效明细合计差额、订单扣款与流水净扣款差额。
- 账本连续性、当前余额与期末账本余额差额、重复业务键、孤立关联。
- 订单属性、发色、省市、客户来源、负责人、下单日期、渠道覆盖率。
- 生产单、零价单、售后重做、草稿、待审核、终止、删除等数量。
- 同店异名、同名不同实体等疑似客户身份问题，仅进入人工核对，不自动合并。

启用门槛：金额核对样本必须逐分一致；账本无法桥接的客户标记“资金待核对”，不生成余额预测。非核心维度可以带缺失比例上线；某维度已知覆盖率低于 80% 时默认不输出该维度强建议。80% 是建议门槛，管理员配置留版本。

### 2.3 数据分层

| 层级 | 内容 | 处理方式 |
| --- | --- | --- |
| 首期可直接使用 | 有效业务订单、数量、快照、充值账本、客户当前档案 | 数据体检和统一口径后启用 |
| 首期必须补齐 | 分析权限、指标注册、数据质量信息、分析快照元数据、颜色标准映射、行动记录 | 本功能建设，不反改原始订单 |
| 必须从上线起采集 | 正式生效及变更事件、金额/属性版本、归属/团队变更、会员/结算方式变更 | 保障未来历史回看与稳定归因；旧历史缺失明确标注 |
| 条件启用 | 发货及时率、历史会员迁移、实际银行到账日、产品推荐、短期预测 | 数据达到验收门槛才展示 |
| 后续外部数据 | 线索/报价、真实库存、成本、售后原因、推广投入、外部市场数据 | 独立接入和身份匹配后扩展 |

## 3. 使用角色与关键场景

| 角色 | 进入页面最需要的答案 | 主要动作 |
| --- | --- | --- |
| 内贸业务员 | 我的哪些客户该联系、该谈什么产品、是否需要充值/账务核对 | 打开画像、查看证据、创建跟进、登记结果 |
| 内贸主管 | 增长来自哪里、客户结构是否集中、团队哪类经营动作不足 | 比较业务员、查看细分需求、安排带教和跟进 |
| 产品/生产协同人员 | 哪类规格需求持续增加、特单需求在哪里集中 | 看授权的汇总、查看需求组合和履约关联 |
| 财务/审核人员 | 已入账充值、待审核申请、欠款和调整是否异常 | 下钻账本、进入原审核/核对页面 |
| 管理员 | 数据是否可信、规则是否合适、权限是否正确 | 维护映射/门槛、查质量与审计 |

典型路径：

1. **每日客户经营**：打开“我的总览” → 查看复购到期与资金提醒 → 进入客户画像 → 核对常购规格和近期订单 → 记录联系计划。
2. **每周产品复盘**：打开“订单与产品” → 对比近 28 天与前 28 天 → 选择头套 → 查看工艺 × 发长热力图 → 区分大客户集中采购和多客户普遍增长。
3. **月度主管复盘**：查看需求、充值和客户留存 → 按门店类型、区域、客户规模分组比较 → 判断人员客户组合变化 → 形成有证据的经营简报。

## 4. 信息架构与页面组织

入口：内贸业务菜单下新增“经营决策台”，建议路由 `/domestic/decision`。

采用一个工作台和七个页签，不新建七套互不相通的报表：

| 页签 | 核心问题 | 主要模块 |
| --- | --- | --- |
| 经营总览 | 当前状况与优先行动 | 六项核心指标、趋势、贡献拆解、重点客户、洞察 |
| 订单与产品 | 买什么、怎么买、结构如何变 | 金额/数量/订单、属性分布、交叉分析、产品组合、价格 |
| 充值与资金 | 钱何时进来、如何消耗、哪里需要核对 | 充值趋势、余额桥接、申请审核、预存/欠款、充值后行为 |
| 客户经营 | 客户是谁、偏好什么、下一步做什么 | 分群、RFM、客户列表、客户 360° 画像、生命周期 |
| 业务员画像 | 经营结构与可改进之处 | 自身变化、客户组合、复购/激活、资金经营、带教 |
| 需求趋势 | 哪些结构变化值得验证 | 地区/来源、增长组合、扩散度、季节性、条件预测 |
| 行动与简报 | 建议是否执行、是否有结果 | 待办、规则/AI建议、周月简报、采纳与结果 |

“数据口径与质量”始终可从页头进入。数据范围、业务时间、生成时间、样本量、质量提示放在用户可见位置。

### 4.1 全局筛选

基础层默认展示：时间区间、比较周期、数据范围、业务员、客户、产品类型。高级筛选收起，包含省市、客户来源、门店类型、结算方式、会员、订单类别/类型/渠道及所有产品属性。

- 默认本月至今，提供近 7/28/90/180 天、本季度、本年、自定义。
- 对比默认上一等长期间；月初至今可选择上月同期；同比只有覆盖完整时可用。当前未结束日按已发生数据提示，不与完整日无提示比较。
- 同字段多选为 OR、不同字段为 AND；产品维度必须在**同一条明细**同时命中，不能“第一行命中颜色、第二行命中长度”合成一个命中。
- 选项来自范围内数据和字典；停用但历史存在的值仍可用于历史查询。
- 筛选条用可删除标签显示当前条件、结果量和“重置”。返回上页恢复图表选择、排序、页码和滚动位置。
- 保存个人视图：名称、指标、维度、筛选、时间是滚动/固定、排序；分享视图只分享条件，接收人重新鉴权查询。

### 4.2 产品筛选对订单与资金的影响

必须显式分成三种语义，不能让同一个数字悄悄换口径：

| 视图 | 定义 | 界面名称 |
| --- | --- | --- |
| 匹配明细 | 仅汇总所有条件同时命中的明细金额和件数 | 匹配产品金额 / 匹配件数 |
| 含匹配产品的整单 | 先匹配明细，订单 ID 去重后计算整单金额和单数 | 相关整单金额 / 相关订单数 |
| 相关客户资金 | 先按订单条件形成客户集合，再看这些客户的全部账户资金 | 相关客户充值 / 相关客户余额 |

示例：一单红色产品 1,000 元、黑色产品 2,000 元，筛红色时匹配产品金额 1,000 元，相关整单金额 3,000 元。该客户充值 5,000 元只显示“相关客户充值 5,000 元”，不能标成“红色产品充值”。

充值页默认不继承产品筛选。用户从产品页跳来时可明确开启“按相关客户分析资金”，显示客户圈选期与资金分析期；未开启时提示哪些产品条件未应用。客户风险以授权范围内的完整购买历史评估，不以被筛掉后的产品订单间隔判断客户整体流失。

### 4.3 下钻与比较

- 图表点击分组 → 过滤后的列表 → 订单/账本证据抽屉；面包屑记录分析路径。
- 支持至多 4 个客户/业务员/产品组合并排比较，保留同期、范围、分母和样本提示。
- 聚合人数与订单数去重，跨产品分组可能重叠；界面提示“分组不可直接相加”，总计独立重算。
- 金额、数量、占比、增速可切换；增速旁同时展示上期/本期绝对值，防止“小基数高增速”误导。

## 5. 统一指标口径

### 5.1 统计粒度、时间与状态

| 分析对象 | 唯一粒度 | 默认时间 |
| --- | --- | --- |
| 订单 | `order_id` | `order_date` 下单日 |
| 产品需求 | `order_item_id` | 所属订单下单日 |
| 客户 | `customer_id`，当前业务实体为门店 | 截止日 + 指定观察窗口 |
| 充值/资金 | `ledger_id` | `ledger.created_at` 入账时间 |
| 资金申请 | `request_id` | 申请时间；审核耗时使用审核时间 |
| 发货 | 经核验的发货事件/明细 | 实际发货时间，与下单趋势分开 |
| 业务员 | `ark_user_id` + 明确归因方式 | 与对应事实时间一致 |

所有业务时间统一北京时间，日期区间在接口转为 `[开始日00:00, 结束日次日00:00)`；按日/月补零仅适用于已确认覆盖区间，未接入期间显示“无历史覆盖”。

**默认有效经营订单**：`order_kind=business AND deleted_flag=0 AND status IN (1,2,3)`。草稿 0、终止 4、待审核 5、驳回 6 单独展示；生产单独立作为生产需求，不混入经营指标。现有 `ORDER_INACTIVE_STATUSES` 未排除终止，不能直接拿它当本决策台有效订单条件。

有效订单中的免费补单、售后重做仍有真实生产需求：订单与产品页保留并拆分“有偿需求 / 零价需求 / 售后重做”。客户复购、RFM 和常规购买周期默认只用正金额且排除售后重做的商业购买订单；订单类型取运行时字典及明确的语义映射，不让 AI 猜哪些类型是售后。

### 5.2 当前重算与历史快照

现有订单和明细会被改单、删行、终止，日期也可能补录，因此首期历史订单报表为 **“截至本次刷新，按当前有效状态重算所选下单期间”**。后续改单可以改变旧月份数字。

- 原始正式生效额、某个历史日期的完整在手订单、历史退单率，不能仅凭当前表准确还原。
- 账本事件按真实入账日期展示；十月终止九月订单，当前重算会影响九月有效订单额，退款资金事件发生在十月，两者差异正常。
- 上线起补采正式生效、改价、增减数量/明细、终止、删除及归属变更事件，记录 before/after、事件时间、业务日期、操作人和稳定 ID；删除明细前保存快照。
- 事件与原业务变更同事务落库；后续聚合可异步。不能只靠定时扫描 `updated_at` 捕获已删除数据或多次中间变化。
- 基线以首次完整只读抽取时间建立；旧数据只能生成“基线当时状态”，不能伪装成历史事件。
- 保存简报包含数据版本和结果快照，旧简报固定展示当时数字；“按最新数据重算”生成新版本。

历史 `as_of` 画像只有在事件/快照覆盖期内才启用真正时点回看。覆盖之前可以查看“历史期间、当前重算”的订单事实和已有账本，不展示当时会员/负责人/余额预测等无法验证的时点状态。

### 5.3 核心订单指标

| 指标 | 公式或定义 | 注意事项 |
| --- | --- | --- |
| 有效订单金额 | 有效订单 `total_amount` 求和 | 下单需求额，不命名为财务收入 |
| 订单数 | 有效订单 ID 去重 | 列出零价/售后占比 |
| 下单件数 | 有效明细 `SUM(order_qty)` | 不是明细行数、报工数或逐件码行数 |
| 下单客户数 | 有效订单客户 ID 去重 | 门店数，不是终端顾客人数 |
| 订单均额 | 有效订单金额 / 有效订单数 | 默认含有效零价单；可切有偿口径但需改名称 |
| 加权成交单价 | 匹配明细成交金额 / 匹配件数 | 不能平均各行单价；跨规格值称“混合单价” |
| 件单量 | 有效件数 / 有效订单数 | 件数增长与订单频率增长分开 |
| 明细成交金额 | `SUM(unit_price × order_qty)` | `unit_price` 已含手工费，不重复相加 |
| 手工费金额 | `SUM(labor_fee × order_qty)` | 验证历史计价版本后启用 |
| 原价优惠金额 | `SUM(discount_amount × order_qty)` | 仅有可信原价的明细；特单/旧手工定价单独列 |
| 人工价偏离 | `SUM((unit_price-labor_fee-default_discount_price) × order_qty)` | 默认优惠价快照非空才可算，负值表示更低 |
| 活跃客户贡献 | 本期各客户金额与份额 | 可分新增、持续复购、回流、减少下单 |
| 客户集中度 | Top1/Top5/Top10 客户金额 / 总金额 | 分母为正才展示 |
| 同比/环比 | `(本期-对比期)/对比期` | 对比期为 0 显示“新增/无基数”；负基数不常规计算增速 |
| 份额变化 | 本期份额 - 上期份额 | 单位是百分点，不是百分比增长 |

主表与明细合计不符时：总览继续明确采用主表额，产品采用明细额，显示差异和待核对单数；不能无提示配平、按比例分摊或将差异塞进某产品。金额统一人民币、Decimal、两位小数；导出保留精度，不从“万元”显示值反算。

### 5.4 新客、复购、留存

- **系统首购客户**：授权且有覆盖的历史中首笔商业购买发生在本期。未掌握完整历史时称“系统首次记录客户”；客户历史档案已有更早购买证据时列“历史客户首次入系统”，不计真实新客。
- **复购订单**：本次商业购买之前存在另一笔商业购买，按 `(order_date, order_id)` 排序判断；人工订单类型仅作对照，不替代事实计算。
- **期间复购客户占比**：本期购买且此前存在购买的客户 / 本期购买客户；这是本期结构，不能解释为客户留存率。
- **30/60/90 天二购率**：首购 cohort 中观察窗口已完整结束的客户为分母；窗口内再次商业购买为分子。未成熟 cohort 灰显，不提前判未复购。
- **次月留存率**：首购月 cohort 中次自然月发生商业购买的客户 / 该 cohort 客户；月份未结束标“进行中”。
- **同日多单**：订单指标分别计数；周期模型合并为一个购买日，避免业务拆单制造零天补货周期。
- **回流客户**：本期购买前的空窗超过已有有效周期的 2 倍；无个体周期者用已公开的分群阈值或标样本不足，不能随意定义。

## 6. 经营总览

### 6.1 首屏

桌面布局建议：全局筛选 → 3 列 × 2 行指标 → 左侧订单/充值分开的小趋势图 + 右侧三条重点 → 下方客户机会与产品变化。

六项主指标：有效订单金额、下单件数、下单客户数、已入账充值额、预存余额合计、欠款余额合计。每卡含定义入口、变化、分母/样本、时间基准、数据是否完整。订单数、均额、复购、待审核申请作次级指标。

余额是时点存量，不能与充值期间流量使用同一种“合计”解释；余额卡比较两个时点且必须具备可核验历史账本。

### 6.2 经营变化解释

支持以下依次展开：

1. 金额变化来自件数还是混合单价。
2. 件数变化来自更多客户、更多订单，还是每单更多件。
3. 变化集中于哪几个客户、业务员、地区和规格组合。
4. 排除最大客户后变化是否仍存在。

数学分解使用固定、可重复的顺序，且仅对同一明细集合的成交金额执行 `明细金额=件数×混合单价`：两期件数均大于零时，数量贡献 `(Q1-Q0)×P0`，混合单价贡献 `Q1×(P1-P0)`，两项加总为明细金额差。明确后者含产品结构效应，不直接说涨价；同规格配对后才分析成交价变化。

总览订单主表金额与明细金额有差异时，另列“主明细核对差异变化”；`主表金额变化=明细金额变化+核对差异变化`，不能强行将差异归因给件数或价格。基期件数为零时整体列“新增需求”，本期件数为零时列“需求归零”，两期均零则无可分解需求；均不计算不存在的单价。

示例提示：“近 28 天下单件数增加 18%，其中两个客户贡献增量的 72%。建议先核实是否集中补货。”所有数字均须从当前证据生成，此处为演示。

### 6.3 默认行动队列

按“待核对资金异常 → 已确认交付风险 → 高价值客户复购异常 → 复购到期 → 产品推荐机会”分层显示，同一客户合并信号。资金不足不能覆盖已存在的待审核充值申请，应提示先处理申请。

主管可查看集中度和团队变化，业务员默认只看本人范围。总览不默认给人员打综合分或公开排名。

## 7. 订单与产品多维分析

### 7.1 维度字典

| 维度 | 来源与粒度 | 可看指标/图形 | 规则 |
| --- | --- | --- | --- |
| 产品类型 | 明细快照 `product_type` | 金额/件数趋势、占比条 | 头套与发片分开适用规则 |
| 工艺 | 快照 `craft` | 排名条、工艺×发长热力图 | 发片当前值混合工艺尺寸 |
| 网帽/网底颜色 | 快照 `net_color` | 类型内件数与结构 | 与头发颜色分开；发片不适用 |
| 头发颜色 | 明细 `color` + 标准映射 | 色系/色号、趋势、客户偏好 | 原文自由文本，首期保留未归类 |
| 下单数量 | 明细数量与订单总件数 | 分布、散点、件单量 | 数量既是指标也是分箱维度；订单/行分箱名称分开 |

| 具体发型/要求 | hairstyle、style_requirement | 检索、人工标签、需求主题 | 文本主题属推断；不从图片猜正式属性 |
| 普货/特单 | `order_category` | 金额/件数/客群交叉 | 区分标准需求与个性化需求 |
| 订单类型 | `order_type` | 首单/复购/返单/补单/售后 | 录入标签与计算复购并排显示 |
| 订单渠道 | `order_channel` | 各渠道成交结构 | 是本次下单触点，不等于获客来源 |
| 客户来源 | 客户档案 | 获客来源后的复购/充值 | 当前档案重分类需提示；不能据此算获客成本 |
| 区域 | 客户省市 | 排名、热力表、可选地图 | 客户经营地域，不推断终端消费者位置 |
| 门店类型/等级 | 客户档案 | 分群偏好、价格带 | 人工等级、系统分层、会员三个概念分开 |
| 会员/定价规则 | 明细快照与版本 | 优惠覆盖、价格分布 | 订单历史用快照，资金页当前会员另标 |
| 业务员/客户 | 明确的归因与范围 | 贡献、广度、集中度 | 不能用财务操作人归为销售业绩 |
| 时间 | 下单日、周、月、季度 | 趋势与季节性 | 发货/入账时间分别分析 |

每个维度的缺失状态至少区分 `已知 / 未填写 / 不适用 / 历史未采集 / 待归类`。`不适用` 不进入字段完整率分母，其他未知计入。维度覆盖率默认是“该维度已知的适用明细数 / 适用明细总数”，客户档案维度按客户数计算；金额/件数图另附金额/件数加权覆盖率，不用大量小单掩盖关键大单属性缺失。自动建议的80%门槛要求记录覆盖率与当前展示指标的加权覆盖率均达标。

### 7.2 发色与组合标准化

- 建立独立分析映射：原文、标准色号、色系、纯色/混色/挑染、映射来源、审核人、版本和生效时间。
- 原文永远可查，标准化只写分析层。别名由人工审核后生效；AI 只提交候选，不自动改变正式指标。
- 同一明细存在多个颜色时，默认用一个互斥的“颜色组合”统计金额/数量，保证加总可核对。
- “包含某色”是另一个标签视图，一条明细可以命中多色；显示重叠，禁止把各色金额相加当总额。不知道各色数量时不均摊。
- 网帽颜色独立于发色。图片未识别不猜颜色，发色缺失可显示“图片描述，未结构化”。
- 发片 craft 拆出工艺族/尺寸使用明确映射表。例如已批准的 `U型13*15` → U型、13*15；特单和未知保留复合原值。映射升级可以重算分析视图，但必须带版本，旧简报不被覆盖。

### 7.3 预置分析模板

| 模板 | 图形与指标 | 决策价值 |
| --- | --- | --- |
| 工艺 × 发长 | 热力图，件数/金额切换，带客户数 | 主力规格与需求空白 |
| 尺码 × 发长 | 热力图，头套与发片分别看 | 规格组合是否集中 |
| 工艺 × 发型系列 | 热力图，适用头套 | 造型与工艺的共现需求 |
| 发色 × 发型系列 | 热力图/排名表，已标准化样本 | 推荐色系和造型搭配 |
| 区域 × 产品组合 | 热力表，客户数和件数双证据 | 地域需求差异 |
| 门店类型 × 价格带 | 100% 堆叠条 + 样本量 | 不同客群的成交结构 |
| 客户 × 产品组合 | 偏好矩阵、Top3占比 | 常购款、试购后未续购 |
| 件数 × 加权单价 | 散点，气泡为客户数 | 规模款、高价小众款；不能当利润矩阵 |

### 7.4 价格与需求结构

- 以成交价带、同规格中位价和加权价分析，展示会员、定价规则与手工费拆分。
- 同规格价格比较必须固定产品属性、订单类别、会员快照/定价版本，剩余差异再标成“人工价偏离候选”。
- 价格降低后订单增长只能称同步变化；没有报价未成交样本与实验设计，不能证明价格弹性。
- 当前缺完整成本，不输出毛利、利润排行榜、“低利润客户”或利润最优价。
- 库存缺失时只提示“需求增加，建议核对库存与交期”，不给出确定采购量。

## 8. 充值与资金分析

### 8.1 两类客户分别解释

| 客户 | 正余额 | 负余额 | 主要分析 |
| --- | --- | --- | --- |
| 先充值后下单 `prepay` | 尚可使用的账户余额 | 按当前业务规则不应出现，进入核对 | 充值持续性、余额覆盖、充值后下单、闲置余额 |
| 先下单后付款 `credit` | 预付或多付余额 | 账户欠款 | 新增扣款、充值冲抵、欠款变化和持续时间 |

“充值”在信用客户中可能实质冲抵旧欠款；界面允许显示“充值/补款入账”。余额不足提示不等于可对客户宣称逾期，逾期需要约定账期、应付日和逐笔核销证据。

### 8.2 资金指标与余额桥接

| 指标 | 定义 |
| --- | --- |
| 已入账充值额/笔数 | `transaction_type=recharge` 的账本金额/行数；业务键去重核验；不重复加申请表 |
| 充值客户数/客均充值 | 充值客户去重；充值额 / 充值客户数 |
| 单笔充值分布 | 成功充值金额的中位数、分位区间、金额档位 |
| 充值间隔 | 客户充值日期去重后的正间隔；至少 3 个充值日才形成个体周期 |
| 首次/再次充值 | 以覆盖范围内全部成功充值史判断；初始化不算首充 |
| 订单首次扣款 | `order_charge` 的负值绝对额 |
| 订单调整 | `order_adjustment` 正负分列，负为补扣、正为退回 |
| 订单退款 | `order_refund` 正向入账，表示余额退回，不表示银行现金退款 |
| 初始化/人工调整 | `init`、`adjust` 单列，不计销售或现金流入；`level_adjust` 为零金额等级审计 |
| 预存余额合计 | 截止时点逐客户 `MAX(balance,0)` 后求和 |
| 欠款余额合计 | 截止时点逐客户 `MAX(-balance,0)` 后求和 |
| 净账户余额 | 正余额合计 - 欠款合计，仅作辅助；不抵销展示两类客户风险 |
| 待审核充值 | `request_type=recharge AND status=pending` 的申请额和数量，独立于已入账 |
| 审核耗时 | 已审核申请的审核时间 - 申请时间；待审时长另算，展示中位/P90 |

账户桥接：

`期末余额 = 期初余额 + 充值 + 订单退款 + 订单调整正额 - 订单首次扣款 - 订单调整负额绝对值 + 初始化 + 人工调整净额`。

跨客户汇总先按客户核对，不用一个客户的差额抵消另一个客户。时间相同时按账本 ID 稳定排序；期初取区间前最后一条账本 `balance_after`，没有前序但有首条流水可取其 `balance_before`。无足够记录时显示“期初未知”，不得默认为零；不查询期末之后的客户当前余额冒充历史余额。

充值表明系统已确认入账，不代表独立核验银行实际到账日期。未来如需资金日历，增加银行交易日期、银行交易唯一标识与对账状态；不能 OCR 凭证后直接当正式日期。

### 8.3 页面图表

1. 充值额与充值客户数趋势：金额图和人数图对齐时间，避免混用难读双轴。
2. 账户余额瀑布：期初 → 充值/扣款/退回/调整 → 期末，可下钻每类流水。
3. 客户资金矩阵：横轴近 90 天商业购买额、纵轴余额，点大小为充值额；prepay/credit 分面。
4. 充值金额档位和充值频次分布，支持会员、地区、业务员和门店类型切分。
5. 余额与最近下单时间矩阵：识别“余额较高但长期未购买”“频繁购买但需要核对补款”等。
6. 待审申请队列：等待时长、所属客户、金额、处理入口；本人申请与审核人权限分别控制。

### 8.4 充值与下单联动

- **充值后首单等待**：每笔充值后，寻找该客户下一笔商业购买，按入账时间与可验证的正式生效时间计算。旧订单只有日期时仅能展示日粒度，同日先后不可判断，不计算精确小时。
- **7/30 天充值后购买比例**：月度 cohort 以每客户每月第一笔成功充值为锚点，粒度为 `(customer_id, cohort_month)`；分母只含观察满 7/30 天的客户月记录，分子为对应锚点后窗口内发生商业购买的记录。同月多笔充值不重复计，同一客户跨月可以进入多个 cohort，跨月合计明确命名“客户月记录”，不是去重客户数；重叠窗口内的同一购买可用于各月观察，但不做充值金额归因。若查看整个查询期的客户级比例，则另用“每客户查询期首次充值”唯一锚点，分子分母都按客户去重，不合并月度 cohort 比例。
- **充值与扣款比**：同期间净订单扣款 / 充值，只能称“期间资金使用比”，可能大于 100%，不命名为该次充值转化率。
- **逐笔充值消耗率**：首期不做。钱在账户里可混用，涉及期初、退款与人工调整，无法从相邻订单就确认某笔充值被消耗。
- **信用客户本次补款的余额改善**：可算 `min(本次充值额, max(-balance_before,0))`，仅表示账户层面欠款减少，不代表具体发票/订单核销。
- **余额预计覆盖天数**：仅 prepay、余额可靠且近 90 天至少 3 个购买日时，`可用正余额 / (近90天有偿订单扣款毛额/90)`；单独提示同期退款/调整，异常多时不预测。没有消费记为“暂无有效消耗速度”，不显示无限天。

### 8.5 资金行动规则（建议初值）

| 信号 | 条件示例 | 建议 | 抑制条件 |
| --- | --- | --- | --- |
| 余额可能不足 | prepay，预计覆盖 <14 天，且进入复购观察期 | 核对下一次订单与补款需求 | 待审充值足以覆盖、余额待核对、近期已跟进 |
| 长期未使用余额 | 正余额，90 天无商业购买 | 了解经营计划、需求和交付问题 | 新开户/历史不完整不强判 |
| 欠款扩大 | credit，欠款连续两个完整周期增加 | 财务与业务员核对账户 | 不直接标“逾期”或“坏账” |
| 充值节奏变化 | 个体充值周期有效且当前间隔 >1.5 倍周期 | 核实需求变化 | 余额仍高且近期少下单时合并成需求跟进 |
| 已充值未下单 | 成熟30天 cohort 内无商业购买 | 核对首单准备和产品选型 | credit 补款主要冲旧欠款时不提示“激活失败” |
| 资金调整频繁 | 同客户30天人工调整≥3次 | 内部核对账务原因 | 不向客户自动推送、不解释为欺诈 |

## 9. 客户画像与分群

### 9.1 客户画像结构

画像实体为内贸门店客户 ID，不把明细上的顾客姓名建成终端个人画像。

| 模块 | 内容 | 展示 |
| --- | --- | --- |
| 基础档案 | 门店、区域、来源、门店类型、当前负责人、客户等级、结算方式 | 资料卡，标人工维护/系统事实 |
| 经营价值 | 30/90/180/365 天订单额、件数、购买日数、客单、客户贡献 | KPI + 趋势；历史档案值独立栏 |
| 购买偏好 | 工艺、发色、网帽色、尺码、发长、发量、发型系列、常购组合 | 偏好条/矩阵，金额与件数切换 |
| 价格与规模 | 加权价、价格带、每单件数、普货/特单、会员优惠覆盖 | 同规格对比，避免混合单价误判 |
| 资金行为 | 充值频次/规模、余额、欠款、调整、充值后购买 | 时间线和资金桥接 |
| 关系阶段 | 系统首购、持续购买、待复购、节奏异常、回流 | 规则标签，注明窗口和样本 |
| 履约体验 | 发货、未交付、售后重做线索 | 仅有证据时展示，售后原因另需采集 |
| 建议行动 | 建议联系时间、话题、推荐组合、需先核对事项 | 事实/推断/建议分栏 |

偏好以近 180 天为默认，同时展示全历史对照；至少 3 个购买日、主要维度有效覆盖率≥80%才输出“偏好”标签，否则称“已购记录”。按件数占比排序，注明购买日数、客户自身样本和最近发生日期。

### 9.2 RFM 与客户经营分层

采用透明的三个独立维度，不默认拼成一个神秘总分：

- R：距最近商业购买的天数。
- F：近 180 天商业购买日数（避免拆单影响）。
- M：近 180 天商业购买金额（不加充值）。

在同结算方式、门店类型等可比组内按分位分层。分组不足 30 客户时不输出分位等级，只显示原值或经用户选择扩大可比范围；并列值同档，不强行分成等人数。分群规则带版本与计算日期。

可解释标签：高价值持续购买、新客培育、复购稳定、需求上升、购买节奏异常、高余额待沟通、欠款需核对、特单偏好、产品需求集中。多个标签可共存，但“人工生命周期状态”“当前会员”“系统经营标签”分栏。

### 9.3 复购周期与流失线索

1. 客户近 365 天至少 4 个不同商业购买日，取最近最多 6 个正间隔的中位数作为个体周期 C。
2. 不足时，按结算方式 + 门店类型 + 主产品类型寻找同群；至少 20 客户有有效周期才使用“同群参考周期”，等权汇总客户周期。
3. 同群也不足则仅显示距上次购买天数，状态“样本积累中”，不强制套 30 天流失规则。
4. 距上次购买达到 C 提醒“预计进入复购窗口”；超过 1.5C 标“购买节奏延后”；超过 2C 标“需核实需求变化”。这些是规则线索，不是经校准的流失概率。
5. 尚有未发货订单时，优先提醒核实交付；停业、暂停合作等人工状态会抑制普通促单建议，保留必要的资金核对。

**候选池必须包括过去购买但本期零订单的客户**。不能先筛本期下单客户再找流失。若从产品筛选进入，以截至观察日历史买过该产品的授权客户圈选，并明确与总览“本期相关客户”集合不同。

### 9.4 产品推荐

首期规则推荐分三种：常购组合复购、近半年购买变化、同类客户共购探索。推荐卡展示“推荐原因、证据客户/订单数、产品属性、未知库存/交期、建议询问问题”。

相似客户推荐在授权数据内计算；面向普通业务员，默认只用其范围，避免借推荐泄漏其他业务员客户。若未来开放跨团队匿名统计，须单独配置权限和最小匿名群体门槛，不能复用管理员缓存。

同购关联建议初值：至少 20 个客户样本、共购至少 5 客户，再展示支持度与提升度；不足时只列自身常购，不输出“其他同类门店普遍购买”。推荐不得把售后重做当喜好增强。

## 10. 业务员画像

### 10.1 三种身份不能混用

| 身份 | 用途 | 首期处理 |
| --- | --- | --- |
| 客户当前负责人 | 当前客户服务与经营任务 | 默认画像“当前客户组合”，历史金额归入当前客户组合并明确会随转移变化 |
| 订单/充值发生时负责人 | 稳定历史贡献分析 | 上线起事件快照；旧记录未知，不用当前负责人倒填 |
| 创建人/申请人/账本操作人 | 录入、协作、审核流程追溯 | 独立筛选，不命名销售贡献 |

主管切换“当前客户组合 / 历史发生归因”。历史归因未覆盖的时期禁用对应排名，并显示未知归因额；团队关系也需有效期，不用当前部门追溯多年业绩。

### 10.2 画像指标

| 维度 | 指标 | 可解释标签示例 |
| --- | --- | --- |
| 客户经营规模 | 当前负责客户数、活跃客户、商业购买额、件数 | 客户组合规模较大 |
| 新客培育 | 系统首购、成熟 cohort 二购、首购到二购周期 | 二购跟进表现较好 |
| 老客经营 | 持续复购、回流、购买间隔变化 | 老客复购稳定 |
| 产品经营 | 工艺/系列覆盖、特单比例、单一组合集中度 | 特单服务较多、需求集中 |
| 资金经营 | 已入账充值、预存/欠款、待核对客户、行动完成 | 账户核对及时 |
| 稳定性 | Top客户集中度、活跃客户流失线索 | 大客户依赖较高 |
| 执行动作 | 已认领行动、按期完成、结果记录 | 跟进记录完整 |

可视化以条形、趋势和散点为主；如使用雷达图，须能展开原值、分母和计算规则，不能只给“能力 87 分”。

### 10.3 公平比较与带教

- 先比本人同期变化，再比相同客户规模、客户年龄、门店类型、区域和结算方式的可比组。
- 没有分配线索量、报价和跟进质量数据，不能计算完整成交转化率或评价个人能力高低。
- 不把财务审批速度、历史继承的大客户、客户转移产生的金额直接归为业务员能力。
- 同组不足 5 位业务员或关键指标不足 20 个有效客户样本时，关闭百分位排名，只展示事实和样本不足提示；门槛均可配置并留版本。
- 默认提供带教建议：“成熟二购客户样本较少，建议补充首单后回访记录”，避免“业务能力差”等定性。
- 本画像用于经营复盘；如将来接绩效，需要单独确认归因、历史缺口、投入数据和人事规则。

## 11. 本公司内贸成交需求趋势

### 11.1 看趋势的五个角度

1. 规模：金额、件数、客户数、购买频次。
2. 结构：规格组合份额、价格带、普货/特单、会员与门店类型。
3. 广度：增长是否跨客户、跨业务员、跨地区；Top1客户占比。
4. 持续性：连续多个完整周期是否保持，而非单周偶然峰值。
5. 证据质量：数据覆盖变化、映射版本、少数大单、售后/零价是否扭曲。

### 11.2 趋势信号

| 信号 | 建议识别条件 | 输出 |
| --- | --- | --- |
| 持续增长组合 | 连续3个完整周期件数增长，近周期≥10客户、≥30件 | “增长候选”，展示绝对值和分布 |
| 客户扩散 | 客户数和件数同时增长，排除最大客户后仍增长 | 建议小范围验证其他同类客户需求 |
| 大单驱动增长 | 单客户贡献增量>50% | 明示集中采购，先核对是否常态 |
| 需求下降 | 两个完整周期件数下降且可比覆盖稳定 | 拆解减少购买客户与订单数量 |
| 新出现组合 | 过去完整覆盖中未出现、本期出现 | “本系统新出现”，不说行业新品 |
| 潜在季节规律 | 至少24个月完整历史、对应月份重复变化 | 展示历史区间，提示样本与事件干扰 |

增长门槛不满足时仍展示基础图表，只抑制自动标签。高维扫描优先预置组合，要求连续验证期并披露总扫描组合数，避免从成千上万格中挑偶然高增速当确定机会。

### 11.3 条件预测与情景推演

P1 才启用短期预测；先以滚动中位数/季节朴素法建立基线，经回测后选择简单模型，不默认上复杂模型。

- 预测目标：未来 4 周商业需求件数/金额、客户复购窗口；充值预测与需求预测分别评估。
- 建议门槛：至少26个完整周、20个非零周；季节模型至少2个完整年度。低量组合归并到上级维度或不预测。
- 滚动时间回测，训练/验证按时间隔离；比较 WAPE/MAE 与朴素基线，分母为零时不用 WAPE。未优于基线则保留基线或关闭。
- 区间必须由历史残差/可核验方法生成，并报告覆盖率；不足以校准时不画貌似精确的置信带。
- 促销、交期、客户集中采购等作为解释上下文，不能假设 AI 已掌握外部原因。
- 情景模拟允许用户输入“某客户订单增减/预计补款”，结果标“假设推演”，与正式预测和已发生事实分区，不回写业务数据。

## 12. AI 推断与建议

### 12.1 三层职责

| 层级 | 谁负责 | 输出示例 |
| --- | --- | --- |
| 事实 | 统一指标服务 | “近28天，某组合件数从80增至104” |
| 规则线索/模型预测 | 可版本化计算规则 | “增量主要来自2个客户；证据不足以判断普遍增长” |
| AI解释与建议 | 统一 AI facade | “建议先询问这两家门店本次是否集中备货，再做小范围推荐” |

AI 不计算账本、不确定订单状态、不修改颜色映射、不认定欠款逾期、不修改客户评级或负责人。

### 12.2 功能入口

- 总览“生成经营简报”：最多三条重点、一项数据限制、可展开证据。
- 客户画像“下一次沟通建议”：常购产品、近期变化、需要询问的问题、建议行动。
- 产品页“解释变化”：比较期、贡献来源、可能原因、验证步骤。
- 自然语言问数：例如“近90天华东头套客户里，哪些已到复购期但余额偏低？”转换成受控指标查询计划，显示筛选解释后运行。
- 周/月复盘简报：复用保存视图，生成可分享的授权报告；定期自动生成属于 P1 配置能力，默认不自动对外发送。

### 12.3 输出契约

每条建议必须包括：

`insight_id、category、title、scope、period、facts、evidence_refs、hypotheses、alternative_explanations、recommended_action、owner、due_hint、evidence_grade、limitations、metric_version、rule_version、data_version、generated_at`。

- facts 只引用服务端返回值；数字与证据引用逐项校验，失败则该条不展示。
- hypothesis 明确“可能/待核实”，不得用“客户因价格不满”冒充已知原因。
- evidence_grade 表示样本和覆盖质量，不是主观生成的准确率：无关键对账异常时，高证据要求覆盖率≥95%且客户≥30；未达高证据但覆盖率≥80%且客户≥10为中证据；其余低证据。覆盖率采用上文记录与展示指标加权覆盖率中的较低值。个体周期建议用自己的样本门槛，并明确“个体依据”，不能套群体人数。
- evidence_refs 指向后端鉴权证据抽屉；报告只列当前读者可见证据，不泄漏隐藏客户名称。
- 值域运行时从数据库注入；客户备注等源材料视为数据，不能改变模型权限和查询工具。

### 12.4 防止无依据与权限泄漏

- 只提供本次授权范围内的聚合数据、必要匿名客户标识和证据 ID；不发送手机号、地址、银行凭证、终端顾客姓名。
- 自然语言只能选择注册指标/维度、受控过滤与只读查询，不允许模型生成任意 SQL 或写业务数据。
- 不足样本、映射覆盖差、对账异常的指标带不可推断标记，模型不能绕过。
- 模型不可用时，事实图表、规则建议仍正常可用，显示“AI解释暂不可用”。
- 同用户同范围同数据版本复用任务；后台任务具备排队、运行、成功、失败、超时状态。重试不重复建行动。
- 建议初始限制：同用户同时1个AI生成任务，单次≤20条候选证据、最多5条建议；文本/token上限、日预算在管理配置中设定。超预算继续使用规则摘要，不默默付费扩大调用。
- 模型、preset、提示版本、耗时和调用成本留审计；不在日志输出完整客户隐私或凭证。

## 13. 行动闭环与效果评估

### 13.1 行动对象

行动包含客户/产品/业务员关联、来源洞察、触发事实快照、建议、优先级、负责人、截止日、状态、结果、下次跟进时间。

状态：`建议 → 已认领 → 进行中 → 已完成 / 已忽略`；延后需要新的日期，忽略可选原因，完成必须选择结果（已联系、需求待定、计划补款、已有采购、暂不需要、数据不准等）。允许仅内部记事，不等同于已联系客户。

### 13.2 去重、失效与提醒

- 同客户同规则同观察窗口使用稳定业务键，刷新和 AI 重试不重复生成。
- 同客户一天只展示一张合并卡，默认最多三条原因；七天内同一未变化信号不重复提醒。
- 新订单/充值/申请出现后重算，已失效建议标“条件已变化”，保留历史依据。
- 客户转移后撤销原负责人访问与提醒，按新负责人范围重新分配；历史行动只按当前授权展示，旧链接不恢复权限。
- 只有显式配置订阅后才启用内部通知；对客户发消息需要用户选择内容并在原有渠道执行，本功能不自动发送。

### 13.3 结果指标

- 行动采纳率 = 已认领有效建议 / 可认领建议，重复、自动失效项单列。
- 按期完成率 = 截止日前完成的行动 / 本期已到期行动。
- 后续下单关联率 = 完成联系后观察满30天且发生商业购买的客户 / 观察满30天的已联系客户。
- 后续充值关联率同理，排除仅“计划补款”却没有账本的情况。
- 以上是观察关联，不叫 AI 增量收益；要证明增量，需要随机对照或可信准实验，并控制客户重复触达与原有趋势。
- “数据不准/建议无用”的反馈进入规则复盘，不直接喂模型修改金额或客户事实。

## 14. 权限、数据范围与隐私

### 14.1 建议权限（均为新增设计，未注册）

| 权限 | 用途 |
| --- | --- |
| `domestic_decision:read` | 进入决策台，默认本人当前负责客户的经营数据 |
| `domestic_decision:read_all` | 全内贸数据范围，`kind=data`，不单独控制菜单 |
| `domestic_decision_finance:read` | 在已有客户范围内读取资金、余额与账户证据 |
| `domestic_decision_action:write` | 在授权范围内认领、更新本人行动 |
| `domestic_decision_report:write` | 生成AI简报/导出报告，受预算与范围限制 |
| `domestic_decision:admin` | 维护规则、分析映射、质量配置；不自动赋全量资金权限 |

主管团队范围由服务端已核验的内贸团队授权配置解析，不能只接前端传入 `team_id`。若现有组织数据不能表达该范围，首期只开放本人/显式全量两个档位，团队版待补齐后启用，不让主管默认获得全公司。

### 14.2 与旧权限的衔接

现有订单阅读按创建人限权，客户操作按当前负责人限权，两者不一致。本方案明确选择“客户经营范围”作为新决策台授权模型，但须由角色管理显式分配新权限，不能自动继承 `domestic:read`、`domestic:admin` 或外贸 `order_intelligence:*` 来扩大范围。

- 新决策台证据使用专门的只读证据端点，按新范围返回允许字段；不直接通过旧详情端点绕过创建人检查。
- 跳转原订单编辑、充值、审核、凭证下载时，仍按原操作权限执行；有分析权限不等于有编辑/审核权限。
- 资金页、资金导出、AI上下文必须同时满足基础分析权限、客户范围、资金阅读权限。
- 负责人变更立即影响访问，后台任务结果读取、导出下载、缓存命中、保存报告、建议证据都重新校验。历史归因维度只改变分组，不扩大可访问事实集合。
- 本人当前客户历史可用于客户服务，但这是新权限的明确授权范围；移出客户不再可见。没有当前客户的业务员看到空状态，不能回退为全量。
- 公海未分配客户只对具备全量范围者显示，单独归入“未分配”；不把无主客户默认送给所有业务员。
- 没有资金权限时，不仅隐藏资金页，还移除总览余额卡、客户画像资金段、AI资金建议、筛选选项和导出列。

### 14.3 缓存与导出

缓存键包含用户/范围签名、权限版本、归因方式、日期、过滤、指标/映射版本、数据版本；不能仅以日期缓存公司聚合后再在前端过滤。

导出默认仅当前筛选下的可见列，附口径、区间、数据截止点、覆盖率与版本。图表可导出图片，明细可导出表格，长报告走后台；下载链接私有且过期，下载时再次鉴权。分享不生成公开客户数据链接。

## 15. 交互、图表和异常状态

### 15.1 可视化规范

- 趋势用折线/柱、分布用直方/条形、比较用横向条、二维组合用热力、客户分群用散点、资金变化用瀑布、留存用 cohort 表。
- 排名默认 Top10 + 其他，维度较多不使用多块饼图；禁用3D图和装饰性大屏仪表盘。
- 所有图表有表格替代和键盘可达的筛选/下钻入口，不能依赖颜色或悬浮作为唯一信息。
- 金额/数量单位明确；预存增长不默认标“利好绿”，欠款增长不与订单增长共用相同语义。
- 沿用 [DESIGN.md](../../DESIGN.md)、`tokens.css`、既有 ECharts 与列表/抽屉组件。数字用等宽数字，筛选高频操作不加计数滚动动画。
- 图表更新不延迟业务数据展示，减少动态偏好下关闭移动动画；加载时保留容器和清晰文字。
- 主站响应式：移动端优先指标、重点客户和行动，复杂矩阵使用内部横向滚动/表格；不新增 `/m/` 领域入口。

### 15.2 状态契约

| 状态 | 页面行为 |
| --- | --- |
| 首次加载 | 骨架和加载说明，不显示假零值 |
| 空数据 | 说明范围与时间，提供重置或换区间 |
| 本人无客户 | 提示当前无归属客户，提供现有客户管理入口 |
| 无权限 | 说明缺少对应阅读权限，不展示存在但不可见的客户数量 |
| 字段缺失 | 显示未知桶和覆盖率；不静默过滤 |
| 小样本 | 基础图可看，预测/强结论禁用，显示最低证据要求 |
| 资金异常 | 受影响客户资金预测暂停，保留可核对流水 |
| 局部失败 | 某模块显示重试，其他已成功模块保留；不把失败当0 |
| 旧数据 | 标“截至××”，刷新失败仍保留上次版本并提示过期 |
| 快速切换 | 只接收最新查询响应，取消/忽略旧请求，防止串客户/串范围 |
| AI失败 | 显示规则结论与重试，不阻塞图表 |
| 导出处理中 | 返回任务状态，可离开页面后回来下载 |

## 16. 数据与技术设计建议

本节用于开发拆解，不代表已新增表、接口或生产任务。采用现有 FastAPI + SQLAlchemy + Vue 3 + ECharts，不为首期先引入独立数仓或BI平台。

### 16.1 模块边界

- 新分析领域建议 `backend/app/domestic_decision/`，拥有查询、指标、画像、规则、AI简报、分析映射和行动；从 domestic 域读取业务事实。
- 原始写流程仍归 `app/domestic/`，新增可靠业务事件由业务服务在原事务中落地，分析层只消费，不反向修改余额。
- 前端建议 `frontend/src/views/domestic_decision/`，API client 注册到既有 clients，菜单注册到 navigation。
- 外贸模块只复用适用的图表、任务模式和工具函数；不导入其 OKKI 数据权限/订单有效状态作为内贸逻辑。
- AI统一走 `app.ai.service.chat`，建议独立 preset `domestic_decision_brief`；字典运行时注入。

### 16.2 最小分析数据模型

| 对象（建议名） | 关键字段 | 引入阶段 |
| --- | --- | --- |
| 指标注册定义 | code、粒度、公式、过滤、单位、版本、可用维度、权限 | P0；优先代码配置，避免任意公式SQL |
| `ark_domestic_analysis_attr_mappings` | 原值、标准值、属性、适用类型、来源、审核、版本 | P0颜色/工艺尺寸映射 |
| `ark_domestic_analysis_events` | source_event_key、实体ID、event_type、occurred_at、business_date、before/after、owner快照、版本 | P0上线起采集 |
| `ark_domestic_analysis_views` | owner、过滤、维度、指标、时间模式、共享范围 | P0保存视图 |
| `ark_domestic_analysis_briefs` | task_id、request_key、范围签名、证据快照、输出、版本、状态、过期/错误 | P0按需简报 |
| `ark_domestic_analysis_actions` | customer_id、rule_key、evidence、assignee、due_at、状态、结果、幂等键 | P0最小闭环 |
| 历史归属/状态事件 | 客户、owner/team/会员/结算方式、有效时间区间 | 可作为统一事件的特定类型，不重复建同义表 |
| 日聚合/画像快照 | 统计日、范围维度、指标版本、data_version | P1或实际压测需要时物化 |

事件采用至少一次消费 + 业务键幂等，按事件序列稳定重放；修正数据产生新事件，不在分析侧篡改原业务账本。只保存必要的业务字段，不把客户联系方式、银行凭证复制到分析事件。

### 16.3 事实查询与一致性

- 订单、明细、客户账本先各自按唯一粒度计算，再按明确粒度关联；禁止订单×明细×充值流水直接宽表 join 后 SUM。
- 订单筛选使用 EXISTS 或去重ID集合；客户维度变化明确选择当前档案或事件快照。
- 同一次页面分析用同一 `analysis_run_id` 和数据水位。P0多图结果宜在一次只读一致性事务内生成；需要跨请求下钻时保存短期证据结果/事实ID及版本。
- 没有历史版本的源行被改动后，不用旧水位配最新明细假装一致：提示“数据已变化”，整组刷新并换 run ID。只取 MAX(updated_at) 不足以构成可重现快照。
- 下钻金额/数量与卡片对账；从聚合进入明细携带查询摘要，不相信前端自行传入的金额或客户范围。
- 数据质量和分析水位一同返回；缓存建议5分钟，业务事件可失效相关客户缓存，历史事件驱动受影响日期重算。
- 财务核对显示事务水位；余额变更后刷新可以看到已提交事件，不读取业务事务中间态。

### 16.4 API 草案

统一前缀建议 `/api/domestic-decision`，成功返回项目 `ok()` 信封。下表是待实现契约。

| 方法/路径 | 输入重点 | 输出重点 |
| --- | --- | --- |
| `GET /filters` | 权限范围、日期、当前过滤 | 可用维度/字典、历史值、覆盖率 |
| `POST /analysis-runs` | 指标、维度、筛选、比较方式、归因方式 | run_id、总览/图表、watermark、版本、warnings |
| `GET /analysis-runs/{id}/rows` | 分组、分页、排序 | 同口径订单/明细/客户证据；变化则要求刷新 |
| `GET /customers/{id}/profile` | 观察窗口、可用as_of、范围 | 画像事实、规则标签、质量、证据 |
| `GET /salespeople/{id}/profile` | 范围、窗口、归因 | 原值、可比组、样本、趋势 |
| `POST /finance-runs` | 客户圈选、资金时间、截止点 | 充值/桥接/余额/待审；需资金权限 |
| `GET /evidence/{type}/{id}` | 类型与ID | 经字段裁剪的只读证据；每次鉴权 |
| `POST /briefs` / `GET /briefs/{id}` | run_id、用途、幂等键 | 异步生成状态、结构化建议、证据引用 |
| `GET /actions` / `POST /actions` / `PATCH /actions/{id}` | 过滤、幂等键、状态及版本 | 分页行动、冲突检查、结果 |
| `GET/POST/PATCH /views` | 个人视图定义 | 版本化视图；读取时重新解析权限 |
| `POST /exports` / `GET /exports/{id}` | run_id、可见列、格式 | 后台状态、私有下载入口 |
| `GET /data-quality` | 范围、区间 | 对账差额、缺失覆盖、问题数和处理入口 |

所有分析结果公共元数据至少包括 `period、comparison_period、time_basis、attribution_mode、scope_summary、data_as_of、coverage_start、metric_version、mapping_version、rule_version、sample_size、warnings`。权限范围由服务端计算，前端仅能申请进一步缩小。

### 16.5 性能与运营目标

建议以隔离压测数据 10 万订单/50 万明细/100 万流水、20 个并发分析用户作为第一档验收基线，正式开发前结合只读体检调整，不把这些规模当生产现状。

- 缓存命中总览 P95≤2秒；普通未命中聚合 P95≤5秒；单客户画像 P95≤3秒。
- 预计超过5秒的跨年/高维任务返回后台任务状态；大导出异步，取消只取消任务不影响源数据。
- 前台分析限制时间范围、维度基数、分页大小；首期建议最长36个月同步查询，超限走异步。
- 记录慢查询、聚合耗时、缓存命中率、刷新延迟、账本差异、AI失败/成本和权限拒绝。
- 根据真实执行计划增建索引；聚合表只在证据显示必要时加。调度遵守现有单活约束。

## 17. 分期范围与上线门槛

| 阶段 | 可交付能力 | 明确完成证据 |
| --- | --- | --- |
| P0-A 数据与最小闭环 | 只读体检、统一指标/权限、订单趋势、核心规格、充值桥接、客户基础画像 | 源单对账通过，权限负向验证，样本客户可从总览下钻到证据 |
| P0-B 首期完整功能 | 所有适用属性、多维交叉、颜色映射、RFM/周期、业务员当前组合、规则洞察、按需AI、保存视图、最小行动闭环 | 下方核心验收用例通过；数据缺口明确降级 |
| P1 深化 | 事件覆盖后的稳定归因、历史时点、成熟cohort、条件预测、订阅简报、共购推荐扩展 | 时点回放与回测通过，采纳/结果可追踪 |
| P2 经营联动 | 报价/线索、售后原因、成本、库存交期、推广和外部市场数据 | 每项有独立身份匹配、口径、权限与效果验收 |

P0应优先上线“选一客户 → 看订单与资金 → 核对规格偏好 → 形成有证据行动”的端到端流程，再补复杂图形。P0-B完成才称首期完整，不把单个总览大屏当需求全部完成。

建议试运行覆盖不同结算方式、头套/发片、历史/新客户、普通业务员/主管/财务；先只读对比与人工校验，再启用内部行动，不自动对外执行。

## 19. 需要在开发启动时确认的业务项

这些事项不妨碍本次设计完成。当前采用下列默认方案，实施前结合只读体检与业务评审确定；不静默扩大权限或造历史。

| 事项 | 本文默认 | 实质影响 |
| --- | --- | --- |
| 历史完整覆盖起点 | 只读体检后设置；之前标系统记录口径 | 新客、留存、同比与周期可信度 |

| 历史销售归因 | 有发生时快照才用，旧数据未知 | 不用于未经确认的绩效排名 |
| 售后/零价购买 | 总需求保留、商业复购排除售后和零价 | 购买周期与经营需求两个口径不同 |
| 发色标准 | 原文保留，分析映射人工审核 | 颜色分析覆盖与维护责任 |
| 充值日期 | 账本入账日 | 不等于银行到账日 |
| 实际现金退款 | 当前没有独立完整确认链，暂不展示该指标 | 不能将余额退回当银行退款 |
| 规则门槛与AI预算 | 使用本文建议初值，管理配置留版本 | 需要试运行校准，无效规则可关闭 |
| 交期/库存/成本 | 缺可靠链路时只作待核对上下文 | 不能先输出利润和确定备货量 |

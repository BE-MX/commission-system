# 产品风向标 + 客户产品线索（2026-11-18，B 版）

状态：P0、P1 已在分支 claude/product-sales-radar 实现（未合并、未部署）；P2 待做。第 7 节五个点 2026-11-18 亮哥确认全部按建议执行。来源分析：`tmp/okki-product-sales-2026/` 下的 Codex 全公司销量报告（只作口径参考，不沿用其内容和版式）。

## 1. 要解决的问题

业务员每周要回答「该给哪位客户推什么款、拿什么理由推」。现有工具有两个缺口：

- 「订单经营决策台」按件数统计，不同克重的款没法横向比较，也看不出颜色×发长的风向。
- 客户工作台能回答「先找谁」，但没有产品层面的理由，话术也拿不到「这款公司最近卖得好」这类证据。

B 版的做法：新做一个以产品为主体的页面（产品风向标），再把产品信号作为线索挂到业务员已经在用的客户作战卡和工作台事项上。**不新建待办，不另起机会引擎。**

## 2. 已确认的决策（2026-11-18）

| 决策 | 内容 |
|------|------|
| 第一使用者 | 业务员，看完要决定「推什么给谁」（公司级产品汇总对所有业务员开放，仅产品级 kg/件数，见第 7 节第 1 条） |
| 入口 | 独立新页面，菜单放在「客户经营」组 |
| 计量 | 跨款汇总（型号、颜色、发长、品类）用 kg；单个 SKU 用件数；两者并列显示 |
| 有效订单 | 与战报 GMV 一致，复用 `order_intelligence.service.VALID_ORDER_SQL` |
| 重量 | `okki_order_items.quantity × okki_products.unit`（g），除以 1000 得 kg |
| 历史品名 | 建映射表，人工确认后固化，多模块共用 |
| 历史粒度（2026-11-18 追加） | 旧产品库时期（2025 年至 2026 年 3 月）只看型号级 kg（默认克重，标估算）；颜色×发长从 2026 年 4 月起分析。不再追溯旧 SKU 属性 |
| 客户层 | 页面只讲产品；「哪些客户买过这款」深链到决策台或客户工作台，不在新页面重做 |

## 3. 实测事实（2026-11-18，只读查询）

| 年份 | 有效订单 | 明细行 | 能命中 okki_products 的行 |
|------|---------:|-------:|-------------------------:|
| 2024 | 2,342 | 6,050 | 0 |
| 2025 | 5,697 | 20,014 | 0 |
| 2026（截至 11-18） | 7,972 | 29,949 | 21,530 |

- **2025 全年没有一行能命中产品表。** 要做同比，2025 年的数据完全依赖品名解析。所以映射表的范围是 2025-01 起，不只是 2026 年 4 月前。
- 2026 年确切重量覆盖率：1–3 月 3.9% / 2.9% / 44.1%，4–6 月约 73–78%，7 月起约 96%。
- `ark_catalog_skus` 和 `ark_catalog_external_identities` 当前是 **0 行**。产品主档目前只有表结构（commerce_migration 在建），现阶段不能依赖它取克重。
- 客户经营的订单明细投影 `ark_customer_order_items` 只有 2,276 行，`product_family` 和 `color` 全空。客户工作台现有的产品维度基本不可用，产品线索必须直接从 OKKI 明细计算。
- 现有的品名解析规则至少有三套，而且互相不一致：
  - 决策台：`order_intelligence/service.py` 的 `_load_product_rows`。
  - 备货：stock 的 `parse_name`。
  - 报表：`report/category_service.py`。
- 决策台的颜色解析有 bug，Python 和 SQL 两处都取倒数第二段：
  - Python：`order_intelligence/service.py` 的 `_load_product_rows`。
  - SQL：`order_intelligence/filtering.py` 的 `color_expression`，筛选就用这个表达式。
  - `#8TP8/18` 这种色号本身带斜杠，会被解析成「18」。stock 的 `overview_service._parse_name` 已经处理了 `#X/Y` 的情况。
- `okki_products.unit` 是「20g」这样的字符串，不是数字。发票明细里的 `ark_invoice_items.net_weight_grams` 就是从它映射来的。另外 `ark_custom_products.unit` 也是现成的克重来源。
- 决策台前端目前不读任何 URL 参数，页面权限是 `order_intelligence:read`。
- **历史品名只能提取型号**（2025-01 起明细 49,963 行实测）：
  - 产品表未命中的有 28,433 行，去重后 1,041 个品名，其中 1,022 个只有一段（如「B3新天才发帘（帘宽12"）」），不含颜色、发长和克重。
  - 带克重末段的品名只有 16 个。
  - 未命中行里有 23,230 行带旧 SKU 编号（如 `B3 new genius weft_13`，约 800 个），但属性定义已不在任何本地表。
  - 同一 SKU 的单价从 1 到 651 都有，不能反推克重。
  - 前 100 个品名覆盖 88% 的未命中行，前 200 个覆盖 92%，人工确认量小。

## 4. 范围与分期

### P0 地基（不对业务员开放）

1. **领域模块 `app/product_sales/`**：router / models / schemas / service 四件套（宪法 1）。
2. **品名映射表 `ark_product_sales_name_mappings`**，建在 commission_db，不写 lsordertest。
   - 键：规范化后的 `product_name` 哈希。
   - 值：model / `unit_grams`（默认克重）。历史行的颜色、发长固定为「未知」，不做猜测。
   - 预填规则：把历史品名规范化后，去当前产品表（`okki_products.model`）里找同名型号，取该型号最常见的 `unit` 作为默认克重建议，待人工确认。
   - 置信度四档：
     - `exact`：okki_products 命中，且 `unit` 能解析出克数；命中但解析不出，降为 `derived` 或 `unknown`。
     - `derived`：品名末段是克重格式（如 `/1g`），同时品名能对上已有 `exact` 产品的型号和规格。只有末段格式、没有对上的，降为 `assumed`。
     - `assumed`：只有型号，靠默认克重推算。
     - `unknown`：解析不出型号或克重，不计入 kg，只计入件数。
   - 克重的旁证来源依次是：`okki_products.unit`、`ark_custom_products.unit`、`ark_invoice_items.net_weight_grams`。
   - 记录来源规则版本、确认人、确认时间。
   - 预留可空的 `catalog_sku_id`：catalog 有数据后再挂钩，不在本期造第二份产品主档。
3. **口径函数** `product_sales.metrics.load_lines(scope, window)`：
   - 每条明细输出标准化维度、件数、kg、置信度。
   - 解析优先级：products 命中 > 人工确认的映射 > 规则解析 > 「未知」。
   - 新页面用这个函数。决策台和备货本期不迁移，只登记为技术债。
4. **映射确认页**（`product_sales:admin`）：
   - 待确认队列按「涉及件数、行数」从大到小排，不按 kg 排（kg 本身依赖待确认的克重）。
   - 支持批量确认同一规则产出的结果。
   - 单价或金额只作为判断克重档位的旁证展示，不自动写入。
   - **延后到 P1 前（2026-11-18）**：单价/金额旁证列、按预填来源一键批量确认。P0 先用勾选批量确认；实测同一 SKU 单价跨度 1~651，旁证价值待评估。
5. **可信度规则**：
   - 分母是该月全部有效明细的件数。不用 kg 当分母，因为 `unknown` 行算不出 kg。
   - 某月 `exact + derived` 的件数占比低于 90%，就标为「估算月」。
   - 预期结果：2025 全年和 2026 年 1–6 月大概率都是估算月。所以第一版同比基本不可用，环比从 2026 年 7 月起才可信。这是数据现状决定的，不靠改规则绕过。
   - 估算月不参与环比、同比结论，图上用斜纹区分。AI 也会拿到这个标记，不对估算月下结论。
   - 人工确认 `assumed` 只说明「采纳这个假设」，**不会把它升级为确切值**。
6. **单独修复决策台颜色解析 bug**，独立提交。Python 和 SQL 两处要一起改，对齐 stock 的 `#X/Y` 规则。
7. **身份映射覆盖率实测**（P2 能不能做的前置条件）：
   - 对照 `customer/work_item_source_service.py` 的反查写法：okki + company_id + verified + strong + one_to_one，配 `logical_owner_expression`。
   - 合并过的客户用 `resolve_canonical_customer_id` 归并，因为一个主档可能对应多个 company_id。
   - 不能用 `projection_okki_order.okki_customer_identity`：它是带 FOR UPDATE 的写路径。
   - 统计有效订单客户里能对上主档的比例。覆盖率太低的话，P2 需要先补身份，或者降级。

### P1 产品风向标页面

- **主视图 · 风向变化**：
  - 颜色×发长、品类在近 90 天与前 90 天的 kg 变化。颜色和发长只统计能解析出该维度的行，同时显示被排除的件数。
  - 小款冒头：上期不在前 20 的款（型号×颜色×发长）里，本期 ≥1 kg 且增长 ≥50% 或新出现。款切得很细、单款占比普遍很低，所以按上期排名而不是占比界定（2026-11-18 实测后调整）。
  - B1、B3 占比近 80%，型号榜基本不变，所以型号只做筛选条件，不做主榜。
- **每个款显示**：kg、件数、我卖的份额、可信度标记。点开看月度走势和维度分布。
- **客户深链**：「查看买过这款的我的客户」跳到决策台客户行动清单，并带上型号、颜色筛选。这一步要对决策台做三处最小改动，属于「不改决策台口径」的例外：
  - 前端读取 `?tab=customers&models=&colors=` 这几个 URL 参数。
  - 颜色值统一走 P0 修好的规范化规则，保证两边传的值能对上。
  - 没有 `order_intelligence:read` 权限时不显示这个链接，改为在新页面内提示。
- **AI「解读这款」**：
  - 按需调用 `app.ai.service.chat`。输入是结构化摘要，包括维度变化、可信度和对比期；枚举值在运行时注入（宪法 7）。
  - 回答里的数字只能来自输入摘要。
  - 同步调用，用 `enforce_total_timeout=True` 保证 30 秒内结束。
  - 结果存表 `ark_product_sales_ai_insights`，按「范围 + 款 + 窗口 + 映射版本」做键，24 小时内直接复用。存表而不放内存，是为了多实例共享、重启不丢、能审计。
- **权限**（宪法 8 三步）：
  - `product_sales:read`（page）：公司级产品汇总对所有业务员可见。
  - `product_sales:read_all`（data）：把「我的份额」扩展为团队和个人筛选。
  - `product_sales:admin`：映射确认。

### P2 客户产品线索（回流）

- **线索类型**：在读取时现场计算，**不写成客户事实或事件**。客户经营的规则是「建议文本不能写成事实」。
  - 颜色或发长迁移：客户常买的款，公司层面正在向某颜色或发长迁移。
  - 热款缺口：同国家或同画像的客户近 90 天在买、他从没买过的款。
  - 上次买的款：只作补货参考。补货节奏沿用决策台已有的客户级典型周期，不做「客户×款」的周期，因为数据太稀疏。
- **展示位置**：
  - 客户作战卡总览新增「产品线索」区块，每个客户最多 2 条，每条附证据（kg、占比、可信度）。
  - 工作台事项上只加一个「有产品线索」标签，不新增事项。
- **话术**：作战卡里现有的话术来源都接不上现场计算的线索：
  - agent_runtime 的 `repurchase_action_card` 写入 `ark_customer_actions.suggested_message`，要求 `claim_evidence_required`，而现场计算的线索拿不出可引用的证据 ID。
  - `mail_outreach` 生成的是正式外发邮件，场景不同。
  - 所以 P2 在线索卡片上放一个「用这条线索写话术」按钮，调用 `app.ai.service.chat`，生成结果只供复制，不写进客户行动或事实。见第 7 节第 5 条。
- **身份映射**：按 P0 第 7 步实测的结论执行。对不上主档的客户不显示线索，宁缺毋滥。

## 5. 二阶、三阶影响与对策

| 影响 | 对策 |
|------|------|
| 平台出现第三个「销量」数字（决策台按件、备货按件、风向标按 kg） | 页面统一用「kg 销量 / 件数」字样并显示口径说明。三处共用一个口径函数登记为下一期技术债，本期不改另两处的计算 |
| 映射表成为事实上的产品维度来源，catalog 将来上线后出现两份 | 预留 `catalog_sku_id`，catalog 有数据后映射表退化为「历史品名 → SKU」这一层 |
| 估算月让 AI 编出不存在的增长 | 可信度阈值同时作用于 UI 和 AI 输入，估算月禁止下趋势结论 |
| 产品线索刷屏，业务员习惯性无视 | 每个客户最多 2 条；P2 上线 4 周后看点击和采纳数据，再决定是否加反馈闭环 |
| 全量明细跨库查询慢（2025 起约 5 万行） | 结果按权限、窗口缓存 5 分钟，和决策台同一策略；映射在 SQL 外用内存字典查 |
| 新增 OKKI 品名持续产生未映射行 | 规则自动预填，计入「估算」；确认页显示新增待确认数。不做阻断 |

## 7. 已决定（2026-11-18 亮哥确认：全部按建议）

1. **公司级产品汇总是否对所有业务员开放**：P1「我卖的份额」和 P2「热款缺口」都需要公司级数据。建议开放：只给按产品汇总的 kg 和件数，不含客户和业务员明细；客户级数据仍按本人范围。不开放的话，P2 热款缺口只能用本人客户池计算，信号会很弱。
2. **默认对比窗口**：建议「近 90 天 vs 前 90 天」，另提供年内累计。2025 年同期依赖估算，同比只在可信月份显示。
3. **映射确认由谁做**：建议产品或运营的一位负责人。工作量预估在实现笔记里用实际去重品名数核算。
4. **P2 的「同画像」**：直接复用决策台的客户画像（国家 × 来源 × 客户性质 × B1/B3），还是只用国家？建议先只用国家，更好解释。
5. **话术生成方式**：建议用独立的轻量按钮，生成结果只复制、不落库。另一个选择是让线索先落库成证据，再接 agent_runtime 的复购行动卡，这样可审计、能闭环，但 P2 成本翻倍。

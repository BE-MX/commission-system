# 手机录物流单：需求与设计

版本：v0.4，2026-11-23。状态：需求定稿，第 10 节问题已全部答复（D10–D16）。v0.2 按独立审查修订（第 12 节）；第 9 节 6 项实施前必须实测。原型见 [prototype/index.html](prototype/index.html)，从仓库根目录静态服务打开，用 `.claude/launch.json` 的 `factory-inbound-prototype` 即可。

## 1. 结论与范围

现在一个包裹的物流单要录两次：业务员先在待发货区用手机拍运单，回到电脑后再在验货单上「上传物流单」。本需求把两次合成一次：

- 业务员在手机上打开「手机录物流单」，看到自己范围内**已提交验货、还没关联物流单**的验货单列表。
- 点某张验货单的「拍运单」，直接进入取景。取景框实时标出运单边缘，按快门后自动裁正、默认增强，**拍完不再弹调整框**。
- 系统从照片读出运单号，条码优先，AI 识别兜底。业务员点「同步物流信息」，看承运商返回的结果和系统核对结论，确认无误后提交。
- 提交即走现有的「录入物流跟踪 + 关联验货单」流程，运单照片作为物流单附件留档。

**关联即对外可见**：运单关联验货单后，客户门户会立刻按 `shipment_tracking_id` 向该客户展示运单号和轨迹（`portal/fulfillment_service.py`）。所以防止把 A 客户的运单关联到 B 客户的验货单，是本需求的头号风险，F4 的核对规则都围绕它设计。

不做：

- 不改电脑端「上传物流单」弹框。它继续可用，和手机端写同一套关联；F5 的幂等、F4 的跨客户阻断两端共用。
- 不改共用手机发货质检页 `/shipping/scan`。
- 不做「先拍照、系统自动猜是哪张验货单」（第 11 节）。
- 不改短链和钉钉推送。物流轮询只改一处：未揽收运单不能提前停止跟踪（F7）。

## 4. 用户流程

```
验货单列表（待录）
  └─ 点「拍运单」
       └─ 取景：实时边缘框 + 实时解条码 ──快门──┬─ 有边缘 → 自动裁正 + 增强
                                                └─ 无边缘 → 拖四角 → 裁正 + 增强
            └─ 存图并识别（条码结果 + AI 识别）
                 └─ 核对页：照片、运单号（标来源）、承运商
                      └─ 「同步物流信息」→ 承运商结果 + 系统核对（客户、国家、9610）
                           └─ 提交 → 成功 → 回列表，定位下一张
```

## 5. 功能需求

### F1 手机验货单列表

- 路由 `/shipping/waybills`，全屏手机布局（同 `/shipping/scan` 的外壳，不套主站侧栏），菜单放「发货检验」组，标题「手机录物流单」。
- 进入权限：`shipping_inspection:write` 或 `:admin`。缺 `tracking:write` 时页面可以进，但「拍运单」按钮置灰，并说明「需要物流单上传权限，请联系管理员」。
- **同时覆盖小满出库和方舟本地出库**两种验货单。范围 = 现有 `_inspection_scope`（订单业务员）**并上**「验货单关联发票的 `merchandiser_id` 是本人」（D12）。关联时的范围校验也改成同一口径，避免出现「看得到、关联不了」。
- **自动排除不走快递的单**（D15）：发票「发货方式」（`express_channel`）现有选项全是快递（DHL普货、FEDEX普货、DHL9610、FEDEX9610、顺丰、其他快递），没有可识别的非快递值。本期在选项里加「自提」「货代/海运」两项；验货单关联的发票全部是这两项时不进「待录」。发货方式为空的历史发票照常列出，不猜。
- 两个页签：
  - **待录**：已提交、且按 `shipment_brief` 口径没有有效物流单的验货单（运单被软删的也算没有），排除不走快递的单。默认只列最近 14 天提交的，底部有「查看更早」；搜索不受日期限制。
  - **今天已录**：今天由本人关联的验货单，显示运单号和录入时间，可以「更换物流单」（二次确认后重走拍摄流程，限制见 F5）。
- 卡片显示：出库单号、客户名、客户国家、提交时间、商品件数；走 9610 的单加「9610」标记（口径见 F4）。件数和国家需要批量跨库查询，现有 `list_records` 不提供。
- 顶部搜索框：出库单号、客户名模糊匹配。

### F2 取景与自动裁正

- 点「拍运单」直接打开后置相机全屏取景，不经过「拍摄文档 / 选择照片」入口页。
- **取景页顶部醒目显示本单客户名和国家**，提醒业务员核对手里的包裹。
- 取景画面实时叠加边缘框（现有找边算法，约每 135ms 一帧）。提示文案：
  - 未找到边缘：「把运单四个角都放进画面」
  - 已找到：「已对准，可以拍照」，边框变为主色
- 取景时同时**从原始视频帧解条码**。读到合法单号就在画面上显示「已读到 12 3456 7890」。原因：裁正、增强后再解一维码，成功率可能下降。
- 按快门后的边缘取值，按顺序：
  1. 对整张照片重新找边（现有逻辑），找到就用；
  2. 重找失败、但取景最后一帧有边缘 → 用取景时的四角坐标（快门拍的就是视频帧，坐标可以直接用）；
  3. 两者都没有 → 进入拖四角步骤。
- 有边缘的情况一律不显示调整步骤，直接裁正、增强、进入识别。
- 核对页保留「重拍」和「调整边缘」两个入口，供裁偏时使用（比如找到的是纸箱边而不是面单）。
- 相机打不开（权限被拒、非 HTTPS）时，退回系统相机拍照，后续流程不变。取景页也提供「从相册选」。

### F3 识别运单号

- 单号来源，按顺序取第一个合法值：
  1. 取景时解到的条码
  2. 裁正图上解到的条码
  3. AI 识别
- 合法条码：符合承运商单号格式的才算。DHL 是 10 位数字；面单上以 `JD` 开头的件号条码、以 `2L` 开头的路由条码一律忽略。
- 条码和 AI 都有结果但不一致时，用条码，并提示「AI 识别为 xxx，已按条码填写」。
- 单号旁标来源：「条码」/「AI 识别」/「手动」。业务员可以点开手改（数字键盘）。改动后来源变为「手动」，之前的同步结果和确认全部作废，需要重新同步。
- 承运商判定：
  - 条码格式能确定的直接定（10 位数字 → DHL），不显示选择器，只标「按单号格式判定为 DHL」；
  - 否则用 AI 结果，并显示选择器让业务员核对；
  - 仍未知时必须选。
  - 写入物流跟踪时 `entry_source` 增加 `barcode` 取值。
- 收件人、国家：优先用 AI 结果，识别不到再用预填（订单联系人、客户国家），折叠在「收件信息」里，可改。发件日期默认今天。**收件国家为必填**（`WaybillCreate` 要求），AI 和预填都没有时，展开「收件信息」并标红，不能提交。
- 条码和 AI 都没读出单号：提示「没读出运单号，请重拍或手动输入」，停在核对页。

### F4 同步物流信息与核对

「同步物流信息」调用新的预览接口（第 6.2 节），只查询、不写库，一次返回承运商结果和系统核对两部分。

**承运商结果**

| 结果 | 页面展示 | 能否提交 |
| --- | --- | --- |
| 查到轨迹 | 当前状态、最新一条事件（时间、地点、描述），可展开最近 5 条；DHL 返回目的国时一并显示 | 能 |
| 暂无记录 | 「承运商暂无这张运单的记录。包裹还没被揽收时很常见，提交后系统会持续跟踪。」 | 能 |
| 查询失败 | 「物流接口暂时查不到，可以重试，也可以先提交，系统稍后自动查询。」+ 重试按钮 | 能，按钮文字为「仍然提交」 |
| 暂不支持查询 | 「方舟还不能查询 UPS 轨迹，提交后只做登记。」 | 能 |
| 单号格式不对 | 「这不像 DHL 运单号（应为 10 位数字）」 | 不能，必须改单号 |

**系统核对**（按单号查已有记录，**不区分承运商**）

| 情况 | 处理 |
| --- | --- |
| 单号是新的 | 正常提交，新建运单 |
| 已有运单，未关联任何验货单，或只关联了**同一客户**（按 company_id 比较）的验货单 | 属于合并发货或先录后关，提示「运单已录入，已关联本客户 N 张验货单」，提交动作改为「关联已有运单」，**承运商沿用已有记录** |
| 已有运单，关联了**其他客户**的验货单 | **红色阻断**：「这张运单已关联到另一位客户的验货单，很可能拍错了包裹，请核对手里的包裹。」不显示对方的客户名和单号，不能提交，无放行入口（D9） |
| 已有运单，不在本人物流跟踪范围内，且没关联其他客户 | 允许关联（D14）：提示「运单已由其他同事录入」，不返回对方的收件信息和录入人；运单原归属不变。`bind_shipment` 对这条路径改为「验货单范围 + 客户核对」，不再套物流跟踪数据范围 |
| 国家不符 | 承运商目的国、AI 识别的收件国家，**统一转成 ISO 国家代码后**分别和客户国家比较；任一不符就黄色警示「运单寄往 X，验货单客户在 Y，请确认没有拍错包裹」，提交前要再确认一次 |
| 收件人不符 | AI 识别的收件人和预填联系人、客户名都对不上时，弱提示「面单收件人 xxx 与客户资料不一致」，不阻断（小客户常以人名建档，误报多） |
| 9610 混发 | 同一运单里会混进 9610 和非 9610 的验货单，或者 9610 的单用了非 DHL 承运商 → 黄色警示，说明会在 9610 核对里报异常（`mixed_waybill` / `non_dhl`），不阻断 |

- 9610 标记口径和现有 `_cross_border_prefill` 一致：发票付款方式含「便捷发货」，且渠道不是 FEDEX9610。
- 预览接口不转发 `WaybillConflict` 里的录入人用户名。
- 没点同步时，提交按钮置灰并提示「先同步物流信息」。修改单号、承运商或收件国家，都要重新同步，之前的二次确认也一并作废。
- 请求进行中按钮置灰，防止连点；不做服务端进程内限流（多实例下无效）。

### F5 提交

- 新运单：调用上传并关联接口，带 `photo_token`、单号来源、同步结果。**手机端不再同步调一次承运商**（预览已经查过），改为异步入轮询队列，避免最坏情况要连等两个 30 秒。
- 已有运单：调用关联接口，按单号匹配跟踪记录，承运商以已有记录为准。
- **幂等**：验货单已经关联同一运单时，直接返回成功，不报「物流单关联已变化」。处理手机网络下「第一次已成功、前端超时重试」的情况。
- 运单归属（D13）：新建运单时，`ShipmentTracking.dingtalk_user_id/name`（物流跟踪数据范围和钉钉推送都看它）填**订单业务员**（发票 `sales_user_id` → `ark_users.dingtalk_id`），`ark_waybills.created_by` 和照片 `created_by` 记拍照人。业务员没绑钉钉时退回记拍照人，并在审计里标出。`create_waybill_with_tracking` 需要增加「归属人」参数，PC 入口不传时行为不变。
- 9610 的单在核对页显示现有提醒「本单走 9610，请确认已在 DHL 填写跨境申报」，并列出阿里信保订单号；不阻断。
- 更换物流单：9610 的单即使已导出报关也允许更换（D16）；核对页提示「本单已导出报关，更换后会在 9610 核对里标为异常」，9610 核对据此报异常。
- 版本冲突（验货单被撤回，或别人刚关联过别的运单）：提示「验货单已变化，已刷新」，回列表。
- 运单已入库但关联失败（现有 `ShipmentLinkError`）：沿用现有提示。
- 成功：轻提示「已录入 · 运单号」，回到「待录」列表并定位到下一张，方便连续处理一排包裹。

### F6 物流单照片存档与查看

识别时拍下的那张物流单照片，就是存档照片，不另拍、不另传。照片随关联一起保存在系统里，之后可以随时查看。

**存档**

- 新增「存图并识别」接口：裁正图和原图一次上传，服务端保存后调用 AI 识别，返回识别结果和 `photo_token`；提交时只带 token。这样图片只传一次，也不会出现「关联成功、照片没存上」。
- 两张都留：增强裁正图用于查看；原图用于事后核对裁偏的情况。
- token 只能被同一用户、同一验货单在 24 小时内用一次；过期没用的照片由定时任务清理。
- 一张验货单每次关联各留一组照片。更换物流单时，旧照片保留并标「已替换」。
- 新文件登记 `core/storage/transfers`（COS 托管）。保留期限与验货照片一致。

**查看入口**

| 位置 | 显示 |
| --- | --- |
| 手机「今天已录」卡片 | 物流单缩略图，点开看大图 |
| 电脑端验货单列表 | 物流单列有照片标记，点开看大图 |
| 电脑端验货单详情「物流单」区块 | 当前照片缩略图；下方「历史照片」列出已替换的照片及替换时间、操作人 |
| 物流跟踪运单详情 | 按运单列出所有关联验货单的物流单照片（同一包裹合并发货时有多张），只显示本人有权查看的验货单 |

**大图查看器**（手机、电脑共用）

- 默认显示增强裁正图，可以切换到「原图」。
- 手机上支持双指缩放，电脑上支持滚轮缩放，方便看清单号和收件信息。
- 显示拍摄人、拍摄时间、单号来源（条码 / AI 识别 / 手动）。
- 有「下载」按钮，下载按当前显示的那张。

**权限与边界**

- 能看到这张验货单的人就能看照片，读图走新端点并校验验货单范围（现有读图端点只查验货照片表）。图片地址不直接暴露，走带 token 的 axios blob，与验货照片一致。
- 不进验货打印，不进客户门户。

### F7 未揽收运单持续跟踪

- 承运商明确回答「查无此单」（DHL `no shipments` 或 404）时，运单创建后 **7 天内**不计入 `consecutive_errors`，照常每 3 小时查一次；真正的接口错误照旧计数。
- 7 天后仍查无此单，停止轮询，并在物流跟踪里标「长期未揽收」，留给专员排查。
- 这一条同时影响电脑端录入的运单，9610 核对的「未揽收」判断也依赖它。

## 6. 数据与接口

### 6.1 数据

新表 `ark_shipping_waybill_photos`，表注释「验货单物流单照片」。迁移编号实施时按 AGENTS.md 查全部分支后确定。

| 列 | 类型与说明 |
| --- | --- |
| `id` | BigInteger 主键 |
| `inspection_id` | BigInteger，FK `ark_shipping_inspections.id` |
| `shipment_tracking_id` | BigInteger，FK `shipment_tracking.id`，提交前为空（只拿到 token、还没提交） |
| `rectified_path` / `original_path` | 增强裁正图、原图的相对路径（`file_service` 约定） |
| `number_source` | 单号来源：barcode=条码，ocr=AI 识别，manual=手动 |
| `sync_result` | 同步结果：found / not_found / failed / unsupported / skipped（电脑端补传照片时为 skipped） |
| `token` | 一次性提交凭证（唯一） |
| `replaced_at` / `replaced_by` | 被更换物流单替代的时间和操作人，空表示当前有效 |
| `created_at` / `created_by` / `updated_at` / `updated_by` | 审计四件套，北京时间 |

不往 `ark_shipping_inspection_photos` 里加类型：那张表的照片会进验货打印和照片数统计，混进去要改多处判断。也不用 `shipment_tracking.source_image_url`：同一运单关联多张验货单时，每次关联各有一份证据，按验货单存更清楚。

审计：`shipment_bound` 事件的 `context.source` 改由调用方传入，手机端记 `mobile`；`payload` 增加 `number_source`、`sync_result`、核对结论。需要从 `create_and_bind` → `_bind_and_commit` → `bind_shipment` 一路加参数。

### 6.2 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |

## 8. 异常与边界

| 情况 | 处理 |
| --- | --- |
| 一个包裹装了多张同一客户验货单的货 | 第二张起核对为「已录入，同一客户」，提交为关联已有运单 |
| 选错卡片，把别的客户包裹的运单拍到本单 | 那张运单已录过 → 跨客户阻断；还没录过 → 只能靠国家、收件人核对和取景页的客户名提醒。出库单不随包裹走（D10），这是本方案接受的剩余风险；第 11 节「先拍后配」可进一步降低 |
| 一张验货单分多个包裹 | 现有模型一张验货单只关联一个物流单，本需求不改 |
| 拍完离开页面或锁屏 | 关相机；已存图未提交的 token 24 小时后清理 |
| 网络差，AI 识别超时 | 条码已读出单号时不受影响；都没有就提示手动输入 |
| 提交超时后重试 | 幂等返回成功（F5） |
| 运单历史上以「未知」承运商录入 | 按单号匹配，承运商沿用已有记录，不会卡死 |

## 9. 实施前实测项

1. **DHL 未揽收运单**：在 DHL 网站建单、还没揽收时，跟踪接口返回 404、空事件，还是只有 `SM` 事件？返回体里能不能拿到目的国？这决定 F4「暂无记录」的判定和 F7 的「查无此单」识别。
2. **条码解码方案**：Android Chrome 自带 `BarcodeDetector`（支持 Code 128），iOS Safari 和部分 App 内置浏览器没有。需要确认业务员的手机和浏览器分布，决定是否引入条码库（如 `zxing-wasm`，新增前端依赖）。
3. **DHL 面单条码**：用真实面单确认哪个条码是 10 位运单号，以及 `JD`、`2L` 条码的实际格式。
4. **现场拍摄条件**：运单装在透明袋里反光；找边时找到的是纸箱边而不是面单。决定 F2 的边缘取值是否要加「面单比例」约束。
5. **AI 识别耗时**：手机网络下的实际耗时。如果常超过 5 秒，核对页先显示条码结果，AI 结果到了再补收件信息。
6. **国家写法**：客户国家（overlay、`customer_info.country_name`）、AI 识别结果、DHL 目的国三种来源的写法，确认能稳定转成 ISO 代码。

## 12. 审查记录

v0.1 由独立代理对照代码审查，主要问题已采纳，修改如下：

- 已有运单的处理从「直接放行」改为「同客户放行、跨客户阻断」（F4、D9）。依据：关联后客户门户立即展示该运单。
- 按单号匹配、承运商沿用已有记录（F4、F5）。依据：判重只按单号，关联却按单号+承运商，两者对不上会卡死。
- 新增 F7。依据：未揽收运单约 30 小时就停止轮询，「提交后自动跟踪」原本做不到。
- 提交幂等、手机端跳过同步轮询（F5）；国家比较统一用 ISO 代码，并加收件人弱核对（F4）；承运商结果增加「暂不支持查询」，因为没有 UPS 适配器。
- 照片改为先存图拿 token、两张都留（F6）；新表补齐审计四件套和注释（6.1）。
- 列表覆盖本地出库，统一范围口径；补收件国家必填和 9610 混发预警。
- F2 快门后的边缘取值规则写清楚；改为从原始视频帧解条码。
- 修正事实陈述：列表范围和关联范围是两套口径；PC 的 PUT 不要求 `tracking:write`；承运商适配器没有 UPS，也没有目的国字段；`shipment_tracking` 有 `source_image_url`。

## 13. 验收标准

1. 业务员和发票指定的跟单员，手机登录后「待录」只出现自己范围内已提交、未关联物流单、走快递的验货单；发货方式为「自提」「货代/海运」的不出现。
2. 点「拍运单」一步进入取景，取景页醒目显示本单客户名和国家；取景时找到边缘，按快门后不出现调整框，直接进入识别，图片为增强效果。
3. 取景和拍后都没找到边缘时，出现拖四角调整。
4. DHL 面单能在取景时读出 10 位条码单号，来源标「条码」；遮住条码时由 AI 识别补上，来源标「AI 识别」；两者不一致时按条码并提示。
5. 未点「同步物流信息」不能提交；五种承运商结果的提示和提交按钮符合 F4。
6. 运单已关联同一客户 → 提交为关联已有运单；已关联其他客户 → 阻断，不显示对方信息；同事录入且未关联其他客户 → 可关联，不显示对方收件信息和录入人。
7. 国家不符（统一为国家代码后比较）时需要二次确认；修改单号、承运商或收件国家后必须重新同步。
8. 提交超时后重试不报错；验货单被撤回时提示并刷新列表。
9. 提交后：物流跟踪出现运单，归属为订单业务员、录入人为拍照人；未揽收运单 7 天内持续轮询；审计记录 `source=mobile`。
10. **照片存档**：识别时拍的照片在提交后可以在四个入口看到（F6）：手机「今天已录」、电脑端验货单列表、验货单详情、物流跟踪运单详情；大图可切换增强图和原图、可缩放、可下载，显示拍摄人、时间、单号来源；更换物流单后旧照片在「历史照片」里仍能查看。
11. 没有该验货单查看权限的人，通过读图端点也取不到照片。
12. 无 `tracking:write` 的账号能看列表，但不能拍运单。
13. 全程在 375px 宽的手机上无横向滚动，按钮可点区域不小于 44px。

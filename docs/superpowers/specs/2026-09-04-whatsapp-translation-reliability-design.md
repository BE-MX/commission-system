# WhatsApp 翻译扩展 v1.2：完整性、响应速度与品牌升级

日期：2026-09-04

状态：设计已由亮哥逐节确认；本文等待最终审阅后进入实现。

前置设计：

- `2026-09-03-whatsapp-translation-extension-design.md`：隐私、授权和数据边界。
- `2026-09-04-whatsapp-translation-v2-ux-quality-design.md`：发送预览、术语表、中文交互和明暗主题。

本文不放宽前置设计的隐私边界。扩展仍只处理 WhatsApp Web 一对一纯文本；聊天正文、译文、联系人、聊天标识、页面 HTML 和截图不得进入持久化存储、日志、测试夹具或 Git。

## 一、结论

v1.2 同时解决四类用户问题：

1. 连续来信偶发漏译：放行已转发的纯文本结构，引入不会饿死的扫描调度、三并发队列和单条消息手动翻译入口。
2. 翻译慢或“连接方舟失败”：缩短排队等待，合并重复请求，在同一额度预留内短重试瞬时上游故障，并把错误拆成可行动的中文状态。
3. “替换到输入框”无反应：用 Chromium 原生编辑动作写入 WhatsApp 受控编辑器，并在显示成功前回读校验。
4. 发送语言需要手选：复用来信翻译已经返回的源语言，自动更新当前对话的发送目标语言；不增加第二次 AI 调用。

同时完成扩展品牌升级：采用亮哥选定的“黑绿双气泡 + `LeShine` + `译`”图标，界面以莱莎黄黑为主色、WhatsApp 绿为状态辅助色。

扩展版本升为 **1.2.0**。这是新增用户能力，不按补丁版本处理。

## 二、已确认的根因

### 2.1 漏译

- `messageParser.ts` 对消息内全部 `data-testid` 使用严格白名单；WhatsApp 的转发标记不在白名单中，因此截图里的“已转发”纯文本会被整条排除。
- MutationObserver 每次变化都会清除并重置 300ms 定时器；页面持续变化时扫描可能被不断后推。
- 批处理逐条 `await`，前一条慢请求会阻塞后续消息。
- 当前没有按消息键维护的统一状态；自动扫描、DOM 变化和手动重试无法共用一个请求生命周期。

### 2.2 替换按钮无反应

按钮到控制器的事件链已经接通。失败发生在 `replaceComposer()`：代码直接设置 `contenteditable.textContent` 后就返回成功，没有验证 WhatsApp 的受控编辑器是否接受变更。WhatsApp 可以立即丢弃这次 DOM 改写，因此用户看到按钮点击后没有结果。

### 2.3 连接失败与长文本慢

- 来信串行执行会放大单个慢请求的影响。
- 扩展只设 20 秒总超时，没有针对浏览器到后端的瞬时网络失败做一次安全重试。
- 后端直连模型只调用一次，连接重置或上游 502/503/504 会直接呈现为通用 AI 不可用。
- 当前提示没有区分扩展网络、莱莎后端、方舟上游、模型超时、授权和额度，用户不知道系统是否会自行恢复。

## 三、来信翻译队列与单条手动入口

### 3.1 支持边界

继续支持：

- 一对一聊天的普通纯文本。
- 一对一聊天中带 WhatsApp“已转发”标记的纯文本。

继续拒绝：

- 群聊、图片、语音、视频、文件、贴纸、联系人卡片、位置、投票和未知结构。
- 同一气泡里无法唯一确定正文节点的结构。

选择器仍只允许存在于 `src/whatsapp/`。新增转发结构必须用脱敏合成夹具覆盖 direct、group 和 unknown 回归测试。

### 3.2 调度模型

内容脚本维护一个聊天代际和一个按 `localKey` 索引的内存状态表：

- `pending`：已发现，等待工作槽位。
- `running`：请求进行中。
- `success`：译文已渲染。
- `retryable_error`：临时失败，可重试。
- `blocked`：授权、额度或不支持等不可自动重试错误。

队列最多同时运行 3 条翻译。自动扫描、DOM mutation 和手动点击都进入同一状态表；同一 `localKey` 同时最多存在一个请求，从源头避免重复调用和重复扣额。

MutationObserver 只在“当前没有扫描定时器”时安排一次短延迟扫描，不再反复重置计时。扫描期间再次发生变化只标记 `dirty`；本轮结束后再补扫一次。持续页面变化因此不能让翻译扫描饿死。

### 3.3 手动“译此消息”

- 消息进入 `pending` 后 1 秒仍未取得工作槽位，气泡下显示低干扰按钮“译此消息”。
- 点击后把该任务提升到等待队列首位，不创建第二个请求。
- 已在 `running` 时按钮变成“翻译中…”，重复点击无效。
- 成功后按钮消失；临时失败时原位置显示“重试翻译”。
- 授权、额度和不支持类型不显示误导性的重试入口，而是显示对应下一步。

聊天切换会递增代际。旧聊天的晚到结果可以完成后台请求，但不得写入新聊天 DOM，也不得改变新聊天语言。

## 四、自动发送语言

### 4.1 数据来源

incoming 翻译响应已经返回 `detected_source_language`。扩展在成功渲染最新有效来信后复用该字段更新发送语言，不增加模型调用、等待或费用。

发送目标语言集合与可识别语言集合对齐：

`zh-CN`、`en`、`es`、`fr`、`ar`、`ja`、`de`、`nl`、`sv`。

因此补齐德语、荷兰语和瑞典语的 outgoing 合同、选择器选项、提示词约束和术语表目标语言支持。

### 4.2 更新规则

- 只采用当前聊天、当前代际中成功完成的最新一条来信。
- 去除空白和标点后没有字母，或只有 1–2 个字母的表情/数字/模糊短消息，不改变发送语言。
- 识别结果不在支持目标语言集合时不改变发送语言。
- 有效结果通过现有 `chat-language/set` 按聊天保存；再次打开该聊天时直接恢复。
- 用户手动选择立即生效并保存；收到下一条可可靠识别的有效来信后，再按“最后一条消息语言”规则自动更新。
- 更新只改变工具条语言选项，不自动翻译输入框、不覆盖预览、不发送消息。已有预览在目标语言改变时作废，避免替换旧语言译文。

## 五、发送栏替换修复

“替换到输入框”使用单一可验证流程：

1. 按钮进入“替换中…”并暂时禁用重复点击。
2. 校验聊天代际未变、输入框内容仍等于生成预览时的原文。
3. 聚焦唯一的 `contenteditable`，用 Selection 选中其全部内容，再使用 Chromium 原生 `insertText` 编辑动作写入译文，使 WhatsApp 编辑器接收到真实编辑事件。
4. 重新读取规范化后的输入框内容；只有与预期译文一致才显示“已替换为译文 · 恢复中文”。
5. 写入失败或回读不一致时保留预览，显示“未能写入输入框，点击重试”。

任何路径都不得查找、点击、触发或调用 WhatsApp 发送控件。

## 六、速度与稳定性

### 6.1 非模型优化

- 三并发工作池消除串行头阻塞。
- 非重置式扫描避免持续 DOM 变化导致等待。
- 按消息状态合并自动、mutation 和手动触发。
- 手动任务优先，保证用户明确操作及时反馈。
- 客户端只渲染状态变化，不做循环动画和高频 DOM 重建。

### 6.2 分层重试和总时限

重试只覆盖真正的瞬时错误：

- 浏览器到莱莎后端：网络中断、网关 502/503/504 最多自动重试 1 次，使用相同 `request_id`。
- 莱莎后端到模型上游：连接错误和上游 502/503/504 最多短重试 1 次；额度只预留一次，最终成功/失败只记一次业务统计。
- 模型已经耗尽主要超时预算时不再追加一个完整超时请求，避免用户等待翻倍。

不重试：授权失效、权限不足、扩展过期、今日额度用完、不支持语言、正文过长和模型返回合同错误。

后端协调器继续合并相同 `request_id` 的在途请求并缓存成功结果。瞬时失败的内部重试发生在同一次额度预留内，避免重复计费。

### 6.3 面向用户的错误状态

- `network_error`：网络暂时中断，正在重试；失败后提示检查网络并点重试。
- `backend_unavailable`：莱莎服务暂时不可用，正在恢复。
- `ai_unavailable`：翻译服务连接失败，可点重试。
- `ai_timeout` / `request_timeout`：本次响应超时，可单条重试。
- `daily_quota_exceeded`：今日额度已用完，显示次日恢复，不自动重试。
- 授权类错误：提示重新授权，不使用“连接方舟失败”这一笼统文案。

日志只记录 request id、方向、语言代码、字符数、阶段耗时、模型日志 id 和错误码，不记录正文或译文。

## 七、模型基准测试

### 7.1 方法

读取系统中已启用的直连文本模型配置，在内存中复用完全相同的 WhatsApp 翻译系统提示词和参数，只替换 provider/model；不修改生产 preset。

每个模型：

- 1 次预热，不计入结果。
- 30 次计量调用：英语、德语、荷兰语、西班牙语、瑞典语各覆盖短、中、长三档脱敏合成商务文本，每个组合 2 轮，随机化模型与样本顺序。
- 输入不得包含真实 WhatsApp 消息、联系人或客户信息。

统计：成功率、P50、P95、最大延迟、超时数、JSON 合同有效率、语义完整性、数字/单位/换行/emoji 保留和可获得的 token/费用数据。

### 7.2 选择原则

推荐“快速且稳定”的模型，不以单次最快为准：

1. 成功率和合同有效率必须先达标。
2. 再比较 P50 与 P95，优先消除慢尾。
3. 翻译漏句、数字改变或格式损坏直接降级。
4. 性能接近时选择成本更低者。

基准测试只生成报告和推荐，不自动切换生产模型。模型切换属于独立生产决策。

## 八、品牌图标与主题

### 8.1 已选图标

采用亮哥确认的第二版演进稿：

- 黑色与 WhatsApp 绿色双对话气泡。
- 两个气泡的关系形成流动的 S 形，呼应 LeShine 原品牌字形。
- 绿色气泡内放白色“译”。
- 大尺寸图标包含黑色 `LeShine` 品牌字样。

生成图只作造型参考。生产资产重绘为干净的矢量源图，使用精确纯色，无渐变、阴影、光效、纹理或棋盘背景。

尺寸策略：

- 48px、128px：保留双气泡、`译` 和 `LeShine`。
- 16px、32px：保留双气泡和 `译`，去掉缩小后不可读的完整品牌字样。

输出 16/32/48/128 PNG，并在 manifest 的 `icons` 与 action 图标中声明。图形借鉴消息应用的沟通语义，但不复制 WhatsApp 官方商标。

### 8.2 主题色

- 主品牌黄：`#FDD956`，用于主要操作、选中态和品牌区域。
- 品牌黑：`#080303`，用于黄底文字、图形和高强调信息。
- WhatsApp 绿：`#25D366`，仅用于连接成功、语言已同步和图标辅助色。
- 浅色背景使用暖白，深色背景使用近黑暖灰；正文始终满足可读对比度。

“翻译”“替换到输入框”等主按钮改为黄底黑字；绿色不再承担主要按钮，以免品牌和状态含义混淆。来信译文左边线、成功点和连接状态可使用绿色。

## 九、验证与发布

### 9.1 自动测试

扩展测试：

- 普通、转发、群聊、媒体和 unknown 结构识别。
- 连续 mutation 不饿死；最多三并发；同消息不重复请求。
- pending 1 秒显示手动按钮、手动优先、运行中防重复、失败后重试。
- 切换聊天后旧结果不渲染、不更新语言。
- 最新有效来信更新目标语言；模糊短消息不更新；聊天之间隔离；手动覆盖。
- 德语、荷兰语、瑞典语 outgoing 合同。
- 受控编辑器拒绝直接 DOM 改写的复现测试；原生编辑后回读成功/失败；永不触发发送。
- 新主题变量、manifest 图标声明和版本 1.2.0。

后端测试：

- 德语、荷兰语、瑞典语目标语言校验和提示词值域。
- 上游连接/502/503/504 的一次短重试；非瞬时错误不重试。
- 重试共用一次额度预留和同一业务结果统计。
- 错误码分类和正文不进入日志。
- 基准脚本使用脱敏样本、不修改 preset、不输出密钥。

执行：

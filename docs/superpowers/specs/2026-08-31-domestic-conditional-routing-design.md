# 内贸条件工序与自动跳过设计

## 目标

让内贸订单明细在保持现有按数量拆批、逐件二维码、计件工资和撤销审计能力的前提下，支持以下真实生产流转：

- “发加工点”按当时产能和交期，把同一订单明细拆批发往丹东或李晓宏。
- 李晓宏手钩完成时，按现场判断把同一批次继续拆为需要递针或不需要递针。
- 毛坯质检按结果把合格件直接放行、问题件送毛坯维修；维修完成后直接汇合，不复检。
- 后处理定型是非阻塞可选工序：做了就扫码计件，没做就直接入库，由入库动作自动记录跳过。
- 普通工人不操作“跳过”按钮；系统根据分流结果或下一道扫码自动生成跳过记录。

本设计只改变内贸报工。外贸生产订单继续使用现有严格线性、整行 0/1 的报工逻辑。

## 当前机制与根因

现有 `process_route_step` 只有顺序号，`ark_domestic_item_progress` 只有实际完成数量。可报数量固定为：

`上一道实际完成数量 - 本道实际完成数量`

因此每道工序都被解释为必经节点，无法表达分支、质检放行和可选定型。当前数据库中的“头套网帽（递针）”也把丹东、李晓宏、毛坯维修和后处理定型全部串成一条18步线性路线。

根本问题不是缺少一个“跳过按钮”，而是系统缺少“某个具体单件已合法通过本道”的独立事实。

## 方案选择

采用“线性路线 + 单件分流结果 + 稀疏跳过记录”，不建设通用 DAG/流程图引擎，也不按条件组合复制大量固定路线。

核心公式改为：

`有效通过单件 = 实际报工单件 ∪ 有效跳过单件`

下一道只接收具体身份已经有效通过上一道的单件。实际报工继续计入工资；自动或人工跳过只改变路线资格，不进入工作量。

## 路线规则

新增内贸专用路线规则，按 `(route_id, process_id)` 绑定到共享路线步骤，不改变共享路线表语义。

规则类型：

1. `required`：默认值，必须实际报工。
2. `decision`：实际报工时必须提交结果分配；每个结果配置需要跳过的后续工序。
3. `optional`：可以实际报工，也可以在下一道报工时自动跳过。

分流规则的配置保存为受服务端校验的 JSON：

```json
{
  "options": [
    {"code": "dandong", "label": "丹东", "skip_process_ids": [30, 31]},
    {"code": "lixiaohong", "label": "李晓宏", "skip_process_ids": [28, 29]}
  ]
}
```

服务端校验结果编码唯一、标签非空、跳过目标属于同一路线且位于触发工序之后，并拒绝会跳过触发工序或路线外工序的配置。

“头套网帽（递针）”与“发片网底（递针）”使用相同条件配置：

- 发加工点：`decision`，丹东结果跳过李晓宏手钩/递针，李晓宏结果跳过丹东收货/发货。
- 李晓宏手钩：`decision`，需要递针不跳过，不需要递针跳过李晓宏递针。
- 毛坯质检：`decision`，合格跳过毛坯维修，需维修不跳过。
- 后处理定型：`optional`。

稳定结果编码依次为 `dandong/lixiaohong`、`needle/no_needle`、`qualified/repair`；编码与跳过目标共同构成业务契约，不能只凭标签或选项目标集合判断等价。两条路线都不允许在上述四个节点之外增加条件规则。

## 运行数据

### 报工结果

现有报工流水增加 `outcome_json`，记录本次结果与数量分配；报工到单件的映射增加 `outcome_code`，使同一次20件质检可以精确保存15件合格、5件维修。

数量模式按稳定的单件序号分配身份；逐件模式只处理二维码对应单件。无论入口如何，落库后都得到同一套逐件事实。

### 跳过流水

新增跳过流水和跳过单件映射：

- 跳过流水保存工序、数量、来源、原因、触发报工流水、操作人、时间和撤销状态。
- 跳过单件映射保存具体 `unit_id`。
- 自动分流跳过来源为 `decision`。
- 下一道触发的可选工序跳过来源为 `optional_bypass`。
- 主管异常放行来源为 `manual`，必须填写原因。

跳过流水不进入工资和工作量查询。

## 数量与资格计算

每个进度步骤对外提供：

- `completed_qty`：实际报工数量。
- `skipped_qty`：有效跳过数量。
- `passed_qty`：两者并集数量。
- `required_qty`：该工序实际需要做的总数量，即上游有效通过数量减去已确定跳过数量。
- `reportable_qty`：当前已经从上游到达、尚未实际报工且未跳过的数量。

进度状态与订单完工判断使用 `passed_qty`，计件统计仍只使用 `completed_qty` 和有效报工流水。

为避免按步骤逐条查询，进度服务一次加载明细全部有效报工单件和跳过单件，在内存按 `progress_id` 归并集合。

## 四个特殊节点

### 发加工点

数量模式一次扫码填写“发丹东”和“发李晓宏”数量，合计可小于当前可报数量；未分配数量保留待处理。逐件模式选择一个目的地。

提交后，本次实际报工照常记入“发加工点”工作量，并按结果为对应单件生成另一条分支的跳过流水。

### 李晓宏手钩

只接收已经选择李晓宏路线的单件。数量模式填写“需要递针”和“不需要递针”，逐件模式二选一；不需要递针的单件自动跳过“李晓宏递针”。

### 毛坯质检

数量模式填写“质检合格”和“需要维修”，逐件模式二选一。合格件自动跳过“毛坯维修”；问题件只有完成维修后才能进入下一道。维修后不返回质检。

### 后处理定型

需要定型的数量正常扫码。入库扫码时：

- 已完成定型的单件直接具备入库资格。
- 尚未定型、但已完成定型前一道工序的单件，由本次入库报工自动生成“跳过后处理定型”。
- 已入库单件不能补扫定型。

数量模式优先选择已经完成定型的单件，再为不足数量自动跳过定型；逐件模式只处理当前二维码单件。

## 扫码交互

后端在 `next_step` 返回规则类型和可选结果。三端共用同一契约：

```json
{
  "rule_type": "decision",
  "outcome_options": [
    {"code": "qualified", "label": "质检合格"},
    {"code": "repair", "label": "需要维修"}
  ]
}
```

- 普通工序保持现有数量确认或逐件自动提交。
- 决策工序即使在逐件模式也必须先选择结果，不能自动提交。
- 数量模式为每个结果提供数量输入；至少一项大于0，合计不超过 `reportable_qty`。
- 后处理定型不显示跳过按钮；直接扫描入库即可。

主站代报工、小程序和 PDA 使用相同字段与校验，不能由客户端自行推断工序名称。

## 撤销与改判

分流结果不能直接编辑，只能撤销原报工后重新提交。

- 若相关单件没有任何下游实际报工，撤销报工时同步撤销由它触发的跳过流水。
- 若任一相关单件已经在更高步骤实际报工，拒绝撤销，并返回具体单件和最早阻塞工序。
- 撤销入库时，同步撤销由该入库流水触发的可选定型跳过，使单件重新可以选择定型或入库。
- 所有判断按具体单件执行，不只比较累计数量。

主管异常跳过使用独立端点，只允许 `domestic:admin`，必须提交数量/单件、原因和幂等请求号。恢复异常跳过同样要求没有下游实际报工。

## 路线管理

工序路线页面在每个步骤旁展示“内贸执行方式”。选择分流判定后维护结果、标签和需要跳过的后续工序；选择可选后显示“下一道扫码自动跳过”的说明。

保存前后端都校验规则。路线预览按不同结果展示有效路径，不要求用户理解图数据库或条件表达式。

“是否递针”改为现场选择，但保留现有“头套网帽（递针）”和“发片网底（递针）”名称作为两类产品的新单入口；对应“无递针”路线不再绑定新单，可在确认无其他用途后停用。该业务数据调整不随 schema 迁移自动修改生产数据。

## 存量切换

最终业务决策是不迁移存量订单路线，只直接切换新单入口：

1. `cap`（头套）的全部工艺映射和已有产品绑定“头套网帽（递针）”；启用工艺字典中缺失的映射由切换事务补建。
2. `piece`（发片）的全部工艺映射和已有产品绑定“发片网底（递针）”；启用工艺字典中缺失的映射由切换事务补建。
3. 已有订单明细及进度保留原路线快照，不删除、不重建、不对账。
4. 两类映射和产品在停写维护窗口内以单事务更新，失败整体回滚。
5. 旧路线不再接收新订单，确认无业务用途后另行停用。

## 异常反馈

错误必须说明当前事实和下一步，例如：

- “这8件已发往丹东，请扫描丹东收货。”
- “这5件质检合格，不需要毛坯维修。”
- “A1-06已经入库，不能补扫后处理定型。”
- “A1-03等5件已完成丹东收货，请先撤销丹东收货。”

不再用笼统的“上一道还没完成”覆盖分支冲突。

## 验收标准

1. 20件可在发加工点拆为丹东12件、李晓宏8件，并分别只进入自己的分支。
2. 李晓宏8件可拆为递针5件、不递针3件并在手钩收货汇合。
3. 质检20件可拆为合格15件、维修5件；维修后直接汇合，不复检。
4. 后处理定型只做部分数量，其余在入库时自动跳过。
5. 数量模式和逐件模式产生一致的逐件结果。
6. 弱网重试不重复报工、分流或跳过，并发扫描不超量。
7. 下游未报工时撤销能完整回退，下游已报工时给出可行动拦截。
8. 自动和人工跳过均不进入工资与工作量。
9. 小程序、PDA、主站代报工行为一致。
10. 存量转换前后数量、身份、流水和工作量守恒。

## 不在范围内

- 通用 DAG/BPMN 工作流引擎。
- 任意布尔表达式或脚本条件。
- 外贸生产报工改造。
- 自动根据订单备注、工艺名称或人员姓名猜测分支。
- 未部署新代码前直接修改生产工艺映射。

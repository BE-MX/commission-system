# 内贸经营决策台

本地实现，尚未生产部署。产品基线见[功能设计](requirements/2026-10-08-domestic-business-decision-workbench.md)，开发及验证状态见[实施与验收](requirements/2026-10-08-domestic-decision-implementation.md)。

决策台读取原内贸订单、属性快照、客户当前档案和余额账本，提供分析、画像、证据下钻、规则建议和内部跟进。订单、充值、审核、调价和发货操作继续由原业务领域执行。决策台的“已充值”跟进结果只是实际跟进记录，不会增加入账金额。

## 2026-10-09 指标与经营分析优化

本次优化在独立 Codex worktree 完成，未发布；不改变原订单、报工与充值写入流程，无数据库迁移。当前指标版本为 `domestic-v2-report-date`，旧分析快照需重新分析。

- 经营总览：业务下单金额按有效业务单的下单日期汇总整单额；发货出库金额按“发货完成”未撤销、正数量报工的北京时间汇总 `report_qty * unit_price`，包括历史下单、本期发货。无效状态、删除单和生产单不参与销售。
- 客户充值金额按统计期内正向已入账充值累计，需要原资金阅读权限。沿用资金范围规则，默认不随产品筛选缩小，明确开启相关客户资金时按各期命中的客户分别计算。下单客户个数按期内有效业务单客户去重。
- 客户经营分充值/非充值两组，分别展示下单客户、整单额、订单数和命中明细折让额 `discount_amount * order_qty`。分组依据是截至期末的实际充值记录，既不把本期没充值的历史充值客户误归类，也不以当前会员等级推断历史充值。
- 充值意向只呈现曾充值并享折让、未充值按原价下单、待审申请等行为；真实意向标为待跟进确认，不能把充值偿债、手工折让当作充值意愿或因果证据。
- 持续复购：近三个自然月均有商业购买且本期商业下单；周期延后：距末次商业购买超过参考周期1.5倍；长期未购：达到配置的 `dormant_days`（默认90天）。售后/零额单不冒充商业复购，同日多单仅一个购买日，停止联系门店单独展示。
- 持续畅销观察：正价非售后商业报工样本达到3个出货日、2周、2客户及2个下单日期。总出货数量仍保留所有有效业务单的实际报工；只有零价/售后的出货单独标记。展示客户集中度、复现发货与对照期出货，不能凭一次大单或一批订单分多天发货认定畅销。
- 毛坯供需按历史规格去掉最终发型系列后去重：生产单“入库”、业务单“毛坯出库”、未入库在制量及90天以上在制量分别展示。生产供给不按业务渠道/类型/类别或最终发型筛选，界面明确说明。未知/待映射规格保留待核验，不推断可互换库存。
- 补货周期是下单日期至整行实际数量入库完成日期的天数，分批入库达到整行数量时才完成；至少3行样本才能与同范围款式中位数比较。它不是纯生产工时或承诺交期。
- 无客户生产单仅在完整全量查询、无客户/负责人/客户属性缩小，并同时拥有 `domestic_decision:read_all` 与 `domestic:read_all` 时纳入；其他查询仅含当前授权客户关联生产单。保存结果和导出也会核对无客户生产阅读权限。
- 利润、真实库存余额和实际低库存风险保持未知。当前缺材料、加工等成本、期初库存和销售批次消耗关联；期间入出库差仅作积压核查线索。亮哥已接受本次先交付该范围。
- 所有新报工事实、工序名称及补货来源参与数据指纹；源数据修改/撤销后下钻返回409。原始报工、每件折让和相关明细可下钻核验。

验证与范围见[优化验收记录](reports/2026-10-09-domestic-decision-metrics.md)。

## 数据口径

- 有效业务订单为 `order_kind=business`、`deleted_flag=0`、状态 1/2/3。主表金额按唯一订单统计；产品金额按 `order_qty * unit_price` 统计，成交价已含手工费。相关整单金额和匹配产品金额分别展示，不能重复汇总。规格条件必须同时命中同一明细。
- 历史规格来自 `attrs_snapshot`。发色文本只经管理员明确映射进入分析标准值；发块的工艺与尺码分别映射组合原值。未知、不适用、待映射和未归类均保留。映射不回写原订单或当前产品库。
- 账本按实际入账记录统计充值，申请单只提供待审和审核耗时。退款为返还账户余额，不是银行现金退款；信用负余额只是欠款，没有付款期限或逐笔核销证据时不能称为逾期。
- 账户期初、期末来自截止时点账本。缺失锚点不填零，不拿未来当前余额补历史。连续性、符号、算术或当前余额对账异常会暂停预测。退款保护包含已终止订单真实退款；无足够购买日或已核验历史、存在异常扣款、退款过高、信用结算等场景不输出余额覆盖估算。待审充值优先核对审核进度。
- 资金默认按日期、客户和当前归属分析，不自动继承产品筛选。用户开启“按相关客户分析资金”后才缩小到当期产品命中的客户。
- 客户购买周期采用完整授权商业历史的不同购买日，产品筛选只确定风险候选池，不人为拉长周期。四个购买日不足时，需至少二十个同群有效周期才提供同群参考。RFM 使用 180 天、同结算方式与门店类型的至少三十个客户；不足则保留 R/F/M 原值。
- 客户偏好采用近 180 天，近期变化比较两个 90 天。推荐只为需求核对线索，库存、交期和真实需求均需确认。共购至少二十个授权购买客户、五个支持客户。停业/停止联系客户保留事实，暂停推荐。
- 业务员归因是当前客户负责人组合，不能冒充历史业绩。存量档案累计金额与系统可核对订单额分开；没有可回放事件证明时，系统首单不等于真实新客。30/60/90 天和次月留存只采用成熟观察窗。

## 权限和状态

基础权限 `domestic_decision:read` 只允许当前本人客户；`domestic_decision:read_all` 可选择全量范围。资金段还需 `domestic_decision_finance:read`；行动记录、AI/导出、配置维护分别需 `domestic_decision_action:write`、`domestic_decision_report:write`、`domestic_decision:admin`。旧内贸读取、充值和审核权限不自动授予这些权限。

后端从数据库重新核对用户、角色及权限，JWT 内旧权限不能绕过撤权。分析、证据、旧报告和私有下载均复核当前客户归属；转交或失权后旧结果不可读。无资金权限时裁剪筛选、维度、画像、资金建议、模型上下文和导出。

一次分析保存固定 `run_id`、查询、数据指纹、口径/映射/配置版本和证据。同一请求在 MySQL 一致性事务生成。交互证据一天有效，下钻时重新核对来源指纹；变化返回 409，过期返回 410，需整组刷新。报告保持生成时事实，读取仍复核当前权限。导出默认只包含当前筛选的事实，不混入用于周期的 `history_*` 证据；按 `focus` 分开产品、客户和资金内容。CSV 保留分精度，并转义可能执行的单元格公式。

行动按客户、规则、分析期间及来源指纹去重；同一信号一周内及未关闭期间复用，结束后同窗口重复认领也复用。客户转交后直接认领即可继承旧行动，无须先打开列表。新订单或资金状态改变原条件时标记暂停提醒；完成需填写真实结果及分类。乐观版本避免覆盖并发修改，请求号复用不同内容返回 409。

保存视图只共享查询条件，不共享数据授权。滚动时间模式相对打开日期重新计算，固定模式保留日期。

## AI 与任务

简报、导出和自然语言查询计划使用持久任务。请求号与内容指纹防重复；刷新可继续查看任务，十分钟无完成的中断任务标为失败，界面明确提供重试。AI 简报和查询计划合用用户每日预算（默认十次，可配置 1–50）。

简报模型只选择程序事实 ID 与已注册假设代码，事实、数字、证据和下一步由服务器提供。输入采用白名单并匿名化订单/资金两套范围的客户名；自由文本、额外事实、概率、利润和未知引用均拒绝。失败或未配置时返回规则事实。查询模型只产生受白名单和运行时可见选项约束的 `AnalysisRequest`，不能执行 SQL；先预览，再由用户应用。规则降级只识别支持的时间、客户、产品、指标组合，不声称理解任意问题。

2. 对目标库只读核验有效订单、快照覆盖、原价、账本连续性、客户归属及售后字典，确认完整覆盖起点后才设置 `coverage_start`；不能用“有过首笔数据”替代覆盖完整性证明。按运行时字典配置售后类型和停止联系状态。
3. 在现有 AI 配置域设置 `domestic_decision_brief` 和 `domestic_decision_plan` 预设、提供方及成本策略。未配置也可使用规则事实和受控查询降级，不硬编码模型凭据。
4. 根据真实规模完成性能基线、MySQL 锁竞争及容量验证。当前隔离功能验收不能证明设计建议的十万订单/五十万明细/百万流水及二十并发 P95。现实现保留分析证据 JSON，应核验大范围结果体积、数据库包大小和历史读取成本，再决定分页事实存储/后台大分析策略。

从本次上线起，原客户、订单、明细、账本增改删在原事务内采集必要 before/after；旧历史不补造。迁移降级拒绝删除报告、行动和事件等审计数据，修复采用前向迁移。历史时点重建、可靠销量预测、自动订阅和跨团队匿名模型仍按设计 P1 门槛保留。

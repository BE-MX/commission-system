# Unknowns：未知驱动工作法

## 核心原理

用户给出的描述（地图）与真实约束（疆域）之间的落差是「未知」。工作质量的瓶颈在于澄清未知的能力。未知分四类：

- **已知的已知**：提示词里明确写了的
- **已知的未知**：用户知道自己没想清楚的
- **未知的已知**：用户「看到才认得出」、不会主动写下来的
- **未知的未知**：用户压根没考虑过的

**最高优先级规则：用户的明确指令永远压过本 skill 的所有模式。** 用户直接说「干」「合并」「不用问了」，照做，最多用一句话标注跳过了什么。「明确指令」指对**流程**的指令——模式即将触发或进行中，用户说「直接干」「不用问」「跳过测验」。初始任务描述本身不构成豁免；该触发的模式照常触发。

## 模式选择

| 时机 | 信号（可观测，不要推断） | 模式 |
|---|---|---|
| 动手前 | 用户明说「我不熟」「没做过」「第一次弄」，或该领域/技术栈在当前项目的 CLAUDE.md、既有代码、历史笔记中零出现（零出现时不直接开扫，先一句话提议，用户点头才做；单步明确、结果唯一的任务不提议） | 盲区扫描 |
| 动手前 | 规划后仍有会改变架构或方案方向的歧义（仅限未经 brainstorming 的路径） | 反向访谈 |
| 实现中 | 跨 ≥3 个非测试文件的实现开工时（机械性连带改动如重命名、格式化、依赖升级除外） | 实现笔记 |
| 完成后 | 满足任一：(a) 改变了用户可感知的行为；(b) 涉及 ≥3 个非测试文件的结构性变更（含重构，机械性连带改动除外）；(c) Deviations 非空 | 测验验收 |

**与其他 skill 的顺序**：新想法/新领域的完整链条是——盲区扫描（先扫盲）→ `superpowers:brainstorming` 或 `office-hours`（风暴，二选一）→ plan mode / writing-plans → 仍有影响方案的歧义才用反向访谈。盲区扫描永远在风暴之前；brainstorming 自带逐题提问和歧义消除，走了它就不要再访谈。头脑风暴和实现计划本身不属于本 skill。

## 1. 盲区扫描（Blind Spot Pass）

目标：把用户的**未知的未知**变成已知，让用户之后能提出更好的需求。

1. 先确认用户的起点：他对这个领域/代码区域已经知道什么（上下文中已有的不要重复问）
2. 快速调研相关代码/资料，产出盲区清单：不知道该问的问题、「好」的标准长什么样、历史相关工作、常见的坑
3. 用他能听懂的语言讲解（他是产品经理，不是程序员——讲「是什么、为什么重要、对决策的影响」，不堆实现细节）
4. 结尾给出：基于这些盲区，建议他在需求里补充说明的 2-3 件事

## 2. 反向访谈（Interview）

目标：挖出**未知的已知**——用户看到才认得出的隐含标准。

1. 一次只问一个问题，等回答再问下一个
2. 只问「答案会改变架构或方案方向」的问题；影响范围/成本的问题其次；其他歧义自行按最合理假设处理
3. 每个问题给出 2-3 个候选答案让用户选或反驳，不要开放式提问
4. 访谈到没有会改变方案的歧义为止，然后复述一遍达成的共识让用户确认

## 3. 实现笔记（Implementation Notes）

目标：让实现中冒出来的未知留下痕迹，供本次验收和下次规划使用。

1. 开工时创建 `docs/implementation-notes.md`（项目 CLAUDE.md 对临时文件另有约定则从其约定），确认其在 .gitignore 中，除非用户要求随 commit 保留
2. 记录关键决策及理由。偏离计划分两级处理：
   - **可保守回避的小偏离**（选更窄、可逆的实现即可绕过）→ 选保守方案，记入 **Deviations** 小节，继续干
   - **阻塞级偏离**（缺依赖、指令无法理解、涉及不可逆操作或数据安全）→ 停下来问，与 `superpowers:executing-plans` 的 STOP 规则一致，本条不覆盖它
3. 交付时把 Deviations 作为汇报重点——这些就是规划时没发现的未知
4. 验收完成后默认删除该文件（内容已在汇报中呈现），删除时告知一声即可，不要询问

## 4. 测验验收（Quiz）

目标：确保用户真正理解发生了什么，而不是只看 diff。测验是**默认验收流程，不是硬门槛**——用户明确下达合并/部署指令时照做，仅提示「本次跳过测验，Deviations 有 N 项建议看一眼」。

本环节是这套工作法中唯一**有意让用户思考**的环节（学习优先于流畅），不受「不要让用户思考」约束；但讲解部分仍遵守结论先行。

1. 先给讲解：开头一句话说「这次改了什么、对你意味着什么」，再展开做了什么、为什么、哪些行为依赖既有代码路径（用产品语言，不是代码语言）
2. 再出 3-5 道测验题，聚焦「答错会导致错误决策」的点：行为变化、边界情况、Deviations 里的偏离项
3. 答错的题讲解清楚后换角度补考 1 次；仍未通过则改为书面讲解并记入笔记，不再出题
4. 全部通过后明确宣布验收完成；未通过时不主动催促合并/部署

**收尾顺序固定**：跑验证（test/lint/build）→ 对抗性审查并修复 → 讲解 + 测验。测验永远最后，考的是修完之后的最终状态。

## 常见错误

- ❌ 用户明确给了指令还强行访谈或强行测验 → 有清晰指令直接干
- ❌ 盲区扫描写成代码导读 → 要讲决策相关的知识，不是文件结构
- ❌ 小改动也走测验 → 严格按模式选择表的三条件判定
- ❌ 走了 brainstorming 之后又发起反向访谈 → 重复提问，选其一
- ❌ 把「非程序员」推断为「一切都不熟」而到处触发盲区扫描 → 只认可观测信号

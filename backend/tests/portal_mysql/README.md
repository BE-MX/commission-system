## Evidence covered

The original five foundation cases passed on MySQL 8.0.46 / InnoDB / REPEATABLE READ:

1. Execute the actual 172 and 173 migration `upgrade()` operations. Compare portal
   column names/nullability, FK columns/targets/delete rules, CHECK names and

   number and initialize its document version to 1; verify barrier seed version.
2. A competing transaction actually waits for the authority barrier, then sees
   the first transaction's committed account status/version.
3. The same wait followed by rollback preserves the previous account status/version.
4. A duplicate command insert waits for the first transaction's commit, gets
   MySQL 1062, and rolls back its earlier Account mutation; exactly one receipt remains.
5. If the first transaction rolls back, the waiting insert commits its receipt and
   Account mutation; exactly one receipt remains.

Waiting is established by the second connection's ID in
`performance_schema.data_lock_waits`, not inferred from elapsed time. Independent
pooled connections are used without a Python serialization lock.

## Scope still unproven

The migration fixture creates only the five upstream FK anchor tables with their
relevant ID types plus an existing invoice number. The historical migration 054
defines `ark_users.id` as unsigned; the generic ORM type alone is insufficient to
recreate that schema. This fixture intentionally does not run all Ark historical
migrations, Alembic version-table transitions, production schema drift or data-volume
upgrades. It does not compare every type/index/default or CHECK expression.

The barrier cases start a new transaction before acquiring the barrier; they do
not prove recovery from a previously established stale InnoDB consistent-read
snapshot. They test the real barrier helper and database current-read ordering,
